# Skill 最佳实践

> 原文：[Best practices for skill creators](https://agentskills.io/skill-creation/best-practices)

## 从真正的专业能力出发

在 Skill 创建过程中，一个常见的错误是：不提供与特定领域相关的背景信息，就直接让大语言模型来生成 Skill——完全依赖大语言模型所具备的通用知识。这样一来，生成的只是些模糊、泛化的指导原则而已（比如“妥善处理错误”、“遵循身份验证的最佳实践”），而缺乏那些能让 Skill 真正发挥作用的具体细节，比如 API 接口的规范、各种边缘情况的处理方式以及项目中的惯例等。

有效的 Skill 源于真正的专业能力。关键在于在创作过程中融入与特定领域相关的背景信息。

### 从实际任务中提取

在与 Agent 的对话过程中，完成一项实际任务。在此过程中，需要提供必要的上下文、进行必要的修正，并明确各项偏好。之后，将其中的可重复使用模式提取出来，形成一个 Skill。需要注意以下几点：

- **行之有效的步骤**——那些最终带来成功的行动顺序
- **所做的修改**——也就是你指导智能体应该采取的行动方向（例如：“使用 X 图书馆而不是 Y 图书馆”，“检查 Z 这种特殊情况”）。
- **输入/输出格式**——数据在输入和输出时的表现形式
- **提供的背景信息**——即与该项目相关的各种事实、惯例或限制条件，这些都是该 Agent 之前所不知道的。

### 利用现有项目成果合成

当你拥有一套现有的知识体系时，可以将这些知识输入到大型语言模型中，让模型据此来生成相应的 Skill。如果你让模型根据团队实际的处理流程和操作手册来生成 Skill，那么其效果会优于那些基于通用“数据工程最佳实践”所生成的 Skill。因为前者能够准确反映你的数据结构、故障模式以及恢复流程。关键在于使用与项目相关的具体资料，而非通用的参考资料。

优质的素材来源包括：

- 内部文档、操作手册和风格指南
- API 规范、架构以及配置文件
- 代码审查意见和问题跟踪记录（有助于了解那些反复出现的问题以及审查人员的期望）
- 版本控制历史记录，尤其是各种补丁和修复措施（通过记录实际发生的变化，可以发现其中的规律）
- 现实世界中的故障案例及其解决方案

## 通过实际执行持续改进

一个 Skill 的初稿通常都需要进一步改进。请将这项 Skill 应用到实际任务中，然后把所有的结果——包括成功和失败的情况——都反馈到后续的改进过程中。思考一下：是什么导致了错误的结果？有哪些环节被忽略了？还有哪些部分可以省略掉？

哪怕只进行一次“执行后再修改”的流程，也能显著提升质量。而在处理复杂的任务时，多次重复这一流程会带来更好的效果。

> 请仔细查看 Agent 的执行过程，而不仅仅是最终结果。如果 Agent 在无效的操作上浪费了时间，常见的原因包括：指令过于模糊（Agent 需要尝试多种方法才能找到有效的解决方案）；指令与当前任务不相关（但 Agent 仍照做）；或者提供的选项太多，且没有明确的默认选项。

如需采用更为系统化的迭代方式，包括编写测试用例、进行断言验证以及评分等操作，请参阅[评估技能输出质量](https://agentskills.io/skill-creation/evaluating-skills)。

## 明智使用上下文

一旦某个 Skill 被激活，其全部内容都会被加载到 Agent 的上下文窗口中，与对话历史、系统上下文以及其他正在运行的 Skill 一起显示出来。该 Skill 中的每一个元素都需要与窗口中的其他内容竞争，以获得 Agent 的注意力。

### 补充 Agent 所缺乏的信息，省略它已掌握的信息

重点介绍那些没有你的专业技能，Agent 就无从知晓的信息：与特定项目相关的规则、特定领域的操作流程、那些不太明显的特殊情况，以及应该使用的特定工具或 API。你无需解释什么是 PDF、HTTP 是如何工作的，或者数据库迁移到底是什么。

````markdown
<!-- 过于冗长：Agent 已经知道 PDF 是什么 -->
## 提取 PDF 文本

PDF（Portable Document Format）是一种包含文本、图像及其他内容的常见文件格式。提取 PDF 文本需要使用库，推荐 pdfplumber，因为它能处理大多数情况。

<!-- 更好：直接说明 Agent 无法自行知道的选择 -->
## 提取 PDF 文本

使用 pdfplumber 提取文本。对于扫描文档，改用 pdf2image 与 pytesseract。

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
````

对于每一项内容，都要问自己：“如果没有这条指令，Agent 会做错吗？”如果不会，就删除它；如果不确定，就通过测试判断。如果 Agent 在没有这项 Skill 时已经能正确完成整个任务，这项 Skill 可能没有增加价值。系统化测试方法见[评估 Skill 输出质量](https://agentskills.io/skill-creation/evaluating-skills)。

### 设计逻辑连贯的单元

确定某个 Skill 应该具备哪些功能，就如同确定某个函数应该执行什么任务一样：你需要让该 Skill 能够完成一个连贯的任务单元，同时还能与其他 Skill 良好地协同工作。如果 Skill 的范围过窄，那么为了完成某项任务，就需要加载多个 Skill，这会增加不必要的开销，还可能导致指令冲突。相反，如果 Skill 的范围过宽，那么就很难精确地调用该 Skill。例如，用于查询数据库并格式化查询结果的 Skill 可以被视为一个完整的任务单元；而如果某项 Skill 还承担了数据库管理的功能，那显然就属于功能过多了。

### 保持适度详细

过于全面的 Skill 反而可能带来负面影响—— Agent 难以筛选出真正有用的信息，还可能因为那些与当前任务无关的指令而陷入无效的尝试中。相比详尽的文档说明，简洁、分步骤的指导方式以及具体的示例往往更有效。当你发现自己不得不处理所有可能的特殊情况时，不妨想想：是否大多数情况最好由 Agent 自行判断来处理。

### 使用渐进式披露组织大型 Skill

该[规范](https://agentskills.io/specification#progressive-disclosure)建议将 `SKILL.md` 控制在 500 行、5,000 个 token 以内，让 Agent 每次运行时只处理必要的核心指令。如果确实需要更多内容，应将详细资料放在 `references/` 或类似目录的独立文件中。

关键在于告诉 Agent 何时加载每个文件。与其使用笼统的“详见参考资料”，不如明确指示“如果 API 返回的状态码不是 200，则读取 `references/api-errors.md`”。这样，Agent 就可以根据需要加载相关内容，而不是提前加载全部内容，这正是[渐进式披露](https://agentskills.io/specification#progressive-disclosure)的运作方式。

## 校准控制力度

并非 Skill 的每个环节都需要同样严格的规范。应根据任务的复杂性来调整指导指令的详细程度。

### 让指令精度匹配任务脆弱性

当存在多种可行的处理方式，且任务本身能够容忍一定的差异时，应给予 Agent 足够的自由度来决策。对于灵活的指令来说，解释其背后的原因往往比机械的命令更有效——能够理解指令目的的智能体，才能做出更符合上下文的决策。在代码审查方面，可以说明需要关注哪些要点，而无需指定具体的操作步骤。

```markdown
## 代码审查流程

1. 检查所有数据库查询是否存在 SQL 注入风险（使用参数化查询）
2. 验证每个端点都执行了身份验证检查
3. 查找并发代码路径中的竞态条件
4. 确认错误消息不会泄露内部细节
```

当操作容易出错、结果必须保持一致，或必须严格遵循特定顺序时，应给出明确指令：

````markdown
## 数据库迁移

严格按照以下顺序执行：

```bash
python scripts/migrate.py --verify --backup
```

不要修改该命令，也不要添加其他参数。
````

大多数 Skill 会同时包含灵活和严格的部分，应分别校准每一部分的控制程度。

### 提供默认方案，而不是选项菜单

当多种工具或方法都可行时，选择一个默认方案，并简要说明替代方案，不要将所有选项并列呈现。

````markdown
<!-- 选项过多 -->
可以使用 pypdf、pdfplumber、PyMuPDF 或 pdf2image 等库。

<!-- 给出明确的默认方案，同时保留例外路径 -->
使用 pdfplumber 提取文本：

```python
import pdfplumber
```

如果扫描版 PDF 需要 OCR，则改用 pdf2image 和 pytesseract。
````

### 优先描述流程，而不是声明具体答案

Skill 应教会 Agent 如何处理一类问题，而不是告诉它某个具体任务应产生什么结果：

```markdown
<!-- 具体答案：只适用于当前任务 -->
通过 `customer_id` 连接 `orders` 表和 `customers` 表，筛选
`region = 'EMEA'` 的记录，并对 `amount` 列求和。

<!-- 可复用的方法：适用于任意分析查询 -->
1. 读取 `references/schema.yaml`，确定相关数据表
2. 按照 `_id` 外键约定连接数据表
3. 将用户要求的筛选条件转换为 WHERE 子句
4. 根据需要聚合数值列，并将结果格式化为 Markdown 表格
```

这不意味着 Skill 不能包含具体细节。[[AI/Agent/Skills/2. Skill 最佳实践#输出格式模板|输出格式模板]]、“禁止输出 PII”之类的约束，以及特定工具的指令都很有价值；关键是处理方法在具体细节变化后仍可复用。

## 有效指令模式

以下模式可以复用于 Skill 内容的组织。并非每个 Skill 都需要全部采用，只选择适合当前任务的模式。

### Gotchas：记录反直觉约束

许多 Skill 中价值最高的内容，是特定环境下违背常规推断的事实。它们不是“妥善处理错误”之类的通用建议，而是 Agent 在未得到说明时很可能犯错的具体事项：

```markdown
## Gotchas

- `users` 表使用软删除。查询必须包含
  `WHERE deleted_at IS NULL`，否则结果会包含已停用的账户。
- 用户 ID 在数据库中名为 `user_id`，在认证服务中名为 `uid`，
  在计费 API 中名为 `accountId`，三者表示同一个值。
- 只要 Web 服务器仍在运行，`/health` 端点就会返回 200，
  即使数据库连接已经中断。应使用 `/ready` 检查服务的完整健康状态。
```

Gotchas 应保留在 `SKILL.md` 中，使 Agent 在遇到相关情况之前就能读到。也可以放入单独的参考文件，但必须说明加载条件；对于反直觉问题，Agent 可能无法自行识别触发时机。

> 当 Agent 犯下需要纠正的错误时，将相应修正加入 Gotchas。这是[[AI/Agent/Skills/2. Skill 最佳实践#通过实际执行持续改进|通过实际执行持续改进]] Skill 最直接的方法之一。

### 输出格式模板

当 Agent 必须生成特定格式的结果时，应直接提供模板。模板比自然语言描述更可靠，因为 Agent 更擅长匹配具体结构。简短模板可以直接放在 `SKILL.md`；较长或仅在特定情况下使用的模板应放入 `assets/`，并由 `SKILL.md` 在需要时引用。

````markdown
## 报告结构

使用以下模板，并根据具体分析调整章节：

```markdown
# [分析标题]

## 执行摘要
[用一段话概述关键发现]

## 关键发现
- 关键发现 1 及其支撑数据
- 关键发现 2 及其支撑数据

## 建议
1. 具体且可执行的建议
2. 具体且可执行的建议
```
````

### 多步骤工作流检查清单

明确的检查清单能帮助 Agent 跟踪进度并避免遗漏步骤，尤其适用于步骤之间存在依赖关系或验证关卡的工作流。

```markdown
## 表单处理流程

进度：
- [ ] 步骤 1：分析表单（运行 `scripts/analyze_form.py`）
- [ ] 步骤 2：创建字段映射（编辑 `fields.json`）
- [ ] 步骤 3：验证映射（运行 `scripts/validate_fields.py`）
- [ ] 步骤 4：填写表单（运行 `scripts/fill_form.py`）
- [ ] 步骤 5：验证输出（运行 `scripts/verify_output.py`）
```

### 验证循环

要求 Agent 在继续下一步之前验证自己的工作：完成工作，运行验证器（脚本、参考检查清单或自检），修复问题并重复执行，直至验证通过。

```markdown
## 编辑流程

1. 完成编辑
2. 运行验证：`python scripts/validate.py output/`
3. 如果验证失败：
   - 查看错误消息
   - 修复问题
   - 再次运行验证
4. 只有验证通过后才能继续
```

参考文档也可以充当“验证器”：要求 Agent 在最终提交前对照参考文档检查结果。

### 计划、验证、执行

对于批量操作或破坏性操作，应让 Agent 先以结构化格式创建中间计划，根据事实来源验证计划，最后才执行操作。

```markdown
## PDF 表单填写

1. 提取表单字段：`python scripts/analyze_form.py input.pdf` → `form_fields.json`
   （列出每个字段的名称、类型以及是否必填）
2. 创建 `field_values.json`，将每个字段名映射到预期值
3. 验证：`python scripts/validate_fields.py form_fields.json field_values.json`
   （检查每个字段名是否存在、类型是否兼容，以及是否遗漏必填字段）
4. 如果验证失败，修改 `field_values.json` 并重新验证
5. 填写表单：`python scripts/fill_form.py input.pdf field_values.json output.pdf`
```

关键是第 3 步：验证脚本将计划文件 `field_values.json` 与事实来源 `form_fields.json` 比对。类似“字段 `signature_date` 不存在；可用字段为 `customer_name`、`order_total`、`signature_date_signed`”的错误消息，能够为 Agent 提供足够信息以自行修正。

### 打包可复用脚本

在[迭代改进 Skill](https://agentskills.io/skill-creation/evaluating-skills) 时，应比较不同测试用例中的 Agent 执行轨迹。如果发现 Agent 每次都在重新实现相同逻辑，例如生成图表、解析特定格式或验证输出，就应将这段逻辑编写为经过测试的脚本，并放入 `scripts/` 复用。

脚本的设计和打包方式见[在 Skill 中使用脚本](https://agentskills.io/skill-creation/using-scripts)。

## 后续步骤

Skill 可以正常工作后，可通过以下指南继续完善：

- **[优化 Skill 描述](https://agentskills.io/skill-creation/optimizing-descriptions)**：测试和改进 `description` 字段，使 Skill 能由正确的提示触发。
