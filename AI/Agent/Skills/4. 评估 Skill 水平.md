# 评估 Skill 输出质量

> 原文：[Evaluating skill output quality](https://agentskills.io/skill-creation/evaluating-skills)

通过评估驱动的迭代，测试 Skill 能否稳定地产生高质量输出。

写完一个 Skill 并用一条提示词试运行，只能说明它偶尔有效。要确认它能否在不同提示词和边界情况中稳定工作，以及是否确实优于不使用 Skill 的基线，需要运行结构化评估（eval），以此建立系统性的改进反馈循环。

## 设计测试用例

每个测试用例包含三个部分：

- **提示词（Prompt）**：真实的用户消息，即用户实际可能输入的内容。
- **预期输出（Expected output）**：用自然语言描述成功结果应具备的特征。
- **输入文件（Input files，可选）**：Skill 完成任务所需的文件。

将测试用例保存在 Skill 目录内的 `evals/evals.json`：

```json
{
  "skill_name": "csv-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "我有一份位于 data/sales_2025.csv 的月度销售数据。你能找出营收最高的 3 个月并制作条形图吗？",
      "expected_output": "一张展示营收最高 3 个月的条形图，包含坐标轴标签和数值。",
      "files": ["evals/files/sales_2025.csv"]
    },
    {
      "id": 2,
      "prompt": "我的下载目录中有一个 customers.csv，部分行缺少电子邮箱。你能清理它，并告诉我缺少邮箱的记录数吗？",
      "expected_output": "一份已处理邮箱缺失值的 CSV，以及缺少邮箱的记录数。",
      "files": ["evals/files/customers.csv"]
    }
  ]
}
```

编写测试提示词时：

- **先从 2～3 个用例开始。** 看到第一轮结果前不要投入过多，之后再扩充用例集。
- **改变提示方式。** 使用不同措辞、信息详细程度和正式程度。既要有“帮我清理一下这个 csv”这样的随意表达，也要有“解析 `data/input.csv`，删除 B 列为 null 的行，并将结果写入 `data/output.csv`”这样的精确指令。
- **覆盖边界情况。** 至少加入一个测试异常输入、非常规请求或指令歧义的用例。
- **使用真实上下文。** 真实用户会提及文件路径、列名和个人场景；“处理这些数据”过于模糊，无法形成有效测试。

此时不必定义具体的通过或失败条件，只需记录提示词和预期输出。看到第一轮实际结果后，再添加详细检查条件，即断言（assertion）。

## 运行评估

每个测试用例都运行两次：一次**使用 Skill**，另一次**不使用 Skill**（或使用 Skill 的旧版本）。后者是比较基线。

### 工作区结构

在 Skill 目录旁创建独立工作区。每轮完整评估使用一个 `iteration-N/` 目录，其中每个测试用例都有自己的评估目录，并分别保存 `with_skill/` 与 `without_skill/` 的结果：

```text
csv-analyzer/
├── SKILL.md
└── evals/
    └── evals.json
csv-analyzer-workspace/
└── iteration-1/
    ├── eval-top-months-chart/
    │   ├── with_skill/
    │   │   ├── outputs/       # 本次运行生成的文件
    │   │   ├── timing.json    # Token 数和运行时间
    │   │   └── grading.json   # 断言评定结果
    │   └── without_skill/
    │       ├── outputs/
    │       ├── timing.json
    │       └── grading.json
    ├── eval-clean-missing-emails/
    │   ├── with_skill/
    │   │   ├── outputs/
    │   │   ├── timing.json
    │   │   └── grading.json
    │   └── without_skill/
    │       ├── outputs/
    │       ├── timing.json
    │       └── grading.json
    └── benchmark.json         # 汇总统计数据
```

主要由作者手动编写的是 `evals/evals.json`。其余 JSON 文件（`grading.json`、`timing.json` 和 `benchmark.json`）在评估过程中由 Agent、脚本或作者生成。

### 启动独立运行

每次评估都应从干净的上下文开始，不保留先前运行或 Skill 开发过程中的状态，从而确保 Agent 只遵循 `SKILL.md` 中的指令。在支持子 Agent 的环境中（例如 Claude Code），每个子任务天然具有独立上下文；不支持时，应为每次运行使用单独会话。

每次运行需提供：

- Skill 路径（无 Skill 基线不提供；旧版本基线提供快照路径）
- 测试提示词
- 输入文件
- 输出目录

单次使用 Skill 的运行指令示例：

```text
执行以下任务：
- Skill 路径：/path/to/csv-analyzer
- 任务：我有一份位于 data/sales_2025.csv 的月度销售数据。
  你能找出营收最高的 3 个月并制作条形图吗？
- 输入文件：evals/files/sales_2025.csv
- 将输出保存到：csv-analyzer-workspace/iteration-1/eval-top-months-chart/with_skill/outputs/
```

基线运行使用相同提示词，但不提供 Skill 路径，并将结果保存到 `without_skill/outputs/`。

改进已有 Skill 时，应在修改前通过 `cp -r <skill-path> <workspace>/skill-snapshot/` 创建快照。基线运行指向该快照，并将结果保存到 `old_skill/outputs/`，而不是 `without_skill/outputs/`。

### 记录时间与 Token

时间数据可比较 Skill 相对基线增加的时间和 Token 成本。显著改善输出质量但使 Token 用量增至三倍，与质量更好且成本更低，是两种不同的权衡。每次运行结束后记录 Token 数和耗时：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332
}
```

> 在 Claude Code 中，子 Agent 任务结束时的[任务完成通知](https://platform.claude.com/docs/en/agent-sdk/typescript#sdk-task-notification-message)会包含 `total_tokens` 和 `duration_ms`。应立即保存这些值，因为系统不会在其他位置持久化它们。

## 编写断言

断言是对输出应包含什么或实现什么的可验证陈述。应在查看第一轮输出后再添加断言，因为运行前往往还无法准确判断“好”的结果是什么。

好的断言应客观且可观察：

- `"输出文件是有效的 JSON"`：可通过程序验证。
- `"条形图包含坐标轴标签"`：具体且可观察。
- `"报告至少包含 3 条建议"`：可计数。

薄弱的断言包括：

- `"输出很好"`：过于模糊，无法评定。
- `"输出必须准确使用短语 'Total Revenue: $X'"`：过于脆弱，措辞不同但内容正确的输出也会失败。

并非所有质量特征都需要断言。写作风格、视觉设计、结果是否“感觉正确”等特征很难分解为通过或失败条件，更适合在[[AI/Agent/Skills/4. 评估 Skill 水平#人工审核|人工审核]]中判断。断言只用于可客观检查的内容。

为 `evals/evals.json` 中的每个测试用例添加断言：

```json
{
  "skill_name": "csv-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "我有一份位于 data/sales_2025.csv 的月度销售数据。你能找出营收最高的 3 个月并制作条形图吗？",
      "expected_output": "一张展示营收最高 3 个月的条形图，包含坐标轴标签和数值。",
      "files": ["evals/files/sales_2025.csv"],
      "assertions": [
        "输出包含一个条形图图片文件",
        "图表恰好展示 3 个月",
        "两个坐标轴都有标签",
        "图表标题或说明中提到营收"
      ]
    }
  ]
}
```

## 评定输出

评定是根据实际输出逐条检查断言，并以具体证据记录 `PASS` 或 `FAIL`。证据必须引用或指向输出内容，不能只表达主观看法。

最简单的方法是将输出和断言交给 LLM，让它逐项判断。对于可由代码检查的断言，例如 JSON 是否有效、行数是否正确、文件是否存在且尺寸符合要求，应使用验证脚本。脚本执行机械检查比 LLM 判断更可靠，并可跨迭代复用。

```json
{
  "assertion_results": [
    {
      "text": "输出包含一个条形图图片文件",
      "passed": true,
      "evidence": "在 outputs 目录中找到 chart.png（45KB）"
    },
    {
      "text": "图表恰好展示 3 个月",
      "passed": true,
      "evidence": "图表显示了三月、七月和十一月的条形"
    },
    {
      "text": "两个坐标轴都有标签",
      "passed": false,
      "evidence": "Y 轴标记为 'Revenue ($)'，但 X 轴没有标签"
    },
    {
      "text": "图表标题或说明中提到营收",
      "passed": true,
      "evidence": "图表标题为 'Top 3 Months by Revenue'"
    }
  ],
  "summary": {
    "passed": 3,
    "failed": 1,
    "total": 4,
    "pass_rate": 0.75
  }
}
```

### 评定原则

- **只有存在具体证据时才判定为 `PASS`。** 不应作有利推定。例如，断言要求“包含摘要”，而输出只有一个名为“摘要”的章节和一句空泛内容，应判定为 `FAIL`：标题存在，但没有实质内容。
- **同时审查断言本身，而不只审查结果。** 评定时留意断言是否过于容易（无论 Skill 质量如何都通过）、过于困难（即使输出良好也失败），或无法仅根据输出验证；下一轮应修正这些断言。

> 比较两个 Skill 版本时，可以采用**盲评**：将两份输出交给 LLM 评审模型，但不透露各自来自哪个版本。评审模型根据自己的评分标准评估组织结构、格式、可用性和完成度等整体质量，避免受“新版本理应更好”的预期影响。盲评是断言评定的补充，因为两份输出即使通过全部断言，整体质量仍可能差异明显。

## 汇总结果

完成一轮中所有运行的评定后，按配置计算汇总统计数据，并将其保存到评估目录旁的 `benchmark.json`，例如 `csv-analyzer-workspace/iteration-1/benchmark.json`：

```json
{
  "run_summary": {
    "with_skill": {
      "pass_rate": { "mean": 0.83, "stddev": 0.06 },
      "time_seconds": { "mean": 45.0, "stddev": 12.0 },
      "tokens": { "mean": 3800, "stddev": 400 }
    },
    "without_skill": {
      "pass_rate": { "mean": 0.33, "stddev": 0.10 },
      "time_seconds": { "mean": 32.0, "stddev": 8.0 },
      "tokens": { "mean": 2100, "stddev": 300 }
    },
    "delta": {
      "pass_rate": 0.50,
      "time_seconds": 13.0,
      "tokens": 1700
    }
  }
}
```

`delta` 表示 Skill 增加的成本（时间和 Token）及带来的收益（通过率）。例如，增加 13 秒但将通过率提高 50 个百分点通常值得接受；如果 Token 用量翻倍而通过率只提高 2 个百分点，则可能不值得。

> 标准差 `stddev` 只有在每个测试用例运行多次时才有意义。早期只有 2～3 个用例且每个用例仅运行一次时，应关注原始通过数量和 `delta`；随着测试集扩大、每个用例运行次数增加，统计指标才会更有价值。

## 分析规律

汇总统计可能掩盖重要规律。计算基准数据后，应进一步检查：

- **删除或替换在两种配置中始终通过的断言。** 这类断言无法说明 Skill 的价值，只会抬高使用 Skill 时的通过率；模型在没有 Skill 时也能满足它们。
- **调查在两种配置中始终失败的断言。** 可能是断言本身有误、测试用例过难，或检查了错误目标，应在下一轮前修正。
- **研究使用 Skill 时通过、基线中失败的断言。** 这些结果最能证明 Skill 的价值，应找出产生差异的具体指令或脚本。
- **结果在多次运行间不一致时，收紧指令。** 如果同一个测试有时通过、有时失败，并在基准中表现为较高的 `stddev`，可能是评估受模型随机性影响而不稳定，也可能是 Skill 指令有歧义，导致模型每次作出不同解释。增加示例或更具体的指导可减少歧义。
- **检查时间和 Token 的异常值。** 如果某个测试耗时是其他测试的三倍，应阅读其执行轨迹，即模型在本次运行中的完整操作日志，以定位瓶颈。

## 人工审核

断言评定和规律分析只能检查预先想到并写成断言的问题。人工审核者能从新的角度发现未预料的问题，包括结果技术上正确却偏离实际目的，或难以表达为通过、失败条件的质量问题。每个测试用例都应将实际输出与评分结果放在一起审核。

为每个测试用例记录具体反馈，并将其保存在工作区中，例如评估目录旁的 `feedback.json`：

```json
{
  "eval-top-months-chart": "图表缺少坐标轴标签，而且月份按字母顺序而不是时间顺序排列。",
  "eval-clean-missing-emails": ""
}
```

“图表缺少坐标轴标签”可以直接指导修改；“看起来很差”则不能。空反馈表示审核者认为输出没有问题。进入[[AI/Agent/Skills/4. 评估 Skill 水平#迭代改进 Skill|迭代阶段]]时，优先改进收到具体反馈的测试用例。

## 迭代改进 Skill

完成评定和人工审核后，可以获得三类信号：

- **失败的断言**指出具体缺口，例如缺少步骤、指令不明确，或未处理某种情况。
- **人工反馈**指出更广泛的质量问题，例如处理方法错误、输出结构不佳，或结果技术上正确但没有帮助。
- **执行轨迹**解释问题发生的原因。Agent 忽略指令，可能说明指令有歧义；Agent 在无效步骤上耗时，则可能需要简化或删除相关指令。

将这三类信号连同当前 `SKILL.md` 交给 LLM，请其提出修改建议，是转化反馈的有效方式。LLM 可以综合失败断言、审核意见和执行行为中的规律，完成手工分析较为繁琐的关联。提示 LLM 时应包含以下原则：

- **从反馈中归纳。** Skill 会用于多种不同提示词，不能只修补当前测试用例；修改应解决底层共性问题。
- **保持 Skill 精简。** 少而准确的指令通常优于穷尽式规则。若执行轨迹显示存在不必要的验证或中间输出，应删除相应指令；如果增加规则后通过率停滞，Skill 可能受到过度约束，可尝试删除部分指令并观察结果是否维持或改善。
- **解释原因。** 基于原因的指令（“执行 X，因为 Y 往往会导致 Z”）比僵硬命令（“始终执行 X，绝不执行 Y”）更有效。模型理解目的后，更能可靠地遵循指令。
- **打包重复工作。** 如果每次测试都重新编写相似的辅助脚本，例如图表生成器或数据解析器，应将其打包到 Skill 的 `scripts/` 目录。具体方法见[在 Skill 中使用脚本](https://agentskills.io/skill-creation/using-scripts)。

### 迭代循环

1. 将评估信号和当前 `SKILL.md` 交给 LLM，请其提出改进建议。
2. 审查并应用修改。
3. 在新的 `iteration-<N+1>/` 目录中重新运行全部测试用例。
4. 评定并汇总新结果。
5. 进行人工审核，然后重复以上过程。

当结果已满足要求、人工反馈持续为空，或不同迭代之间不再有显著改进时，即可停止。

> [`skill-creator` Skill](https://github.com/anthropics/skills/tree/main/skills/skill-creator) 可以自动完成这一流程中的大部分工作，包括运行评估、评定断言、汇总基准数据以及展示结果供人工审核。
