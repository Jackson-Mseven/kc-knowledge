# 优化 Skill 描述

> 原文：[Optimizing skill descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)

只有被激活，Skill 才能发挥作用。`SKILL.md` frontmatter 中的 `description` 字段，是 Agent 判断是否需要为当前任务加载某项 Skill 的主要依据。描述不充分会导致 Skill 应触发时未触发；描述范围过宽则会导致不应触发时误触发。

本文介绍如何系统测试并改进 Skill 描述，提高触发准确率。

## Skill 的触发机制

Agent 通过[渐进式披露](https://agentskills.io/specification#progressive-disclosure)管理上下文。启动时，它只加载每项可用 Skill 的 `name` 和 `description`，这些信息刚好足以判断 Skill 何时可能相关。当用户任务与描述匹配时，Agent 才会将完整的 `SKILL.md` 读入上下文并执行其中的指令。

因此，描述承担了触发判断的全部信息责任。如果描述没有说明 Skill 何时有用，Agent 就不会知道何时应该使用它。

需要注意：Agent 通常只会在任务需要超出自身基础能力的知识或能力时查阅 Skill。即使描述完全匹配，“读取这个 PDF”这类简单的单步请求也可能不会触发 PDF Skill，因为 Agent 可以直接用基础工具完成。涉及专门知识的任务，例如陌生 API、特定领域工作流或少见格式，才最能体现优质描述的价值。

## 编写有效描述

测试前，先明确优质描述的基本特征：

- **使用祈使表达**：将描述写成对 Agent 的指令，例如“在……时使用此 Skill”，而不是“此 Skill 用于……”。Agent 正在判断是否行动，因此应直接告诉它何时行动。
- **关注用户意图，而非内部实现**：描述用户想完成什么，不要描述 Skill 内部如何工作。Agent 匹配的是用户提出的需求。
- **宁可写得更主动**：明确列出 Skill 适用的上下文，包括用户没有直接说出领域名称的情况，例如“即使用户没有明确提到 ‘CSV’ 或 ‘analysis’”。
- **保持简洁**：通常几句话到一个短段落即可，既要覆盖 Skill 的范围，又不能在存在大量 Skill 时过度占用 Agent 上下文。[规范](https://agentskills.io/specification#description-field)将描述硬性限制为 1,024 个字符。

## 设计触发评测查询

要测试触发行为，需要准备一组评测查询：使用真实的用户提示，并标注每条提示是否应该触发 Skill。

`eval_queries.json`：

```json
[
  { "query": "我在 ~/data/q4_results.xlsx 中有一份表格，C 列是收入，D 列是支出。你能添加利润率列，并高亮低于 10% 的项目吗？", "should_trigger": true },
  { "query": "把这个 json 文件转换为 yaml，最快的方法是什么？", "should_trigger": false }
]
```

建议准备约 20 条查询：8～10 条应触发查询，以及 8～10 条不应触发查询。

### 应触发查询

这类查询用于检验描述是否覆盖了 Skill 的能力范围，应从多个维度制造差异：

- **措辞**：同时包含正式、随意、带拼写错误或缩写的表达。
- **明确程度**：有些提示直接说出 Skill 领域，例如“分析这个 CSV”；有些只描述需求而不点明领域，例如“老板要我根据这个数据文件制作图表”。
- **细节**：同时包含简短提示和上下文丰富的提示，例如简短的“分析我的销售 CSV 并制作图表”，以及带文件路径、列名和背景说明的较长请求。
- **复杂度**：改变步骤数和决策点。既包含单步任务，也包含多步工作流，用于测试相关任务埋在较长流程中时，Agent 能否识别出 Skill 仍然适用。

最有价值的应触发查询，是 Skill 确实有帮助、但提示本身没有明显暴露关联的情况。此时描述措辞才会影响触发；如果查询已经明确提出了该 Skill 正好能完成的任务，任何合理描述都可能触发。

### 不应触发查询

最有价值的负例是**近似但不匹配的查询**：它们与 Skill 共享关键词或概念，实际却需要不同能力。这类查询检验的是描述是否精确，而不仅是覆盖面是否足够广。

对于 CSV 分析 Skill，以下负例过弱：

- `"编写一个 Fibonacci 函数"`：显然无关，无法检验描述。
- `"今天天气如何？"`：没有关键词重叠，过于简单。

更有效的负例包括：

- `"我需要更新 Excel 预算表中的公式"`：与 Skill 共享“表格”和“数据”等概念，但任务需要编辑 Excel，而不是分析 CSV。
- `"你能编写一个 Python 脚本，读取 CSV 并将每一行上传到 PostgreSQL 数据库吗？"`：任务涉及 CSV，但目标是数据库 ETL，而不是数据分析。

### 让查询接近真实使用

真实用户提示包含通用测试查询所缺少的上下文，应覆盖：

- 文件路径，例如 `~/Downloads/report_final_v2.xlsx`
- 个人背景，例如 `"我的经理让我……"`
- 具体细节，例如列名、公司名和数据值
- 随意表达、缩写和偶发拼写错误

## 测试描述能否触发

基本方法是：安装 Skill 后，将每条查询交给 Agent 执行，并观察 Agent 是否调用了该 Skill。首先确认 Agent 已注册并能够发现它；具体方式因客户端而异，可能是 Skill 目录、配置文件或 CLI 参数。

多数 Agent 客户端都会提供一定的可观测能力，例如执行日志、工具调用历史或详细输出，从而显示一次运行查阅了哪些 Skill，具体方式应以客户端文档为准。Agent 加载了目标 Skill 的 `SKILL.md`，即表示 Skill 已触发；Agent 未查阅该文件便继续执行，则表示未触发。

查询满足以下任一条件即为“通过”：

- `should_trigger` 为 `true`，且 Skill 被调用；
- `should_trigger` 为 `false`，且 Skill 未被调用。

### 多次运行

模型行为具有非确定性，同一条查询可能在一次运行中触发 Skill，在另一次运行中不触发。因此，每条查询应重复运行多次，3 次可作为合理起点，然后计算**触发率**：Skill 被调用的运行次数占总运行次数的比例。

应触发查询的触发率高于阈值时通过；不应触发查询的触发率低于阈值时通过。`0.5` 是一个合理的默认阈值。

20 条查询各运行 3 次，共需调用 60 次，适合用脚本自动执行。下面是通用结构；请根据实际 Agent 客户端，替换 `claude` 调用以及 `check_triggered` 中的检测逻辑：

```bash
#!/bin/bash
QUERIES_FILE="${1:?用法：$0 <queries.json>}"
SKILL_NAME="my-skill"
RUNS=3

# 本例使用 Claude Code 的 JSON 输出检查 Skill 工具调用。
# 请将此函数替换为适用于你的 Agent 客户端的检测逻辑。
# 如果调用了 Skill，应返回 0（成功）；否则返回 1。
check_triggered() {
  local query="$1"
  claude -p "$query" --output-format json 2>/dev/null \
    | jq -e --arg skill "$SKILL_NAME" \
      'any(.messages[].content[]; .type == "tool_use" and .name == "Skill" and .input.skill == $skill)' \
      > /dev/null 2>&1
}

count=$(jq length "$QUERIES_FILE")
for i in $(seq 0 $((count - 1))); do
  query=$(jq -r ".[$i].query" "$QUERIES_FILE")
  should_trigger=$(jq -r ".[$i].should_trigger" "$QUERIES_FILE")
  triggers=0

  for run in $(seq 1 $RUNS); do
    check_triggered "$query" && triggers=$((triggers + 1))
  done

  jq -n \
    --arg query "$query" \
    --argjson should_trigger "$should_trigger" \
    --argjson triggers "$triggers" \
    --argjson runs "$RUNS" \
    '{query: $query, should_trigger: $should_trigger, triggers: $triggers, runs: $runs, trigger_rate: ($triggers / $runs)}'
done | jq -s '.'
```

> 如果 Agent 客户端支持，可以在结果已经明确时提前终止单次运行：Agent 要么已经查阅 Skill，要么已经开始在不使用 Skill 的情况下执行任务。这样可以显著降低完整评测集的运行时间和成本。

## 用训练集与验证集避免过拟合

如果根据全部查询优化描述，就有过拟合风险：描述可能只适用于这些特定措辞，面对新查询时却失效。

解决方法是拆分查询集：

- **训练集（约 60%）**：用于识别失败并指导改进。
- **验证集（约 40%）**：暂时保留，仅用于检查改进能否泛化。

两个集合都应按比例包含应触发和不应触发查询，不能把全部正例意外放进同一个集合。随机打乱后，应在各次迭代中固定拆分结果，保证比较基准一致。

使用[[AI/Agent/Skills/3. 优化 Skill 描述#多次运行|上述脚本]]时，可以将查询拆分为 `train_queries.json` 和 `validation_queries.json`，再分别运行脚本。

## 优化循环

1. **评测当前描述**：同时在训练集和验证集上运行。训练集结果指导修改，验证集结果判断修改能否泛化。
2. **识别训练集中的失败**：哪些应触发查询没有触发？哪些不应触发查询发生了误触发？
   - 只允许训练集中的失败指导修改。无论是自己修改描述，还是提示 LLM 修改，都不要将验证集结果带入优化过程。
3. **修改描述并关注泛化**：
   - 应触发查询失败，说明描述可能过窄。扩大描述的适用范围，或补充 Skill 何时有用的上下文。
   - 不应触发查询发生误触发，说明描述可能过宽。明确 Skill **不做什么**，或者说明它与相邻能力的边界。
   - 不要把失败查询中的具体关键词直接添加进描述，这会导致过拟合。应找出这些查询代表的一般类别或概念，并在描述中覆盖该类别。
   - 多次迭代仍没有进展时，不要继续小幅调整，而应尝试结构不同的描述方式。新的切入角度或句式可能比继续微调更有效。
   - 确认描述仍低于 1,024 个字符；描述往往会在优化过程中不断增长。
4. **重复步骤 1～3**：直到训练集查询全部通过，或继续修改已无法带来有意义的改进。
5. **按验证通过率选择最佳版本**：验证通过率是验证集中通过查询所占的比例。最佳描述不一定是最后生成的版本；早期版本的验证通过率可能更高，而后续版本已经对训练集过拟合。

通常迭代 5 次已经足够。如果性能没有提升，问题可能来自查询本身，例如过于简单、过于困难或标签错误，而不是描述。

> [`skill-creator`](https://github.com/anthropics/skills/tree/main/skills/skill-creator) Skill 可以端到端自动执行这个循环：拆分评测集、并行计算触发率、使用 Claude 提议描述改进，并生成可实时查看的 HTML 报告。

## 应用优化结果

选出最佳描述后：

1. 更新 `SKILL.md` frontmatter 中的 `description` 字段。
2. 确认描述没有超过[1,024 个字符的限制](https://agentskills.io/specification#description-field)。
3. 确认描述能够按预期触发。可以先手动尝试几条提示作为快速检查；如需更严格的测试，编写 5～10 条全新的查询，混合应触发与不应触发情况，再通过评测脚本运行。由于这些查询从未参与优化，它们更能真实检验描述能否泛化。

优化前后的对比：

```yaml
# 优化前
description: 处理 CSV 文件。

# 优化后
description: >
  分析 CSV 和表格数据文件，包括计算汇总统计、添加派生列、生成图表和清理杂乱数据。
  当用户希望探索、转换或可视化 CSV、TSV 或 Excel 文件中的数据时使用此 Skill，
  即使用户没有明确提到“CSV”或“分析”。
```

改进后的描述更具体地说明了 Skill 的能力，包括汇总统计、派生列、图表和数据清理；同时扩大了适用条件，包括 CSV、TSV 和 Excel，以及用户没有明确使用相关关键词的情况。
