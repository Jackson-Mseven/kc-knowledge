# 一、Redis 基础入门

### Redis 是什么

Redis 是一个**内存型 Key\-Value 数据库**，特点：

- 读写极快（内存操作）

- 支持多种数据结构

- 常用于缓存、队列、排行榜、分布式锁

---

### 核心数据结构

必须熟练掌握这 5 种：

#### String（最常用）

```Bash
SET name "kincy"
GET name
```

用途：

- 缓存

- 计数器

- token

---

#### Hash（对象）

```Bash
HSET user:1 name "tom" age 18
HGET user:1 name
```

用途：

- 用户信息

- 商品信息

---

#### List（队列）

```Bash
LPUSH queue task1
RPOP queue
```

用途：

- 消息队列

- 任务队列

---

#### Set（去重集合）

```Bash
SADD tags "js" "redis"
SMEMBERS tags
```

用途：

- 标签系统

- 去重

---

#### Sorted Set（ZSet，重点）

```Bash
ZADD rank 100 user1
ZADD rank 200 user2
```

用途：

- 排行榜

- 延迟队列

---

#### HyperLogLog（2\.8\.9\+）

Redis **HyperLogLog（HLL）** 是一种用于估算集合中**不重复元素数量**的数据结构（不是100%精确，但是省内存），适合统计：

- 日活用户数（DAU）

- 独立访客数（UV）

- 独立 IP 数

- 搜索关键词去重数量

```Bash
PFADD users:2025-01-01 user:1001
```

##### HyperLogLog 的原理

可以把 HyperLogLog 想象成一种**“省空间的去重计数器”**。

每一次新增不会存入实际的值，而是会将其转为哈希（可以理解为为每个值都生成了一个随机数），然后随机分配到寄存器（不保存有哪些值，只保存目前的最大值）中，然后根据这些记录估算总量（如果数据量少很难出现特别的值，而总量较大时则更有可能出现）。

##### HyperLogLog 的误差为什么是0\.81%？

HyperLogLog 的典型误差大约是：`误差 ≈ 1.04 ÷ √寄存器数量`。

而 Redis 使用大约：16384个寄存器，计算出来为 0\.008125，转为百分比约为 0\.81%。

假设真实的值有 100w 个，误差大约为 8100 个，估算结果在 `991900 ~ 1008100` 之间，这只是一个典型范围，不代表结果一定不会超出这个范围。

### KEYS 命令

#### KEYS：查所有 key

```Bash
KEYS *
```

⚠️ 重要：生产环境不要用 KEYS \*

原因：

- Redis 是单线程 

- KEYS \* 会**全量扫描内存**

- 数据多时会卡死（阻塞） 

👉 类比：

> 在 10 万个对象里同步 for 循环查 key。
> 
> 

---

#### KEYS：模糊匹配

```Plain Text
KEYS user:*
```

---

#### SCAN：分页查询（生产环境推荐）

```Plain Text
SCAN 0 MATCH user:* COUNT 100
```

👉 特点：

- **渐进式扫描（不会卡死）**

- 分批返回

- 类似分页

---

#### DEL：删除 key

```Plain Text
DEL user:1
```

批量删除

```Plain Text

```

#### EXISTS：判断 key 是否存在

```Plain Text

```

返回：

- 1 = 存在

- 0 = 不存在

---

#### EXPIRE / TTL（非常重要）

##### 设置过期时间

```Plain Text

```

##### 查看剩余时间

```Plain Text

```

返回：

- 0 剩余秒数

- \-1 永不过期

- \-2 key不存在

##### 精确设置过期（更常用）

```Plain Text

```

### 发布订阅

Redis 的**发布订阅（Pub/Sub）**是一种消息传递模式：

> 发布者把消息发到某个频道，订阅了这个频道的消费者就能收到消息。
> 
> 

```Bash
# 订阅频道
SUBSCRIBE news

# 订阅多个频道
SUBSCRIBE news sports weather

# 发布消息
PUBLISH news "服务器即将重启"

# 取消普通订阅
PUNSUBSCRIBE news

# 取消模式订阅
PUNSUBSCRIBE news:*
```

### 事务

Redis 事务可以一次执行多个命令， 并且带有以下两个重要的保证：

事务是一个单独的隔离操作：事务中的所有命令都会序列化、按顺序地执行。事务在执行的过程中，不会被其他客户端发送来的命令请求所打断。

事务是一个原子操作：事务中的命令要么全部被执行，要么全部都不执行。

一个事务从开始到执行会经历以下三个阶段：

1. 开始事务。

2. 命令入队。

3. 执行事务。

示例：

```Bash
# 标记事务开始
MULTI

# 修改
SET user:1:name Alice
SET user:1:age 18

# 一次性执行队列中的所有命令
EXEC
```

#### 命令

|**命令**|**描述**|
|---|---|
|MULTI|标记事务开始|
|EXEC|一次性执行队列中的所有命令|
|DISCARD|放弃事务|
|WATCH key \[key \.\.\.\]|监视一个\(或多个\) key ，如果在事务执行之前这个\(或这些\) key 被其他命令所改动，那么事务将被打断|
|UNWATCH|取消 WATCH 命令对所有 key 的监视|

#### 特性

1. **原子执行**

    事务中的命令会连续执行，执行过程中不会插入其他客户端的命令。

2. **不支持传统回滚**

    如果事务执行过程中某条命令失败，Redis 不会自动撤销之前已经成功执行的命令。

    > 这是 Redis 事务和数据库事务的一个重要区别。
    > 
    > 

#### 错误处理

- **命令入队阶段出错**

    有些错误发生在 `EXEC` 之前，例如命令参数数量错误：

    ```Bash
    MULTI
    SET key
    EXEC
    ```

    如果 Redis 在入队阶段发现命令格式不正确，整个事务可能无法执行。

- **执行阶段出错**

    有些错误只有真正执行时才会发现：

    ```Bash
    SET counter hello
    
    MULTI
    INCR counter
    SET name Alice
    EXEC
    ```

    `INCR counter` 会失败，因为 `counter` 不是数字。

    但 `SET name Alice` 仍然可能执行成功。

    因此 Redis 事务不是：`全部成功，或者全部失败`，而是：`命令按顺序执行，某条失败不影响其他命令继续执行`。

#### 乐观锁

`WATCH` 用于解决：在我读取数据并准备修改之前，如果其他客户端改过这个数据，就不要执行我的事务。

例如库存扣减：

```Plain Text
WATCH stock

GET stock
```

假设返回：`10`，然后开始事务：

```Plain Text
MULTI
DECR stock
EXEC
```

如果从 `WATCH stock` 到 `EXEC` 之间，其他客户端修改了 `stock`：

```Plain Text
SET stock 20
```

那么当前事务会执行失败，`EXEC` 返回空结果。这表示：

```Plain Text
被监视的数据发生变化，事务没有执行
```

#### 在 Redis Cluster 中的限制

> [**Redis Cluster 是什么？**](https://qx8wba2yxsl.feishu.cn/wiki/NUpFwUaq5ikyRRk5NPkcjaONnsg#share-UGtUdskJwoMz1bxTKmycrWFznRe)
> 
> 

在 Redis Cluster 中，一个事务中的多个命令通常需要操作同一个哈希槽。

例如：

```Bash
MULTI
SET user:1:name Alice
SET user:1:age 18
EXEC
```

这些 Key 可能被分配到不同节点，事务可能无法执行。

可以使用 Hash Tag，让相关 Key 落到同一个槽：

```Bash
SET user:{1}:name Alice
SET user:{1}:age 18
```

`{1}` 会作为哈希标签，使两个 Key 使用相同的哈希槽。

#### 使用 Lua 脚本实现复杂原子操作

> [什么是 Lua 脚本？](https://qx8wba2yxsl.feishu.cn/wiki/NUpFwUaq5ikyRRk5NPkcjaONnsg#UTDwdYVOdolYQgxeQmmcRfB6nMe)
> 
> 

很多需要“读取、判断、修改”的操作，使用 Lua 脚本更方便。

- **使用事务**

    ```Bash
    WATCH stock
    GET stock
    MULTI
    DECR stock
    EXEC
    ```

    客户端需要多次和 Redis 通信。

- **使用 Lua 脚本**

    可以把读取、判断、修改放到 Redis 内部一次执行：

    ```Lua
    local stock = tonumber(redis.call('GET', KEYS[1]))
    
    if not stock or stock <= 0 then
        return 0
    end
    
    redis.call('DECR', KEYS[1])
    return 1
    ```

    Lua 脚本的优点：

    - 在 Redis 内部执行

    - 具有原子性

    - 减少网络往返

    - 适合复杂判断逻辑

    但脚本执行期间会占用 Redis 主线程，脚本不能写得过于复杂或执行时间过长。

#### Redis 的单线程为什么还可以中断事务？

因为 Redis 事务分成了两个阶段：

- **阶段一：准备事务（****`MULTI`**** 后，****`EXEC`**** 前）**

    此时事务可以通过 `DISCARD` 或 `WATCH` 放弃。

- **阶段二：执行事务**

    当 Redis 开始执行 `EXEC` 后，事务中的命令会连续执行，其他客户端不能在这两条命令之间插入命令。

    > 这就是 Redis 事务的原子性。
    > 
    >

### Redis Cluster

Redis Cluster 是把 Redis 拆成多个节点一起工作，解决数据量大、单机性能和高可用问题。

#### 单机  Redis 的问题

一开始可能只有一个 Redis：

```Bash
应用 ──> Redis
```

但随着业务增长，可能遇到：

- 数据量超过单机内存

- 单个 Redis 的读写压力太大

- Redis 故障后服务不可用

- 单机网络或 CPU 成为瓶颈

这时可以使用 Redis Cluster：

```Bash
应用
 ├──> Redis 节点 A
 ├──> Redis 节点 B
 └──> Redis 节点 C
```

Redis Cluster 会把数据分散到多个 Redis 节点上。

#### Redis Cluster 如何分配数据？

Redis Cluster 一共有 16,384 个哈希槽，每个 Key 会根据名称计算出一个哈希槽：

```Bash
user:1  ->  槽位 500
user:2  ->  槽位 8200
order:1 ->  槽位 13000
```

不同节点负责不同的槽位：

```Bash
节点 A：负责 0 ~ 5000
节点 B：负责 5001 ~ 10000
节点 C：负责 10001 ~ 16383
```

所以：

```Bash
user:1 由节点 A 保存
user:2 由节点 B 保存
order:1 由节点 C 保存
```

这叫做**数据分片**。

#### 应用如何找到正确节点？

应用不一定需要自己计算槽位。

Redis Cluster 客户端通常会自动处理：

```Bash
应用请求 Redis 节点 A
节点 A 发现 Key 应该在节点 B
节点 A 返回 MOVED
客户端自动请求节点 B
```

客户端通常会自动维护槽位和节点信息。

Node\.js 中常见的 `ioredis` 用法：

```JavaScript
import Redis from 'ioredis';

const redis = new Redis.Cluster([
  {
    host: '127.0.0.1',
    port: 7000,
  },
  {
    host: '127.0.0.1',
    port: 7001,
  },
]);

await redis.set('user:1:name', 'Alice');

const userName = await redis.get('user:1:name');

console.log(userName);

await redis.quit();
```

#### Redis Cluster 的主节点和副本节点

Redis Cluster 通常会为主节点配置副本：

```Bash
主节点 A
   └── 副本节点 A1

主节点 B
   └── 副本节点 B1

主节点 C
   └── 副本节点 C1
```

主节点负责读写，副本节点复制主节点数据。

如果主节点 A 发生故障：

```Bash
主节点 A 发生故障
        ↓
副本节点 A1
        ↓
提升为新的主节点
```

这样可以提高可用性。

#### Redis Cluster 主要解决什么问题？

1. **数据容量扩展**

    单个 Redis 内存不够时，可以把数据分到多个节点。

    ```Bash
    节点 A 保存一部分
    节点 B 保存一部分
    节点 C 保存一部分
    ```

2. **读写压力分散**

    不同 Key 可以分散到不同节点，避免所有请求都集中到一个 Redis。

3. **节点故障自动切换**

    主节点故障时，副本节点可以接替工作。

#### Redis Cluster 的限制

1. **多个 Key 可能不在同一个节点**

    例如：

    ```Bash
    SET user:1:name Alice
    SET user:1:age 18
    ```

    这两个 Key 可能被分配到不同节点。

    如果你执行涉及多个 Key 的操作：

    ```Bash
    MGET user:1:name user:1:age
    ```

    Redis Cluster 可能无法执行，因为两个 Key 不在同一个节点上。

2. **使用 Hash Tag 让 Key 落在同一个节点**

    可以在 Key 中使用 `{}`：

    ```Bash
    user:{1}:name
    user:{1}:age
    user:{1}:email
    ```

    Redis Cluster 只使用 `{}` 中的内容计算槽位：

    ```Bash
    user:{1}:name  -> 根据 1 计算
    user:{1}:age   -> 根据 1 计算
    user:{1}:email -> 根据 1 计算
    ```

    所以它们会被放到同一个槽位。

    这样就可以执行：

    ```Bash
    MGET user:{1}:name user:{1}:age user:{1}:email
    ```

    常见设计：

    ```Bash
    user:{1001}:profile
    user:{1001}:permissions
    user:{1001}:settings
    ```

    同一个用户的数据使用相同的 Hash Tag。

3. **Redis Cluster 不是简单的“内存加法”**

    Redis Cluster 可以扩展整体容量，但要注意：

    - 某个 Key 仍然只保存在一个主节点上；

    - 多 Key 操作需要考虑槽位；

    - 客户端需要支持 Cluster；

    - 部分命令在 Cluster 中有额外限制；

    - 运维复杂度高于单机 Redis。

### Lua 脚本

Lua 是一种脚本语言。

Redis 支持在服务器内部执行 Lua 脚本，把多条 Redis 命令写在一起。

例如，先判断库存，再扣减库存：

```Bash
读取库存
判断库存是否大于 0
如果大于 0，就扣减库存
```

如果在客户端分成多次执行：

```Bash
GET stock
判断 stock
DECR stock
```

多个客户端可能同时读取到相同库存，导致超卖。

Lua 脚本可以把这些操作放到 Redis 内部一次执行。

#### Lua 脚本的基本结构

Redis 中通常使用：

```Bash
EVAL script keyCount key... arg...
```

一个简单脚本：

```Bash
return redis.call('GET', KEYS[1])
```

执行：

```Bash
EVAL "return redis.call('GET', KEYS[1])" 1 user:1:name
```

解释：

```Bash
EVAL：执行 Lua 脚本
1：后面有 1 个 Key
user:1:name：传给 KEYS[1]
```

Lua 中的两个重要变量：

```Bash
KEYS：传入的 Redis Key
ARGV：传入的普通参数
```

#### Lua 脚本为什么是原子的？

Redis 通常使用单线程执行命令。

Lua 脚本开始执行后，Redis 会把整个脚本执行完，再处理其他客户端的命令：

```Bash
Lua 脚本开始
  ├── GET
  ├── 判断
  └── DECR
Lua 脚本结束
其他客户端命令继续执行
```

其他客户端不能插入到脚本中间。

因此下面这些操作可以作为一个整体执行：

```Bash
读取数据
判断条件
修改数据
```

这就是 Lua 脚本的原子性。

#### 库存扣减示例

假设：

```Bash
SET product:1:stock 2
```

Lua 脚本：

```Lua
local stock = tonumber(redis.call('GET', KEYS[1]))

if not stock or stock <= 0 then
    return 0
end

redis.call('DECR', KEYS[1])

return 1
```

含义是：

1. 获取库存；

2. 转成数字；

3. 如果库存不存在或小于等于 0，返回 `0`；

4. 否则扣减库存；

5. 返回 `1`。

执行：

```Bash
EVAL "
local stock = tonumber(redis.call('GET', KEYS[1]))

if not stock or stock <= 0 then
    return 0
end

redis.call('DECR', KEYS[1])

return 1
" 1 product:1:stock
```

返回：`1`，表示扣减成功。返回：`0`，表示库存不足。

#### Node\.js 中执行 Lua 脚本

使用 `ioredis`：

```JavaScript
import Redis from 'ioredis';

const redis = new Redis();

const decreaseStockScript = `
  local stock = tonumber(redis.call('GET', KEYS[1]))

  if not stock or stock <= 0 then
    return 0
  end

  redis.call('DECR', KEYS[1])

  return 1
`;

const result = await redis.eval(
  decreaseStockScript,
  1,
  'product:1:stock',
);

console.log(result === 1 ? '扣减成功' : '库存不足');

await redis.quit();
```

#### Lua 脚本中的 `redis.call` 和 `redis.pcall`

- `redis.call`

    ```Bash
    redis.call('GET', KEYS[1])
    ```

    如果 Redis 命令执行失败，脚本通常会报错。

    适合你希望错误直接暴露出来的场景。

- `redis.pcall`

    如果命令失败，返回错误对象，而不是立即中断脚本。

    适合需要自己处理错误的场景。

简单理解：

```Bash
redis.call：出错就报错
redis.pcall：出错后交给脚本处理
```

#### Lua 脚本在 Redis Cluster 中的限制

Lua 脚本中的所有 Key，通常必须位于同一个哈希槽。

错误示例：

```Bash
KEYS[1] = user:1:balance
KEYS[2] = account:1:log
```

这两个 Key 可能不在同一个节点。

正确做法是使用相同的 Hash Tag：

```Bash
user:{1}:balance
account:{1}:log
```

这样两个 Key 会落在同一个槽位，Lua 脚本才能正常处理。

Node\.js 示例：

```JavaScript
const script = `
  local balance = tonumber(redis.call('GET', KEYS[1]))

  if not balance or balance < tonumber(ARGV[1]) then
    return 0
  end

  redis.call('DECRBY', KEYS[1], ARGV[1])

  return 1
`;

const result = await redis.eval(
  script,
  1,
  'user:{1}:balance',
  30,
);
```

这里：

```Bash
KEYS[1]：Redis Key
ARGV[1]：扣减金额
```

如果使用 Redis Cluster，应该通过支持 Cluster 的客户端执行。

#### Lua 脚本的注意事项

1. **不要执行很长的脚本**

    Lua 脚本执行时会阻塞 Redis 处理其他命令。

    不要在脚本中做：

    - 大量循环；

    - 处理几十万条数据；

    - 复杂计算；

    - 长时间等待；

    - 调用外部 HTTP 服务。

    Redis Lua 脚本不能直接安全地调用外部服务。

2. **脚本要尽量简短**

    适合：

    ```Bash
    检查并扣减库存
    检查锁并删除锁
    计数器加一并判断结果
    写入多个相关 Key
    ```

    不适合：

    ```Bash
    完整订单流程
    复杂业务编排
    耗时数据分析
    ```

3. **Key 和参数要分开传入**

    推荐：

    ```JavaScript
    redis.eval(script, 1, 'stock:{1}', 10);
    ```

    不要把 Key 直接拼进脚本字符串，应该通过：`KEYS` 和 `ARGV` 传入。

    这样更安全，也更容易兼容 Redis Cluster。

---

### Redis 为什么设计成单线程？

#### 简化数据安全问题

如果多个线程同时修改同一个 Redis 数据结构，就需要处理：

- 锁

- 竞争

- 死锁

- 数据不一致

- 加锁和解锁开销

单线程下，命令按照顺序执行：

```Bash
一个命令执行完成
再执行下一个命令
```

很多操作天然就是安全的，不需要为每个数据结构加锁。

#### 天然保证命令级原子性

例如：

```Bash
INCR counter
```

在单线程模型下，整个 `INCR` 执行期间不会被其他命令插入。

因此不会出现：

```Bash
读取 counter
其他命令修改 counter
写回 counter
```

这类并发覆盖问题。

#### Redis 主要是内存操作

Redis 的数据主要放在内存中，很多命令执行非常快。

例如：

```Bash
GET
SET
INCR
HSET
SADD
```

它们通常不需要大量 CPU 计算。

在这种情况下，使用多个线程不一定更快，因为多线程还会带来：

- 线程切换

- 锁竞争

- 数据同步

- 调度成本

单线程反而足够高效。

#### 代码和架构更简单

单线程模型让 Redis 的核心逻辑更容易维护：

```Bash
命令进来
执行命令
返回结果
```

不需要让大量数据结构同时面对多个线程修改。

这也是 Redis 稳定性较高的重要原因之一。

---

#### 网络请求也容易顺序处理

Redis 的典型流程是：

```Bash
读取客户端请求
解析命令
执行命令
返回结果
```

单线程可以高效地使用事件循环处理大量连接。

这和 Node\.js 的事件循环思想有些相似：

```Bash
不是每个连接都创建一个线程
而是用事件循环管理大量连接
```

#### Redis Cluster 有多少个线程？

Redis Cluster 由多个 Redis 实例组成，每个实例通常都有自己的主线程。
