# RocketMQ 使用指南

Apache RocketMQ 是面向业务消息的分布式消息与流平台。
它以 Topic 和 MessageQueue 组织消息，重点能力包括局部顺序、延迟投递、事务消息、消费重试和死信处理。
本篇默认读者已掌握 Producer、Consumer、ACK、Consumer Group 和至少一次投递。
通用概念、幂等与 Outbox 的完整解释分别见 [[后端/消息队列/1. 消息队列基础入门|消息队列基础入门]] 和 [[后端/消息队列/2. 消息队列进阶知识|消息队列进阶知识]]。

本文只展开 RocketMQ 特有的模型、版本边界、Java API 和生产运维方法。
文中的版本结论以 Apache RocketMQ 4.x 传统 Remoting 客户端和 5.x 新客户端两条产品线区分。
RocketMQ 的客户端、Broker、Proxy 和控制器仍在演进；上线前应根据实际版本重新核对官方兼容矩阵、配置参考和发布说明。

## 1. RocketMQ 的定位与边界

### 1.1 它擅长解决什么问题

RocketMQ 适合需要以下能力的业务链路：

- 订单、支付、库存等按业务键保持局部顺序的事件；
- 超时取消、到期提醒等延迟触发；
- 本地事务结果与消息可见性需要最终一致协调的事务消息；
- 需要消费重试、死信队列和按 Consumer Group 隔离进度的异步处理；
- 写入吞吐较高、消息需要持久化并能按位点重放的事件流；
- Java 服务较多，团队能够维护 Broker 存储、复制和升级的系统。

RocketMQ 的强项是把业务消息常用能力放进统一平台，而不是让应用自行拼接多个调度和重试组件。
选择它仍然需要承担 Topic、MessageQueue、客户端版本、Broker 存储和高可用的治理成本。

### 1.2 它不负责什么

RocketMQ 不是业务主数据库。
CommitLog 能保留消息，不适合按任意业务字段完成强事务查询和报表。

RocketMQ 事务消息不是数据库与 Broker 之间的通用 XA 事务。
它通过半消息和事务回查确认“消息最终应提交还是回滚”，本地事务仍由应用数据库负责。

RocketMQ 不提供跨 MessageQueue 的全局顺序。
顺序范围必须收敛到同一个业务键、Message Group 或 MessageQueue。

RocketMQ 也不是精确到达的作业调度器。
延迟消息表示达到投递时间后可以被消费，Broker 负载、网络和消费者积压仍会增加实际执行延迟。

### 1.3 与 Kafka、RabbitMQ 的直观差异

| 维度 | RocketMQ | Kafka | RabbitMQ |
| --- | --- | --- | --- |
| 核心组织 | Topic + MessageQueue | Topic + Partition | Exchange + Queue |
| 典型优势 | 顺序、延迟、事务和业务重试 | 长保留、高吞吐、流处理生态 | 灵活路由、任务分发、协议生态 |
| 消费进度 | 4.x 以 Queue Offset 为主；5.x 以消息 ACK/不可见时间为主 | Group 在各 Partition 上的 Offset | Queue 投递状态与 ACK |
| 延迟消息 | 原生能力，4.x 与 5.x 模型不同 | 通常依赖应用或外部调度 | TTL、DLX 或插件 |
| 事务消息 | 半消息、本地事务、回查 | Kafka 内部事务和 Offset | 不提供同等业务事务消息模型 |
| 复杂路由 | Tag/SQL 过滤，能力相对克制 | 通常按 Topic/Key | Exchange/Binding 很灵活 |
| 长期生态 | Java 业务系统常见 | 数据平台和流处理广泛 | AMQP 任务与集成场景广泛 |

不要按“功能数量”选型。
需要长期事件归档和成熟流处理生态时，Kafka 往往更自然；需要 Exchange 级复杂路由时，RabbitMQ 更直接；延迟、顺序和事务消息是一级需求时，RocketMQ 值得优先验证。

## 2. 架构与核心对象

### 2.1 一次发送和消费经过哪些组件

```text
Producer
  | 1. 查询 Topic 路由
  v
NameServer ---------------------+
                               |
  +----------------------------+
  | 2. 返回 Broker 和 MessageQueue
  v
Broker Master / Leader
  | 3. 追加 CommitLog
  +--> 4a. 按策略刷盘与复制 --> Broker Replica
  +--> 4b. 异步 Dispatch --> ConsumeQueue / IndexFile

Consumer
  | 5. 查询路由并从 Broker 拉取
  | 6. 处理成功或返回失败
  v
消费进度 / Retry Topic / DLQ
```

Producer 和 Consumer 不通过 NameServer 转发消息体。
NameServer 只提供路由发现；客户端取得路由后直接连接 Broker，5.x 新客户端通常通过 Proxy 访问服务端。

### 2.2 NameServer

NameServer 保存集群、Broker、Topic 和 MessageQueue 的路由信息。
Broker 周期性向 NameServer 注册，客户端周期性刷新路由。

多个 NameServer 节点彼此独立，不通过共识协议复制一份强一致状态。
Broker 向配置的多个 NameServer 注册，客户端可连接任一可用节点获得路由。

NameServer 不保存消息，也不维护消费者业务进度。
NameServer 可用而 Broker 不可写时，发送仍然失败；Broker 可用但路由未注册或已过期时，客户端会报告找不到 Topic 路由。

生产环境通常部署多个 NameServer 并分散到不同故障域。
客户端应配置多个地址，网络策略只开放实际需要的端口。

### 2.3 Broker

Broker 接收消息、追加存储、复制数据、构建逻辑索引并向消费者提供读取接口。
一个 Broker 实例属于某个 Cluster，并具有 `brokerName` 和身份标识。

传统 4.x 部署常使用 Master/Slave 角色。
Master 接收写入，Slave 复制并提供容灾或读取能力；传统模式的故障切换能力取决于具体部署方式，并非所有组合都能自动选主。

5.x 可以使用 Controller 管理 Broker 副本组和主从切换。
这与传统静态 Master/Slave 配置不是同一个高可用模型，不能只增加 Controller 进程就认为迁移完成。

### 2.4 Producer

Producer 负责选择 Topic、构造消息属性、取得路由并把消息发送到目标 Broker。
普通消息可以按客户端负载均衡策略分散到多个 MessageQueue。

需要顺序时，Producer 必须用稳定业务键选择相同顺序范围。
发送重试要复用同一个业务消息 ID，并接受“Broker 已写入但响应丢失”的未知状态。

### 2.5 Consumer

Consumer 属于一个 Consumer Group。
4.x Remoting 客户端在集群消费时按 MessageQueue 分配实例；5.x 新客户端改为消息粒度负载均衡，同一 MessageQueue 的消息可以交给同组不同实例。
不同 Consumer Group 始终拥有独立的消费状态。

RocketMQ 的“Push”客户端并不是 Broker 主动把消息推入应用回调。
客户端内部仍通过长轮询拉取，再以监听器形式交给业务代码。

消费成功后客户端更新 ACK 或消费位点。
消费失败、超时或进程崩溃可能导致重新投递，因此业务处理必须幂等。

### 2.6 Topic、MessageQueue 与 Consumer Group

Topic 是消息的逻辑类别，例如 `order-events`。
MessageQueue 是 Topic 下的物理读写与局部顺序单元，也是 4.x Queue 粒度消费分配的基本范围。
5.x PushConsumer 与 SimpleConsumer 的普通消息使用消息粒度负载均衡，不能再用 Queue 数直接推导最大 Consumer 实例数。

增加 MessageQueue 数量可以分散写入，并提高 4.x Queue 粒度消费的并行上限，但也会增加路由、文件、分配和监控开销；5.x 普通消息的实例并行度不能只按 Queue 数估算。
如果应用用 `hash(key) % queueCount` 选 Queue，扩容 Queue 还可能改变相同 Key 的映射。

Consumer Group 表示一个逻辑订阅者，例如 `billing-v1`。
同一 Group 的实例必须保持相同的订阅表达式和消费语义；订阅不一致会产生难以解释的遗漏或重复。

### 2.7 Tag 与 Key

Tag 用于 Topic 内的一级业务分类和服务端过滤，例如 `OrderCreated`、`OrderPaid`。
一个消费者组应使用稳定的订阅表达式，不要让不同实例动态订阅不同 Tag。

Key 用于消息查询和业务定位。
它会进入索引，但不是数据库唯一约束；多条消息可以使用同一个 Key。

推荐同时保留以下标识：

| 字段 | 用途 |
| --- | --- |
| RocketMQ Message ID | 定位一次物理写入 |
| 业务 `messageId` | Producer 重试和 Consumer 幂等 |
| Key | 按订单号、支付号等查询消息 |
| Consumer Group | 区分独立消费进度和重试链路 |
| Trace ID | 关联请求、发送、消费和数据库操作 |

## 3. 存储：CommitLog、ConsumeQueue 与 IndexFile

### 3.1 CommitLog 是权威消息日志

Broker 把不同 Topic 和 MessageQueue 的消息顺序追加到 CommitLog。
顺序追加减少随机写，在页缓存和磁盘吞吐稳定时能获得较高写入性能。

CommitLog 记录消息体、属性、Topic、Queue 信息和时间等数据。
消息在 CommitLog 中的物理位置用于后续逻辑索引定位。

CommitLog 文件按固定大小滚动，旧文件再根据保留、磁盘水位和清理策略删除。
清理通常以文件为单位，不会因为某一条消息已消费就立即回收对应字节。

### 3.2 ConsumeQueue 是逻辑消费索引

ConsumeQueue 按 Topic 和 MessageQueue 组织逻辑条目。
每个条目至少能定位 CommitLog 中的物理 Offset、消息大小和过滤相关信息。

Consumer 使用 Queue Offset 扫描 ConsumeQueue，再回到 CommitLog 读取消息体。
因此消费进度中的 Offset 是某个 MessageQueue 的逻辑位置，不是 CommitLog 的全局物理位置。

ConsumeQueue 可以从 CommitLog 重建。
这意味着 CommitLog 是恢复消息主体的核心，但重建期间消费可用性和磁盘 I/O 会受到影响。

### 3.3 IndexFile 支持按 Key 查询

IndexFile 根据消息 Key 和时间范围建立哈希索引。
`mqadmin queryMsgByKey` 或管理工具可用它定位候选消息。

哈希索引可能发生冲突，Key 也不要求唯一。
查询结果仍需核对 Topic、业务 ID、时间和消息内容，不能把 IndexFile 当作权威业务查询库。

大量高基数 Key 会增加索引写入和磁盘占用。
只为真正需要审计和定位的业务字段设置 Key。

### 3.4 Dispatch 与可见性

消息写入 CommitLog 后，Broker 的分发逻辑继续生成 ConsumeQueue 和 IndexFile。
如果 Dispatch 明显落后，Producer 可能已经成功写入，但 Consumer 暂时看不到对应逻辑位置。

监控不能只看发送 TPS。
还要观察 CommitLog 最大位点、Dispatch 落后、ConsumeQueue 可读位点和消费者积压。

### 3.5 页缓存与内存映射

RocketMQ 依赖顺序写、内存映射文件和操作系统页缓存。
Broker 进程堆大小不能等同于消息缓存总量，机器仍需为页缓存保留足够内存。

磁盘写入尾延迟、脏页回写和容器内存限制都会影响 Broker。
不要在同一磁盘上同时运行不可控的大型扫描、备份压缩和消息回放。

### 3.6 同步刷盘与异步刷盘

同步刷盘在返回发送成功前等待数据按配置落到磁盘。
它缩小 Broker 进程或机器故障时的数据丢失窗口，但写入延迟受磁盘 `fsync` 尾延迟影响。

异步刷盘通常先写页缓存，再由后台线程刷盘。
吞吐和延迟更好，但突然断电或操作系统故障可能丢失尚未刷盘的数据。

选择不能只看消息是否“重要”。
需要用业务 RPO、磁盘性能、复制策略和发送确认边界共同决定。

### 3.7 同步复制与异步复制

同步复制等待副本达到协议规定的位置后再确认写入。
它降低单个 Master 故障时丢失已确认消息的概率，但副本或网络变慢会放大发送延迟。

异步复制由 Master 先确认，Slave 随后追赶。
它提高可用性和吞吐，但故障切换时可能丢失尚未复制的数据。

刷盘与复制是两个独立维度：

| 刷盘 | 复制 | 主要风险 |
| --- | --- | --- |
| 异步 | 异步 | 最近消息可能在进程、机器或主节点故障时丢失 |
| 同步 | 异步 | 本机磁盘较稳，但切换到落后副本仍可能缺消息 |
| 异步 | 同步 | 多副本已收到，但共同断电时仍取决于刷盘边界 |
| 同步 | 同步 | 丢失窗口较小，尾延迟和可用性成本最高 |

具体 Broker 模式和确认语义随版本变化，应通过故障测试验证，而不是只根据配置名称推断。

## 4. 四类消息

### 4.1 普通消息

普通消息不要求特定顺序或未来投递时间。
Producer 可以批量、压缩和在多个 MessageQueue 间均衡发送。

订单创建后的统计事件、日志投递和可并行处理的通知通常使用普通消息。
如果业务需要顺序、延迟或事务语义，应使用对应类型和专用 Topic，不要只在 payload 中增加一个布尔字段模拟。

### 4.2 FIFO 或顺序消息

顺序消息在满足对应版本前提时保证同一顺序范围内的发布和消费次序。
4.x 常通过稳定的 MessageQueue 选择器加顺序监听器实现；5.x 还要求 FIFO Topic、Message Group、Producer 串行发送和顺序 Consumer Group 配合。

顺序消息仍然可能重复。
如果前一条消息持续失败，同一范围内的后续消息可能被阻塞，以保护顺序。

全局顺序意味着把所有消息放进一个顺序范围，吞吐、故障隔离和扩容能力都会下降。
大多数订单系统只需要 `orderId` 级顺序。

### 4.3 延迟消息

延迟消息在指定时间之前不可被普通消费者取得。
4.x 传统客户端通过固定 Delay Level 选择预定义档位。

5.x Timer Message 支持按投递时间戳或延迟时长表达目标时间，不要求业务映射到传统固定档位。
可设置的最远未来时间和触发精度取决于 Broker 版本、消息类型和服务端配置。

延迟消息不是业务状态锁。
订单超时消息到达后仍需在数据库事务中检查订单是否保持 `PENDING`，不能覆盖已经支付的订单。

### 4.4 事务消息

事务消息先发送一条对消费者不可见的半消息。
Broker 接受半消息后，Producer 执行本地事务，再返回 Commit、Rollback 或 Unknown。

Commit 使消息可见，Rollback 放弃消息，Unknown 让 Broker 后续回查 Producer。
回查处理器只能读取持久化的本地事务状态，不能依赖内存，也不能在每次回查中重新执行扣款或库存变更。

## 5. Producer 的可靠发送

### 5.1 发送结果的含义

发送 API 成功表示 Broker 在所选刷盘、复制和协议边界上接受了消息。
它不表示 Consumer 已处理，也不表示下游数据库已经提交。

发送超时是未知状态。
Broker 可能尚未写入，也可能已写入但响应丢失；重试应复用业务 `messageId`，Consumer 使用唯一约束或 Inbox 去重。

### 5.2 路由缓存与故障切换

Producer 从 NameServer 或 Proxy 取得 Topic 路由，并在本地缓存。
新建 Topic、Broker 切换和 MessageQueue 变化不会瞬间出现在所有客户端。

路由失败时先区分：

- Topic 不存在或类型不匹配；
- Broker 尚未向 NameServer 注册；
- 客户端把 NameServer 地址误当成 5.x Proxy Endpoint；
- 容器返回了客户端不可达的 `brokerIP1`；
- ACL、TLS 或网络策略阻止客户端取得路由。

### 5.3 Retry 的边界

连接重置、临时超时和 Broker 切换可以有限重试。
Topic 不存在、权限拒绝、消息过大和序列化错误不会因立即重试恢复。

Producer 内部 Retry 只能覆盖发送过程。
数据库已提交但发送一直失败时，应由 Outbox 保存事件并异步发布，而不是让业务请求无限等待。

### 5.4 批量、压缩和大消息

批量能减少网络往返和系统调用，但一批失败会扩大重试范围。
顺序、延迟和事务消息对批量的支持与限制并不相同，必须按当前客户端文档核对。

消息体应只包含消费者完成动作所需的数据。
图片、压缩包和视频放对象存储，消息携带受权限保护的对象引用、摘要和版本。

生产前同时压测消息数速率与字节速率。
大量小消息更受协议和 CPU 影响，大消息更受网络、复制和磁盘影响。

### 5.5 Tag、Key 和业务 Envelope

Tag 用于粗粒度订阅，Key 用于查询，业务 Envelope 用于版本、幂等和追踪。
不要把同一个字段同时当作三种概念而不说明语义。

推荐消息属性至少包含：

```json
{
  "messageId": "evt_01J5ZQ7D9Y3M8N4K6T2R1C0BAX",
  "eventType": "OrderPaid",
  "schemaVersion": 3,
  "aggregateId": "order-1001",
  "aggregateVersion": 7,
  "occurredAt": "2026-08-07T10:00:00Z",
  "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "payload": {
    "paymentId": "pay-9001"
  }
}
```

RocketMQ 的物理 Message ID 不能替代上述业务 `messageId`。
人工重放或重新发布会产生新的物理写入，但业务逻辑仍应识别同一个事件。

## 6. 消费模型与版本边界

### 6.1 4.x Remoting 客户端

4.x Java 客户端常见接口包括：

- `DefaultMQPushConsumer`：内部长轮询拉取，以 Listener 回调形式交付；
- `DefaultLitePullConsumer`：应用控制 Poll 节奏，客户端仍管理分配和进度；
- `DefaultMQPullConsumer`：较早的低层 Pull API，已进入废弃路径，不应作为新项目起点；
- `MessageListenerConcurrently`：并发消费；
- `MessageListenerOrderly`：按 Queue 顺序消费。

这些 API 连接 NameServer 并直接与 Broker 使用 Remoting 协议通信。
不要把 5.x gRPC 客户端的 Endpoint、SimpleConsumer 或 Message Group 配置直接复制到这套 API。

### 6.2 5.x 新客户端

5.x 新客户端主要提供以下消费形态：

| 类型 | 交付方式 | 进度处理 | 适合场景 |
| --- | --- | --- | --- |
| PushConsumer | 客户端长轮询后调用 Listener | Listener 返回成功或失败 | 常规持续消费 |
| SimpleConsumer | 应用显式 `receive` | 成功后显式 `ack` | 需要控制批量、轮询和在途时间 |

5.x 新客户端通常连接 Proxy Endpoint，而不是把 NameServer `9876` 地址直接填入 `endpoints`。
Proxy 再负责与 Broker 集群通信。

PushConsumer 适合大多数服务。
业务成功后返回 `ConsumeResult.SUCCESS`；返回失败或抛出异常会进入客户端与服务端约定的重试路径。

SimpleConsumer 的消息在 Invisible Duration 内不可被其他消费者重新取得。
处理成功后必须显式 ACK；长任务要在支持的客户端中及时延长不可见时间，否则会发生并发重复。

### 6.3 Push 与 Pull 不等于投递语义

Push、Pull 和 SimpleConsumer 描述应用如何取得消息。
At-least-once、Retry、DLQ 和幂等描述故障后的业务语义。

把 PushConsumer 换成 SimpleConsumer 不会自动获得 Exactly-once。
显式 ACK 只是让提交点更可控，数据库事务和 ACK 仍是两个副作用。

### 6.4 消费负载均衡

4.x Remoting 客户端的 Clustering 模式按 MessageQueue 分配：同组一个 Queue 同时归一个实例，实例下线后由其他实例接管。
因此 4.x 中实例数量超过可分配 Queue 后，多出的实例会空闲。

5.x PushConsumer 和 SimpleConsumer 默认只使用消息粒度负载均衡，同一 MessageQueue 可以由同组多个实例共同处理。
5.x 扩容不受“实例数不得超过 Queue 数”的硬上限，但仍受 Broker/Proxy、最大在途消息、顺序 Message Group 和下游容量限制。

消费状态由 Broker 和客户端协议管理。
运维时必须先确认使用 4.x 还是 5.x 客户端，再查看 Queue Offset、ACK/Invisible Duration、实例负载与重试状态，不能只看进程是否在线。

### 6.5 4.x 广播消费

4.x Remoting 客户端的 Broadcasting 模式让每个 Consumer 实例各自收到一份消息。
它表达的是“每个实例执行”，而不是“每个业务订阅者执行一次”。

传统广播模式的消费进度和失败恢复能力不同于集群模式，通常不使用同样的服务端重试链路。
实例离线、扩容和重启都可能让行为难以审计。

配置刷新、进程本地缓存失效等确实需要每实例执行的动作可以考虑广播。
关键订单、支付和通知事件优先使用不同 Consumer Group 的集群消费。
5.x 新 Java 客户端没有对应的 Broadcasting 配置；要让多个逻辑订阅者各收一份，应创建多个 Consumer Group。

### 6.6 ACK、消费进度、Retry 与 DLQ

PushConsumer 的 Listener 成功返回后，客户端推进消费结果；失败则按 Group 策略重试。
SimpleConsumer 只有在应用显式 ACK 后才完成本次消费。

重试消息通常进入与 Consumer Group 关联的内部 Retry Topic。
超过最大尝试次数或无法继续处理后进入 Group 对应的 DLQ。

Retry 和 DLQ 是按 Group 隔离的。
搜索服务失败不会改变通知服务的消费进度，但两者都必须监控自己的最老未处理消息年龄。

不要让应用直接依赖 Retry Topic 或 DLQ 的内部命名规则实现业务路由。
使用管理 API、Console 或版本匹配的运维命令查看和受控重放。

### 6.7 失败分类

| 错误 | 是否自动重试 | 处理 |
| --- | --- | --- |
| 网络短暂失败 | 是 | 指数退避并限制总时长 |
| 数据库连接池暂时耗尽 | 是 | 降低并发，修复容量 |
| 下游限流 | 是 | 尊重 Retry-After 或退避 |
| Schema 不兼容 | 否 | 隔离并修复 Producer/Consumer |
| ACL 拒绝 | 否 | 修复权限，不热循环 |
| 业务不变量冲突 | 通常否 | 记录状态并人工或补偿处理 |
| 重复消息 | 不应报错 | 幂等返回成功并 ACK |

顺序消息遇到失败时不能简单跳过。
跳过会让后续状态越过缺失版本；持续重试又会阻塞同一顺序范围，必须由业务明确选择暂停、隔离还是补偿。

import java.nio.charset.StandardCharsets;
import org.apache.rocketmq.client.apis.ClientConfiguration;
import org.apache.rocketmq.client.apis.ClientServiceProvider;
import org.apache.rocketmq.client.apis.message.Message;
import org.apache.rocketmq.client.apis.producer.Producer;

public final class NormalProducer {

    public static void main(String[] args) throws Exception {
        String endpoints = requireEnv("ROCKETMQ_ENDPOINTS");

                .setTag("OrderCreated")
                .setKeys(orderId, eventId)
                .setBody(body.getBytes(StandardCharsets.UTF_8))
                .build();

            SendReceipt receipt = producer.send(message);
            System.out.printf("sent messageId=%s%n", receipt.getMessageId());
        }
    }

    private static String requireEnv(String name) {

### 7.3 PushConsumer

`PushConsumerApp.java`：

```java
package demo;

import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;
import java.util.Collections;
import java.util.concurrent.CountDownLatch;
import org.apache.rocketmq.client.apis.ClientConfiguration;
import org.apache.rocketmq.client.apis.ClientServiceProvider;
import org.apache.rocketmq.client.apis.consumer.ConsumeResult;
import org.apache.rocketmq.client.apis.consumer.FilterExpression;
import org.apache.rocketmq.client.apis.consumer.FilterExpressionType;
import org.apache.rocketmq.client.apis.consumer.PushConsumer;
import org.apache.rocketmq.client.apis.message.MessageView;

public final class PushConsumerApp {
    private PushConsumerApp() {}

    public static void main(String[] args) throws Exception {
        String endpoints = requireEnv("ROCKETMQ_ENDPOINTS");
        String topic = System.getenv().getOrDefault("ROCKETMQ_TOPIC", "order-events");
        String group = System.getenv().getOrDefault("ROCKETMQ_GROUP", "billing-v1");

        ClientServiceProvider provider = ClientServiceProvider.loadService();
        ClientConfiguration configuration = ClientConfiguration.newBuilder()
            .setEndpoints(endpoints)
            .build();
        FilterExpression filter = new FilterExpression("OrderCreated", FilterExpressionType.TAG);

        PushConsumer consumer = provider.newPushConsumerBuilder()
            .setClientConfiguration(configuration)
            .setConsumerGroup(group)
            .setSubscriptionExpressions(Collections.singletonMap(topic, filter))
            .setMessageListener(messageView -> consume(messageView))
            .build();
        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            try {
                consumer.close();
            } catch (Exception error) {
                System.err.println("close failed: " + error.getMessage());
            }
        }));
        new CountDownLatch(1).await();
    }

    private static ConsumeResult consume(MessageView messageView) {
        try {
            String body = decode(messageView.getBody());
            // 在返回 SUCCESS 前完成 Inbox 与业务数据库事务。
            System.out.printf("received id=%s body=%s%n", messageView.getMessageId(), body);
            return ConsumeResult.SUCCESS;
        } catch (RuntimeException error) {
            System.err.printf("consume failed id=%s error=%s%n",
                messageView.getMessageId(), error.getMessage());
            return ConsumeResult.FAILURE;
        }
    }

    private static String decode(ByteBuffer source) {
        ByteBuffer copy = source.asReadOnlyBuffer();
        byte[] bytes = new byte[copy.remaining()];
        copy.get(bytes);
        return new String(bytes, StandardCharsets.UTF_8);
    }

    private static String requireEnv(String name) {
        String value = System.getenv(name);
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException(name + " is required");
        }
        return value;
    }
}
```

运行：

```bash
export ROCKETMQ_GROUP='billing-v1'
java -cp 'target/classes:target/dependency/*' demo.PushConsumerApp
```

示例只在处理完成后返回 `SUCCESS`。
真实业务应把 Inbox 插入和订单更新放在同一个数据库事务中；返回 `FAILURE` 可能重投同一消息。

### 7.4 SimpleConsumer

SimpleConsumer 让应用控制单次领取数量和不可见时间。
适合需要自定义批量、主动流控或任务时长的消费者，但 ACK、续期和优雅关闭责任也更明确。

`SimpleConsumerApp.java`：

```java
package demo;

import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;
import java.time.Duration;
import java.util.Collections;
import java.util.List;
import java.util.concurrent.atomic.AtomicBoolean;
import org.apache.rocketmq.client.apis.ClientConfiguration;
import org.apache.rocketmq.client.apis.ClientServiceProvider;
import org.apache.rocketmq.client.apis.consumer.FilterExpression;
import org.apache.rocketmq.client.apis.consumer.FilterExpressionType;
import org.apache.rocketmq.client.apis.consumer.SimpleConsumer;
import org.apache.rocketmq.client.apis.message.MessageView;

public final class SimpleConsumerApp {
    private SimpleConsumerApp() {}

    public static void main(String[] args) throws Exception {
        String endpoints = requireEnv("ROCKETMQ_ENDPOINTS");
        String topic = System.getenv().getOrDefault("ROCKETMQ_TOPIC", "order-events");
        String group = System.getenv().getOrDefault("ROCKETMQ_GROUP", "billing-simple-v1");

        ClientServiceProvider provider = ClientServiceProvider.loadService();
        ClientConfiguration configuration = ClientConfiguration.newBuilder()
            .setEndpoints(endpoints)
            .build();
        FilterExpression filter = new FilterExpression("OrderCreated", FilterExpressionType.TAG);

        SimpleConsumer consumer = provider.newSimpleConsumerBuilder()
            .setClientConfiguration(configuration)
            .setConsumerGroup(group)
            .setAwaitDuration(Duration.ofSeconds(20))
            .setSubscriptionExpressions(Collections.singletonMap(topic, filter))
            .build();
        AtomicBoolean running = new AtomicBoolean(true);
        Thread mainThread = Thread.currentThread();
        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            running.set(false);
            mainThread.interrupt();
            try {
                consumer.close();
            } catch (Exception error) {
                System.err.println("close failed: " + error.getMessage());
            }
        }));

        try (consumer) {
            Duration invisibleDuration = Duration.ofSeconds(60);
            while (running.get() && !Thread.currentThread().isInterrupted()) {
                List<MessageView> messages = consumer.receive(16, invisibleDuration);
                for (MessageView message : messages) {
                    try {
                        System.out.printf("received id=%s body=%s%n",
                            message.getMessageId(), decode(message.getBody()));
                        // 在 ack 前完成幂等业务事务。
                        consumer.ack(message);
                    } catch (Exception error) {
                        System.err.printf("processing failed id=%s error=%s%n",
                            message.getMessageId(), error.getMessage());
                        // 不 ACK；消息在不可见时间到期后可再次投递。
                    }
                }
            }
        }
    }

    private static String decode(ByteBuffer source) {
        ByteBuffer copy = source.asReadOnlyBuffer();
        byte[] bytes = new byte[copy.remaining()];
        copy.get(bytes);
        return new String(bytes, StandardCharsets.UTF_8);
    }

    private static String requireEnv(String name) {
        String value = System.getenv(name);
        if (value == null || value.isBlank()) {
            throw new IllegalArgumentException(name + " is required");
        }
        return value;
    }
}
```

处理时长接近 60 秒时不能继续沿用示例默认值。
应提高 Invisible Duration，或使用当前客户端支持的变更不可见时间 API，并让最大在途数受数据库连接池约束。

## 8. 顺序消息的正确设计

### 8.1 先缩小顺序范围

订单状态只要求同一 `orderId` 有序，不要求所有订单全局有序。
账户流水通常按 `accountId` 有序，设备命令按 `deviceId` 有序。

顺序键基数太低会形成热点；基数太高且随机会失去业务顺序。
选择前应写出“哪些消息交换顺序会破坏不变量”。

### 8.2 4.x 的 Queue 选择与顺序监听

4.x Remoting 客户端常用 `MessageQueueSelector` 根据业务键选择固定 Queue。
Consumer 使用 `MessageListenerOrderly`，客户端对分配到的 Queue 串行交付并维护锁。

Queue 数变化可能改变哈希结果。
扩容前应验证既有 Key 与新消息的路由过渡，不能只在线增加 Queue 后假设历史顺序仍成立。

### 8.3 5.x 的 FIFO Topic 与 Message Group

5.x 把 FIFO 作为明确的消息类型。
完整顺序链路必须同时满足：Topic 类型为 FIFO、同一业务聚合使用相同 Message Group、Producer 按该 Group 串行发送、Consumer Group 开启顺序消费。
多个 Producer 并发发送同一 Message Group，或 Consumer Group 仍按普通并发模式运行，都不能仅靠 `setMessageGroup` 获得端到端顺序。

普通 Topic、FIFO Topic、Delay Topic 和 Transaction Topic 的类型约束属于 5.x 服务端契约。
创建 Topic 时应声明正确类型，并验证 Proxy、Broker 和客户端都支持相同能力。

以下 CLI 形状分别创建 FIFO Topic 和顺序 Consumer Group；参数细节仍以部署版本的 `mqadmin help` 为准：

```bash
sh mqadmin updateTopic \
  -n localhost:9876 -c DefaultCluster -t order-fifo \
  -a +message.type=FIFO

sh mqadmin updateSubGroup \
  -n localhost:9876 -c DefaultCluster -g order-fifo-consumer \
  -o true
```

5.x Producer 构造 FIFO 消息的关键差异是增加 Message Group：

```java
Message fifoMessage = provider.newMessageBuilder()
    .setTopic("order-fifo")
    .setTag("OrderStatusChanged")
    .setKeys("order-1001")
    .setMessageGroup("order-1001")
    .setBody("{\"status\":\"PAID\",\"version\":2}"
        .getBytes(StandardCharsets.UTF_8))
    .build();
```

这段代码复用 7.2 中声明的 `provider` 和 `StandardCharsets`。
它只展示 FIFO 消息构造差异，不是另一套独立 Producer。

### 8.4 重试、热点与顺序阻塞

同一顺序范围的前一条消息失败时，后续消息通常需要等待。
如果错误不可恢复，应将该业务聚合转入可审计的人工或补偿状态，不能无限重试占住 Queue。

热点 Order 或 Account 会限制单 Message Group 的吞吐。
需要更高并行度时应拆分业务聚合或减少单聚合事件数量，不能用随机后缀破坏必须的顺序。

Consumer 仍应检查 `aggregateVersion`。
顺序传输不能消除 Producer 多实例、历史回放、跨 Topic 事件和人工修复造成的业务乱序。

## 9. 延迟消息：4.x 与 5.x

### 9.1 4.x 固定 Delay Level

传统 RocketMQ 通过 Broker 配置一组延迟等级。
Producer 调用 `setDelayTimeLevel(level)` 选择其中一个档位，不能直接指定任意时间戳。

默认部署常见从秒、分钟到小时的固定档位，但档位内容可以由 Broker 配置改变。
应用不能把“Level 3 永远等于 10 秒”当作跨集群协议，应把档位表纳入配置和变更审计。

Broker 会先把延迟消息放入内部调度结构，到期后再恢复其真实 Topic 和 Queue。
调度积压、磁盘压力和 Broker 重启都会影响实际投递时间。

### 9.2 5.x Timer Message

5.x 新客户端可在消息上设置 Delivery Timestamp：

```java
long deliverAt = System.currentTimeMillis() + Duration.ofMinutes(15).toMillis();
Message delayedMessage = provider.newMessageBuilder()
    .setTopic("order-timeout")
    .setTag("CheckPaymentTimeout")
    .setKeys("order-1001")
    .setDeliveryTimestamp(deliverAt)
    .setBody("{\"orderId\":\"order-1001\"}"
        .getBytes(StandardCharsets.UTF_8))
    .build();
```

这段代码复用 7.2 的 `provider`，并需要 `java.time.Duration`。
5.x 官方标准能力通常以秒级投递精度和有限的未来时间窗口描述 Timer Message；具体最大窗口应以所部署版本的官方参数和实测拒绝边界为准。

5.x Timer Message 不是 4.x Delay Level 的客户端语法糖。
它依赖新的消息类型、Broker 定时存储和兼容的客户端/Proxy，升级客户端本身不会让旧 Broker 自动获得该能力。

### 9.3 延迟消息的业务正确性

消息到期时只能触发一次状态检查：

```text
收到 CheckPaymentTimeout
  -> 按 orderId 锁定或条件更新订单
  -> status == PENDING 且 deadline <= now 才取消
  -> 已支付、已取消或版本更高则幂等结束
  -> 提交事务后确认消息
```

不要用 Broker 送达时间替代数据库权威时间。
时钟偏差、积压和重试都可能使消息晚到；Consumer 必须按业务 Deadline 再校验。

长期、可修改、可取消且精度要求高的调度任务，更适合保存到专用调度存储。
RocketMQ 只负责传递触发信号，不负责复杂日历和任务依赖。

## 10. 事务消息与回查边界

### 10.1 完整状态机

```text
Producer -> Broker: 发送半消息
Broker -> Producer: 半消息已保存
Producer -> Database: 执行本地事务
Producer -> Broker:
  COMMIT   -> 消息对 Consumer 可见
  ROLLBACK -> 消息不再投递
  UNKNOWN  -> 等待事务回查

Broker -> Transaction Checker: 查询本地事务结果
Checker -> Broker: COMMIT / ROLLBACK / UNKNOWN
```

半消息已保存后才执行本地事务，避免 Consumer 提前看到尚未决定的业务事实。
本地事务完成但最终状态没有送达 Broker 时，回查负责恢复决定。

### 10.2 本地事务表

事务处理器应在本地数据库事务中同时更新业务表和事务状态表：

```sql
BEGIN;

WITH paid AS (
  UPDATE orders
  SET status = 'PAID', version = version + 1
  WHERE order_id = :order_id
    AND status = 'PENDING'
  RETURNING order_id
)
INSERT INTO mq_transaction_log (
  transaction_id, business_key, state, updated_at
)
SELECT :transaction_id, order_id, 'COMMIT', now()
FROM paid
ON CONFLICT (transaction_id) DO NOTHING
RETURNING business_key, state;

-- 仅当返回 COMMIT，或既有同一 transaction_id 的 COMMIT 记录通过校验时提交。
-- 未更新订单且不存在终态记录时，由应用写入不可变 ROLLBACK 或返回 UNKNOWN。
COMMIT;
```

这条 CTE 只有在订单状态更新成功时才写入 `COMMIT`。
应用必须检查事务日志插入结果：冲突时读取既有记录并校验 `business_key` 与终态一致；更新未命中且没有既有记录时，应按业务事实写入不可变的 `ROLLBACK` 或返回 `UNKNOWN`，不能写入 `COMMIT`。
终态记录使用 `ON CONFLICT DO NOTHING`，不能因为重复执行或回查而把 `ROLLBACK` 覆盖成 `COMMIT`。

### 10.3 回查必须只读持久化结果

回查可能在原 Producer 重启后由另一个实例执行，也可能重复执行。
Checker 应按 Transaction ID 或稳定业务键查询事务表，然后返回最终状态。

以下做法不可靠：

- 从进程内 Map 查询本地事务结果；
- 收到回查后重新扣款或更新库存；
- 查询超时时直接返回 Commit；
- 本地事务没有审计记录，只通过订单“看起来已支付”猜测；
- 多个服务用不同规则解释同一 Transaction ID。

查询暂时失败时可以返回 Unknown，让 Broker 后续再查。
持续 Unknown 必须告警，因为服务端不会无限期替业务保留不确定状态。

### 10.4 事务消息的原子边界

事务消息协调的是本地事务结果与 RocketMQ 消息最终可见性。
它不能把 Consumer 数据库、第三方支付、邮件、搜索和人工操作纳入同一个原子提交。

Consumer 仍可能重复收到已提交事务消息。
订单、库存和账务消费者仍要使用唯一业务键、版本条件更新或 Inbox。

如果团队已使用通用 Outbox，并需要跨多种 Broker 或 CDC 发布，继续使用 Outbox 往往更容易审计。
事务消息适合团队能够稳定维护 Producer 回查服务，且希望使用 RocketMQ 原生协调能力的场景。

## 11. 幂等、积压与容量

RocketMQ 默认仍是 At-least-once 业务链路。
Producer 超时重试、消费结果丢失、Invisible Duration 到期、进度重置和 DLQ 重放都会产生重复。
幂等实现复用 [[后端/消息队列/2. 消息队列进阶知识|消息队列进阶知识]] 中的唯一约束、Inbox 和版本条件更新，不应只缓存 RocketMQ Message ID。

积压应同时观察 Group 在每个 MessageQueue 上的差值和最老未消费时间。
平均 Lag 正常但单 Queue 持续增长，通常表示热点 Key、顺序阻塞或该 Queue 所在 Broker 异常。

```text
净恢复速率 = 稳定消费速率 - 当前生产速率
恢复时间约 = backlog / 净恢复速率
磁盘基线约 = 峰值写入字节率 × 保留时间 × 副本数 × 写放大与余量
```

延迟、事务、Retry 和 DLQ 会产生额外内部写入，不能只按业务 Topic 入站字节估算磁盘。
4.x 扩 Consumer 还受可分配 MessageQueue 数限制；5.x 消息粒度负载均衡没有该硬上限，但两者都受 Broker/Proxy、顺序范围和数据库容量约束。
扩容前应先处理热点、慢 SQL 或重试风暴。

## 12. 安全、监控与部署

### 12.1 ACL 与 TLS

- Producer 只获得目标 Topic 的写权限，Consumer 只获得目标 Topic 和 Group 的读权限；
- NameServer、Broker、Proxy 和管理端口放在受控网络，不直接暴露公网；
- 生产链路必须验证 CA 与主机名；Java `5.0.7` 原生 SSL 开关不满足该要求，应使用已验证的更新客户端或可信 TLS Sidecar/代理；
- Access Key、Secret Key 和证书由密钥系统注入，日志只记录凭证版本或掩码；
- `mqadmin`、Offset Reset、DLQ 重放和 Topic 删除使用独立运维身份并完整审计；
- 凭证轮换应验证长连接重建，新旧凭证只在有限窗口同时有效；
- 消息体最小化个人信息，日志和 DLQ 导出遵守相同的数据保留策略。

### 12.2 必须监控的 RocketMQ 指标

| 层级 | 重点指标 | 直接动作 |
| --- | --- | --- |
| NameServer | Broker 注册、路由变化、请求错误 | 检查注册链路和节点时间 |
| Broker 写入 | Put TPS、p99、拒绝、Page Cache Busy | 检查磁盘延迟、刷盘和限流 |
| 存储 | CommitLog/ConsumeQueue 位点、磁盘水位、清理失败 | 扩容或限速，避免强删文件 |
| 复制 | 副本差值、复制延迟、可切换副本数 | 修复网络/副本后再切换 |
| Consumer | Group Lag、最老消息、消费失败、实例分配 | 找热点 Queue 和慢下游 |
| 特殊消息 | Timer 延迟、事务 Unknown/回查、Retry/DLQ | 修复调度或本地事务查询 |
| 业务 | 幂等冲突、订单差异、重复副作用 | 对账并受控修复 |

### 12.3 生产拓扑

NameServer 至少跨两个故障域部署多个实例。
关键 Broker 使用满足 RPO 的副本组；传统 Master/Slave、DLedger 和 5.x Controller 模式应按一种经过验证的方案部署，不能混合概念。

Broker 数据盘使用稳定低延迟磁盘并预留页缓存。
Proxy 可独立扩容并限制连接数；它故障不应连带删除 Broker 数据。

Topic 的读写 Queue 数、消息类型、ACL 和 Consumer Group 都应通过配置管理创建。
RocketMQ 的 CommitLog 由 Broker 共享，默认保留策略属于 Broker/存储节点配置，不是可按 Topic 独立设置的属性；需要显著不同保留期时通常应拆分集群。
禁止应用启动时无界创建 Topic 或修改生产属性。

### 12.4 升级与灾备

升级前保存 Broker、NameServer、Proxy、Controller、ACL、Topic 和 Group 配置，并核对客户端兼容矩阵。
先在同等数据量的预发布环境验证滚动重启、复制追平、路由刷新、事务回查和 Timer Message。

传统 Master/Slave 与 Controller 模式的升级顺序不同，应遵循目标版本官方说明。
启用 5.x Topic 类型、Proxy 或存储特性后，要单独验证回滚是否仍能读取数据。

副本不是备份：误删 Topic、错误 Offset Reset 和坏消息会同步到副本。
灾备需保存配置与 ACL，并演练备用集群路由、Producer 切换、Consumer 起点、重复处理和业务对账。

## 13. Docker 与 CLI 最小实验

以下命令固定 `5.3.2` 作为可复现实验版本；若镜像不可用，应从 Apache 官方发布页选择同一 Broker/Proxy 版本后整体替换。
它只适合本机学习，不包含生产 ACL、TLS、副本和持久卷。

```bash
docker network create rocketmq-demo

docker run -d --name rmqnamesrv \
  --network rocketmq-demo \
  -p 9876:9876 \
  apache/rocketmq:5.3.2 \
  sh mqnamesrv

docker run -d --name rmqbroker \
  --network rocketmq-demo \
  -p 10909:10909 -p 10911:10911 \
  -p 8080:8080 -p 8081:8081 \
  -e NAMESRV_ADDR=rmqnamesrv:9876 \
  apache/rocketmq:5.3.2 \
  sh mqbroker -n rmqnamesrv:9876 --enable-proxy
```

检查集群并创建普通 Topic：

```bash
docker exec rmqbroker sh mqadmin clusterList -n rmqnamesrv:9876
docker exec rmqbroker sh mqadmin updateTopic \
  -n rmqnamesrv:9876 -c DefaultCluster -t order-events
docker exec rmqbroker sh mqadmin topicRoute \
  -n rmqnamesrv:9876 -t order-events
```

此时第 7 节 Java 客户端使用 `ROCKETMQ_ENDPOINTS=127.0.0.1:8081`。
CLI 使用 `rmqnamesrv:9876` 是因为命令运行在 Docker 网络内并查询 NameServer；两个地址不能互换。

常用只读命令：

```bash
docker exec rmqbroker sh mqadmin topicList -n rmqnamesrv:9876
docker exec rmqbroker sh mqadmin consumerProgress \
  -n rmqnamesrv:9876 -g billing-v1
docker exec rmqbroker sh mqadmin queryMsgByKey \
  -n rmqnamesrv:9876 -t order-events -k order-1001
```

`resetOffsetByTime`、Topic 删除和 DLQ 重放会改变状态，执行前先运行 `mqadmin help <command>`，记录范围和回滚方案。

停止实验：

```bash
docker rm -f rmqbroker rmqnamesrv
docker network rm rocketmq-demo
```

如果传统 Remoting 客户端从 NameServer 得到不可达的容器地址，应显式配置 Broker 对客户端可达的 `brokerIP1`。
5.x Java 示例经已发布的 Proxy 端口连接，不应通过修改 `/etc/hosts` 掩盖错误路由。

## 14. Node.js 客户端边界

Apache RocketMQ 官方 `rocketmq-clients` 仓库已经包含 Node.js 5.x gRPC 客户端，npm 包名为 `rocketmq-client-nodejs`。
截至 2026-08-07，官方仓库 `package.json` 为 `1.0.7`，要求 Node.js `>=16.19.0`，并建议使用 `>=18.17.0`。

官方状态表列出 Normal、FIFO、Delay、Transaction Producer，以及 SimpleConsumer 和 PushConsumer；PullConsumer 尚未完成。
该客户端连接 Proxy Endpoint，不是 4.x Remoting NameServer 客户端。

社区中还存在名称相近的 npm 包。
不能仅凭包名包含 `rocketmq` 判断官方身份；应核对仓库是否属于 `apache/rocketmq-clients`、npm 的 Repository 元数据、发布标签和实际维护状态。

Node.js 核心链路上线前仍要验证事务、FIFO、Timer、TLS/ACL、重平衡和优雅关闭是否满足当前 Broker/Proxy 版本。
若所需能力尚未覆盖，再考虑由 Java 发布服务消费 Outbox，而不是自行猜测或封装不存在的 API。

## 15. 排障速查

| 现象 | 优先检查 | 不要做 |
| --- | --- | --- |
| `No route info` | Topic、消息类型、Broker 注册、地址类型、`brokerIP1` | 无限重试 |
| 发送超时 | Proxy/Broker p99、磁盘、刷盘、复制、限流 | 生成新业务 ID |
| 消费不到 | Group、Tag、Queue 分配、Offset、ACL、Topic 类型 | 随意重置 Offset |
| 重复消费 | ACK/Invisible Duration、重平衡、进度重置、重放 | 用内存 Set 去重 |
| 顺序破坏 | Queue 选择、Message Group、Producer 并发、版本号 | 宣称跨 Queue 全局有序 |
| 单 Queue 积压 | 热点 Key、前序失败、下游慢查询 | 只增加实例 |
| DLQ 激增 | Schema、权限、业务不变量、重试上限 | 直接清空 DLQ |
| 事务持续 Unknown | 本地事务表、Checker 可用性、查询延迟 | 回查时重新执行业务 |
| 延迟消息晚到 | Timer 堆积、Broker 负载、Consumer Lag | 把投递时间当精确定时 |
| 磁盘快速上涨 | Retention、Retry/DLQ、事务半消息、Dispatch | 手工删除 CommitLog |

## 16. 测试、适用场景与限制

上线前至少验证：发送响应丢失、Broker 重启、副本落后、Consumer 崩溃、Invisible Duration 到期、顺序消息失败、Timer 晚到、事务回查、DLQ 重放和滚动升级。
每项实验都要核对物理消息数、业务结果数、Lag、重复数和最终对账。

优先选择 RocketMQ：Java 服务占主导；延迟、局部顺序和事务消息是核心需求；团队能维护 Broker/Proxy/Controller；需要按 Group 隔离重试与死信。

谨慎选择 RocketMQ：团队没有值班和恢复能力；主要需求是复杂 AMQP 路由；主要需求是多年事件湖与流处理生态；Node.js 客户端成熟度是硬约束；无法接受版本能力差异。

## 17. 高频面试题

### NameServer 会转发消息吗？
不会。它提供路由发现，消息数据由客户端直接发送到 Broker，5.x 新客户端通常经 Proxy 接入。

### CommitLog、ConsumeQueue 和 IndexFile 分别做什么？
CommitLog 保存消息主体，ConsumeQueue 提供 Topic/Queue 逻辑消费索引，IndexFile 提供按 Key 和时间定位的辅助索引。

### PushConsumer 是真正的服务端 Push 吗？
不是。客户端内部长轮询 Pull，再把消息交给 Listener。

### 4.x Delay Level 与 5.x Timer Message 有何区别？
前者选择 Broker 预设档位；后者表达投递时间戳或延迟时长，并依赖 5.x 消息类型、Broker 和 Proxy 能力。

### 事务回查为什么不能重新执行本地事务？
回查可能重复且发生在其他实例；它只能读取持久化事务结果，否则会造成重复扣款或状态漂移。

### 顺序消息为什么仍需幂等和版本号？
顺序范围内仍可能重复，人工回放和跨 Topic 来源也可能乱序；版本号用于拒绝旧状态和识别缺口。

### Consumer 增加后为什么 Lag 不下降？
4.x 可能已经没有可分配 MessageQueue；5.x 则应检查 Broker/Proxy、最大在途消息、顺序 Message Group、Retry 和数据库瓶颈，不能套用 Queue 数上限。

### 同步刷盘等于同步复制吗？
不等于。刷盘控制本机持久化边界，复制控制副本达到的位置，两者必须分别配置和验证。

### 广播消费为什么不适合关键业务事件？
4.x Broadcasting 按实例而非逻辑订阅执行，实例变化、离线和传统重试/进度边界更难审计；5.x 新客户端应使用多个 Consumer Group 表达多个逻辑订阅者。

### 5.x Java 客户端为什么不能填 NameServer 地址？
新客户端使用 Proxy Endpoint；NameServer 地址属于路由服务和传统 Remoting 客户端边界。

### IndexFile 能否替代业务查询库？
不能。Key 可重复且哈希可能冲突，索引只用于消息定位和排障。

### 如何证明 RocketMQ 灾备可用？
实际切换备用入口，验证路由、消息、消费起点、重复处理和业务对账，并测量 RPO/RTO。
