# Kafka 使用指南

Kafka 是面向高吞吐事件流的分布式追加日志。
它把记录持久化到 Topic 的 Partition 中，让多个 Consumer Group 按各自 Offset 独立读取和回放。
Kafka 的优势来自顺序写、批处理、分区并行和可保留日志；代价是只提供分区内顺序、运维依赖磁盘与副本健康，而且任务重试、逐条 ACK、复杂路由需要应用自己建模。

本文只展开 Kafka 特有的机制与工程实践。
Producer、Consumer、投递语义、幂等和 Outbox 的通用定义见 [[后端/消息队列/1. 消息队列基础入门|消息队列基础入门]] 与 [[后端/消息队列/2. 消息队列进阶知识|消息队列进阶知识]]。

## 版本边界

本文面向 Apache Kafka 4.x：4.x 集群使用 KRaft，不再把 ZooKeeper 模式作为可选运行架构。
维护 Kafka 3.x 或更早集群时，应先按对应版本官方迁移文档处理 ZooKeeper、协议与配置差异。
Kafka 的默认配置、支持的升级路径、Consumer Group 协议和镜像启动参数会随版本变化。
生产变更必须以实际部署版本的 Apache Kafka 官方文档、配置参考和升级说明为准。
文中不依赖某个小版本默认值；出现配置名时，重点说明它控制的边界。

KafkaJS 示例按 `2.2.4` 的公开 `Kafka`、`Producer`、`Consumer`、`send`、`run`、`commitOffsets`、`stop` 和 `disconnect` API 编写。
该版本使用 Classic Consumer Group Protocol，`idempotent` Producer 选项仍标记为 Experimental；升级客户端时必须重新验证协议、重试和故障恢复行为。
不同客户端的默认 Partitioner、重试次数、超时和事务 API 不完全相同，不能直接照搬配置值。

## 1. Kafka 的定位与边界

### 1.1 Kafka 解决什么问题

Kafka 适合把持续产生的事件写成可复制、可并行读取、可在保留期内回放的日志。
典型用途包括：

- 服务间领域事件与异步数据传播；
- Change Data Capture（CDC）和数据库增量同步；
- 日志、指标、埋点等高吞吐采集管道；
- 搜索索引、缓存、数仓等派生视图更新；
- Kafka Streams、Flink 等流处理系统的输入和输出；
- 需要多个独立订阅者按各自进度读取同一份历史数据的场景。

Consumer 成功读取不会删除记录。
记录是否仍可读取由 Retention 和 Compaction 决定，而不是由某个 Consumer 的处理结果决定。
因此 Kafka 更接近“可回放事件日志”，不是“消费后立即删除的任务箱”。

### 1.2 Kafka 不自动提供什么

Kafka 不自动保证数据库更新与消息发布共同提交。
应用写数据库后再写 Kafka 仍有双写窗口，通常需要 Outbox 或 CDC。

Kafka 不保证跨 Partition 全局顺序。
同一业务实体需要有序时，必须使用稳定 Key 把相关记录路由到同一 Partition，并让 Consumer 按该 Partition 的顺序处理。

Kafka 不保证外部副作用 Exactly-once。
Kafka Transaction 可以原子提交 Kafka 内的输出记录和 Consumer Offset，但不能把 PostgreSQL、HTTP、邮件或支付接口自动纳入同一事务。

Kafka Core 也没有 RabbitMQ 风格的 Exchange、逐条 NACK、原生 Dead Letter Queue 或任意延迟投递。
Retry Topic、DLQ、延迟调度和复杂路由通常由应用、Kafka Streams、Kafka Connect 或其他调度系统实现。

### 1.3 什么时候不优先选择 Kafka

单任务领取、逐条 ACK/重新入队、优先级、复杂动态路由或精确延迟执行是核心需求时，任务队列或路由型 Broker 通常更直接。
消息量很小且团队无法承担分区、磁盘、升级和恢复成本时，Kafka 的能力也可能超过实际需要。
选型要比较保留与回放、顺序范围、路由、延迟、跨地域恢复和团队成本，不能只看峰值 TPS。

## 2. 集群与元数据架构

### 2.1 Broker

Broker 是 Kafka 集群的数据节点。
它接收 Produce/Fetch 请求，保存 Partition Replica，参与副本同步，并向客户端提供 Topic、Partition 和 Leader 元数据。

一个 Partition 的不同 Replica 分布在不同 Broker 上。
同一 Broker 可以同时是一些 Partition 的 Leader 和另一些 Partition 的 Follower。
客户端先取得元数据，再直接连接目标 Partition 的 Leader；请求不必经过一个固定网关。

KRaft 使用 `node.id` 标识 Broker 或 Controller 节点，并要求集群内唯一；旧资料中的 `broker.id` 属于历史配置语境。
生产环境还要为 Broker 设置稳定地址、独立数据目录、磁盘水位告警和机架信息。
如果客户端通过 NAT、容器或多网卡访问，`advertised.listeners` 必须发布客户端真正可达的地址。

### 2.2 Controller 与 KRaft

KRaft 使用 Raft 元数据 Quorum 管理 Topic、Partition、副本分配、Broker 注册、配置和 ACL 等集群元数据。
Controller 节点维护元数据日志，其中一个是 Active Controller，其余作为 Quorum 成员跟随提交记录。

Active Controller 负责处理元数据变更和 Partition Leader 选举。
Controller 故障时，只要 Quorum 仍有多数成员可通信，就能选出新的 Active Controller。
丢失多数派时，不能安全提交新的元数据变更。

开发环境可以让同一进程同时承担 Broker 与 Controller 角色。
较大生产集群通常把 Controller 角色与数据 Broker 分离，避免数据 IO、GC 或磁盘故障同时影响元数据 Quorum。

Controller Quorum 常用奇数成员以形成明确多数派。
成员过少降低容错，成员过多增加协调和变更成本；应根据故障域和官方容量建议选择，而不是把所有 Broker 都设为 Controller。

### 2.3 Topic 与 Partition

Topic 是逻辑事件流名称，Partition 是其物理并行单元。
每个 Partition 是独立的有序追加日志，记录用单调递增的 Offset 标识位置。

Partition 数决定三个重要边界：

1. 同一 Consumer Group 的最大稳定并行度；
2. Key 的顺序范围；
3. Leader、副本、文件和元数据的数量。

更多 Partition 可以增加并行度，但不会免费提升性能。
它会增加文件句柄、内存索引、Leader 选举、Rebalance、复制和运维成本。

Partition 数可以增加，但常规操作不能直接减少。
增加 Partition 后，默认 Key 映射可能变化；同一 Key 的新记录可能进入不同 Partition，从而破坏跨扩容时点的顺序假设。

### 2.4 Replica、Leader 与 Follower

Replication Factor 表示每个 Partition 保存多少份 Replica。
其中一个 Replica 是 Leader，其他是 Follower。
常规 Produce 写入 Leader，Follower 主动从 Leader Fetch 并追加相同记录。

客户端收到成功响应的安全程度取决于 `acks`、当前 ISR 和 `min.insync.replicas`。
Replication Factor 只说明副本目标数量，不说明当前有多少副本已经同步，也不等于备份。

Leader 故障后，Controller 从符合选举条件的 Replica 中选择新 Leader。
如果允许 Unclean Leader Election，落后的 Replica 也可能成为 Leader，以可用性换取已确认记录丢失的风险。
关键数据通常应关闭这种降级路径，并通过足够的副本与故障域维持 ISR。

### 2.5 ISR、LEO、High Watermark 与 Last Stable Offset

ISR（In-Sync Replicas）是当前被认为与 Leader 保持足够同步的 Replica 集合。
它是动态状态，不等于静态 Replica 列表。

LEO（Log End Offset）表示某个 Replica 日志末端的下一个 Offset。
不同 Replica 短时间内可能有不同 LEO。

High Watermark 表示已经复制到所需同步副本、普通 Consumer 可以安全读取的边界。
Leader 已本地追加但尚未越过 High Watermark 的记录，不应被当作已稳定提交的数据。

事务 Topic 还涉及 Last Stable Offset。
`read_committed` Consumer 只能读取已完成事务所允许看到的边界，并跳过已中止事务的记录。

监控只看 Broker 存活不够。
ISR Shrink、Under-Replicated Partition、Offline Partition、Controller Quorum Lag 才能直接暴露复制和元数据风险。

### 2.6 写入路径

一次典型写入经历以下步骤：

```text
Producer
  -> 获取 Topic/Partition Leader 元数据
  -> 按 Key 或 Partitioner 选择 Partition
  -> 在客户端累积 Batch 并压缩
  -> 向 Leader 发送 ProduceRequest
  -> Leader 追加本地日志
  -> Follower Fetch 并复制
  -> 满足 acks 与 min.insync.replicas
  -> Producer 收到成功响应
```

Producer 超时不等于 Broker 没有写入。
响应可能在返回途中丢失，重试必须允许同一逻辑事件再次出现。
Idempotent Producer 可以抑制符合其会话和序列号边界的重复写入，但 Consumer 仍要做业务幂等。

### 2.7 读取路径

Consumer 先加入 Group 并取得 Partition 分配，再向各 Leader 发起 Fetch。
Broker 可以等待积累一定数据后返回，以减少空轮询和网络开销。

```text
Consumer Group
  -> Coordinator 完成成员管理与分配
  -> Consumer 从已提交 Offset 开始 Fetch
  -> 反序列化并执行业务处理
  -> 提交“下一条要读取的 Offset”
  -> 继续 Fetch
```

Fetch 到客户端内存不表示业务完成。
业务事务成功后再 Commit 是常见 At-least-once 边界；处理完成但 Commit 失败会产生重复。

## 3. 日志、Segment 与清理

### 3.1 追加日志与 Offset

Partition Log 主要采用追加写。
Offset 是记录在某个 Partition 内的位置，不是全局 ID，也不直接代表业务时间。
不同 Partition 可以出现相同 Offset。

Offset 由 Broker 分配。
应用不能用 Offset 代替全局 `messageId`、订单号或幂等键。
跨 Topic 追踪应使用业务 Envelope、Trace Context 和稳定事件 ID。

删除旧记录不会把后续 Offset 重新编号。
Offset 可能因 Retention、Compaction、事务控制记录或日志截断而不连续，Consumer 不应假设每个整数都对应一条可见业务记录。

### 3.2 Segment 文件

Partition 不会永久写入一个无限增长的文件，而是滚动为多个 Segment。
一个 Segment 通常包含日志数据及 Offset/时间索引等伴随文件。
Segment Base Offset 用于定位记录范围。

当前写入的是 Active Segment。
达到大小或时间条件后滚动为 Closed Segment，Retention 和 Compaction 主要以 Segment 为处理单位。
因此配置 Retention 后，文件不一定在精确时刻或精确字节数立即删除。

Segment 太大会延长滚动、清理和恢复粒度。
Segment 太小会增加文件、索引和后台清理开销。
调整前应使用真实消息大小、吞吐和保留期压测。

### 3.3 Page Cache 与顺序 IO

Kafka 倾向依赖操作系统 Page Cache，而不是把全部消息复制到 JVM Heap。
追加写、批量 Fetch 和页缓存命中使高吞吐成为可能。

Broker Heap 仍承担请求、索引、网络缓冲和元数据等对象。
给 JVM 分配过多内存可能挤压 Page Cache，反而增加磁盘读。

是否使用零拷贝、何时落到物理介质会受操作系统、传输路径、压缩、TLS 和 Kafka 版本影响。
容量评估应看实际磁盘延迟、Page Cache 命中和 Flush 行为，不要把“顺序写”理解成磁盘永远不会成为瓶颈。

### 3.4 Delete Retention

`cleanup.policy=delete` 按时间或大小清理旧 Segment。
它适合保留一个有限回放窗口的事件流。

时间 Retention 回答“记录至少需要保留多久”。
大小 Retention 为 Partition 存储提供上限约束。
两者同时启用时，满足清理条件的旧 Segment 可以被删除。

Retention 必须覆盖：

- Consumer 可接受的最长离线时间；
- 故障修复与重新部署时间；
- 重建索引、回放和审计窗口；
- 跨地域复制可能出现的最大延迟。

Consumer Lag 接近保留窗口时，风险不是“处理变慢”而是 Offset 指向的数据会被删除。
这时需要限流 Producer、扩充安全消费能力、延长 Retention 或从权威快照重建。

### 3.5 Log Compaction

`cleanup.policy=compact` 以 Record Key 为单位保留较新的值，适合变更日志和可恢复状态主题。
Compaction 是异步后台过程，不保证 Topic 在任意时刻每个 Key 只剩一条记录。

同一 Key 的旧值可能在一段时间内仍可见。
没有 Key 的记录无法获得按业务键压缩的语义。
Key 的序列化必须长期稳定，否则逻辑上相同的实体会被当成不同 Key。

值为 `null` 的记录通常用作 Tombstone，表示删除该 Key。
Tombstone 需要保留一段时间，让离线 Consumer 有机会看到删除；之后才可能被清理。
因此不能把 Compacted Topic 当成能永远证明历史删除的审计库。

`cleanup.policy=compact,delete` 可以同时做压缩和时间/大小清理。
选择它意味着既要维护每个 Key 的较新状态，又接受超过保留窗口的数据消失。

### 3.6 Compaction 不是数据库快照

Compacted Topic 可能包含多个版本、Tombstone 和尚未清理的旧记录。
重建状态时 Consumer 必须按日志顺序应用记录，而不是任选每个 Key 的第一条。

Compaction 不提供跨 Key 事务查询、二级索引或低延迟随机更新。
需要按多条件查询和维护强约束时，仍应把结果写入数据库或 State Store。

### 3.7 大消息的成本

大消息同时放大 Producer 缓冲、网络请求、Broker Page Cache、副本复制、Consumer Fetch、GC 和失败重试成本。
修改单个最大消息配置通常不够，Producer、Broker、Replica Fetch 和 Consumer Fetch 的相关上限必须一致。

图片、视频和大文档通常放对象存储。
Kafka 记录只保存对象 ID、版本、校验和、内容类型和受控访问方式。
对象生命周期必须覆盖 Kafka 的回放窗口，否则历史事件会引用已删除对象。

## 4. Producer 设计

### 4.1 Key 与 Partitioner

Record Key 同时影响路由、局部顺序和热点风险。
订单事件通常用 `orderId`，账户流水可用 `accountId`，设备遥测可用 `deviceId`。

有 Key 时，客户端 Partitioner 通常根据 Key 计算 Partition。
具体哈希算法和默认策略属于客户端行为；跨语言 Producer 需要相同路由时，应显式定义并测试算法。

无 Key 记录可以使用粘性或轮转策略形成 Batch。
不能依赖无 Key 记录进入同一 Partition，也不能据此建立业务顺序。

好 Key 应同时满足：

- 同一业务聚合稳定映射；
- 基数足够，负载不集中在少数值；
- 不包含需要隐藏的敏感原文；
- 生命周期内序列化格式稳定。

### 4.2 增加 Partition 对 Key 的影响

常见取模路由会把 `hash(key) % partitionCount` 作为分区结果。
Partition 数变化后，结果可能变化。
因此 Topic 扩分区前要判断是否存在跨扩容时间点的严格顺序要求。

可选处理方式包括：

- 接受扩容边界，只保证单个时期内的顺序；
- 创建新 Topic，迁移 Producer 和 Consumer；
- 使用显式路由表，在迁移完成前保持旧 Key 归属；
- 在 Consumer 端用 `aggregateVersion` 检测和处理乱序。

不要在生产高峰直接扩分区，然后才验证顺序与负载。

### 4.3 Batch、`linger.ms` 与 `batch.size`

Kafka Producer 按 Partition 累积 Batch。
`batch.size` 控制单个 Batch 的目标上限，`linger.ms` 允许客户端短暂等待更多记录进入 Batch。

更大的 Batch 通常减少请求数、提高压缩率和吞吐。
代价是增加等待、内存占用和单批失败重试成本。

低流量 Topic 即使配置大 Batch 也可能因等待到期发送小批次。
高吞吐压测要同时观察 Record Queue Time、Request Latency、Batch Size、Compression Ratio、Buffer Available 和错误率。

### 4.4 Compression

Kafka 对 Record Batch 压缩，而不是逐条独立压缩。
常见 Codec 包括 gzip、snappy、lz4 和 zstd；实际支持取决于 Broker 与客户端版本。

压缩减少网络和 Broker 磁盘占用，也提高 Batch 的价值。
它会消耗 Producer CPU，Consumer 解压也有成本。

选择 Codec 要用真实载荷比较：

- 压缩比；
- Producer CPU 与延迟；
- Broker 网络与磁盘；
- Consumer CPU；
- 跨语言客户端兼容性。

已经压缩的图片、视频或加密随机数据通常压缩收益很低。

### 4.5 `acks`

`acks=0` 不等待 Broker 响应。
应用无法从发送结果知道记录是否被 Leader 接受，适合明确允许丢失的低价值数据。

`acks=1` 等待 Leader 本地接受。
Leader 在 Follower 复制前故障时，已返回成功的记录仍可能丢失。

`acks=all` 等待当前 ISR 满足提交要求。
它需要与 `min.insync.replicas` 配合；ISR 少于最小值时，Broker 应拒绝写入而不是降低持久性。

关键事件常见组合是：

```properties
acks=all
enable.idempotence=true
min.insync.replicas=<按副本数与故障预算设置>
```

`min.insync.replicas` 是 Broker/Topic 配置，不是仅靠 Producer 能强制的属性。
值过低扩大丢失窗口，值过高会在副本故障时降低写可用性。

### 4.6 Retry、超时与未知状态

Kafka 客户端会对部分临时错误刷新元数据并重试，例如 Leader 切换或短暂网络失败。
认证、授权、消息过大和无效配置通常不能靠重试恢复。

需要区分：

- 连接建立超时；
- 单次请求超时；
- Record 在客户端排队与重试的总交付截止时间；
- 业务 HTTP 请求自己的截止时间。

总交付截止时间必须覆盖预期重试，但不能无限增长。
发送超时属于未知状态：记录可能已写入，只是响应丢失。
重试同一业务事件时复用 `messageId`，Consumer 用数据库唯一约束或 Inbox 去重。

### 4.7 Idempotent Producer

Idempotent Producer 通过 Producer ID、Epoch 和每个 Partition 的 Sequence Number 识别符合协议边界的重复批次。
它主要解决同一 Producer Session 内因重试导致的日志重复和乱序风险。

它不解决：

- 应用重启后重新构造一条新的业务事件；
- 两个服务同时发布相同业务事实；
- Consumer 重复执行业务副作用；
- 外部数据库、HTTP 或邮件接口的幂等；
- 人工 Replay 产生的再次处理。

启用幂等后，客户端会约束 `acks`、Retry 和 In-flight 请求组合。
不要覆盖为与客户端要求冲突的值；升级客户端时核对官方配置验证规则。

### 4.8 In-flight 请求与顺序

允许多个 ProduceRequest 同时在途可以提高吞吐。
未启用幂等时，如果前一批失败并重试、后一批先成功，日志顺序可能改变。

幂等 Producer 用 Sequence Number 检测不合法顺序，并对可支持的 In-flight 范围提供顺序保护。
仍然不能让来自不同 Producer 的记录获得统一业务顺序。

必须严格排序的业务还应携带 `aggregateVersion`。
Consumer 发现版本缺口时暂停、重试或从权威数据修复，而不是静默覆盖。

### 4.9 Producer 缓冲与背压

Broker 变慢时，记录会在 Producer Buffer 中等待。
无界地在应用层再套一层数组或 Promise 队列，只会把 Kafka Lag 转成进程 OOM。

Producer 需要设置可解释的缓冲上限和等待时间。
达到上限时根据业务选择阻塞、返回 503、降级采样或写本地 Outbox。

监控至少包括：

- Record Send Rate 与字节速率；
- Record Error/Retry Rate；
- Request Latency p95/p99；
- Buffer Available 与 Buffer Exhaustion；
- Batch Size 与 Compression Ratio；
- 每个 Topic/Partition 的异常分布。

### 4.10 Topic 自动创建

生产环境不应依赖拼错 Topic 名后自动创建默认配置 Topic。
Topic 应通过 Infrastructure as Code 或审核过的管理流程创建，显式设置 Partition、Replication Factor、Retention、Compaction 和权限。

客户端通常应关闭 `allowAutoTopicCreation` 或对应能力。
发布前检查 Topic 存在、Schema 兼容和账户有 Write 权限。

## 5. Consumer 与 Consumer Group

### 5.1 Consumer Group 的职责

Consumer Group 表示一个逻辑订阅者。
同一 Group 内，稳定状态下一个 Partition 只分配给一个成员；不同 Group 可以独立消费相同 Topic。

Group Coordinator 管理成员、心跳、Generation、分配协议和已提交 Offset。
Consumer 加入、离开、超时、修改订阅或 Topic Partition 变化都可能触发 Rebalance。

实例数超过可分配 Partition 数后，多出的实例会空闲。
此时继续扩容不会提高吞吐，应检查 Partition、热点 Key 和下游容量。

### 5.2 Subscribe 与手工 Assign

使用 Group Subscription 时，Coordinator 在成员间分配 Partition，并在成员变化时 Rebalance。
它适合普通可伸缩服务。

手工 Assign 让应用固定读取明确的 Topic/Partition。
它适合离线工具、精确回放和自定义分配系统，但应用需要自行管理实例冲突、故障接管和 Offset。

生产业务 Consumer 不应混用两种所有权模型。
两个实例手工读取同一 Partition 时，Kafka 不会自动阻止重复业务处理。

### 5.3 Fetch 与 Poll Loop

Consumer 通过持续 Poll/Fetch 推进会话和数据读取。
Fetch 批量参数在吞吐、等待时间和内存之间取舍。

单批记录过多会增加：

- 反序列化与业务处理时间；
- Rebalance 时重复处理的范围；
- Consumer 内存和 GC 压力；
- Commit 前的在途数据量。

单批太小则增加请求与 Commit 开销。
应使用真实单条处理时长和下游并发预算计算，而不是只追求最大吞吐。

### 5.4 Offset 表示下一条位置

Consumer Commit 的 Offset 通常表示“下一条要读取的位置”。
如果成功处理 Offset `42`，应提交 `43`。

提交 `42` 会再次读取已完成记录。
处理失败却提交更大的 Offset 会跳过失败记录以及它之前未完成的连续范围。

Offset 属于 `Group + Topic + Partition`。
复制一个 Group 名会共享进度；创建新 Group 会得到独立进度，并根据 Offset Reset 策略决定没有已提交位置时从哪里开始。

### 5.5 自动 Commit 与手动 Commit

自动 Commit 简化代码，但提交时机可能早于真实业务副作用完成。
如果框架在记录仍位于应用缓冲时提交，进程崩溃会丢失业务处理。

关键业务常用手动 Commit：

```text
Fetch Record
  -> 校验与反序列化
  -> Inbox/业务事务成功
  -> Commit nextOffset
```

处理成功而 Commit 失败会重复，不会自动丢失。
所以手动 Commit 仍然必须配合幂等，不应把 Commit 失败当成“撤销数据库事务”。

### 5.6 批量 Commit 的连续前缀

同一 Partition 内并发处理一批记录时，只能提交已经连续成功的最大 Offset 之后的位置。
例如 `40`、`41`、`43` 成功而 `42` 失败，不能提交 `44`，否则 `42` 被跳过。

可选策略包括：

- Partition 内串行处理，不同 Partition 并行；
- 维护完成集合，只推进连续前缀；
- 失败时暂停该 Partition，等待重试完成；
- 明确允许跳过时，先可靠写入 DLQ，再推进 Offset。

不要用一个全局 Promise Pool 混合所有 Partition 后提交批末 Offset。

### 5.7 Offset Reset

没有有效已提交 Offset，或原 Offset 已因 Retention 消失时，Consumer 需要 Reset 策略。
常见语义是从最早可用位置或最新位置开始。

这不是普通失败重试选项。
从最新开始可能跳过历史业务，从最早开始可能触发大规模 Replay。

生产 Consumer 应对“无 Offset”给出明确启动策略，并对 Unexpected Offset Reset 告警。
关键投影最好能从权威快照加增量日志重建，而不是假设 Kafka 永久保存全部历史。

### 5.8 Rebalance 为什么造成抖动

Rebalance 会撤销并重新分配 Partition。
在所有权切换期间，消费可能暂停；旧成员已处理但未提交的记录会被新成员再次读取。

常见触发原因：

- 部署扩缩容或容器频繁重启；
- Session/Heartbeat 超时；
- 单批处理超过最大 Poll 间隔；
- Node.js Event Loop 被同步 CPU 任务阻塞；
- Topic Partition 数或订阅集合变化；
- 网络抖动或 Group Coordinator 切换。

Rebalance 不是数据错误，但会放大尾延迟和重复处理。
应监控频率、持续时间、撤销/分配数量和 Rebalance 后的 Lag 变化。

### 5.9 Classic Assignor 与新 Consumer Group Protocol

Kafka 4.x 同时存在 Classic Consumer Group Protocol 与 KIP-848 引入的新 Consumer Group Protocol，二者的分配和心跳责任不同。

Classic Protocol 由 Group 成员协商共同支持的客户端 Assignor：

| Assignor | 核心特点 | 主要风险 |
| --- | --- | --- |
| Range | 按 Topic 分段分配 | 多 Topic 时可能让部分成员长期更忙 |
| RoundRobin | 在成员间轮转 | 迁移数量可能较多，依赖成员订阅一致性 |
| Sticky | 尽量均衡并保留原分配 | 仍属于一次 Rebalance 的整体分配 |
| Cooperative Sticky | 增量撤销与迁移 | 升级必须保证成员协议兼容 |

新 Consumer Group Protocol 把分配逻辑放到 Broker 侧，可通过 `group.remote.assignor` 选择服务端支持的策略；Heartbeat 间隔和 Session Timeout 也由 Broker 配置控制。
同一 Group 迁移协议或 Assignor 时必须遵循客户端和 Broker 的官方迁移流程，不能假设两套配置键等价。

本文 KafkaJS `2.2.4` 示例使用 Classic Protocol，不支持把 KIP-848 的 `group.protocol=consumer` 配置直接复制进示例。

### 5.10 Static Membership

Static Membership 用稳定 `group.instance.id` 将重启后的实例识别为同一成员。
它可以减少短暂重启造成的完整 Rebalance，适合实例身份稳定的部署。

它不等于永久锁定 Partition。
实例明确离组、超时、订阅变化或身份重复仍会触发重新分配。

每个并行实例必须使用唯一且稳定的 ID。
把同一个 ID 配给两个活跃 Pod 会触发 Fencing 或成员冲突。

### 5.11 Session、Heartbeat 与最大处理间隔

Classic Protocol 中，客户端配置 Session Timeout 和 Heartbeat；新 Consumer Group Protocol 中，对应间隔由 Broker 端配置控制。
最大 Poll 间隔约束应用两次有效 Poll 之间允许的最长处理时间。

参数过小会在 GC、网络抖动或慢业务时误踢成员。
参数过大则延长真实故障的接管时间。

处理时长超过预算时，优先：

- 减小单批记录数；
- 将 CPU 密集计算移到 Worker Thread 或独立服务；
- 限制下游超时并隔离慢请求；
- 在客户端允许的执行模型中及时 Heartbeat；
- 最后才根据实测 p99 调整超时。

### 5.12 Consumer 并发

最安全的基本模型是 Partition 内串行、Partition 间并行。
这样 Offset 连续性和 Key 顺序最容易推理。

如果 Partition 内也并发，必须维护连续提交水位，并保证同一 Key 不被并发执行。
对数据库写入还要让所有实例总并发不超过连接池和锁冲突预算。

Node.js 中 Promise 并发不会自动产生 CPU 并行。
同步解析、压缩或加密长时间占用 Event Loop 会延迟 Heartbeat。

### 5.13 Pause、Resume 与背压

Consumer 处理能力低于输入时，可以暂停一个或多个 Partition，等待下游恢复后 Resume。
Pause 只停止新的 Fetch，不会撤销已在内存中的记录，也不会自动延长业务截止时间。
背压要同时限制每个 Partition 的在途记录、进程总并发、下游连接、Retry 速率和恢复追赶速率。
不要暂停后忘记恢复。
Pause 状态、持续时间和原因必须可观测，并设置自动恢复或运维处置路径。

### 5.14 Lag 的正确含义

常见 Lag 是 Partition 最新可消费位置与 Group 已提交 Offset 的差值。
它表示尚未提交的位置数量，不等于正在等待的业务条数，也不直接等于时间。

以下情况会误导只看 Lag 的判断：

- 单条记录大小和处理成本差异很大；
- Consumer 已处理很多记录但尚未 Commit；
- Topic 暂停生产，Lag 固定但消息越来越旧；
- 事务或 Compaction 让物理 Offset 与可见记录数不一一对应。

应同时监控 Lag、Lag 增长率、最老未处理事件时间、处理延迟和业务 SLO。

## 6. 顺序、重复、Retry 与 DLQ

### 6.1 Kafka 能保证的顺序

Kafka 只在单个 Partition 的日志中定义顺序。
Producer 使用相同 Key 并保持一致 Partitioner，才能让相关记录进入同一 Partition。

Consumer 仍可能观察到业务乱序：

- 多个 Producer 的本地时钟和发送时间不同；
- 上游事务提交顺序与事件发生时间不同；
- Retry Topic 改变记录所在日志；
- Consumer 对同一 Partition 做不受控并发；
- 扩分区改变 Key 映射；
- 跨集群复制存在独立延迟。

因此业务事件应携带 `aggregateVersion` 或可比较的领域序号。
发现旧版本时安全忽略，发现缺口时暂停并修复，不能只按 `occurredAt` 猜顺序。

### 6.2 重复、Retry 与 DLQ

Produce 超时、Commit 丢失、Rebalance、Reset Offset 和 Replay 都会产生重复。
Record Offset 只能标识某次日志写入，跨 Topic 或重新发布仍要用稳定 `messageId`、业务唯一键或实体版本幂等。
Inbox、Payload Hash、外部 API Idempotency Key 的完整设计见 [[后端/消息队列/2. 消息队列进阶知识|消息队列进阶知识]]。

Kafka Core 没有任意延迟的逐条重新入队，常见做法是建立有限层级的 Retry Topic：

```text
orders.v1
  -> orders.v1.retry.1m
  -> orders.v1.retry.10m
  -> orders.v1.dlq
```

Topic 名称本身不会产生延迟。
Retry 记录必须携带 `attempt` 和 `notBefore`，再由 Kafka Streams 的持久 State Store 与时间触发器、外部持久调度器或受控 Retry Dispatcher 到期后写入下一 Topic。
Consumer 可靠写入下一 Retry Topic 后才提交原 Offset；重试必须有限、有退避，不能在回调中长时间 `sleep` 占住 Partition。
跨 Topic 会改变原顺序，严格保序流应暂停 Partition 或故障聚合，不能为了降低 Lag 跳过账本事件。

永久错误进入 DLQ 时保留原 Topic/Partition/Offset、Key/Value、`messageId`、Schema、应用版本和错误分类。
DLQ Produce 失败就不提交原 Offset；回放必须用隔离 Group、限速并在结束后对账。

## 7. Transaction 与 Exactly-once

### 7.1 Kafka Transaction 的原子边界

Transactional Producer 可以把多个 Kafka Partition 的 Produce 以及关联 Consumer Group Offset 放入同一个 Kafka Transaction。
Commit 后，这些写入对 `read_committed` Consumer 作为已提交结果可见；Abort 后业务记录被过滤。

典型 Consume-Transform-Produce 流程：

```text
读取 input Topic
  -> beginTransaction
  -> 计算并写 output Topic
  -> 将 input Offset 加入 Transaction
  -> commitTransaction
```

输出记录与输入 Offset 要么都提交，要么都不提交。
这正是 Kafka 内部 EOS 的核心边界。

### 7.2 `transactional.id` 与 Fencing

每个并行 Transactional Producer 需要稳定且唯一的 `transactional.id`。
Broker 用 Producer ID/Epoch 识别旧实例。
新实例以同一身份初始化后，旧实例会被 Fencing，防止两个进程同时提交同一事务身份。

容器部署不能让所有副本共享一个 `transactional.id`。
也不能每次重启都生成完全无关 ID，否则失去对旧未决事务的恢复和 Fencing 语义。

### 7.3 `read_committed`

默认隔离级别取决于客户端配置。
需要 EOS 语义的下游 Consumer 必须显式使用 `read_committed` 或对应选项。

`read_uncommitted` 可以看到尚未完成或后来中止事务中的业务记录。
如果一部分 Consumer 使用 `read_committed`、另一部分没有，两个系统会得到不同业务视图。

事务控制记录和中止记录仍占用日志 Offset。
所以 Offset 差值不总等于 `read_committed` Consumer 实际会交付的记录数。

### 7.4 外部系统边界

下面的操作不自动进入 Kafka Transaction：

- PostgreSQL/MySQL 事务；
- Redis 更新；
- Elasticsearch 索引；
- HTTP、gRPC 和第三方 API；
- 文件、对象存储、邮件和支付；
- 人工审批。

如果 Consumer 先写数据库，再提交 Kafka Transaction，提交失败会重复写数据库。
如果先提交 Kafka Transaction，再写数据库，进程崩溃会漏写数据库。

这类边界仍使用 Inbox、唯一约束、条件版本更新、Outbox、幂等 API 和对账。
不要把“Kafka EOS”写成“整个业务 Exactly-once”。

### 7.5 事务成本与适用条件

Transaction 引入 Coordinator、事务状态、Marker、超时、Fencing 和额外请求。
长事务会推迟 `read_committed` Consumer 可见位置，并占用更多 Broker 资源。

适合 Transaction 的场景：

- Kafka Topic 到 Kafka Topic 的原子流处理；
- 同一处理结果写多个 Kafka Partition；
- 输出记录与输入 Offset 必须共同提交。

不适合仅为掩盖 Consumer 非幂等而启用事务。
外部副作用占主导时，Inbox/Outbox 往往更容易审计和恢复。

### 7.6 Kafka Streams 的 EOS

Kafka Streams 可以把输入 Offset、输出 Topic 和内部 State Store Changelog 纳入 Kafka Transaction 管理。
启用其 Exactly-once Processing Guarantee 后，Kafka 内的处理结果可以避免因任务重启而重复提交。

它仍不能让外部数据库或 HTTP Sink 自动 Exactly-once。
把结果写外部系统时，要使用幂等 Sink、Connect 对应能力或独立对账。

## 8. Kafka Connect、Kafka Streams 与 Schema Registry

### 8.1 Kafka Connect

Kafka Connect 是标准化 Source/Sink Connector 运行时。
Source Connector 把外部系统数据写入 Kafka，Sink Connector 把 Kafka 记录写到外部系统。
Distributed Mode 用内部 Topic 保存 Connector 配置、Offset 和任务状态，并在 Worker 之间重新分配 Task。

Connect 不等于“装上插件就可靠同步”。
必须核对 Connector 的 Offset 边界、删除语义、Schema 兼容、错误容忍、DLQ、重试、幂等和目标系统事务能力。
Connector 声称的 Exactly-once 也只在其明确支持的 Source/Sink 与配置边界内成立。

### 8.2 Kafka Streams

Kafka Streams 是嵌入 Java 应用的流处理库，不是单独部署的 Broker 服务。
它提供 `KStream`、`KTable`、Window、Join、State Store、Changelog 和任务恢复。
Partition 决定任务并行度；需要 Join 的数据必须满足可兼容分区和 Key 设计。

State Store 是可恢复派生状态，不应成为缺少备份和契约的唯一业务权威。
窗口计算还要明确 Event Time、Grace Period、迟到数据和结果更新语义。

### 8.3 Schema Registry

Schema Registry 不是 Apache Kafka Broker Core 的内置组件，而是配套的 Schema 存储与兼容检查服务。
常见实现支持 Avro、Protobuf 或 JSON Schema，并把 Schema ID 编入 Record。

Registry 解决格式版本查找和兼容规则，不自动保证业务语义兼容。
金额从“分”改成“元”，即使字段类型不变也属于破坏性语义变更。
Registry 需要独立的高可用、权限、缓存、备份和故障策略。

## 9. 安全与多租户

### 9.1 TLS 与身份认证

TLS 保护客户端到 Broker、Broker 间以及 Controller 通信。
客户端必须验证 CA、主机名和证书有效期；不要用关闭验证来修复证书配置错误。

Kafka 可通过 mTLS 或 SASL 机制认证身份。
常见 SASL 机制包括 SCRAM、GSSAPI/Kerberos 和 OAUTHBEARER；是否可用及回调实现取决于版本和部署平台。
PLAIN 不能替代 TLS，凭证也不能写进镜像、源码、Topic 或普通日志。

### 9.2 ACL

启用 Authorizer 后，ACL 可以限制 Topic、Consumer Group、Transactional ID、Cluster 等资源操作。
Producer 只获得目标 Topic 的 Write/Describe，Consumer 只获得目标 Topic Read 和指定 Group 权限。
管理工具、Connect Worker、Streams 应用和回放任务使用独立身份。

通配 ACL 容易让新 Topic 自动暴露给无关服务。
权限变更应进入代码审查和审计，并定期清理已下线 Principal。

### 9.3 配额与隔离

共享集群要按 Principal、Client ID 或租户设置 Produce/Fetch 配额，并隔离关键与非关键 Topic。
Retention、Partition 数、大消息、回放和 Retry Topic 都会消耗公共磁盘与网络。
达到配额时客户端应退避，不要在应用内无界排队。

强监管、不同数据驻留要求或无法共享故障预算的租户，通常应使用独立集群，而不是只依赖命名约定。

## 10. Docker 与 CLI 最小实践

下面用 Apache 官方镜像启动单节点 KRaft，只用于本地学习。
示例固定 `4.0.0` 以避免 `latest` 漂移；团队可替换为已验证的 4.x Tag，并按该版本官方说明调整参数。
单节点、Replication Factor 1 没有节点容错，不能作为生产拓扑。

```bash
docker run -d --name kafka-local \
  -p 9092:9092 \
  apache/kafka:4.0.0
```

创建三分区业务 Topic 与 DLQ Topic：

```bash
docker exec kafka-local /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create \
  --topic orders.v1 \
  --partitions 3 \
  --replication-factor 1

docker exec kafka-local /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create \
  --topic orders.v1.dlq \
  --partitions 3 \
  --replication-factor 1
```

查看 Topic 与副本分配：

```bash
docker exec kafka-local /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --describe \
  --topic orders.v1
```

启动 Console Producer，并用冒号前内容作为 Key：


输入一行：

Offset Reset 会改变消费进度。

## 11. KafkaJS 自包含 TypeScript 示例

安装并运行：

```bash

MODE=consume KAFKA_BROKERS=localhost:9092 npx tsx kafka-app.ts
```

下面模块包含可靠性边界明确的 Producer、手动 Offset Commit、幂等业务接口、DLQ、优雅关闭和错误路径。
`MemoryOrderHandler` 只让本地示例可运行；生产实现必须用数据库唯一约束或 Inbox 持久化相同接口的幂等状态。

```typescript
import { randomUUID } from 'node:crypto';
import {
  CompressionTypes,
  Kafka,
  logLevel,
  type Consumer,
  type KafkaMessage,
  type Producer,
} from 'kafkajs';

type OrderCreated = {
  messageId: string;
  type: 'OrderCreated';
  schemaVersion: 1;
  orderId: string;
  occurredAt: string;
};

interface IdempotentOrderHandler {
  processOnce(event: OrderCreated): Promise<'processed' | 'duplicate'>;
  close(): Promise<void>;
}

class MemoryOrderHandler implements IdempotentOrderHandler {
  private readonly processed = new Set<string>();

  public async processOnce(event: OrderCreated): Promise<'processed' | 'duplicate'> {
    if (this.processed.has(event.messageId)) return 'duplicate';
    console.info(JSON.stringify({ action: 'create-order-projection', orderId: event.orderId }));
    this.processed.add(event.messageId);
    return 'processed';
  }

  public async close(): Promise<void> {}
}

class InvalidMessageError extends Error {}

function parseBrokers(value: string | undefined): string[] {
  const brokers = (value ?? 'localhost:9092').split(',').map((item) => item.trim()).filter(Boolean);
  if (brokers.length === 0) throw new Error('KAFKA_BROKERS is empty');
  return brokers;
}

function decodeOrder(message: KafkaMessage): OrderCreated {
  if (!message.value) throw new InvalidMessageError('message value is empty');
  let value: unknown;
  try {
    value = JSON.parse(message.value.toString('utf8'));
  } catch (error) {
    throw new InvalidMessageError(`invalid JSON: ${String(error)}`);
  }
  if (typeof value !== 'object' || value === null) throw new InvalidMessageError('value is not an object');
  const event = value as Partial<OrderCreated>;
  if (event.type !== 'OrderCreated' || event.schemaVersion !== 1 ||
      typeof event.messageId !== 'string' || typeof event.orderId !== 'string' ||
      typeof event.occurredAt !== 'string') {
    throw new InvalidMessageError('OrderCreated schema validation failed');
  }
  return event as OrderCreated;
}

function encodeHeaderValue(value: unknown): string | string[] | null {
  if (value === undefined || value === null) return null;
  if (Array.isArray(value)) {
    return value.map((item) => Buffer.isBuffer(item)
      ? item.toString('base64')
      : Buffer.from(String(item), 'utf8').toString('base64'));
  }
  return Buffer.isBuffer(value)
    ? value.toString('base64')
    : Buffer.from(String(value), 'utf8').toString('base64');
}

function encodeHeaders(
  headers: KafkaMessage['headers'],
): Record<string, string | string[] | null> {
  return Object.fromEntries(
    Object.entries(headers ?? {}).map(([key, value]) => [key, encodeHeaderValue(value)]),
  );
}

const topic = process.env.KAFKA_TOPIC ?? 'orders.v1';
const dlqTopic = `${topic}.dlq`;
const kafka = new Kafka({
  clientId: 'orders-example',
  brokers: parseBrokers(process.env.KAFKA_BROKERS),
  logLevel: logLevel.INFO,
});
const producer: Producer = kafka.producer({
  idempotent: true,
  maxInFlightRequests: 5,
  allowAutoTopicCreation: false,
});
const consumer: Consumer = kafka.consumer({
  groupId: process.env.KAFKA_GROUP_ID ?? 'orders-projection-v1',
  allowAutoTopicCreation: false,
});
const handler: IdempotentOrderHandler = new MemoryOrderHandler();

let producerConnected = false;
let consumerConnected = false;
let stopping = false;

async function publish(event: OrderCreated): Promise<void> {
  await producer.send({
    topic,
    acks: -1,
    timeout: 30_000,
    compression: CompressionTypes.GZIP,
    messages: [{
      key: event.orderId,
      value: JSON.stringify(event),
      headers: { messageId: event.messageId, schemaVersion: String(event.schemaVersion) },
    }],
  });
}

async function sendToDlq(
  sourceTopic: string,
  partition: number,
  message: KafkaMessage,
  error: Error,
): Promise<void> {
  await producer.send({
    topic: dlqTopic,
    acks: -1,
    messages: [{
      key: message.key,
      value: JSON.stringify({
        application: 'orders-example',
        applicationVersion: process.env.APP_VERSION ?? 'dev',
        sourceTopic,
        partition,
        offset: message.offset,
        timestamp: message.timestamp,
        keyBase64: message.key?.toString('base64') ?? null,
        headersBase64: encodeHeaders(message.headers),
        valueBase64: message.value?.toString('base64') ?? null,
        errorType: error.name,
        errorMessage: error.message,
        failedAt: new Date().toISOString(),
      }),
    }],
  });
}

async function commitNextOffset(sourceTopic: string, partition: number, offset: string): Promise<void> {
  await consumer.commitOffsets([{
    topic: sourceTopic,
    partition,
    offset: (BigInt(offset) + 1n).toString(),
  }]);
}

async function runWithHeartbeats<T>(
  operation: Promise<T>,
  heartbeat: () => Promise<void>,
  intervalMs = 3_000,
): Promise<T> {
  let heartbeatError: unknown;
  let heartbeatTask: Promise<void> | undefined;
  const timer = setInterval(() => {
    if (heartbeatTask || heartbeatError) return;
    heartbeatTask = heartbeat()
      .catch((error: unknown) => { heartbeatError = error; })
      .finally(() => { heartbeatTask = undefined; });
  }, intervalMs);

  try {
    const result = await operation;
    if (heartbeatTask) await heartbeatTask;
    if (heartbeatError) throw heartbeatError;
    return result;
  } finally {
    clearInterval(timer);
  }
}

async function runConsumer(): Promise<void> {
  await consumer.connect();
  consumerConnected = true;
  await consumer.subscribe({ topic, fromBeginning: false });
  await consumer.run({
    autoCommit: false,
    partitionsConsumedConcurrently: 3,
    eachMessage: async ({ topic: sourceTopic, partition, message, heartbeat }) => {
      if (stopping) return;
      try {
        const event = decodeOrder(message);
        const result = await runWithHeartbeats(handler.processOnce(event), heartbeat);
        await commitNextOffset(sourceTopic, partition, message.offset);
        console.info(JSON.stringify({
          topic: sourceTopic, partition, offset: message.offset,
          messageId: event.messageId, result,
        }));
      } catch (error) {
        const failure = error instanceof Error ? error : new Error(String(error));
        if (failure instanceof InvalidMessageError) {
          await sendToDlq(sourceTopic, partition, message, failure);
          await commitNextOffset(sourceTopic, partition, message.offset);
          console.error(JSON.stringify({ offset: message.offset, result: 'sent-to-dlq', error: failure.message }));
        } else {
          console.error(JSON.stringify({ offset: message.offset, result: 'retry-after-restart', error: failure.message }));
          throw failure;
        }
      }
      await heartbeat();
    },
  });
}

async function shutdown(reason: string): Promise<void> {
  if (stopping) return;
  stopping = true;
  console.info(JSON.stringify({ action: 'shutdown', reason }));
  const failures: unknown[] = [];
  if (consumerConnected) {
    try { await consumer.stop(); } catch (error) { failures.push(error); }
    try { await consumer.disconnect(); } catch (error) { failures.push(error); }
    consumerConnected = false;
  }
  if (producerConnected) {
    try { await producer.disconnect(); } catch (error) { failures.push(error); }
    producerConnected = false;
  }
  try { await handler.close(); } catch (error) { failures.push(error); }
  if (failures.length > 0) throw new AggregateError(failures, 'shutdown failed');
}

process.once('SIGTERM', () => void shutdown('SIGTERM').catch(console.error));
process.once('SIGINT', () => void shutdown('SIGINT').catch(console.error));
consumer.on(consumer.events.CRASH, ({ payload }) => {
  process.exitCode = 1;
  console.error(JSON.stringify({ action: 'consumer-crash', error: payload.error.message }));
  void shutdown('consumer-crash').catch(console.error);
});

async function main(): Promise<void> {
  await producer.connect();
  producerConnected = true;
  if ((process.env.MODE ?? 'consume') === 'produce') {
    await publish({
      messageId: randomUUID(),
      type: 'OrderCreated',
      schemaVersion: 1,
      orderId: process.env.ORDER_ID ?? 'order-1001',
      occurredAt: new Date().toISOString(),
    });
    await shutdown('produce-complete');
    return;
  }
  await runConsumer();
}

void main().catch(async (error: unknown) => {
  process.exitCode = 1;
  console.error(error);
  await shutdown('startup-or-producer-error').catch(console.error);
});
```

永久格式错误只有在 DLQ 写入成功后才 Commit。
临时业务错误不 Commit，让 Consumer 重启或人工恢复后再次处理；`processOnce` 的持久化实现使重复安全。
KafkaJS `2.2.4` 的幂等 Producer 会使用近似无上限的内部重试来维持其协议保证，不能通过全局有限 `retries` 覆盖；业务请求应先写 Outbox，由独立 Publisher 在有界资源和停机策略下持续发送。
`runWithHeartbeats` 只保护异步等待期间的 Group 会话；同步 CPU 阻塞仍会阻止 Timer 和 Heartbeat，必须移到 Worker Thread 或独立服务。
生产部署还应加入 TLS/SASL、运行时 Schema 库、Trace Context、受控 Retry Topic 和真实数据库集成测试。

## 12. 生产容量与运维

### 12.1 容量估算

先分别测每秒记录数和每秒字节数。
粗略磁盘需求为“压缩后写入字节率 × 保留秒数 × Replication Factor”，再加 Segment、索引、重写、恢复和增长余量。
Broker 还要为副本追赶、Reassignment、Compaction 和故障后流量预留网络与磁盘带宽。

Partition 数按单 Partition 实测安全吞吐、Consumer 并行度、Key 顺序和未来扩展共同确定。
压测必须包含 `acks=all`、真实副本数、真实消息大小、压缩、Consumer 处理、单 Broker 故障和 Replay。

### 12.2 监控基线

| 层级 | 关键指标 |
| --- | --- |
| Controller | Active Controller、Quorum 成员、提交与 Fetch Lag、选举异常 |
| Broker | 请求延迟/队列、网络、CPU、GC、文件句柄、磁盘使用率与 IO 延迟 |
| Replica | Under-Replicated、Under-Min-ISR、ISR Shrink、Offline Partition |
| Producer | Send/Error/Retry Rate、请求延迟、Batch、压缩比、Buffer Exhaustion |
| Consumer | Group 状态、Rebalance、Commit 错误、Lag、最老事件年龄、处理耗时 |
| 业务 | 重复、乱序、Schema 错误、Retry/DLQ、对账差异 |

磁盘使用率必须按挂载点看，集群平均值会掩盖单 Broker 或单 Log Directory 即将写满。
告警要给出 Topic/Partition、Leader、Replica、Group 和处置 Runbook。

### 12.3 磁盘与热点

磁盘接近满时，先停止非关键流量和大规模 Replay，定位异常 Retention、热点 Partition 与副本分配。
不要直接删除 Kafka 数据目录中的 Segment 文件。
应通过 Topic Retention、受控删除、扩容磁盘或 Replica Reassignment 恢复空间。

热点 Key 会让一个 Partition 的 Leader、网络和 Consumer 饱和，即使集群平均负载很低。
先统计 Key/Partition 字节率；允许乱序时拆分 Key，需要顺序时拆业务聚合或独立热点 Topic。

### 12.4 扩分区与副本重分配

扩分区前记录 Producer Partitioner、顺序要求、当前 Key 分布、Consumer 并行度和回滚方案。
扩分区只创建新 Partition，不会自动把旧记录搬过去，也不保证副本在新增 Broker 间自动均衡。

增加 Broker 后使用官方 Reassignment 工具生成、审核并限速执行迁移。
迁移期间监控 Replica Lag、ISR、磁盘和请求延迟，完成后验证 Leader 与 Replica 的故障域分布。

### 12.5 滚动升级

Kafka 4.x 小版本与跨版本升级都应遵循目标版本官方 Upgrade Guide。
先备份 Topic 配置、ACL、Connector/Schema 配置和当前元数据，再验证客户端兼容与回滚路径。

一次只变更一个故障域内允许的节点，等待 ISR 和 Controller Quorum 恢复后再继续。
不要同时重启到失去 `min.insync.replicas` 或 Controller 多数派。
协议/Metadata Version 的推进应放在所有节点升级并稳定之后，且确认该步是否可逆。

### 12.6 灾备

Replica 解决集群内节点故障，不解决误删、错误配置、区域故障或错误事件传播。
跨集群可使用 Apache Kafka MirrorMaker 2 等方案复制 Topic，并单独验证 ACL、Schema、Topic 配置和 Consumer Offset 迁移。

跨地域通常是异步复制，RPO 不会天然为零。
切换时还要防止双边 Producer、重复消费和 Key 顺序分叉。
灾备演练必须实际验证生产切换、Consumer 定位、回切与业务对账，而不只检查目标 Topic 有数据。

### 12.7 常见故障定位

| 现象 | 优先检查 | 响应 |
| --- | --- | --- |
| Produce 超时 | Leader、ISR、Under-Min-ISR、磁盘、网络、配额 | 恢复副本或容量，不盲目无限重试 |
| Lag 持续增长 | 慢 Partition、处理 p99、Rebalance、下游饱和 | 限流、修复热点或在安全边界扩容 |
| 循环 Rebalance | Heartbeat、最大 Poll 间隔、Pod 重启、CPU 阻塞 | 减批次、修复健康检查和慢处理 |
| 认证成功但被拒绝 | Topic/Group/Transactional ID ACL | 按最小权限补齐，不授予集群通配 |
| Offset Out of Range | Retention、错误 Reset、跨集群 Offset | 从快照重建或经审批 Reset |
| 单 Broker 磁盘暴涨 | Leader/Replica 分布、热点、Retention、Compaction | 限流并做受控 Reassignment |
| `read_committed` 停滞 | 长事务、未决事务、Transaction Coordinator | 处理被 Fencing/超时的 Producer |

排障顺序是“业务影响 -> Group/Topic/Partition -> Leader/Replica -> Broker/磁盘/网络 -> 客户端日志”。
先保存 Offset、时间窗口和配置证据，再做 Reset、删除 Topic 或 Reassignment 等改变状态的操作。

## 13. 优势、限制与选型

Kafka 的主要优势是高吞吐、保留与回放、多 Consumer Group、分区扩展和流处理生态。
主要限制是只保证分区顺序、任务语义需自行构建、Partition/磁盘运维复杂，并且外部系统仍需幂等和对账。

| 需求 | Kafka | RabbitMQ | RocketMQ |
| --- | --- | --- | --- |
| 长期可回放事件流 | 强 | 不是主要模型 | 支持，但生态模型不同 |
| 复杂路由与逐条 ACK | 需应用建模 | 强 | 更偏 Topic/Tag 与消费组 |
| 高吞吐数据管道 | 强 | 通常非首选 | 强 |
| 延迟/定时消息 | 需额外模式 | TTL/插件等方案 | 产品能力更直接 |
| 流处理生态 | Kafka Streams/Connect 丰富 | 较弱 | 以消息业务生态为主 |
| 运维重点 | Partition、磁盘、副本、Rebalance | Queue、内存水位、路由、Quorum | Broker/NameServer、存储、消费组 |

选型结论必须来自回放窗口、路由、顺序、延迟、吞吐、跨地域和团队能力，不来自单次 Benchmark。
完整通用选型维度见 [[后端/消息队列/3. 消息队列高级能力|消息队列高级能力]]。

## 14. 高频面试题

### `acks=all` 是否等于所有 Replica 都写入？

不是。它等待当前 ISR 满足提交条件；还要用 `min.insync.replicas` 约束可接受的同步副本数量。

### 为什么 Consumer Commit 的是下一条 Offset？

Commit 表示恢复时下一条要读取的位置。处理完 `42` 应提交 `43`，否则会再次读取 `42`。

### Idempotent Producer 为什么不能替代 Consumer 幂等？

它只抑制协议会话内 Produce Retry 的重复，不能覆盖 Consumer 崩溃、Replay、业务重复发布和外部副作用。

### 增加 Consumer 为什么 Lag 不下降？

可能实例数已超过 Partition 数，也可能热点 Partition、Rebalance 或数据库成为瓶颈。

### KRaft Controller 和 Broker 有什么区别？

Controller Quorum 提交集群元数据并负责选举，Broker 保存 Partition Replica 并服务数据请求；开发环境可合并角色，生产故障预算应分开评估。

### Compaction 是否保证每个 Key 只剩最后一条？

不保证。Compaction 异步运行，旧版本会暂时存在；Tombstone 也只在删除保留窗口内存在。

### Kafka Transaction 的 Exactly-once 边界是什么？

Kafka 内多 Partition 输出与 Consumer Offset 可以原子提交；数据库、HTTP、邮件和支付不在该边界内。

### Cooperative Rebalance 是否消除重复？

不会。它减少不必要的 Partition 撤销，处理完成但未 Commit 的记录仍可能再次读取。

### 为什么扩分区可能破坏同一 Key 的顺序？

常见路由依赖 Partition 总数；数量变化后同一 Key 可能映射到新 Partition。

### 如何区分消息数量 Lag 与用户延迟？

同时观察最老未处理事件年龄、处理耗时和业务 SLO；Offset 差值本身不代表时间。
