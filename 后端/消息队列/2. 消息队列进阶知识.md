# 消息队列进阶知识

消息队列把生产者和消费者之间的直接调用改成可持久化、可重试、可观测的异步边界。 它解决的是时间解耦、削峰、广播、失败隔离和事件传播。
它不自动解决数据库与消息的原子提交、业务幂等、全局顺序或下游副作用的一次性。 本文从消息生命周期开始，逐步进入 Producer、Consumer、事件契约、分布式一致性和典型业务场景。
文中使用 Queue、Topic、Partition、Consumer Group、Offset 等通用术语。 具体客户端的 ACK、Commit、Confirm 和事务 API 可能不同，阅读实现时必须回到对应 Broker 的语义。

## 一、先建立消息生命周期模型

### 1.1 四个角色

Producer 产生消息。 Broker 接收、路由、持久化、复制并向 Consumer 提供读取接口。
Consumer 拉取或接收消息，执行业务副作用，再确认处理结果。 Consumer Group 表示一个逻辑订阅者。
同一个 Consumer Group 内，分区通常只分配给一个成员。 不同 Consumer Group 可以各自完整消费同一个 Topic。
Queue 通常表示竞争消费。 Topic 通常表示事件流或发布订阅。
Partition 把一个逻辑流拆成多个可以并行读写的日志。

### 1.2 一条消息经历什么

消息先在应用内创建 Envelope 和 payload。 Producer 序列化消息，并按 key 或路由规则选择 Topic、Queue、Partition。
Broker 接收请求，可能先写内存，再写 WAL 或日志文件。 Broker 根据副本和 quorum 规则确定是否提交。
Producer 获得发送结果后才能知道 Broker 是否确认。 Consumer 获取消息，消息可能暂时不可见，也可能只是推进了读取游标。
Consumer 执行数据库更新、调用外部服务或生成下游消息。 业务副作用持久化成功后，Consumer 执行 ACK、NACK 或 Offset Commit。
如果确认响应丢失，Broker 可能再次投递。 如果 Consumer 在确认前崩溃，重启后通常从未确认位置重放。
因此，“收到消息”不等于“业务处理成功”。

~~~text
创建 Envelope
  -> 序列化与路由
  -> Broker 接受与持久化
  -> 副本提交
  -> Consumer 读取
  -> 业务副作用提交
  -> ACK 或 Offset Commit
~~~
### 1.3 ACK、NACK、Offset、Commit 与 Visibility Timeout

ACK 是对一条消息或一批消息的成功确认。 NACK 表示消费失败，可能触发重新投递、延迟重试或 DLQ。
Offset 是日志中的位置，不表示业务已经成功。 Commit 把 Consumer Group 的消费位点持久化。
Visibility Timeout 是任务被领取后暂时不可见的租约。 租约过期前没有 ACK，消息会重新可见。
队列型 Broker 的 ACK 对象通常是消息 ID。 日志型 Broker 的 Commit 对象通常是分区和 Offset。
不能把某个系统的 ACK 直接翻译成另一个系统的 Commit。

### 1.4 投递语义

At-most-once 通常先 Commit 再处理。 它允许丢失，不主动重复。
它适合可重新计算的指标或明确允许丢失的通知。 At-least-once 通常先处理再 ACK 或 Commit。
它不主动丢失，但确认失败会重复。 订单、库存、索引等场景通常选择它并配合幂等。
Exactly-once 只在明确定义的原子边界内成立。 例如 Broker 事务可以原子提交多条消息。
它不能把邮件、HTTP、第三方支付或任意数据库自动纳入同一事务。 业务效果的一次性通常依靠唯一约束、Inbox、版本条件更新和可重复操作。

### 1.5 顺序的真实范围

多数系统只保证单 Queue、单 Partition 或单聚合键范围内的顺序。 不同 Partition 之间没有自然的全局顺序。
同一 Partition 也可能因重试、批量发送和多个来源出现到达时间差异。 需要保序时，使用稳定的聚合键作为分区键。
订单事件可以使用 orderId。 随机 ID 会把同一订单拆散，不能保证 Created、Paid、Shipped 的顺序。
严格的全局顺序会牺牲并行度。 优先把不变量收敛到单个聚合，而不是强行建立全局锁。

## 二、Producer 的可靠发布

### 2.1 Producer Confirm 解决什么问题

Producer 本地调用成功只说明请求写入了客户端网络缓冲区。 它不等于 Broker 已接收，也不等于副本已经提交。
Confirm 是 Broker 返回的可验证发送结果。 发送结果至少要区分成功、可重试失败和不可重试失败。
可重试失败包括连接断开、临时超时、Leader 切换和限流。 不可重试失败包括认证失败、权限拒绝、Schema 不兼容和消息过大。
网络超时无法证明消息没有写入。 超时后重试必须接受重复的可能。
消息必须携带稳定 messageId，消费者不能依赖发送请求次数去重。

### 2.2 可靠发送的最小流程

先生成稳定的 messageId。 再完成 Schema 校验和序列化。
调用 Producer API 并等待 Confirm。 成功后记录发送延迟和 Broker 返回的分区、Offset 或消息 ID。
失败后按照错误分类决定重试或隔离。 应用请求是否等待 Confirm，取决于业务对“已接受”的定义。
支付指令通常不能只返回“已放入内存队列”。 可丢失的埋点可以采用低延迟的非阻塞发送。

### 2.3 Retry、指数退避和抖动

重试只适用于可能恢复的错误。 对参数错误、权限错误和 Schema 错误重试不会改变结果。
基础退避时间可以使用 min(cap, base × 2^attempt)。 加入随机抖动可以避免多个实例同时重试形成惊群。
重试必须设置最大次数或最大总时间。 总时间应小于业务请求的截止时间或消息的有效期。
下面是一个可复用的 TypeScript 发送骨架。

~~~typescript
type PublishError = {
  retryable: boolean;
  code: string;
};

const sleep = (milliseconds: number): Promise<void> =>
  new Promise((resolve) => setTimeout(resolve, milliseconds));

const backoff = (attempt: number, baseMs: number, capMs: number): number => {
  const exponential = Math.min(capMs, baseMs * 2 ** attempt);
  const jitter = Math.floor(Math.random() * Math.max(1, exponential / 2));
  return exponential / 2 + jitter;
};

async function publishWithRetry(
  send: () => Promise<void>,
  classify: (error: unknown) => PublishError,
): Promise<void> {
  const maxAttempts = 5;

  for (let attempt = 0; attempt < maxAttempts; attempt += 1) {
    try {
      await send();
      return;
    } catch (error) {
      const result = classify(error);
      if (!result.retryable || attempt === maxAttempts - 1) {
        throw error;
      }

      await sleep(backoff(attempt, 100, 5_000));
    }
  }
}
~~~
发送重试不会自动重试业务函数。 业务函数如果先写数据库再发送，应该使用 Outbox。

### 2.4 幂等发布

Producer 重试同一逻辑事件时必须复用原 messageId。 不要在每次 retry 中重新生成 messageId。
Broker 侧的 idempotent producer 可以减少日志重复。 它通常只覆盖同一 Producer Session、同一分区或协议规定的范围。
它不能阻止业务代码重新创建一条内容不同但含义相同的事件。 事件 ID、业务唯一键和 Producer sequence number 解决的问题不同。
支付事件可同时携带 eventId 和 paymentId。 消费者用 eventId 防止同一事件重复。
数据库用 paymentId 唯一约束防止重复扣款。 发布日志要记录 eventId、producer、attempt、结果和耗时。
不要把原始 payload 或 Token 写进普通日志。

### 2.5 批量发送与压缩

批量发送减少网络往返、系统调用和协议开销。 批量过大则会增加单次失败重试成本和尾延迟。
批量窗口应同时设置消息数、字节数和等待时间。 压缩减少网络和磁盘占用。
压缩会消耗 Producer 和 Broker CPU。 小消息、低延迟流可能从压缩中获益有限。
大消息应先确认 Broker、客户端和下游的最大消息限制。 把图片或视频直接塞入消息会放大复制、重试和回放成本。
更常见的做法是把对象存到对象存储，消息只携带受权限保护的引用。 生产压测必须同时观察吞吐、p99、CPU、GC、网络和压缩比。

### 2.6 背压与发送超时

背压表示下游处理能力低于输入速率，系统需要让生产端减速。 无界内存队列会把 Broker 的积压变成 Producer 进程的 OOM。
应用内发送缓冲应设置最大消息数和最大字节数。 超过阈值时可以阻塞、拒绝、降级或持久化到本地 Outbox。
发送超时要区分连接超时、请求超时和总业务截止时间。 每次重试都不能重置总截止时间。
下游限流错误应以可识别码返回，让 Producer 退避而不是忙等。 背压恢复后要确认积压下降、重复率没有飙升。
扩容 Producer 不能修复下游数据库已经饱和的问题。

### 2.7 Outbox：把本地事务和事件记录绑在一起

Outbox Pattern 在业务表事务中同时写入业务数据和待发布事件。 业务提交成功时，Outbox 记录必然存在。
发布器从 Outbox 领取记录并发送到 Broker。 发送 Confirm 与标记 published 之间仍然有崩溃窗口。
因此 Outbox 保证共同提交，不保证只发送一次。 Outbox 表至少需要 eventId、eventType、aggregateId、payload、schemaVersion、status、attempts 和 createdAt。
发布器要使用租约、行锁或 claim token，避免多个实例长期抢占同一行。 租约过期后允许另一个实例重新发布。
可重试网络错误使用退避。 Schema 错误、权限错误和不可序列化数据进入隔离状态并报警。
Outbox 积压和最老事件年龄表示业务事件的新鲜度。 下面的 SQL 展示本地事务的核心形状。

~~~sql
BEGIN;

WITH changed AS (
  UPDATE orders
  SET status = 'PAID', version = version + 1
  WHERE id = :order_id
    AND status = 'PENDING'
  RETURNING id, version
)
INSERT INTO outbox_events (
  event_id, event_type, aggregate_id, aggregate_version, payload, status
)
SELECT :event_id, 'order.paid', id, version, :payload, 'PENDING'
FROM changed;

COMMIT;
~~~
`changed` 为空时不会插入事件；应用仍应检查 Outbox `INSERT` 的影响行数，并在订单更新未命中时返回明确结果。INSERT 和业务更新必须在同一个本地事务中。
发布器和消费者仍需处理重复、乱序和死信。 数据库事务与可靠消息的更完整对比见 [[后端/数据库/8. 分布式数据库与水平扩展/3. 分布式事务与可靠消息|分布式事务与可靠消息]]。

## 三、Consumer 的可靠处理

### 3.1 Consumer 并发模型

Consumer 并发通常来自多个实例、多个线程、异步任务或多个 Partition。 同一 Consumer Group 内，一个 Partition 同时只应有一个活跃处理者。
消费者数量超过 Partition 数时，多出的实例没有有效工作。 增加并发不能突破单 Partition、单聚合键或下游数据库的吞吐上限。
同一聚合需要保序时，应让其固定到同一 Partition。 不同聚合可以并行处理。
并发消费者要限制数据库连接、HTTP 连接和 CPU 线程池。 任务处理过久会触发 Visibility Timeout 或 Consumer 心跳超时。
处理循环和心跳线程应避免被同步 CPU 任务长时间阻塞。 Rebalance 会撤销旧分配并建立新分配。
成员加入、退出、崩溃、订阅变化和 Partition 变化都会触发 Rebalance。 反复 Rebalance 会导致吞吐抖动和重复处理。

### 3.2 ACK 时机

至少一次消费应遵循“读取 -> 业务副作用提交 -> ACK/Commit”。 先 ACK 再写数据库会在进程崩溃时丢失消息。
先写数据库再 ACK，ACK 响应丢失只会导致重复。 批量 ACK 可以提高吞吐。
一条坏消息可能阻塞整批后续消息。 需要明确逐条确认、部分提交和暂停分区的策略。
Offset Commit 只是保存读取进度，不替代业务事务。 如果数据库事务和 Offset 不在同一原子边界，消费者必须可幂等。

### 3.3 优雅关闭

优雅关闭的目标是停止接收新任务，同时完成有限数量的在途任务。 收到 SIGTERM 后先停止拉取或拒绝新连接。
设置关闭截止时间。 等待在途任务成功提交并 ACK。
超过截止时间则取消或让租约自然过期。 关闭数据库连接池、HTTP Agent、Redis 和 Broker 客户端。
最后退出进程。 未完成任务不要提前 ACK。
Node.js 服务的退出、超时和消费者边界可参考 [[前端/Node/2. Node 进阶|Node 进阶]]。 下面是与 Broker 无关的关闭结构。

~~~typescript
type Message = { ack(): Promise<void> };
type Consumer = { stopPulling(): Promise<void>; close(): Promise<void> };
type Database = { close(): Promise<void> };

let accepting = true;
const inFlight = new Set<Promise<void>>();

async function processBusiness(_message: Message): Promise<void> {
  // 生产实现应在这里执行数据库事务和下游副作用。
}

async function handleMessage(message: Message): Promise<void> {
  if (!accepting) {
    throw new Error('consumer is shutting down');
  }

  const task = processBusiness(message);
  inFlight.add(task);

  try {
    await task;
    await message.ack();
  } finally {
    inFlight.delete(task);
  }
}

const consumer: Consumer = {
  async stopPulling(): Promise<void> {},
  async close(): Promise<void> {},
};
const database: Database = { async close(): Promise<void> {} };

async function shutdown(deadlineMs: number): Promise<void> {
  accepting = false;
  await consumer.stopPulling();

  const waitForTasks = Promise.allSettled([...inFlight]).then(() => undefined);
  const deadline = new Promise<void>((resolve) => setTimeout(resolve, deadlineMs));
  await Promise.race([waitForTasks, deadline]);

  await consumer.close();
  await database.close();
}
~~~
上例声明了最小适配器接口，实际实现需要把 `stopPulling`、`ack` 和 `close` 绑定到具体 Broker 客户端，并保证 shutdown 只执行一次。

### 3.4 Consumer 幂等与 Inbox

重复消息来自 Consumer 崩溃、ACK 丢失、超时重投、Producer retry 和人工 replay。 不要用单进程内存 Set 作为长期去重表。
多实例、重启和扩容都会绕过内存状态。 Inbox Pattern 在业务事务中记录 eventId 和 consumerName。
eventId 通过数据库唯一约束去重。 首次处理时插入 Inbox，更新业务状态，写入必要的 Outbox，再提交事务。
事务提交后 ACK。 重复 eventId 只返回已处理结果或安全跳过。
Inbox 可以保存 payload 摘要、处理结果、错误分类和 processedAt。 重复 ID 但 payload 摘要不同应报警并拒绝静默覆盖。
Inbox 保留期要覆盖最大重试、回放和人工修复窗口。 纯投影还可以使用 aggregateVersion 条件更新。
例如只接受 incomingVersion 大于 storedVersion 的更新。

### 3.5 Retry 与错误分类

可重试错误包括临时网络失败、数据库连接池耗尽、限流和依赖服务暂时不可用。 不可重试错误包括 Schema 不兼容、权限错误、参数错误和业务不变量冲突。
重试必须使用指数退避、抖动、最大次数和最大总时间。 固定间隔无限重试会形成热循环。
重试消息应携带原始 eventId、attempt、firstFailedAt 和 lastErrorCode。 每次重试都不能生成新的业务 ID。
重试 Topic 或延迟队列可以把失败消息从主消费流隔离。 若同一 Partition 必须严格有序，坏消息处理方式要特别谨慎。
可以暂停该 Partition 等待修复，也可以把该聚合转入重排缓冲。 直接跳过会产生版本缺口，只有业务明确允许才可使用。

### 3.6 DLQ 与 Poison Message

DLQ 保存超过重试上限、格式错误或明确不可处理的消息。 Poison Message 是每次处理都会失败并不断阻塞消费的消息。
进入 DLQ 时记录原 Topic、Partition、Offset、eventId、尝试次数、失败分类和最后错误。 DLQ 应保留原 payload 或受控对象引用。
人工处理前先确认故障范围和修复版本。 修复 Schema 或业务代码后使用隔离 Consumer Group 回放。
回放必须限制速率和并发，并验证幂等。 DLQ 不是永久垃圾桶。
设定保留期限、容量报警和最终处置策略。 不可恢复的个人数据要遵守删除和合规要求。

### 3.7 积压、限速与故障隔离

Consumer Lag 是生产位置与确认位置的差值。 Oldest Message Age 是最早未处理消息的等待时长。
Age 比数量更接近用户等待体验。 积压恢复时间可以估算为“积压量 / (消费速率 - 生产速率)”。
当消费速率不高于生产速率时，单纯增加消费者无效。 先定位慢 Partition、热点 key、重试热循环和外部依赖瓶颈。
增加消费者可能把压力转移到数据库、缓存或第三方 API。 为非关键 Topic 设置独立配额和并发上限。
必要时暂停低优先级消费者，让关键事件先恢复。 恢复后验证 Lag、Oldest Message Age、重复率、DLQ 和业务结果。

### 3.8 Replay 与 Reprocess

Replay 是从保留日志或快照重新读取历史事件。 Replay 可以修复投影、重建索引、迁移 Schema 和验证新代码。
不要直接让生产 Consumer Group 从最早位置重跑。 先建立隔离 Consumer Group 或重放 Topic。
限定时间、Partition、Offset、版本或业务键范围。 记录代码版本、Schema 版本、起止 Offset、操作者和原因。
对邮件、支付和外部 API 等副作用，必须使用幂等键或只重放到安全投影。 回放速率应低于下游安全容量。
回放结束后与权威数据对账，确认没有漏数和重复副作用。

## 四、事件契约与数据治理

### 4.1 Event Envelope

Envelope 是业务 payload 外的稳定元数据层。 建议字段包括 messageId、eventType、occurredAt、producer、schemaVersion、aggregateId、aggregateVersion 和 traceparent。
messageId 在重试和重放中保持稳定。 eventType 表达发生的事实，不要只暴露数据库表名。
occurredAt 表示业务发生时间。 Broker 接收时间和 Consumer 处理时间应单独记录。
aggregateVersion 用于检测缺口、乱序和旧消息。 traceparent 用于把 HTTP、Producer 和 Consumer Span 关联起来。
Envelope 不应包含 Token、密码、完整支付凭证或不必要的个人信息。 一个最小事件可以长这样：

~~~json
{
  "messageId": "evt_123",
  "eventType": "order.paid",
  "schemaVersion": 2,
  "aggregateId": "order_42",
  "aggregateVersion": 7,
  "occurredAt": "2026-08-04T10:00:00Z",
  "payload": {
    "amountMinor": 1999,
    "currency": "CNY"
  }
}
~~~
金额的单位必须进入字段名或 Schema 说明。 不要让消费者猜测整数究竟代表元还是分。

### 4.2 JSON、Avro、Protobuf 与 Schema

JSON 可读、调试简单、跨语言门槛低。 JSON 体积较大，类型约束和兼容检查需要额外工具。
Avro 把 Schema 和二进制编码分离。 Avro 常与 Schema Registry 配合，适合事件流和数据管道。
Protobuf 通过字段编号提供紧凑编码和生成代码。 Protobuf 删除字段后不能重用 field number。
格式选择要比较性能、调试体验、兼容策略、生态和团队成本。 Schema 还应定义必填性、默认值、枚举、单位、时间格式和隐私分类。
生产者发布前做 Schema lint 和兼容性检查。 消费者使用旧样本和新样本做反序列化测试。
未知字段应按协议规则忽略或保留。 大 Blob 通常放对象存储，消息携带受控引用。

### 4.3 Schema Evolution

Backward compatibility 使新消费者可以读取旧消息。 Forward compatibility 使旧消费者可以读取新消息。
Full compatibility 同时满足两者。 新增带默认值的可选字段通常比较安全。
删除必填字段、改变类型、改变单位和重用字段编号可能破坏消费者。 新增枚举值要求旧消费者提供未知值分支。
重大语义变化应创建新 eventType 或新主版本。 不要只修改 schemaVersion，却让同一 eventType 表示完全不同的业务含义。
采用双写、双读和迁移窗口逐步切换。 记录旧消费者的停止时间、最大回放窗口和回滚路径。
运行时遇到未知版本，应进入可观测的拒绝或隔离路径。 不能静默丢弃无法解码的消息。

### 4.4 Schema Registry

Schema Registry 保存 Schema、版本和兼容规则。 生产者发送 schemaId，消费者按 ID 获取并缓存定义。
Registry 降低重复传输和格式漂移。 Registry 不可用时，已有缓存可以继续解码。
没有缓存且无法获取 schemaId 时，应进入重试或隔离队列。 Registry 本身需要高可用、访问权限和备份。
契约发布应包含命名空间、所有者、数据分类、兼容级别和废弃时间。 格式兼容不等于业务语义兼容。
金额从分改成元，在类型上都可能是整数，但已经改变业务含义。

### 4.5 CDC 与领域事件

CDC 从 binlog、WAL 或变更表捕获数据库变化。 CDC 适合大量既有表同步、搜索索引和数仓管道。
CDC 记录的是数据变化，不一定等于领域事实。 “订单已支付”是业务语义。
“orders.status 从 PENDING 更新为 PAID”是数据变化。 需要隐藏表结构、控制字段和表达业务语义时，优先 Outbox。
需要同步历史表或构建分析管道时，CDC 更直接。 CDC 事件应包含实体标识、操作类型、源位点、事务 ID 和发生时间。
消费中断超过 binlog 或复制槽保留窗口时，必须从全量快照重新初始化。 不能通过跳过缺失位点假装数据连续。

## 五、分布式一致性与集成模式

### 5.1 Outbox 与 Inbox 的组合

Producer 侧 Outbox 解决本地业务数据和待发送事件的共同提交。 Consumer 侧 Inbox 解决消息重复和业务结果的共同提交。
两者组合仍然是至少一次的链路。 发布器可能重复发送。
消费者可能重复收到。 外部系统可能重复执行。
因此事件 ID、业务唯一键和版本条件更新必须贯穿链路。 典型链路如下：

~~~text
本地业务事务 + Outbox
  -> Producer Confirm
  -> Broker durable log
  -> Consumer read
  -> Inbox + 业务事务
  -> ACK
~~~
每一个箭头都应有超时、重试、监控和恢复动作。

### 5.2 Saga 编排与协同

Saga 把长流程拆成多个本地事务。 每一步成功后发布下一步事件。
失败时执行补偿动作。 编排式 Saga 由协调者持久化流程状态。
协同式 Saga 让各服务监听事件自行推进。 补偿不是数据库回滚。
退款、释放库存和撤销权益本身也可能失败。 每一步都要定义正向命令、补偿命令、幂等键、超时和人工介入状态。
迟到的补偿不能覆盖更新后的业务版本。 事件应携带 sagaId、stepName 和 aggregateVersion。
Saga 适合允许中间状态和最终一致的长流程。 能收敛到单个本地事务时，优先避免跨服务事务。

### 5.3 事务消息与 Exactly-once

事务消息可以把 Broker 内的多条写入原子提交。 它也可以把 Producer 状态和消息提交关联起来。
它不能自动纳入外部数据库、HTTP、邮件、支付和人工操作。 必须区分 Broker 日志一次性、Offset 一次性和业务副作用一次性。
这三层不在同一原子边界时，仍然需要幂等。 事务超时、协调者故障和未决事务会占用资源。
为少量重复引入事务协议，可能换来更高延迟和复杂恢复。 通常更容易审计的做法是数据库本地事务加 Outbox。
消费者提交 Offset 前完成本地事务，并让重复消息安全执行。

### 5.4 数据库、缓存、搜索同步

关系型数据库通常是业务权威来源。 缓存、搜索和数仓通常是可重建的派生系统。
推荐路径是主库事务写入业务数据和 Outbox。 消费者再更新缓存、索引和分析表。
请求内直接双写主库和搜索有网络失败窗口。 缓存通常采用 Cache Aside。
写入主库成功后删除或失效缓存。 并发回填、删除失败和热点失效仍会产生陈旧读。
搜索文档更新要携带实体版本。 只有更高版本才能覆盖旧索引。
权限校验不能因为命中搜索或缓存而省略。 索引映射变更或消息保留不足时，从主库快照重建。
数据库、缓存、消息队列、搜索与数仓的职责边界见 [[后端/数据库/0. 数据库概览与选型/4. 数据库、缓存、消息队列、搜索与数仓的边界|多存储职责边界]]。

### 5.5 对账、修复和最终一致闭环

最终一致系统必须能回答“现在是否一致”和“如何恢复”。 对账使用稳定业务 ID。
比较状态、版本、金额、数量和必要的更新时间。 区分暂时延迟、可自动修复和必须人工确认的差异。
修复应重新产生幂等命令或事件。 不要直接手工修改多个派生系统来抹平差异。
回放使用隔离 Consumer Group 或独立重放 Topic。 限制时间、版本、业务键、速率和并发。
记录起止 Offset、代码版本、Schema 版本、操作者和原因。 修复后再次进入对账。
关键指标包括差异数、自动修复成功率、最老差异年龄和人工待处理量。

## 六、典型架构与业务场景

### 6.1 异步任务与 Work Queue

Work Queue 让多个 Worker 竞争处理任务。 每条任务通常只由一个 Worker 完成。
适合邮件、转码、报表、批处理和重试型工作。 任务消息应包含 taskId、任务类型、参数摘要、截止时间和幂等键。
Worker 先校验任务版本、权限和截止时间。 成功后 ACK。
临时错误退避重试。 超过次数进入 DLQ。
外部 API 调用必须设置超时和幂等请求键。 任务状态应持久化供前端查询。
队列为空不代表所有任务已经完成。

### 6.2 发布订阅与 Fan-out

发布订阅让多个独立消费者分别处理一个事实事件。 每个订阅者有独立 Consumer Group、进度、失败和保留策略。
新增订阅者可以从保留日志或快照初始化。 一个订阅者积压不应阻塞其他订阅者。
Fan-out 会线性放大网络、存储和下游写入。 高扇出场景可使用中间投影或批量分发。
事件发布者不应在同步请求中等待所有订阅者完成。 需要同步结果时，使用状态 API 或明确的命令响应。

### 6.3 延迟、定时和优先级

延迟消息表示最早可执行时间，不保证精确触发时刻。 Broker 原生延迟、TTL 加 DLQ、时间轮和外部调度器各有精度与可靠性差异。
消息应携带 expiresAt。 消费者收到过期消息时重新检查业务状态。
订单超时取消不能只依赖延迟消息。 消费者必须在数据库事务中按版本确认订单仍为待支付。
优先级队列可能造成低优先级饥饿。 使用配额、老化策略或拆分队列避免饥饿。
定时任务需要 jobId、时区规则、重复触发保护和补偿扫描。

### 6.4 微服务事件驱动

事件驱动让服务通过事实事件解耦部署和调用链。 事件描述已发生的事实。
命令表示请求某个服务执行动作。 不要把内部数据库表直接暴露成公共契约。
不要依赖隐式全局顺序。 用 Schema、事件版本、幂等和重放建立恢复边界。
事件风暴会造成高扇出和级联故障。 应限制订阅范围、设置超时、断路和配额。
最终一致的用户界面要显示处理中、失败、重试和人工处理状态。

### 6.5 订单、支付、库存和通知

订单服务的本地事务通常是订单状态的权威来源。 订单创建后发布 OrderCreated。
库存、支付和通知服务分别处理并发布结果。 支付回调、库存扣减和超时取消可能乱序或重复。
服务应按订单状态机和版本条件更新。 库存数量约束必须在库存数据库事务中维护。
不能用队列消息数量直接当库存账本。 支付金额、币种和外部流水号必须服务端校验。
支付操作使用 paymentId 或 idempotency key 去重。 通知失败可以重试和进入 DLQ。
通知失败不应回滚已完成的订单支付。 订单、支付和库存应建立对账任务。
用户看到“已入队”时不能被误导为“支付已完成”。

### 6.6 搜索、缓存和数仓

主库事件通过 Outbox 或 CDC 发布。 搜索消费者更新索引。
缓存消费者删除或刷新热点键。 数仓消费者写入事实和维度数据。
搜索更新要检查实体版本。 删除事件不能因乱序重新创建已删除文档。
缓存必须设置 TTL、回源限流和权限校验。 数仓同步要记录源位点、去重键和迟到数据规则。
映射变更时执行全量快照、增量追平和差异校验。 不要用手工修改索引代替修复主库。

### 6.7 流式处理与实时计算

流式处理持续消费事件，按 key、窗口和状态生成聚合。 实时指标、风控、推荐和监控都属于典型用途。
需要 checkpoint、状态存储、迟到事件策略和可重放输入。 事件时间与处理时间必须区分。
Watermark 说明系统认为某个时间点之前的事件基本到齐。 允许迟到时间决定窗口还能否被修正。
窗口结果应携带窗口起止、版本和计算批次。 状态存储要有 TTL，避免无限膨胀。
热点 key、反压和外部 Sink 故障会拉高 Lag。 结果是派生视图，需要支持重算和对账。

## 七、生产运维检查

### 7.1 性能与容量

按 Topic、Partition 和 Consumer Group 分层测 Throughput、Latency 和 Lag。 消息数速率不能替代字节速率。
分区数按峰值字节速率除以单分区实测安全吞吐估算。 保留期、消息大小、副本数、压缩比和重放并发决定磁盘容量。
测试正常、峰值、消费者故障、回放和单节点故障。 观察 CPU、磁盘 IO、网络、GC、连接池和下游延迟。
扩容前确认瓶颈确实在队列，而不是数据库或第三方 API。

### 7.2 可观测性

Producer 监控发送成功率、Confirm 延迟、重试率和失败码。 Broker 监控磁盘、IO、网络、连接、请求队列和副本同步。
Consumer 监控处理耗时、ACK/Commit 失败、Lag、Oldest Message Age 和 Rebalance。 业务侧监控重复数、丢失数、差异数和 DLQ。
Trace Context 关联 HTTP、Producer、Consumer 和数据库 Span。 指标标签避免使用 messageId、用户 ID 和完整错误文本。
错误、DLQ、超时和尾延迟应提高采样率。 消息队列的容量和 SLO 方法可参考 [[后端/数据库/11. 可观测性与性能工程/1. 指标、SLO与容量规划|指标、SLO 与容量规划]]。

### 7.3 安全与资源隔离

Authentication 证明身份。 TLS 保护传输。
ACL 限制 Topic、Consumer Group、Schema 和管理 API 的权限。 生产者、消费者、运维和回放任务使用独立身份。
生产者只写指定 Topic。 消费者只读指定 Topic 和 Group。
回放账号限制时间、范围和审批。 证书自动轮换并验证主机名和 CA。
多租户还要隔离命名空间、配额、保留空间和网络。 达到配额时限流或拒绝，不允许无界排队。

### 7.4 备份、恢复和演练

副本解决节点故障。 备份解决误删、逻辑错误和全站损坏。
备份范围包括日志、元数据、Schema、ACL、配置、Offset 和密钥。 恢复先恢复 Broker、元数据、Schema 和权限。
再按业务优先级启动消费者。 如果下游事务状态不确定，从安全位点重放。
依靠 Inbox 和幂等避免重复副作用。 定期做消息解码、备份可读性和完整恢复演练。
记录实际 RPO、RTO、恢复步骤和容量余量。

## 八、常见面试题

### 为什么先 ACK 再写数据库会丢消息？

ACK 让 Broker 认为消息已经完成。 如果进程在 ACK 后、数据库提交前崩溃，消息不会再次投递。
因此至少一次消费应在业务副作用成功后确认。

### ACK 丢失为什么通常带来重复而不是丢失？

业务已经成功提交，但 Broker 没收到确认。 Broker 仍把消息视为未完成并重新投递。
消费者需要通过 Inbox、唯一约束或版本更新安全处理第二次。

### Producer Confirm 和 Consumer Commit 有什么区别？

Confirm 说明 Broker 对生产请求的接收或提交结果。 Commit 说明 Consumer Group 保存了读取位置。
两者处于消息生命周期的不同边界。 它们都不直接代表业务副作用已经完成。

### 为什么 Exactly-once 不能覆盖发送邮件？

Broker 事务和邮件服务没有共同的原子提交协议。 消费者可能已发送邮件但尚未提交 Offset。
重试会再次发送。 邮件服务需要幂等键、去重表或可接受的重复策略。

### 如何保证订单事件有序？

用 orderId 作为稳定 Partition Key。 同一订单进入同一 Partition。
消费者按 aggregateVersion 检查缺口和旧版本。 跨订单不假设全局顺序。

### 增加消费者为什么不一定提高吞吐？

消费者数量可能已经超过 Partition 数。 也可能是热点 key 把工作集中到一个 Partition。
还可能是数据库或第三方 API 已经成为瓶颈。

### 什么时候选择 Outbox 而不是 CDC？

需要表达领域事实、隐藏表结构和控制事件字段时选择 Outbox。 需要同步既有大量表、构建数据管道或捕获历史变更时 CDC 更直接。
CDC 的数据变化不一定等于业务事件。

### 如何处理 Poison Message？

限制重试次数和总时间。 记录失败分类和原始位置。
转入 DLQ，修复代码或数据后隔离回放。 不能让它无限阻塞主消费流。

### 如何安全回放支付事件？

先建立隔离 Consumer Group。 限定事件范围和速率。
确认 paymentId 唯一约束和外部支付 API 幂等能力。 只重放可验证的状态投影，回放后做订单支付对账。

### 如何判断消费积压是否影响用户？

同时观察 Lag 和 Oldest Message Age。 再映射消息类型对应的业务 SLO。
低优先级分析流积压不一定影响下单。 支付确认流的最老年龄超标则需要立即升级。

### 为什么副本不是备份？

副本会同步误删、逻辑错误和错误发布。 备份保留可回到历史时间点的数据。
两者承担的故障类型不同。

### 为什么延迟消息不能直接取消订单？

延迟消息可能重复、乱序或延迟到达。 消费者必须在订单数据库事务中检查当前状态和版本。
已支付订单不能被迟到的取消消息覆盖。

### 如何避免 Schema 变更击穿旧消费者？

新增可选字段并提供默认值。 先做兼容性检查和旧样本测试。
重大语义变化创建新事件版本。 等待旧消费者迁移完成后再删除旧字段。

### 如何处理热点 Partition？

先按 Partition 和 key 统计流量。 确认业务是否必须保持同一 key 顺序。
不需要全序时增加可控分片后缀。 需要顺序时拆分聚合或在下游按版本合并。
不能只通过增加消费者解决固定热点。

### 消费者优雅关闭要注意什么？

先停止拉取新消息。 等待在途事务完成或让租约过期。
确认后再 ACK。 设置截止时间，最后关闭连接池和客户端。

### 如何设计消息链路的指标标签？

保留集群、Topic、Group、Partition 等低基数维度。 messageId 和用户 ID 放在日志或 Trace，不放进长期时序标签。
否则高基数会让监控系统内存和查询成本失控。

### 如何证明最终一致性真的完成？

建立源数据与派生结果的对账。 记录差异、修复、回放和人工处理结果。
修复后再次对账。 只看到 Broker 发送成功不能证明业务结果一致。

## 九、学习后的落地顺序

先为消息定义 Envelope、稳定 ID、事件类型和 Schema。 再确定 Producer Confirm、Retry、超时和 Outbox 边界。
然后设计 Consumer 的 ACK 时机、幂等、Inbox、DLQ 和 Replay。 接着明确顺序、分区、Consumer Group 和容量模型。
最后补齐指标、Trace、权限、备份、恢复和对账。 对已有系统改造时，先选择一个低风险 Topic 做端到端演练。
记录重复、乱序、积压、DLQ 和恢复结果。 再把稳定的模式推广到支付、库存和多存储同步等关键链路。
消息队列的价值取决于故障时是否仍然可解释、可恢复和可对账。
