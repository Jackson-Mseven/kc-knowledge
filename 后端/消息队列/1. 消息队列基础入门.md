# 消息队列基础入门

消息队列（Message Queue，MQ）让一个服务把消息交给中间系统，再由另一个服务稍后处理。
它把一次同步调用拆成“提交消息”和“处理消息”两个阶段。
这种拆分可以降低调用方与下游的时间耦合、地址耦合和故障耦合。
它也引入了延迟、重复、乱序、积压和最终一致性等新的系统状态。
本篇从通用模型出发，建立阅读 Kafka、RabbitMQ、RocketMQ、Pulsar 或 Redis Streams 文档所需的共同词汇。

## 先建立一张全局图

```text
业务请求
   |
   v
Producer --发送消息--> Broker --保存/路由--> Queue 或 Topic
                                         |
                                         v
                                  Consumer 处理消息
                                         |
                    +--------------------+--------------------+
                    |                                         |
               ACK/Commit                              Retry / DLQ
                    |                                         |
             消息完成或推进位点                     延迟重试或人工处理
```

Producer 是消息生产者，Consumer 是消息消费者，Broker 是消息代理。
Queue 通常描述竞争消费的一组待处理任务，Topic 通常描述可被多个订阅者读取的消息流。
消息写入 Broker 不代表业务动作已经完成。
Consumer 处理成功并确认后，Broker 才能推进这条消息的完成状态。

推荐先阅读本篇，再根据实现选择具体中间件专题。
通用边界也可以结合 [[后端/数据库/0. 数据库概览与选型/4. 数据库、缓存、消息队列、搜索与数仓的边界|数据库、缓存、消息队列、搜索与数仓的边界]]。

## 1. 消息队列解决什么问题

### 1.1 时间解耦

同步 RPC 要求调用方等待下游返回。
下游变慢时，请求线程、连接和用户等待时间都会增加。

异步消息只要求 Producer 在约定的超时内完成提交。
发票生成、搜索索引、邮件发送等工作可以在稍后执行。
调用方需要通过状态查询、回调或通知知道最终结果。

```text
同步：创建订单 -> 调用支付 -> 调用库存 -> 调用通知 -> 返回
异步：创建订单 -> 写入 OrderCreated -> 返回处理中
                              |-> 支付服务
                              |-> 库存服务
                              |-> 通知服务
```

时间解耦不是“永远不等待”。
用户必须立即知道订单是否创建成功时，订单本地事务仍然要同步完成。
只有耗时或可延后的副作用才适合放入消息处理链路。

### 1.2 空间解耦

Producer 不需要知道 Consumer 的实例地址、容器数量和部署位置。
Broker 通过 Queue、Topic、Subscription 或路由规则找到目标。
Consumer 可以扩容、缩容或短暂重启，而不要求 Producer 改地址。

解耦依赖稳定的消息契约。
如果 Producer 发送的是数据库整行快照，Consumer 仍然依赖表结构，空间解耦会被隐式耦合抵消。
消息应表达业务事实、命令或任务，而不是无边界地复制内部对象。

### 1.3 削峰和缓冲

假设 Producer 峰值为每秒 10,000 条，Consumer 稳定处理每秒 4,000 条。
短时间内 Broker 会积累约 6,000 条每秒的 backlog。
缓冲可以把峰值摊平，但不能消除总工作量。

如果峰值持续，积压最终会达到磁盘、保留时间或用户延迟上限。
因此必须同时设置最大积压、最老消息年龄和恢复速率。
无限制地增加 Consumer 可能先打满数据库连接池，再让系统整体失败。

### 1.4 一对多分发

一个 `OrderPaid` 事件可能被积分、发票、通知和数据分析服务分别读取。
发布者只描述“订单已经支付”这个事实，不需要逐一调用这些服务。
每个订阅者都有自己的消费进度、失败处理和上线节奏。

### 1.5 失败隔离

邮件供应商不可用时，通知消息可以延迟重试。
订单主流程不必因为邮件接口超时而回滚已经提交的订单。
失败隔离需要 Retry、Dead Letter Queue（DLQ）、超时和监控配合。
只把异常吞掉并继续 ACK 会把可恢复故障变成数据丢失。

## 2. 消息队列不能替代什么

- **消息队列不是业务主数据库。**
它通常保存短期传输记录、事件日志或任务状态，不适合作为任意条件查询的主数据源。
需要按用户、金额和状态组合查询时，应读取数据库或专用查询模型。

- **消息队列不是分布式事务的自动实现。**
“数据库提交成功”和“消息发送成功”是两个独立副作用。
要保证二者的一致性，通常使用本地事务加 Outbox，再由发布器投递。
更完整的事务边界、幂等和对账说明见 [[后端/数据库/8. 分布式数据库与水平扩展/3. 分布式事务与可靠消息|分布式事务与可靠消息]]。

- **消息队列也不是无限缓存。**
Retention、TTL、磁盘配额和备份成本都限制可保存时间。
消息的保留时间必须由恢复目标、回放窗口和合规要求推导。

- **消息队列不能自动提供全局顺序。**
一旦使用多个 Partition 或多个并行 Consumer，不同分区之间通常没有顺序关系。
必须把顺序要求限定在同一聚合、分区或 Queue 的范围内。

## 3. 三个核心角色

### 3.1 Producer

Producer 构造消息并发送到 Broker。
它负责选择目标、序列化载荷、计算路由键、设置超时并处理发送结果。
Producer 不应把“调用 send 方法返回”当作业务完成。

发送结果至少应区分以下状态：

| 状态 | 含义 | 能否宣称业务完成 |
| --- | --- | --- |
| 本地已入队 | 客户端暂存到内存或本地 buffer | 不能，进程可能崩溃 |
| Broker accepted | Broker 接受了请求 | 取决于持久化策略 |
| Durable | 消息写入持久介质 | 仍不能说明 Consumer 已处理 |
| Replicated | 达到副本/Quorum 确认 | 仍不能说明业务副作用完成 |
| Consumer ACK | Consumer 确认处理完成 | 只表示该 Consumer 的处理完成 |

网络超时是未知状态。
Broker 可能已经保存消息，只是 Confirm 响应没有回到 Producer。
重试时应复用同一个逻辑 `message_id`，而不是无条件生成新消息。

### 3.2 Broker

Broker 接收、保存、复制、路由和投递消息。
它还维护 Queue/Topic 的元数据、权限、订阅进度、确认状态和保留策略。

Broker 的持久化机制可能是顺序日志、WAL、Segment、页或其他实现。
应用关心的是确认边界：写入内存、写入本地磁盘、复制到副本还是提交到 Quorum。
不同中间件的配置名称不同，不能仅凭参数名推断相同语义。

Broker 还承担流量保护。
当 Producer 速率超过处理能力时，Broker 可能限流、拒绝、延迟确认或触发配额。
Producer 必须处理这些结果，而不是持续把消息堆在无界内存中。

### 3.3 Consumer

Consumer 从 Queue 或 Subscription 取得消息，执行本地业务动作，然后确认、重试或拒绝。
Consumer 的吞吐由并发数、批量大小、下游能力和消息处理时长共同决定。

Consumer 必须明确 ACK 时机。
一般顺序是“读取 -> 执行业务副作用 -> 持久化处理结果 -> ACK/Commit”。
如果先 ACK，再写数据库，进程崩溃会造成消息丢失。
如果写入成功但 ACK 响应丢失，消息可能再次投递，必须允许重复。

## 4. 消息的生命周期

一条消息可以经历以下状态：

```text
Created
  -> Sent
  -> Accepted
  -> Durable / Replicated
  -> Available
  -> Delivered / In-flight
  -> ACK / Commit
  -> Completed

Delivered 失败 -> NACK / lease timeout -> Retry
Retry 次数耗尽 -> Dead Letter Queue
Available 超过 TTL -> Expired
Retention 到期 -> Purged
```

`Created` 表示应用决定产生一条逻辑消息。
`Sent` 表示 Producer 发起发送。
`Accepted` 表示 Broker 接受请求，但持久化级别需要进一步确认。
`Available` 表示消息可被 Consumer 领取。
`In-flight` 表示消息已交给 Consumer，但还未确认。
`Completed` 表示 Broker 记录了成功确认或消费位点。

失败链路不一定回到主 Queue。
可以根据错误类型进入延迟 Retry Topic、重试队列或 DLQ。
消息过期和 Retention 清理属于存储生命周期，不等于业务已经成功处理。

消息建议携带以下元数据：

| 字段 | 用途 |
| --- | --- |
| `message_id` | 标识一次逻辑消息，支持幂等与审计 |
| `type` | 区分事件、命令或任务 |
| `schema_version` | 解释载荷版本 |
| `occurred_at` | 业务事实发生时间 |
| `producer` | 识别发布服务和版本 |
| `correlation_id` | 关联一次业务流程 |
| `causation_id` | 记录由哪条消息触发 |
| `partition_key` | 选择顺序和并行范围 |
| `attempt` | 记录重试次数 |

不要在消息中放置数据库连接、短期内存引用和真实凭证。
大文件或大图片应放对象存储，消息只携带稳定引用、版本和访问权限信息。

## 5. Queue、Topic、Partition、Subscription 与 Consumer Group

### 5.1 Queue

Queue 是等待处理的消息集合。
多个 Consumer 可以竞争领取消息，同一条消息通常只交给一个逻辑接收者。
Queue 更接近“任务清单”，关注消息是否完成、失败和重试。

适合 Queue 的问题通常是：“这个任务由某个 worker 完成一次即可吗？”
例如生成缩略图、发送一封邮件或刷新一个缓存条目。

### 5.2 Topic

Topic 是按名称发布的消息流或路由目标。
多个 Subscription 可以读取同一 Topic 的消息，各自维护独立进度。
Topic 更适合描述已经发生的业务事实。

一个 `OrderCreated` Topic 可以同时服务搜索、通知和数据仓库。
新增订阅者可以从当前时间开始读取，也可以从保留的历史位置回放。

### 5.3 Partition

Partition 是 Topic 内的独立有序子流。
Producer 根据 `partition_key` 把消息放入某个分区。
同一个键通常映射到同一个 Partition，从而获得局部顺序。

```text
Topic: order-events
  Partition 0: order-101 Created -> Paid
  Partition 1: order-102 Created -> Paid
  Partition 2: order-103 Created -> Paid
```

一个 Consumer Group 内，同一 Partition 在同一时刻通常只分配给一个 Consumer。
因此 Group 的有效并行度受 Partition 数量限制。
实例数超过 Partition 数不会继续提升该 Group 的并行度。

Partition 数量也会影响顺序、存储和 Rebalance。
增加分区可能改变某些哈希路由的归属，扩容前应确认中间件的映射规则。

### 5.4 Subscription

Subscription 表示某个逻辑订阅者对 Topic 的读取状态。
它可以保存 offset、cursor、过滤规则、消费模式和重试状态。
两个 Subscription 读取同一个 Topic 时，互不共享消费进度。

通知服务确认一条消息，不会让搜索服务跳过这条消息。
每个 Subscription 都要有自己的容量、告警和保留窗口。

### 5.5 Consumer Group

Consumer Group 是共享一个消费进度的一组 Consumer 实例。
组内实例负责分工，组外的另一个 Group 可以独立读取同一消息。

```text
Topic order-events
  Group search:
    C1 -> P0
    C2 -> P1
  Group notification:
    C3 -> P0, P1（独立位点）
```

Consumer Group 只解决组内分工。
它不提供跨 Group 的事务，也不保证每个 Group 都能赶上实时消息。
组内实例变化会触发分区重新分配，期间可能出现暂停和重复处理。

## 6. 四种常见通信模型

### 6.1 点对点

点对点模型把一条消息交给一个逻辑接收者。
多个实例可以竞争处理，但不会让每个实例都执行一次。
确认成功后，消息通常从待处理集合中移除或标记完成。

它适合命令和单次任务。
任务失败时需要重新可见、延迟重试或 DLQ。

### 6.2 发布订阅

发布订阅模型让多个订阅者分别获得一份消息。
发布者不需要等待或了解所有订阅者。
每个订阅者可以独立扩容、暂停和回放。

发布订阅并不保证订阅者永远在线时也能收到消息。
订阅者离线时间超过 Retention 后，消息可能已被清理。

### 6.3 Work Queue

Work Queue 是多个 worker 竞争完成任务的模式。
任务通常有处理状态、租约、超时、重试和死信。

```text
Queue image-jobs
  image-worker-1 领取 job-1
  image-worker-2 领取 job-2
  image-worker-3 空闲等待
```

扩容 worker 可以增加吞吐，但受 CPU、对象存储、数据库和第三方 API 的最小瓶颈约束。
必须设置并发上限，避免任务数量越多就建立越多下游连接。

### 6.4 Event Stream

Event Stream 把消息和消费位点分离。
消息在保留窗口内作为可回放日志存在。
消费者可以暂停、追赶、重新构建投影或从某个时间点重新计算。

Event Stream 适合审计、CDC、实时计算和多个独立投影。
回放会再次触发 Consumer 代码，不能绕过幂等、权限和副作用保护。

| 维度 | 点对点/Work Queue | 发布订阅/Event Stream |
| --- | --- | --- |
| 主要目标 | 完成一个任务 | 传播和保存一个事实 |
| 进度 | 通常完成即移除 | 每个订阅保存位点 |
| 新消费者 | 通常只处理新任务 | 可从历史回放 |
| 失败处理 | Retry/DLQ | 位点暂停、重试和隔离输出 |
| 典型载荷 | `GenerateInvoiceTask` | `InvoiceGeneratedEvent` |

## 7. Command、Event、Task 与 Notification

消息名称应表达发送者和接收者之间的责任。

| 类型 | 含义 | 接收者责任 | 是否通常可回放 |
| --- | --- | --- | --- |
| `Command` | 请求某个目标执行动作 | 执行或明确拒绝 | 需谨慎，重放可能重复动作 |
| `Event` | 描述已发生的事实 | 自主决定是否响应 | 可以，前提是 Schema 和幂等可用 |
| `Task` | 等待 worker 完成的工作项 | 给出成功/失败状态 | 可重试，按任务状态处理 |
| `Notification` | 告知状态或提醒 | 可降级或忽略 | 通常没有强制回放要求 |

`CreateInvoiceCommand` 是发给目标服务的请求。
它可能携带权限、期望版本、截止时间和 `idempotency_key`。

`OrderPaidEvent` 是订单已支付的事实。
库存、积分和通知服务可以分别订阅，发布者不要求它们采用相同处理方式。

`GenerateInvoiceTask` 代表一个必须完成或明确失败的工作。
它需要重试次数、截止时间、错误原因和最终状态。

短信提醒可以是 `Notification`。
短信不可用时，产品可能降级为站内信，而不是回滚已经完成的订单。

同一个用户动作可以同时产生 Command 和 Event。
HTTP 请求边界接收 `RegisterUserCommand`，本地事务提交后发布 `UserRegisteredEvent`。
两者不要使用相同的重试和权限逻辑。

## 8. Pull、Push、Polling 与 Streaming

### 8.1 Pull

Pull 由 Consumer 主动请求下一批消息。
Consumer 可以按自己的处理能力选择批量大小、并发和请求频率。
Pull 的优点是流量控制明确，缺点是需要处理空响应、长轮询和请求超时。

```ts
for (;;) {
  const messages = await broker.pull({ max: 20, wait_ms: 1000 })
  for (const message of messages) {
    await handle(message)
    await broker.ack(message.id)
  }
}
```

示例中的 `broker` 是抽象接口，不代表某个特定产品的 API。
真实实现还要处理连接重试、取消信号、并发信号量和优雅关闭。

### 8.2 Push

Push 由 Broker 通过长连接或回调主动投递。
低流量、低延迟场景可以减少 Consumer 的空请求。
没有 `prefetch`、租约或并发上限时，慢 Consumer 可能被持续投递并耗尽内存。

Broker 应在 Consumer 过载时暂停投递或降低窗口。
Consumer 仍然要限制处理并发，不能把背压责任完全交给 Broker。

### 8.3 Polling

Polling 是定时 Pull。
短轮询会反复产生没有消息的请求，长轮询可以在有消息前保持请求。
轮询间隔、最大等待时间和代理 `idle timeout` 必须协调。
多个实例需要加入随机抖动，避免同时唤醒形成流量尖峰。

### 8.4 Streaming

Streaming 建立持续数据流，让 Consumer 连续读取日志或事件。
Consumer 仍需记录已处理位点，不能把“读入客户端 buffer”当作业务完成。
断线后要从最后确认的位置恢复，处理心跳、半开连接、重连退避和优雅关闭。

| 方式 | 流量控制 | 延迟 | 实现重点 |
| --- | --- | --- | --- |
| Pull | Consumer 主动控制 | 低到中 | 批量、长轮询、超时 |
| Push | Broker 控制窗口 | 低 | prefetch、背压、连接状态 |
| Polling | 由定时器间接控制 | 取决于间隔 | 空请求、抖动、代理超时 |
| Streaming | 持续连接加位点 | 低 | 心跳、重连、offset 恢复 |

## 9. ACK、NACK、Offset、Commit 与 Visibility Timeout

### 9.1 ACK

ACK 是 Consumer 告诉 Broker“这条消息已处理成功”。
ACK 的对象通常是消息 ID、Delivery Tag 或一批消息。
ACK 成功后，Broker 可以删除消息、推进任务状态或允许下一条继续投递。

ACK 应在业务副作用完成后发送。
如果下游数据库事务还没有提交，提前 ACK 会扩大丢失窗口。

### 9.2 NACK

NACK 是 Consumer 明确拒绝或报告处理失败。
Broker 可以根据配置重新入队、延迟、丢弃或转入 DLQ。
NACK 本身不说明错误一定可重试。

参数错误和 Schema 不兼容反复 NACK 只会制造重试风暴。
应按错误分类决定重试或隔离。

### 9.3 Offset

Offset 是日志流中的位置。
Consumer 读取 offset 不代表业务已处理 offset。
如果进程在读取后、Commit 前崩溃，恢复时通常会重新读取。

Offset 是某个 Partition 和 Consumer Group 的位置。
不能把一个 Group 的 offset 当成另一个 Group 的处理进度。

### 9.4 Commit

Commit 把消费位点持久化到 Broker 或外部存储。
先 Commit 再处理接近 At-most-once，可能丢失但避免重复。
先处理再 Commit 接近 At-least-once，可能重复但不主动丢失。

批量 Commit 时，一条失败消息可能阻塞后续连续 offset。
必须明确能否跳过坏消息、是否使用重试分区以及如何保存空洞。

### 9.5 Visibility Timeout

Visibility Timeout 是任务领取后的暂时不可见租约。
Consumer 在租约内处理并 ACK，未 ACK 或进程崩溃后消息重新可见。

长任务需要续租。
续租时间过短会导致同一任务被两个 worker 同时执行。
续租时间过长会让崩溃任务等待很久才恢复。
最佳值应基于处理时长分位数、重试成本和重复副作用风险设置。

### 9.6 四种机制的对照

| 机制 | 主要对象 | 失败后结果 | 常见模型 |
| --- | --- | --- | --- |
| ACK | 单条消息或投递句柄 | 确认完成或重新投递 | Queue、Push |
| NACK | 失败的投递 | 重试、丢弃或 DLQ | Queue、Push |
| Offset | 日志位置 | 从已提交位置继续 | Topic、Event Stream |
| Commit | 消费进度 | 重复或丢失取决于时机 | Consumer Group |
| Visibility Timeout | 任务租约 | 超时后重新可见 | Work Queue |

它们都描述消费进度，但不应望文生义地互相替换。

## 10. At-most-once、At-least-once 与 Exactly-once

### 10.1 At-most-once

At-most-once 通常先 ACK 或 Commit，再执行处理。
一旦处理进程崩溃，Broker 认为消息完成，不会再次投递。
因此可能丢失，但不会由 Broker 主动重复交付。

它适合丢失成本很低的指标、临时通知或采样事件。
如果数据本身用于计费、库存或审计，不应仅依赖该语义。

### 10.2 At-least-once

At-least-once 先完成处理，再 ACK 或 Commit。
Consumer 崩溃、确认响应丢失或租约到期会导致消息再次投递。
它通常避免无确认消息被永久丢失，但要求业务处理幂等。

订单投影可以使用 `event_id` 唯一约束。
搜索索引可以使用实体版本条件更新。
累计积分不能简单地重复执行 `balance = balance + amount`，应记录业务流水号或采用幂等账本。

### 10.3 Exactly-once

Exactly-once 只在明确的原子边界内成立。
如果消息处理、输出写入和位点提交由同一事务管理，某些流处理系统可以提供一次性结果。
一旦跨出这个边界调用邮件、支付渠道或普通 HTTP 接口，系统仍然可能产生重复。

“Broker 只交付一次”也不等于“业务只执行一次”。
事务提交后客户端断线、下游超时和人工重放都可能再次触发业务代码。

### 10.4 语义选择

| 业务特征 | 推荐起点 | 必须补充 |
| --- | --- | --- |
| 可丢失的统计 | At-most-once | 采样率和丢失监控 |
| 订单、库存、索引 | At-least-once | 幂等键、唯一约束、版本检查 |
| 同一流内状态计算 | 事务或 EOS | 明确输入、状态和输出边界 |
| 外部不可逆副作用 | At-least-once | 供应商幂等键、状态机和对账 |

可靠消息的完整边界可以继续阅读 [[后端/数据库/8. 分布式数据库与水平扩展/3. 分布式事务与可靠消息|分布式事务与可靠消息]]。

## 11. 持久化、复制与确认

### 11.1 Producer 确认

Producer Confirm 让发送方知道 Broker 是否接受了消息。
确认级别可能从“写入 socket”到“复制到 Quorum”逐步增强。
持久化级别越高，通常延迟越大，但节点故障时可恢复性更好。

```ts
const result = await producer.send({
  topic: 'order-events',
  key: order.id,
  value: event,
  timeout_ms: 3000,
})

if (!result.accepted) {
  await outbox.markPending(event.event_id, result.error)
}
```

示例中的结果只表示发布边界。
它不表示通知 Consumer 已经发送邮件，也不表示订单投影已经更新。

### 11.2 Broker 持久化

持久化消息通常先进入日志或 WAL，再按照副本策略同步。
需要确认哪些节点保存了数据、何时可被选为 leader、故障恢复是否会回退已确认消息。

内存队列可以提供更低延迟，但进程或节点故障会丢失尚未落盘的消息。
订单、支付和审计事件应选择满足 RPO 的持久化级别。

### 11.3 Consumer 确认

Consumer 处理成功后发送 ACK 或 Commit。
ACK 前崩溃会导致重复，ACK 后崩溃可能不会重复。
因此正确策略不是追求“绝不重复”，而是让重复处理安全并可观测。

### 11.4 网络超时的未知状态

发送超时可能意味着消息未写入，也可能意味着消息已经持久化但响应丢失。
删除 Outbox 记录或生成新 ID 都可能造成丢失或重复。
恢复操作应保留原 ID，并通过 Broker 查询、幂等 Producer、Consumer 去重或对账确认结果。

### 11.5 Outbox 的位置

业务表和 Outbox 事件在同一个本地事务中提交，可以避免“数据已提交但事件没有记录”。
发布器随后独立发送，并在 Confirm 后标记发布状态。
发布器在 Confirm 与标记之间崩溃时会重复发送同一事件。
因此 Outbox 保证的是共同提交，不是全链路 Exactly-once。

## 12. 顺序、分区键与乱序

### 12.1 顺序范围

消息系统通常只保证有限范围内的顺序。
这个范围可能是单个 Queue、单个 Partition、同一个分区键或一个 Consumer 的串行处理。
不同 Partition、不同 Consumer Group 和不同服务之间通常没有全局顺序。

### 12.2 选择分区键

订单状态需要按 `order_id` 保持局部顺序。
Producer 对同一个 `order_id` 使用稳定哈希即可把事件放到同一 Partition。

```text
hash(order-42) -> P2: Created, Paid, Shipped
hash(order-43) -> P0: Created, Paid
```

不要使用随机 ID 作为分区键。
随机键会把同一订单的事件分散到多个分区，消费者无法依赖分区内顺序。
不要使用会变化的用户属性作为分区键，否则同一聚合可能迁移。

### 12.3 局部顺序不等于发生顺序

Producer 重试、多个应用实例和跨地域网络都会改变消息到达时间。
`occurred_at` 是业务产生时间，Broker offset 是写入顺序，Consumer 完成时间是处理顺序。
三者不能混为一谈。

重要事件应携带 `aggregate_version`。
Consumer 可以拒绝旧版本、等待缺失版本或将无法排序的事件送入隔离队列。

### 12.4 乱序策略

| 业务要求 | 策略 | 代价 |
| --- | --- | --- |
| 只要最终状态 | 版本条件更新 | 需要保存版本 |
| 不能跳过状态 | 重排缓冲和缺口超时 | 增加延迟和内存 |
| 可以丢弃旧事件 | 只接受更大版本 | 需要定义旧事件处理结果 |
| 必须全局有序 | 单分区/单 worker | 吞吐和可用性下降 |

### 12.5 顺序与扩容的冲突

增加 Partition 提高并行度，但会增加路由、Rebalance 和顺序边界复杂度。
同一聚合的消息不能因为扩容而被不同实例同时处理。
真正需要全局顺序的场景应先确认是否可以缩小为聚合级顺序。

## 13. 重复消息与基础幂等

### 13.1 重复从哪里来

- Producer 等待 Confirm 超时后重试。
- Consumer 完成数据库写入，但 ACK 响应没有到达。
- Visibility Timeout 过短，任务仍在运行就重新可见。
- Consumer 在处理过程中崩溃，恢复后从旧 offset 重读。
- 运维人员为了修复故障进行 Replay 或 Reprocess。

重复不是异常边界之外的极端情况。
At-least-once 系统应把重复看作正常路径。

### 13.2 幂等的目标

幂等不是“函数只执行一次”。
它是同一逻辑消息执行多次后，持久化业务结果与执行一次相同。
发送邮件可以用供应商支持的幂等键。
更新投影可以用实体版本。
写入记录可以使用 `event_id` 唯一约束。

### 13.3 唯一约束

对 `event_id` 或自然业务键建立唯一索引是最可靠的并发防线。
进程内 `Set` 无法跨重启和多实例工作。
“先查询再插入”存在并发窗口，最终必须由数据库唯一约束裁决。

```sql
INSERT INTO processed_event(event_id, consumer_name)
VALUES (:event_id, :consumer)
ON CONFLICT (event_id, consumer_name) DO NOTHING;
```

只有实际插入成功的事务继续执行本次副作用。
冲突表示消息已处理，Consumer 可以确认并跳过。

### 13.4 Inbox 与业务事务

Inbox 表记录某个 Consumer 已经接受的 `event_id`。
Inbox 插入和业务更新必须在同一数据库事务中。
业务失败时回滚 Inbox，让消息继续重试。
业务成功后 ACK，重复消息插入冲突并安全跳过。

跨数据库或外部 API 无法直接使用同一事务。
应记录待处理状态、使用外部服务的幂等键，并通过 Outbox、补偿和对账闭环。

### 13.5 版本条件更新

对同一实体，事件携带单调版本。
写入时要求 `incoming_version > stored_version`，旧事件不覆盖新状态。
发现 `incoming_version` 大于当前版本加一时，说明存在缺口，应等待、回放或告警。

### 13.6 去重记录保留时间

去重键至少要覆盖最大自动重试、消息 Retention、人工回放和客户端重复请求窗口。
过早清理去重表会让很久以前的消息重放再次产生副作用。
无限保留又会增加索引和存储成本，可以按业务时间分区归档并保留摘要。

## 14. Retention、TTL、Replay 与清理

### 14.1 Retention

Retention 定义消息或日志保留多久、保留多少字节或 Segment。
日志型系统可能在 Segment 到期后整体删除，队列型系统可能在 ACK 后删除。
未消费消息也可能因为 Retention 到期而消失。

Retention 应由以下约束推导：

- Consumer 最长故障恢复时间。
- 允许的 Replay 时间窗口。
- 数据备份和灾难恢复的 RPO/RTO。
- 隐私和合规删除期限。
- 预计吞吐、消息大小和磁盘容量。

### 14.2 TTL

TTL（Time To Live）规定单条消息的最大寿命。
订单超时取消、活动结束后的优惠券任务可以使用 TTL。
TTL 到期表示消息不再值得执行，不代表执行成功。

不同 Broker 的 TTL 精度和触发方式不同。
它可能在扫描时批量清理，而不是在精确时间点触发业务代码。
需要精确调度时，应使用定时任务、延迟队列或消费端检查业务截止时间。

### 14.3 Replay

Replay 从历史 offset、时间范围、归档或 Outbox 中重新读取消息。
它适合重建搜索投影、修复数据缺口和验证新版本 Consumer。

安全回放的基本流程：

```text
生成 replay_id
  -> 选择时间/offset 范围
  -> 独立 Consumer Group
  -> staging 表或隔离 Topic
  -> 小批量验证
  -> 限速回放
  -> 对账并切换结果
```

回放应记录操作者、代码版本、Schema 版本、范围和处理结果。
不要直接把历史消息打回实时 Topic 并期待业务自动恢复。
历史事件可能使用旧 Schema，也可能触发不可逆的支付、邮件或库存副作用。

### 14.4 Reprocess 与人工处理

Reprocess 是对失败消息重新执行处理流程。
重新执行前先修复根因，区分可重试错误和数据错误。
人工介入应提交可审计的幂等命令，不直接删除消息或手改多个系统。

支付、库存等不可逆动作需要先查询权威系统当前状态。
如果状态已经完成，应跳过重复动作并记录结论。
如果状态不确定，应进入审批或对账流程，而不是盲目补发。

### 14.5 清理

清理包括正常消息过期、已确认消息删除、旧 Segment 归档和 DLQ 清理。
删除 DLQ 前要导出原始载荷、错误原因、消费者版本和人工处理结果。
清理任务应限速，不能在 Broker 资源紧张时与大规模 Replay 同时运行。

## 15. 把一次订单事件串起来

下面用“订单创建后异步更新搜索和通知”串联前面的概念。

### 15.1 本地事务

订单服务在一个本地事务中写入订单和 Outbox 事件。
事件包含 `event_id = order_id + version`、事件类型和最小必要载荷。
事务提交后，订单已经是权威状态，事件记录等待发布。

```text
BEGIN
  INSERT orders(order_id, status, version)
  INSERT outbox(event_id, type, payload, status='pending')
COMMIT
```

### 15.2 发布

发布器按批次读取 pending Outbox。
它发送到 `order-events` Topic，使用 `order_id` 作为分区键。
Broker Confirm 成功后标记发布，但保留 `event_id` 和发送时间。
发送超时只表示未知状态，发布器重试同一事件 ID。

### 15.3 搜索 Consumer

搜索服务使用 `search` Consumer Group。
它按 `order_id` 的版本更新索引。
收到旧版本时跳过，收到缺口时暂停该实体或记录重建任务。
索引成功后 Commit offset。

### 15.4 通知 Consumer

通知服务使用独立的 `notification` Consumer Group。
它可以有自己的并发、Retry 和 DLQ。
邮件服务超时不会阻塞搜索服务的 offset。
邮件供应商请求使用 `event_id` 作为幂等键，避免确认超时后重复发送。

### 15.5 故障情形

| 故障 | 可能结果 | 处理方式 |
| --- | --- | --- |
| 发布器发出后崩溃 | 重复发布 | 复用 ID，Consumer 幂等 |
| 搜索写入成功后崩溃 | 重复索引 | 版本条件更新 |
| 通知供应商超时 | 是否已发送未知 | 外部幂等键和状态查询 |
| Topic 暂时不可用 | Outbox 积压 | 退避、告警、限流 |
| 通知格式错误 | Poison Message | 有限重试后 DLQ |
| Consumer 长时间停止 | backlog 增长 | 监控最老消息年龄，恢复后限速追赶 |

这个例子展示了消息队列的真实边界：
消息发布、消费、外部副作用和业务对账分别需要可靠机制。

## 16. 最小生产检查清单

| 领域 | 发布前必须回答的问题 |
| --- | --- |
| 契约 | 是否有稳定 `message_id`、`schema_version` 和最小载荷？ |
| Producer | 是否有 Confirm、有限 Retry、退避、buffer 和超时？ |
| Broker | 持久化、副本、Retention、TTL、配额和权限是否满足目标？ |
| Consumer | 是否在业务成功后 ACK/Commit，并限制并发和下游 QPS？ |
| 失败处理 | 是否区分瞬时错误、毒丸消息、Retry、DLQ 和人工介入？ |
| 运维 | 是否监控 backlog、最老消息年龄、重试率、DLQ 和业务对账？ |

## 17. 常见错误

### 把发送成功当作业务完成

Producer Confirm 只确认 Broker 的接收或持久化边界。
Consumer 可能尚未运行、可能失败，也可能只写入了部分下游系统。

### 先 ACK 再执行副作用

先 ACK 可以降低重复，但会在进程崩溃时丢失消息。
除非业务明确接受 At-most-once，否则应在副作用成功后确认。

### 通过无限重试掩盖坏消息

Schema 错误、权限错误和载荷损坏通常不会因为等待而恢复。
无限重试会阻塞正常消息并产生重试风暴。

### 只增加 Consumer 实例解决积压

积压可能来自下游数据库、锁、网络或毒丸消息。
扩容前要确认瓶颈和并发上限，否则会让故障扩大。

### 用内存 Set 做可靠去重

进程重启、多实例和回放都会绕过内存 Set。
去重应使用数据库唯一约束、Inbox、版本条件更新或外部幂等键。

### 追求不切实际的全局顺序

全局顺序通常要求单分区或单消费者，吞吐和可用性都会下降。
优先把顺序范围缩小到同一订单、账户或其他业务聚合。

## 18. 精选面试题

### 消息队列主要解决什么问题？

它解决时间解耦、空间解耦、削峰、扇出和失败隔离。
它不替代主数据库、不自动提供分布式事务，也不保证全局顺序。

### Queue 和 Topic 有什么区别？

Queue 通常让多个 Consumer 竞争完成一条任务。
Topic 可以通过多个 Subscription 让不同逻辑消费者各自读取同一事实。
具体语义仍以 Broker 的路由和订阅实现为准。

### Partition 为什么能提高吞吐？

不同 Partition 可以由不同 Consumer 并行读取和处理。
同一 Partition 内通常保持顺序，因此吞吐、并行度和顺序之间存在取舍。

### Consumer Group 的作用是什么？

Group 让多个 Consumer 共享一个消费进度并分工处理 Partition。
不同 Group 有独立进度，可以分别构建搜索、通知和分析投影。

### ACK 和 Commit 是同一个概念吗？

不是。ACK 常确认一条 Queue 消息或投递句柄，Commit 常持久化日志消费位点。
两者都表示消费进度，但失败恢复和批量语义可能不同。

### At-least-once 为什么一定需要幂等？

处理成功后确认响应丢失会导致 Broker 再次投递。
如果业务副作用不可重复，重试会造成重复扣款、重复发券或旧数据覆盖新数据。

### Exactly-once 是否能保证邮件只发一次？

通常不能。Exactly-once 只覆盖它管理的事务边界，普通邮件 API 在事务之外。
需要供应商幂等键、发送状态机、结果查询和对账。

### 为什么发送超时不能直接判断发送失败？

网络可能在 Broker 持久化后断开，客户端只收不到 Confirm。
直接生成新消息会重复，直接删除原消息会丢失。
应复用稳定 ID 并通过幂等、查询或对账确认。

### 如何保证同一订单事件有序？

使用稳定的 `order_id` 作为分区键，把同一订单事件放入同一 Partition。
Consumer 仍需用版本检查处理重试和跨分区来源造成的乱序。

### Retention 和 TTL 有什么区别？

Retention 通常是 Topic、Queue 或日志级别的保留策略。
TTL 通常是单条消息的最大寿命。
二者都可能让未处理消息被清理，不能当作业务成功标志。

### 如何安全 Replay？

使用独立 Consumer Group 或隔离输出，记录 replay_id、范围、代码版本和结果。
先小批量验证，再限速处理，最后对账并切换。
不要直接把历史消息混入实时路径并触发不可逆副作用。

### 积压时为什么不能无限扩容？

Consumer 的下游数据库、连接池和第三方 QPS 可能已经是瓶颈。
无限扩容只会增加超时、锁竞争和重试，必须先定位有效吞吐下降的原因。

## 19. 学习路线

掌握本篇后，可以按以下方向继续深入：

1. 先研究一个具体 Broker 的 Topic/Queue、确认和故障恢复实现。
2. 再学习 Partition、Consumer Group、Rebalance 和容量估算。
3. 为 Producer 增加 Confirm、Retry、批量和背压。
4. 为 Consumer 增加幂等、Retry、DLQ、优雅关闭和可观测性。
5. 最后结合 Outbox、Inbox、CDC 和业务对账设计跨服务一致性。

消息队列的核心能力不是“把消息放进去”，而是在故障、重试、扩容和回放时仍能解释每条消息的状态。
只要明确消息契约、确认边界、顺序范围、重复处理和清理策略，具体中间件的差异就能被放在可比较的维度中。
