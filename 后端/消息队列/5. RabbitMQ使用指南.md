# RabbitMQ 使用指南
RabbitMQ 是以消息路由和 Queue 投递为核心的消息代理。 它最擅长把消息按明确规则送入一个或多个 Queue，再由 Consumer 以受控并发完成短生命周期任务。 与以 Partition Log 为中心的事件流平台相比，RabbitMQ 的优势是 Exchange 路由、低延迟 Push、细粒度 ACK、Prefetch、TTL 和 DLX 组合。
本文默认已经掌握 [[后端/消息队列/1. 消息队列基础入门|消息队列基础概念]]、[[后端/消息队列/2. 消息队列进阶知识|可靠发布、幂等与重试]]。 通用的 Outbox、Inbox、At-least-once 和消息契约不在这里重复展开。 Node.js 的跨中间件工程骨架见 [[后端/消息队列/4. Node.js消息队列使用指南|Node.js 消息队列使用指南]]。
本文以 AMQP 0-9-1 和 RabbitMQ 4.x 为主。 RabbitMQ 3.13 与 4.x 在 Classic Queue 镜像、Quorum Queue 重投上限、优先级和延迟重试上存在差异。 版本敏感结论会明确标注；升级或创建生产 Queue 前仍应核对目标版本的官方 Feature Matrix 和 Release Notes。
## 1. RabbitMQ 的定位与适用边界
### 1.1 它解决的问题
RabbitMQ 把发布者和消费者之间的同步调用改成由 Broker 管理的异步投递。 发布者只面向 Exchange 和 Routing Key，消费者只面向 Queue。 Binding 把二者连接起来，因此可以独立调整路由和消费者规模。
RabbitMQ 常用于以下场景：

- 邮件、通知、图片处理、报表生成等 Work Queue；
- 一个业务事件分发给多个独立服务，每个服务拥有自己的 Queue；
- 按租户、区域、事件类型或命令类型进行 Topic 路由；
- 需要 ACK、Prefetch、有限重试和 DLQ 的低延迟任务；
- 请求与响应生命周期较短的异步 RPC，但必须处理超时、重复和临时 Reply Queue；
- 需要 Quorum Queue 提供节点级复制的关键任务。
RabbitMQ 的 Queue 默认采用破坏性消费语义：消息 ACK 后可被删除。 这非常适合“完成任务”，但不天然适合多个消费者从任意历史位置反复读取同一份长期日志。 RabbitMQ Stream 可以补充回放与高扇出能力，但它的 API、保留模型和 Queue 功能矩阵不同。
### 1.2 不应勉强使用的场景
以下需求应先评估日志型平台、数据库或专用调度系统：

- 需要多年保留并按 Offset 大规模回放事件；
- 大量独立订阅者都要从同一份历史日志读取；
- 单一逻辑 Queue 要承担极端吞吐，且无法按业务键拆分；
- 要对消息做任意条件查询、聚合、关联或强事务报表；
- 要实现秒级以上的超长定时任务，并要求严格的触发精度；
- 要把图片、视频或大文件直接放进消息体；
- 业务要求跨数据库、HTTP 和 Broker 的自动全局事务。
RabbitMQ 不是业务主数据库，也不是分布式事务协调器。 数据库状态与消息共同提交仍应采用 [[后端/数据库/8. 分布式数据库与水平扩展/3. 分布式事务与可靠消息|Outbox、Inbox 与可靠消息]]。
## 2. AMQP 0-9-1 对象模型
### 2.1 完整投递路径
RabbitMQ 的典型路径不是 Producer 直接写业务 Queue，而是先发布到 Exchange。
```text
Producer
  -> TCP Connection
  -> Channel
  -> Exchange
  -> Binding + Routing Key
  -> Queue
  -> Consumer
  -> ACK / NACK
```
Exchange 负责计算路由结果，Queue 负责保存待投递消息。 Binding 是 Exchange 到 Queue 或另一个 Exchange 的路由规则。 Routing Key 是发布时提供的路由输入，不是 Consumer Group，也不是消息唯一 ID。
### 2.2 Connection 与 Channel
Connection 通常是一条长期存在的 TCP 连接。 它承载认证、TLS、Heartbeat、流控和多个 Channel。 频繁为每条消息创建 Connection 会增加 TCP、TLS、认证和 Erlang 进程开销。
Channel 是复用在 Connection 上的轻量协议会话。 Exchange/Queue 声明、发布、消费和 ACK 都发生在某个 Channel 上。 一个 Connection 可以有多个 Channel，但 Channel 不是跨业务并发共享的无状态对象。
Channel 级协议错误会关闭当前 Channel，例如：

- 用不一致属性重新声明已存在的 Queue；
- ACK 一个不存在的 Delivery Tag；
- 在不同 Channel 上 ACK 收到的消息；
- 使用无权限的 Exchange 或 Queue；
- 声明保留名称或非法参数。
因此应把管理拓扑、发布和消费放在职责清晰的 Channel 中。 发布与消费流量较大时，使用独立 Connection 可以避免 Publisher 被资源告警阻塞时影响 Consumer 的 ACK 和 Heartbeat。
Heartbeat 用于发现半开连接，不替代业务超时。 Heartbeat 过低会在短暂网络抖动或事件循环停顿时误判，过高则延长故障发现。 客户端重连必须使用退避和抖动，并在重连后恢复 Channel、Topology 和 Consumer。
### 2.3 Virtual Host
Virtual Host（vhost）是 Exchange、Queue、Binding、Policy 和权限的逻辑命名空间。 同名 Queue 可以存在于不同 vhost，客户端连接时必须选择一个 vhost。
vhost 适合隔离环境、团队或应用权限，但不是物理资源隔离：

- 多个 vhost 仍共享节点 CPU、内存、磁盘和网络；
- 一个 vhost 的大规模积压仍可能触发整个节点的资源告警；
- 跨 vhost 不能直接 Binding；
- 用户权限必须在每个 vhost 单独授予。
需要硬故障域、独立升级或独立容量时，应使用独立集群，而不是只增加 vhost。
### 2.4 Exchange
Exchange 接收发布消息并根据类型、Binding 和 Routing Key 计算目标 Queue。 Exchange 本身通常不长期保存消息。 如果没有任何 Queue 匹配，消息是否返回发布者取决于 `mandatory` 或 Alternate Exchange 配置。
Exchange 常见属性包括：

| 属性 | 含义 |
| --- | --- |
| `name` | vhost 内唯一名称；空字符串表示 Default Exchange |
| `type` | `direct`、`topic`、`fanout`、`headers` 或插件类型 |
| `durable` | Broker 重启后是否保留 Exchange 元数据 |
| `auto-delete` | 最后一个 Binding 消失后是否自动删除，具体时机取决于使用状态 |
| `internal` | 只允许其他 Exchange 路由进入，不允许客户端直接发布 |
| `alternate-exchange` | 主 Exchange 无法路由时的备用目标 |
Default Exchange 名称为空字符串，每个 Queue 会以 Queue 名作为 Routing Key 自动绑定到它。 它适合简单点对点发送，但业务系统通常使用具名 Exchange，使路由所有权、权限和演进边界更清晰。
### 2.5 Queue
Queue 保存已经路由成功、等待投递或等待确认的消息。 AMQP 0-9-1 声明时常见属性包括：

| 属性 | 含义 |
| --- | --- |
| `durable` | Queue 元数据是否在 Broker 重启后恢复 |
| `exclusive` | 仅声明它的 Connection 可用，连接关闭后删除 |
| `auto-delete` | Queue 曾有 Consumer 且最后一个 Consumer 消失后删除 |
| `arguments` | Queue 类型、TTL、DLX、长度、优先级等 RabbitMQ 扩展 |
Queue 声明是“属性相同则幂等”，不是“名称相同就自动修改”。 同名 Queue 已存在但 `durable`、`exclusive`、`auto-delete` 或不可变参数不同，会触发 `PRECONDITION_FAILED` 并关闭 Channel。
Queue 类型 `x-queue-type` 在创建后不可修改。 `x-max-priority` 等参数也不能通过重新声明在线变更。 需要变更不可变属性时，应新建 Queue、调整 Binding、灰度 Consumer、排空旧 Queue，再删除旧资源。
临时 Queue 应优先使用 Broker 生成的名称：
```text
queue.declare(name="", exclusive=true, auto-delete=true)
```
静态名称的临时 Queue 在断线重连时可能与旧 Queue 的异步删除发生竞争。 Server-named Queue 能避免新旧 Connection 争夺同一个名称。
### 2.6 Binding 与 Routing Key
Binding 描述 Exchange 与目标之间的关系。 同一个 Queue 可以绑定多个 Routing Key，一个 Exchange 也可以路由到多个 Queue。 增加订阅者时通常创建新的 Queue 和 Binding，而不是让多个业务订阅者竞争同一个 Queue。
推荐区分两个概念：

- **业务事件名**：例如 `order.created.v1`；
- **消费端 Queue 名**：例如 `billing.order-created.v1`。
前者表达发布契约，后者表达某个逻辑消费者的处理进度与失败边界。 把 Queue 名直接当公共事件名，会让 Producer 与 Consumer 拓扑紧耦合。
## 3. 四种 Exchange 路由
### 3.1 Direct Exchange
Direct Exchange 要求 Binding Key 与 Routing Key 完全相等。 它适合有限集合的命令或明确目标。
```text
Exchange: commands (direct)
  reserve.inventory -> inventory.commands
  capture.payment   -> payment.commands
```
同一个 Routing Key 可以绑定多个 Queue，因此 Direct Exchange 也能扇出。 “Direct”表示精确匹配，不表示只能有一个接收者。
### 3.2 Topic Exchange
Topic Exchange 按 `.` 分隔的单词匹配 Routing Key：

- `*` 匹配恰好一个单词；
- `#` 匹配零个或多个单词。
```text
发布 Routing Key: order.created.cn
Binding order.created.* -> audit.orders
Binding order.#         -> analytics.orders
Binding *.created.cn    -> cn-created-events
```
Routing Key 应保持有限、稳定和可治理。 不要把用户 ID、订单 ID 等高基数值直接展开为 Binding，否则 Binding 数量和权限规则会快速增长。 实体 ID 应放在 Message Property、Header 或 Payload 中。
Topic 规则很灵活，但过宽的 `#` 会让一个 Queue 接收意外流量。 变更事件命名时应先检查所有 Binding，并通过指标验证每个 Queue 的进入速率。
### 3.3 Fanout Exchange
Fanout Exchange 忽略 Routing Key，把消息路由到所有已绑定 Queue。 它适合小规模、明确的广播拓扑。
```text
Exchange: order.events.fanout
  -> billing.order-events
  -> search.order-events
  -> notification.order-events
```
每个 Queue 都保存一份消息，存储、网络和消费成本随绑定数增长。 订阅者很多、需要重复读取或长期保留时，应评估 RabbitMQ Stream，而不是无限增加普通 Queue。
### 3.4 Headers Exchange
Headers Exchange 根据 Message Headers 匹配，不使用 Routing Key。 Binding 中的 `x-match=all` 要求全部 Header 匹配，`x-match=any` 要求任一匹配。
Headers Exchange 可以表达多维条件，但存在以下成本：

- Header 类型和值必须跨语言一致；
- 权限和拓扑难以仅从名称理解；
- 大量 Header 和 Binding 增加计算与治理成本；
- 业务字段变化可能悄悄改变路由结果。
如果 Direct 或 Topic 能清晰表达规则，优先使用它们。 复杂内容筛选通常放到 Consumer，或在上游生成明确的业务 Routing Key。
## 4. 发布确认与无法路由
### 4.1 一次发布的确认边界
一次可靠发布至少经历以下边界：
```text
应用构造消息
  -> amqplib 写入本地 Buffer
  -> TCP 发送
  -> Exchange 路由
  -> Queue 接受、持久化或复制
  -> Publisher Confirm
```
`channel.publish()` 返回 `true` 只表示客户端写缓冲仍有空间。 返回 `false` 表示应等待 `drain`，不是 Broker 拒绝了消息。 如果忽略返回值并持续创建 Buffer，Producer 会先耗尽自己的内存。
普通 Channel 不会为每条发布提供 Broker 级结果。 Confirm Channel 通过 `confirm.select` 开启 Publisher Confirm，Broker 随后用 `basic.ack` 或 `basic.nack` 确认发布序号。
### 4.2 Publisher Confirm 证明什么
Confirm 表示 RabbitMQ 已按目标 Queue 类型完成当前发布的接受边界：

- 对无法路由的消息，Exchange 确认路由结果为空后仍可能发送 ACK；
- 对路由到持久 Queue 的 persistent 消息，确认通常等待相应持久化边界；
- 对 Quorum Queue，确认在消息复制到多数成员并达到该 Queue 的安全边界后发出；
- 对路由到多个 Queue 的消息，要等待相关 Queue 满足确认条件。
Confirm 不表示任何 Consumer 已收到或完成业务处理。 Consumer ACK 与 Publisher Confirm 是消息生命周期两端的独立协议。
网络超时或连接关闭会产生未知状态：消息可能没有到达，也可能已经安全写入但 Confirm 丢失。 Producer 重试必须复用稳定 `messageId`，Consumer 必须幂等。
### 4.3 Confirm 的吞吐策略
逐条发布后立即等待 Confirm 最容易理解，但每条消息都承担一次往返等待。 高吞吐 Producer 常使用以下方式：

- 保持一个有上限的未确认窗口；
- 批量发布后调用 `waitForConfirms()`；
- 使用每条消息的 Confirm Callback 异步关联结果；
- 同时限制消息数、字节数和最大等待时间。
Broker 可以批量确认多个发布序号。 应用不应依赖 Confirm 总是按发布顺序到达。 某一批 Confirm 失败时，整批中部分消息的状态可能未知，仍需稳定 ID 和下游幂等。
### 4.4 `mandatory` 与 `basic.return`
消息无法路由到任何 Queue 时，默认可能被丢弃。 发布时设置 `mandatory=true`，RabbitMQ 会通过 `basic.return` 把无法路由的消息返回当前 Channel。
一个无法路由的 mandatory 消息会先收到 Return，再收到 Publisher Confirm ACK 或 NACK。 因此只等待 Confirm ACK 仍不能证明消息进入了 Queue。 应用必须监听 `return` 事件，并用 `messageId` 关联原发布。
以下状态必须区分：

| 结果 | 含义 |
| --- | --- |
| `publish() === false` | 客户端 Buffer 已满，需要等待 `drain` |
| `basic.return` | Exchange 没有找到目标 Queue |
| Publisher ACK | Broker 完成了该发布的处理边界 |
| Publisher NACK | Broker 无法承担该发布责任 |
| Confirm 超时/断线 | 状态未知，不能直接断言失败 |
Alternate Exchange 可以接管无法路由的消息，适合平台级兜底。 但它会改变 `mandatory` 的观察结果：消息若被 Alternate Exchange 路由成功，就不再作为无法路由返回。 兜底 Queue 仍要有所有者、容量告警和处置流程。
### 4.5 Durable、Persistent 与 Replicated
三个概念不能互相替代：

| 配置 | 保护对象 | 不保证什么 |
| --- | --- | --- |
| durable Exchange | Exchange 元数据 | 消息已保存 |
| durable Queue | Queue 元数据 | transient 消息重启后仍存在 |
| persistent Message | 消息应持久化 | Queue 一定有副本 |
| Quorum Queue | Queue 内容复制到多个成员 | 跨地域备份和业务幂等 |
| Publisher Confirm | 当前发布达到 Broker 确认边界 | Consumer 已处理 |
关键消息通常同时需要 durable Exchange、durable Queue、persistent Message 和 Publisher Confirm。 如果还要求节点故障下继续可用，再使用健康的 Quorum Queue 和奇数副本。
## 5. Consumer、ACK 与 Prefetch
### 5.1 Push Consumer 与 `basic.get`
RabbitMQ 通常通过 `basic.consume` 持续 Push 消息。 长生命周期 Consumer 能减少轮询往返，并让 Prefetch 控制未确认窗口。
`basic.get` 每次只拉取一条消息，适合诊断或极低频管理操作，不适合作为高吞吐消费循环。 Prefetch 对 `basic.get` 不生效。
消费回调收到 `null` 通常表示 Consumer 被 Broker 取消，例如 Queue 被删除。 应用应把它视为订阅失效并重建或退出，而不是继续保持 Ready 状态。
### 5.2 Manual ACK
生产 Consumer 通常使用 `noAck=false`。 Broker 投递时分配 Delivery Tag，Consumer 完成业务副作用后调用 `ack`。
Delivery Tag 只在当前 Channel 内有效：

- 必须在收到消息的同一 Channel 上 ACK；
- ACK 同一 Delivery Tag 两次会关闭 Channel；
- ACK 未知 Tag 会得到 `PRECONDITION_FAILED`；
- Channel 或 Connection 关闭时，未确认消息会自动重新入队。
`ack(message, true)` 会批量确认当前 Channel 上直到该 Delivery Tag 的所有未确认消息。 并发处理时，如果较晚消息先完成，批量 ACK 可能误确认仍在执行或已经失败的较早消息。 除非处理顺序和连续成功前缀可证明，使用单条 ACK 更安全。
### 5.3 NACK、Reject 与 Requeue
`basic.reject` 只处理单条消息。 RabbitMQ 扩展的 `basic.nack` 可以处理单条或批量消息。
`requeue=true` 会尝试把消息放回原位置或靠近 Queue 头部。 多个 Consumer 并发时不能假设它精确回到原位置。 如果所有 Consumer 都因同一依赖故障立即 Requeue，会形成高频重投循环。
`requeue=false` 的结果取决于 Queue 是否配置 DLX：

- 有 DLX：消息被 Dead Letter；
- 无 DLX：消息被丢弃。
消息的 `redelivered` 标记说明它曾被投递过，但不能当作可靠重试次数。 Classic Queue 不替应用维护通用的有界重试计数。 Quorum Queue 有 `x-delivery-count` 和 Delivery Limit，但其计算语义随 4.x 版本演进。
### 5.4 Prefetch 是消费背压窗口
Prefetch 限制未确认投递数量。 当未确认数达到上限，RabbitMQ 暂停向相应 Consumer 继续投递，直到收到 ACK 或 NACK。
RabbitMQ 对 AMQP 0-9-1 的常用行为是把 Prefetch Count 按 Consumer 应用，而不是让 Channel 上所有 Consumer 无条件共享一个窗口。 不要在同一 Channel 上混放大量不同性能的 Consumer；为每类工作建立独立 Channel 更容易推导容量。
`prefetch=0` 表示不设上限，不是暂停消费。 无上限 Prefetch 可能同时扩大：

- Consumer 内存和 Promise 数量；
- Broker 的 Unacked 内存；
- 进程崩溃后的重复投递范围；
- 数据库连接池和下游 API 并发。
Prefetch 的起点可按以下关系估算：
```text
Prefetch <= 单实例允许的业务并发
单实例业务并发 × 实例数 <= 下游安全并发
```
I/O 等待较长时，Prefetch 大于 1 可以提高吞吐。 严格串行或副作用昂贵时，应使用较小窗口。 最终值必须通过真实消息大小、处理延迟分布、下游容量和故障重投测试确定。
### 5.5 公平分发的真实含义
RabbitMQ 会在可接收投递的 Consumer 间分发消息，但“轮询”不等于处理耗时完全公平。 一个 Consumer 可能已经持有多条 Unacked 消息，而另一个 Consumer 更快完成工作。
`prefetch=1` 可以减少慢实例囤积，但会降低有网络往返和 I/O 等待的吞吐。 更合理的目标是：

- 每个 Consumer 的未确认窗口有界；
- 消息处理时间分布可观测；
- 慢实例不会长期占有大量任务；
- 下游总并发不被扩容突破。
### 5.6 顺序与 Single Active Consumer
单个发布 Channel 上的消息会按发布顺序进入每个目标 Queue。 多个发布 Channel 或 Connection 并发时，消息会交错入队。
以下行为会改变 Consumer 观察到的完成顺序：

- 同一 Queue 有多个活跃 Consumer；
- Consumer 并发处理多条消息；
- NACK、连接关闭或超时触发 Redelivery；
- 使用消息优先级；
- 同一业务聚合从多个 Producer 并发发布。
`x-single-active-consumer=true` 让一个 Queue 同时只有一个活跃 Consumer，其他 Consumer 作为故障接管者等待。 它比 Exclusive Consumer 更适合需要连续故障转移的单活消费。 该参数在 Queue 创建时确定，不能通过 Policy 在线切换。
Single Active Consumer 只约束 Broker 投递者数量。 如果活跃 Consumer 内部并发处理，业务完成顺序仍可能变化。 严格顺序还要限制处理并发，并用业务版本检测重复和迟到消息。
## 6. TTL、DLX、Retry 与优先级
### 6.1 消息 TTL 与 Queue TTL
RabbitMQ 有两类容易混淆的 TTL：

| 类型 | 配置 | 过期对象 |
| --- | --- | --- |
| Queue 内消息 TTL | Policy `message-ttl` 或 `x-message-ttl` | Queue 中等待过久的消息 |
| 单条消息 TTL | 发布属性 `expiration`，值为毫秒字符串 | 这条消息在每个目标 Queue 中的寿命 |
| Queue TTL | Policy `expires` 或 `x-expires` | 长时间未使用的整个 Queue |
同时设置 Queue 消息 TTL 和单条消息 TTL 时，较小值生效。 同一消息被路由到多个 Queue 后，会在每个 Queue 独立计算过期。
过期消息不会再投递给 Consumer，但不保证在到达绝对时间点时立刻释放磁盘。 Classic 与 Quorum Queue 通常在消息到达 Queue 头部等检查点处理过期消息。 不同 TTL 的消息混在同一 Retry Queue 时，短延迟消息可能被前面的长延迟消息阻挡。
Queue TTL 只在 Queue 未使用时删除 Queue。 整个 Queue 因 `x-expires` 过期时，其中消息不会进入 DLX。 它用于清理闲置拓扑，不用于业务消息超时处理。
### 6.2 Dead Letter Exchange
DLX 是普通 Exchange，只是被 Queue 配置为失败转发目标。 以下四类事件会触发 Dead Letter：

1. Consumer `reject` 或 `nack` 且 `requeue=false`；
2. 消息 TTL 到期；
3. Queue 超过长度或字节限制并按策略移除消息；
4. Quorum Queue 的消息超过 Delivery Limit。
Queue 自身过期不会逐条 Dead Letter。
DLX 可以通过 Queue 参数配置：
```text
x-dead-letter-exchange
x-dead-letter-routing-key
```
生产环境更推荐使用 Policy，因为 Policy 可以在不重建 Queue 和不发布应用的情况下调整。 应用硬编码的 `x-arguments` 优先级高于普通 Policy，反而可能阻止运维在线修改。 Queue Type、`x-max-priority`、Single Active Consumer 等不可变参数仍需在声明时设置。
Dead Letter 后，AMQP 0-9-1 消息会带 `x-death` 数组。 其中记录来源 Queue、Exchange、Routing Keys、原因、次数和时间等信息。 Broker 会压缩相同 Queue 与原因的历史，应用不应把 `x-death` 当成简单整数 Header。
### 6.3 DLX 的可靠性边界
默认 DLX 转发由 Broker 内部重新发布，但不会为普通 Queue 启用 Publisher Confirm。 源 Queue 可能在目标 Queue 不可用时已经移除消息，因此集群故障中存在丢失窗口。
Quorum Queue 支持可选的 At-least-once Dead Letter：

- 源 Queue 必须是 Quorum Queue；
- `dead-letter-strategy` 设置为 `at-least-once`；
- Overflow 使用 `reject-publish`，不能使用默认 `drop-head`；
- 配置有效的 DLX 和目标 Binding；
- 内部 Dead Letter Consumer 等待目标 Publisher Confirm 后才从源 Queue 移除消息。
At-least-once DLX 可能产生重复，并会在目标不可用时保留源消息、增加 CPU 和内存占用。 如果 DLX 不存在、无法路由或目标 Queue 拒绝消息，源 Queue 可能持续积累 Dead Letter 消息。 因此仍需监控目标可用性、源 Queue 长度和重复处理。
### 6.4 有界 Retry Queue
兼容 RabbitMQ 3.13 与 4.x 的常见重试拓扑如下：
```text
orders.events --order.created.v1--> billing.main
      ^                                  |
      |                                  | 处理失败，显式发布
      |                                  v
      +-- TTL 到期 + DLX -------- billing.retry.5s
billing.main --nack(requeue=false)--> orders.dead --> billing.dlq
```
Consumer 遇到可重试错误时：

1. 读取应用自有的 `x-app-attempt`；
2. 增加次数并发布到 Retry Exchange；
3. 等待 Retry 发布 Confirm，并检查 mandatory Return；
4. Confirm 成功后 ACK 原消息；
5. Retry Queue TTL 到期，由 DLX 路由回主 Exchange；
6. 超过最大次数后 NACK 原消息且 `requeue=false`，进入最终 DLQ。
不能先 ACK 原消息再发布 Retry，否则进程在两步之间崩溃会丢失消息。 也不要直接 `nack(requeue=true)` 做常规重试，它没有延迟，会形成热循环。
需要多个退避档位时，使用多个固定 TTL Queue，例如 `5s`、`30s`、`5m`。 每个 Queue 内保持相同 TTL，避免 Per-message TTL 的队头阻塞。 延迟时间很多或跨度很大时，专用调度器比创建大量 Retry Queue 更可控。
RabbitMQ 4.3 为 Quorum Queue 增加了原生 Delayed Retry 策略。 它不适用于较早版本，配置键和计数语义应以目标 4.3.x 文档为准。 本文的 TypeScript 示例使用 TTL + DLX，以覆盖更广版本。
`rabbitmq_delayed_message_exchange` 是独立插件，不是 AMQP 0-9-1 核心能力。 使用前要验证插件与 RabbitMQ 版本兼容、集群升级路径、延迟范围和故障恢复行为。
### 6.5 Priority Queue
Classic Queue 通过创建时的 `x-max-priority` 开启消息优先级。 优先级数量越多，Broker 维护的内部状态越多；官方建议使用较少的级别，而不是把业务分数原样映射为数百个等级。
发布者通过 Message Property `priority` 设置优先级。 已经被 Prefetch 到 Consumer 的低优先级消息不会被 Broker 收回，因此过大的 Prefetch 会削弱优先级效果。 高优先级持续流入还可能让低优先级消息饥饿。
RabbitMQ 4.3 的 Quorum Queue 支持 0 到 31 的严格优先级，并始终启用；`x-max-priority` 只用于 Classic Queue。 较早的 4.x 版本把 Quorum 优先级映射到两个内部等级，行为不同。 RabbitMQ Stream 不支持消息优先级。
## 7. Classic、Quorum 与 Stream
### 7.1 核心差异

| 维度 | Classic Queue | Quorum Queue | Stream |
| --- | --- | --- | --- |
| 核心模型 | 单副本传统 Queue | Raft 复制 Queue | 复制的追加日志 |
| 消费语义 | ACK 后删除 | ACK 后删除 | 保留期内可重复读取 |
| 节点级复制 | RabbitMQ 4.x 不支持 | 支持，多数派 | 支持，多数派 |
| durable | 可选 | 必须 | 必须 |
| exclusive | 支持 | 不支持 | 不支持 |
| 临时 Queue | 适合 | 不适合 | 不适合 |
| TTL/DLX | 支持 | 支持 | 不支持，使用 Retention |
| 消息优先级 | 创建时开启 | 版本相关，4.3 为严格优先级 | 不支持 |
| Single Active Consumer | 支持 | 支持 | 支持，客户端语义不同 |
| 长积压/回放 | 不擅长 | 超长积压不优先 | 擅长 |
| 高扇出 | 每个订阅者通常一条 Queue | 每个订阅者通常一条 Queue | 多 Consumer 重复读取同一日志 |
### 7.2 Classic Queue
RabbitMQ 4.x 的 Classic Queue 是单副本 Queue。 Cluster 元数据存在于多个节点，不代表 Classic Queue 的消息内容自动复制。 承载该 Queue 的节点不可用时，Queue 会不可用；永久丢失节点可能丢失其内容。
Classic Queue 适合：

- Server-named Exclusive Reply Queue；
- 临时、可重建或允许节点级丢失的任务；
- 需要 Classic 特有功能且已经有外部恢复来源；
- 对共识复制开销敏感、数据安全由上游重建承担的流量。
RabbitMQ 4.0 已移除 Mirrored Classic Queue。 从 3.13 升级到 4.x 前必须把镜像 Classic Queue 迁移到 Quorum Queue、Stream 或接受单副本边界。
RabbitMQ 4.3 默认禁止创建 non-durable 且 non-exclusive 的 Classic Queue，该组合已废弃并计划移除。 临时状态应使用 non-durable Exclusive Queue；长期 Queue 应使用 durable Queue。
### 7.3 Quorum Queue
Quorum Queue 以 Raft 复制日志实现 durable、replicated Queue。 每个 Queue 有 Leader 和若干 Follower，状态变更由 Leader 复制到成员。 默认初始成员数通常是 3，并分布到可用集群节点。
多数派计算为：
```text
quorum = floor(member_count / 2) + 1
```
3 个成员能容忍 1 个成员故障，5 个成员能容忍 2 个成员故障。 偶数成员不会比相邻较小奇数提供更多故障容忍，却增加复制成本。
Quorum Queue 偏向一致性。 失去多数派后不会继续接受正常读写；恢复多数派或完成受控恢复前，Queue 保持不可用。 Publisher Confirm 只有在消息复制到多数成员并达到安全边界后发出。
Quorum Queue 不适合：

- Exclusive 或 non-durable Queue；
- 极高频创建、删除的临时 Queue；
- 只追求最低延迟且数据可丢失的消息；
- 数百万级长期积压和大量独立回放者，此时应评估 Stream；
- 集群少于 3 个有效故障域却声称具备高可用。
RabbitMQ 4.0 起，Quorum Queue 默认 Delivery Limit 为 20。 消息超过上限会被丢弃，若配置 DLX 则进入 DLX。 生产 Quorum Queue 应配置 DLX，避免 Poison Message 在达到上限后静默丢失。
RabbitMQ 4.3 调整了 Delivery Count 的计算，并新增严格优先级与 Delayed Retry。 如果集群在滚动升级期间混合运行不同 4.x Broker 节点，不能假设这些服务端行为完全一致；混合版本只应存在于官方支持的升级窗口。
### 7.4 Stream
RabbitMQ Stream 是持久、复制、Append-only 的日志。 Consumer 读取不会删除消息，可以按 Offset、时间或相对位置重新读取，直到 Retention 清理 Segment。
Stream 适合：

- 大量 Consumer 重复读取同一消息序列；
- 需要 Replay、审计窗口或构建投影；
- 普通 Queue 扇出导致大量重复存储；
- 需要比单 Queue 更高的顺序日志吞吐。
Stream 使用 `x-max-age` 和 `x-max-length-bytes` 等 Retention，而不是消息 TTL。 清理按 Segment 进行，实际保留量可能略大于阈值。
AMQP 0-9-1 客户端可以把 Stream 声明为 `x-queue-type=stream` 并消费，但必须使用 Prefetch 和 ACK 作为 Credit。 需要完整 Stream 特性和最佳吞吐时，官方推荐专用 RabbitMQ Stream Protocol 客户端。
Super Stream 把逻辑 Stream 分成多个 Partition Stream，提高并行度。 它增加分区键、顺序范围和成员管理复杂度，只有单 Stream 达到实测瓶颈后再使用。
### 7.5 Queue Type 迁移
Queue Type 是不可变属性，不能把现有 Classic Queue 原地重新声明为 Quorum Queue。 安全迁移通常采用：

1. 创建新名称的目标 Queue；
2. 复制原 Binding 或建立新版本 Routing Key；
3. 让 Producer 在迁移窗口双路由，或使用受控 Shovel；
4. 启动新 Consumer 并验证重复处理安全；
5. 排空旧 Queue，记录剩余 Ready/Unacked；
6. 停止旧路由并对账；
7. 保留回滚窗口后删除旧 Queue。
直接删除并同名重建会产生投递空窗和消息丢失。
## 8. 拓扑设计与命名
### 8.1 Consumer 拥有 Queue
事件 Exchange 通常由发布域维护，Queue 由逻辑消费者维护。 例如：
```text
Exchange: orders.events.v1
Routing Key: order.created
Queue: billing.order-created.v1
Queue: search.order-created.v1
Queue: notifications.order-created.v1
```
三个 Queue 各自拥有 Prefetch、Retry、DLQ、容量和上线节奏。 Billing ACK 不会推进 Search 的处理状态。
### 8.2 名称应表达责任
推荐名称包含稳定域和用途：

- Exchange：`orders.events.v1`；
- Routing Key：`order.created`；
- Queue：`billing.order-created.v1`；
- Retry Queue：`billing.order-created.v1.retry.5s`；
- DLQ：`billing.order-created.v1.dlq`；
- Policy：`billing-critical-quorum`。
不要把 Pod 名、随机部署 ID 或主机名写入长期 Queue 名。 临时实例状态使用 Server-named Exclusive Queue。
### 8.3 声明与 Policy 的边界
应用启动时声明稳定 Exchange、Queue 和 Binding，可以保证缺失拓扑自动创建。 声明失败必须让 Readiness 保持失败，不能在 Queue 不存在时继续接收业务流量。
以下参数优先由应用在创建时声明：

- Exchange Type；
- Queue Type；
- durable、exclusive、auto-delete；
- `x-max-priority`；
- `x-single-active-consumer`。
以下运行参数优先通过 Policy 管理：

- Message TTL；
- Queue Length / Bytes Limit；
- DLX 与 Dead Letter Routing Key；
- Quorum Delivery Limit；
- Queue Leader Locator 和运维保护参数。
Operator Policy 可以限制应用设置的最大 TTL、长度等资源参数。 它适合平台团队设置硬上限，防止单个应用无界占用集群。
## 9. Docker 与 CLI 最小环境
### 9.1 启动本地 RabbitMQ
下面的命令使用 RabbitMQ 4.x Management Image，创建持久 Volume 和非默认账号：
```bash
docker volume create rabbitmq-data
docker run --detach \
  --name rabbitmq-local \
  --hostname rabbitmq-local \
  --publish 5672:5672 \
  --publish 15672:15672 \
  --env RABBITMQ_DEFAULT_USER=app \
  --env RABBITMQ_DEFAULT_PASS=app-password \
  --env RABBITMQ_DEFAULT_VHOST=app \
  --volume rabbitmq-data:/var/lib/rabbitmq \
  rabbitmq:4-management
```
本地连接串为：
```text
amqp://app:app-password@localhost:5672/app?heartbeat=15
```
Management UI 默认可从 `http://localhost:15672` 访问。 生产环境应固定经过验证的 Patch Image Digest，不使用浮动 Major Tag，也不要把密码放入 Shell History 或镜像。
### 9.2 健康与拓扑命令
```bash
docker exec rabbitmq-local rabbitmq-diagnostics -q ping
docker exec rabbitmq-local rabbitmq-diagnostics check_running
docker exec rabbitmq-local rabbitmq-diagnostics check_local_alarms
docker exec rabbitmq-local rabbitmqctl cluster_status
```
查看 Exchange、Binding 和 Queue：
```bash
docker exec rabbitmq-local rabbitmqctl list_exchanges -p app name type durable
docker exec rabbitmq-local rabbitmqctl list_bindings -p app source_name destination_name destination_kind routing_key
docker exec rabbitmq-local rabbitmqctl list_queues -p app name type state messages_ready messages_unacknowledged consumers memory
```
`messages_ready` 表示尚未交给 Consumer 的消息。 `messages_unacknowledged` 表示已经投递但未 ACK 的消息。 两者都要观察；只看 Queue 总数无法区分消费不足和 Consumer 卡死。
不要在故障中直接执行 `purge_queue` 或 `delete_queue`。 先导出样本、确认业务影响、停止错误 Producer、保留审计记录，再按恢复方案处置。
### 9.3 用 Policy 配置 DLX
以下命令展示 Policy 形状，实际正则应限制到明确 Queue 前缀：
```bash
docker exec rabbitmq-local rabbitmqctl set_policy \
  --vhost app \
  billing-dlx \
  '^billing\.' \
  '{"dead-letter-exchange":"orders.dead"}' \
  --priority 10 \
  --apply-to queues
```
应用 `x-arguments` 与 Policy 同时提供同一键时，应用参数通常优先。 如果 Policy 看似生效但 Queue 行为没有变化，应检查 Effective Policy 和声明参数。

```typescript
function withTimeout<T>(operation: Promise<T>, timeoutMs: number, label: string): Promise<T> {
  let timer: ReturnType<typeof setTimeout> | undefined;
  const timeout = new Promise<never>((_resolve, reject) => {
    timer = setTimeout(() => reject(new Error(`${label} timed out`)), timeoutMs);
  });
  return Promise.race([operation, timeout]).finally(() => { if (timer) clearTimeout(timer); });
}

    return operation;
  }
  private async publishOne(exchange: string, routingKey: string, content: Buffer, options: Options.Publish): Promise<void> {
    const messageId = options.messageId;
    if (typeof messageId !== 'string' || messageId.length === 0) {
      throw new Error('messageId is required for confirmed publishing');
    }
    let backpressure: Promise<unknown[]> = Promise.resolve([]);
    const confirmed = new Promise<void>((resolve, reject) => {
      const writable = this.channel.publish(
        exchange,
        routingKey,
        content,
        { ...options, mandatory: true },
        (error) => { if (error) reject(error); else resolve(); },
      );
      if (!writable) backpressure = once(this.channel, 'drain');
    });
    try {
      await withTimeout(Promise.all([confirmed, backpressure]), CONFIRM_TIMEOUT_MS, `publisher confirm for ${messageId}`);
      await immediate();
      if (this.returnedIds.has(messageId)) {
        throw new UnroutableMessageError(messageId, exchange, routingKey);
      }
    } finally {
      this.returnedIds.delete(messageId);
    }
  }
}
function decodeOrder(message: ConsumeMessage): OrderCreated {
  let value: unknown;
  try {
    value = JSON.parse(message.content.toString('utf8'));
  } catch {
    throw new PermanentMessageError('message body is not valid JSON');
  }
  if (typeof value !== 'object' || value === null) {
    throw new PermanentMessageError('message body must be an object');
  }
  const record = value as Record<string, unknown>;
  if (
    typeof record.messageId !== 'string' ||
    record.eventType !== 'order.created.v1' ||
    typeof record.occurredAt !== 'string' ||
    typeof record.payload !== 'object' ||
    record.payload === null
  ) {
    throw new PermanentMessageError('invalid order.created.v1 envelope');
  }
  const payload = record.payload as Record<string, unknown>;
  if (
    typeof payload.orderId !== 'string' ||
    !Number.isSafeInteger(payload.amountMinor) ||
    (payload.amountMinor as number) < 0 ||
    typeof payload.currency !== 'string'
  ) {
    throw new PermanentMessageError('invalid order payload');
  }
  return value as OrderCreated;
}
function readAttempt(message: ConsumeMessage): number {
  const raw = message.properties.headers?.['x-app-attempt'];
  return Number.isSafeInteger(raw) && (raw as number) >= 0
    ? (raw as number)
    : 0;
}
function isRetryable(error: unknown): boolean {
  return !(error instanceof PermanentMessageError);
}
async function processOrder(order: OrderCreated): Promise<void> {
  console.info(JSON.stringify({
    event: 'order.processed',
    messageId: order.messageId,
    orderId: order.payload.orderId,
    amountMinor: order.payload.amountMinor,
    currency: order.payload.currency,
  }));
}
async function handleDelivery(
  message: ConsumeMessage,
  consumeChannel: Channel,
  retryPublisher: ConfirmPublisher,
): Promise<void> {
  try {
    const order = decodeOrder(message);
    await processOrder(order);
    consumeChannel.ack(message);
  } catch (error) {
    const currentAttempt = readAttempt(message);
    const nextAttempt = currentAttempt + 1;
    if (isRetryable(error) && nextAttempt <= MAX_RETRIES) {
      const messageId = message.properties.messageId;
      if (!messageId) {
        consumeChannel.nack(message, false, false);
        return;
      }
      await retryPublisher.publish(
        RETRY_EXCHANGE,
        RETRY_KEY,
        message.content,
        {
          persistent: true,
          contentType: message.properties.contentType ?? 'application/json',
          contentEncoding: message.properties.contentEncoding,
          messageId,
          type: message.properties.type,
          correlationId: message.properties.correlationId,
          headers: {
            traceparent: message.properties.headers?.traceparent,
            schemaVersion: message.properties.headers?.schemaVersion,
            'x-app-attempt': nextAttempt,
          },
        },
      );
      consumeChannel.ack(message);
      console.warn(JSON.stringify({
        event: 'order.retry-scheduled',
        messageId,
        attempt: nextAttempt,
        delayMs: RETRY_DELAY_MS,
        error: error instanceof Error ? error.message : String(error),
      }));
      return;
    }
    consumeChannel.nack(message, false, false);
    console.error(JSON.stringify({
      event: 'order.dead-letter-requested',
      messageId: message.properties.messageId,
      attempt: currentAttempt,
      error: error instanceof Error ? error.message : String(error),
    }));
  }
}
async function closeAll(
  channels: Array<Channel | ConfirmChannel>,
  connections: AmqpConnection[],
): Promise<void> {
  await Promise.allSettled(channels.map((channel) => channel.close()));
  await Promise.allSettled(connections.map((connection) => connection.close()));
}
async function runProducer(mode: 'producer' | 'unroutable'): Promise<void> {
  const url = parseAmqpUrl(process.env.RABBITMQ_URL);
  const connection = await connect(url);
  let channel: ConfirmChannel | undefined;
  try {
    channel = await connection.createConfirmChannel();
    const publisher = new ConfirmPublisher(channel);
    await assertTopology(channel);
    const order: OrderCreated = {
      messageId: randomUUID(),
      eventType: 'order.created.v1',
      occurredAt: new Date().toISOString(),
      payload: {
        orderId: `order-${Date.now()}`,
        amountMinor: 1999,
        currency: 'CNY',
      },
    };
    await publisher.publish(
      EXCHANGE,
      mode === 'producer' ? MAIN_KEY : 'order.unbound',
      Buffer.from(JSON.stringify(order), 'utf8'),
      {
        persistent: true,
        contentType: 'application/json',
        messageId: order.messageId,
        type: order.eventType,
        timestamp: Math.floor(Date.now() / 1000),
        headers: {
          schemaVersion: 1,
          'x-app-attempt': 0,
        },
      },
    );
    console.info(JSON.stringify({
      event: 'order.published',
      messageId: order.messageId,
      mode,
    }));
  } finally {
    await closeAll(channel ? [channel] : [], [connection]);
  }
}
async function runConsumer(): Promise<void> {
  const url = parseAmqpUrl(process.env.RABBITMQ_URL);
  const connections: AmqpConnection[] = [];
  const channels: Array<Channel | ConfirmChannel> = [];

  try {
    const publishConnection = await connect(url);
    connections.push(publishConnection);
    const consumeConnection = await connect(url);
    connections.push(consumeConnection);
    const publishChannel = await publishConnection.createConfirmChannel();
    channels.push(publishChannel);
    const consumeChannel = await consumeConnection.createChannel();
    channels.push(consumeChannel);

    const retryPublisher = new ConfirmPublisher(publishChannel);
    const inFlight = new Set<Promise<void>>();
    let consumerTag: string | undefined;
    let shuttingDown = false;

    const shutdown = async (exitCode: number): Promise<void> => {
      if (shuttingDown) return;
      shuttingDown = true;
      process.exitCode = exitCode;
      if (consumerTag) {
        await consumeChannel.cancel(consumerTag).catch(() => undefined);
      }
      await withTimeout(
        Promise.allSettled([...inFlight]),
        SHUTDOWN_TIMEOUT_MS,
        'consumer shutdown',
      ).catch((error: unknown) => {
        console.error(JSON.stringify({
          event: 'consumer.shutdown-timeout',
          error: error instanceof Error ? error.message : String(error),
        }));
      });
      await closeAll(channels, connections);
    };

    const failClosed = (component: string, error?: unknown): void => {
      if (shuttingDown) return;
      console.error(JSON.stringify({
        event: 'consumer.transport-failed',
        component,
        error: error instanceof Error ? error.message : error ? String(error) : undefined,
      }));
      setImmediate(() => void shutdown(1));
    };

    process.once('SIGTERM', () => void shutdown(0));
    process.once('SIGINT', () => void shutdown(0));
    publishConnection.on('error', (error: Error) => failClosed('publisher.connection', error));
    publishConnection.on('close', () => failClosed('publisher.connection'));
    consumeConnection.on('error', (error: Error) => failClosed('consumer.connection', error));
    consumeConnection.on('close', () => failClosed('consumer.connection'));
    publishChannel.on('error', (error: Error) => failClosed('publisher.channel', error));
    publishChannel.on('close', () => failClosed('publisher.channel'));
    consumeChannel.on('error', (error: Error) => failClosed('consumer.channel', error));
    consumeChannel.on('close', () => failClosed('consumer.channel'));

    await assertTopology(publishChannel);
    await consumeChannel.prefetch(PREFETCH);
    const reply = await consumeChannel.consume(
      MAIN_QUEUE,
      (message) => {
        if (!message) {
          failClosed('consumer.cancelled-by-broker');
          return;
        }
        const task = handleDelivery(message, consumeChannel, retryPublisher);
        inFlight.add(task);
        void task
          .catch((error: unknown) => {
            console.error(JSON.stringify({
              event: 'consumer.fatal-delivery-error',
              messageId: message.properties.messageId,
              error: error instanceof Error ? error.message : String(error),
            }));
            failClosed('consumer.delivery', error);
          })
          .finally(() => inFlight.delete(task));
      },
      { noAck: false },
    );
    consumerTag = reply.consumerTag;
    console.info(JSON.stringify({
      event: 'consumer.ready',
      queue: MAIN_QUEUE,
      prefetch: PREFETCH,
    }));
  } catch (error) {
    await closeAll(channels, connections);
    throw error;
  }
}
async function main(): Promise<void> {
  const mode = process.argv[2] ?? 'consumer';
  if (mode === 'producer' || mode === 'unroutable') {
    await runProducer(mode);
    return;
  }
  if (mode === 'consumer') {
    await runConsumer();
    return;
  }
  throw new Error('mode must be producer, consumer, or unroutable');
}
void main().catch((error: unknown) => {
  console.error(JSON.stringify({
    event: 'application.failed',
    error: error instanceof Error ? error.stack : String(error),
  }));
  process.exitCode = 1;
});
```
### 10.3 示例中的关键边界
`ConfirmPublisher` 串行化发布，便于用 `messageId` 可靠关联 mandatory Return 与 Confirm。 生产高吞吐实现可以改为有上限的并发 Confirm Window，但不能使用无界 Promise。
Retry 发布的 Confirm 只证明消息进入 Retry Queue，不覆盖 TTL 到期后的内部 DLX 转发。 示例为主 Queue 和 Retry Queue 同时设置 `x-overflow=reject-publish` 与 `x-dead-letter-strategy=at-least-once`，让内部 Dead Letter 在目标 Confirm 后才移除源消息；这仍可能重复，且目标不可用时会在源 Queue 积压。
如果 Retry 发布失败，`handleDelivery` 抛错，进程进入关闭流程；关闭 Channel 会让未确认原消息重新入队。 最终失败日志使用 `order.dead-letter-requested`，因为 NACK 返回时尚不能证明 DLQ 已接受消息。 应由进程管理器使用退避重启，避免本地忙循环。
示例的 `processOrder` 只输出结构化日志，便于本地直接运行。 生产实现应在这里执行 Inbox 与业务数据库事务，并保持“业务提交后 ACK”。 完整 PostgreSQL Inbox 形状见 [[后端/消息队列/4. Node.js消息队列使用指南#8. Inbox、Outbox 与数据库事务|Node.js 指南的 Inbox/Outbox 示例]]。
示例把主 Queue、Retry Queue 和 DLQ 都声明为 Quorum Queue。 单节点 Docker 只能验证 API 和路由，不能验证 Quorum 的节点故障容忍。 高可用测试至少需要 3 个独立 RabbitMQ 节点，并注入 Leader 节点退出和网络分区。
## 11. 安全、TLS 与权限
### 11.1 认证与网络
默认 `guest` 用户只适合本机开发，不应用于远程生产连接。 每个服务使用独立用户或证书身份，开发、测试和生产凭据完全分离。
生产网络只向应用网段暴露 AMQP TLS 端口。 Management UI、HTTP API、Prometheus 和 Erlang Distribution 端口应位于管理网络，并限制来源。
凭据通过 Secret Manager 或运行环境注入。 日志不得输出完整 AMQP URL，因为 URL 中通常含用户名和密码。
### 11.2 TLS
TLS 客户端必须验证 CA、证书有效期和主机名。 不要通过 `rejectUnauthorized=false` 绕过证书错误。
使用 mTLS 时，仍需把证书身份映射到明确用户和权限。 证书轮换要验证：

- 新旧 CA 的重叠窗口；
- 长连接何时重连并加载新证书；
- 失败回滚；
- 过期证书告警；
- 集群内部通信与客户端通信分别配置。
### 11.3 vhost 权限模型
RabbitMQ 在每个 vhost 为用户配置三类正则权限：

| 权限 | 典型操作 |
| --- | --- |
| `configure` | 声明、删除或修改 Exchange 和 Queue |
| `write` | 向 Exchange 发布；创建 Binding 时作用于目标 Queue/Exchange |
| `read` | 从 Queue 消费；创建 Binding 时作用于源 Exchange |
`queue.bind` 需要目标 Queue 的 `write` 与源 Exchange 的 `read`；`exchange.bind` 需要目标 Exchange 的 `write` 与源 Exchange 的 `read`。 生产者通常只需要目标 Exchange 的 `write`，消费者需要 Queue 的 `read`。 如果应用自行声明拓扑，还需要受限的 `configure` 以及 Binding 对应的 `read/write`；拓扑由平台预创建时，运行时 Consumer 可以不拥有任意删除权限。
Topic Exchange 还可使用 Topic Permission 限制允许发布或消费的 Routing Key 模式。 权限正则必须锚定，例如 `^orders\.events\.v1$`，避免无意匹配相似名称。
用户 Tag 主要控制 Management 角色，不替代 AMQP 资源权限。 拥有 `administrator` Tag 也不应成为应用连接 Broker 的常规方式。
## 12. 容量与可观测性
### 12.1 容量由字节和时间共同决定
Queue 容量不能只按消息条数估算。 至少收集：

- 峰值发布消息数与字节数；
- 平均、P95、P99 和最大消息大小；
- 稳态消费速率与故障恢复速率；
- 最大允许积压时间；
- Quorum 副本数；
- Retry、DLQ 和重新发布放大系数；
- 节点故障时剩余磁盘和网络容量。
粗略存储下限为：
```text
积压字节 ≈ 峰值净写入字节速率 × 积压持续时间 × 副本数
```
还要加入索引、Segment、元数据、磁盘水位、恢复复制和增长余量。 磁盘告警阈值必须早于真正耗尽空间，给限流、扩容和排空留出时间。
单个 Queue Replica 的热路径并行度有限。 高吞吐系统应按业务键拆分多个 Queue 或改用 Stream/Super Stream，不能只增加同一 Queue 的 Consumer。
### 12.2 必看指标

| 层次 | 指标 |
| --- | --- |
| Connection | 连接数、创建/关闭速率、Heartbeat 超时、Blocked 状态 |
| Channel | Channel 数、Channel Error、Confirm 延迟、Unconfirmed 数 |
| Exchange | Publish In、Publish Out、Unroutable、Return Rate |
| Queue | Ready、Unacked、Total、Ingress/Egress、Consumer Capacity |
| Consumer | Consumer 数、Prefetch、ACK/NACK、Redelivery、处理延迟 |
| Quorum | Leader 分布、在线成员、多数派、复制状态、重选举 |
| Node | 内存、磁盘水位、文件句柄、Socket、CPU、Scheduler、网络 |
| 业务 | 最老消息年龄、重试、DLQ、重复数、最终对账差异 |
Ready 持续增长通常表示消费能力低于发布速率。 Unacked 持续增长通常表示 Prefetch 过大、Consumer 卡住、数据库变慢或 ACK 路径异常。 Publish Rate 正常但 Queue In 较低，可能是 Binding 错误或大量 Unroutable。
只看 Management UI 的瞬时曲线不足以建立告警。 生产集群应启用官方 Prometheus Plugin，并把关键指标采集到独立监控系统。 SLO 和容量方法可结合 [[后端/数据库/11. 可观测性与性能工程/1. 指标、SLO与容量规划|指标、SLO 与容量规划]]。
### 12.3 资源告警与流控
内存或磁盘水位触发时，RabbitMQ 会限制或阻塞发布连接。 客户端可能收到 Connection Blocked 通知，也可能通过 TCP Backpressure 感知变慢。
Producer 必须：

- 限制应用内 Buffer；
- 观察 `publish() === false` 并等待 `drain`；
- 为 Confirm 设置总截止时间；
- 对未知状态保留原 Message ID；
- 在持续阻塞时让上游限流或写入 Outbox。
不要通过增加 Producer 实例绕过 Broker 流控。 那只会增加连接、Buffer、超时和重复消息。
## 13. 升级、备份与恢复
### 13.1 升级前检查
RabbitMQ 与 Erlang/OTP 有明确兼容矩阵。 升级前必须同时核对 RabbitMQ 目标版本、Erlang 版本、插件和客户端兼容性。
升级路径由官方 Upgrade Guide 决定，不能任意跨越多个 Feature Release。 混合版本集群只用于官方支持的滚动升级，不是长期运行形态。
升级前至少完成：

- 集群与所有 Queue 无资源告警；
- Quorum Queue 拥有多数在线成员；
- Leader 分布和磁盘余量健康；
- Definitions 已导出并加密保存；
- 业务数据库、Outbox 和 DLQ 有恢复方案；
- 已验证客户端重连与 Consumer 幂等；
- 已阅读 Deprecated Features 和 Feature Flags；
- 在等规模预生产环境完成升级与回滚演练。
Feature Flag 启用后可能无法回滚到旧版本。 应在所有节点升级、观察稳定并结束回滚窗口后，再按官方步骤启用必需 Flag。
### 13.2 Definitions 不是消息备份
Definitions 包含用户、vhost、权限、Exchange、Queue、Binding、Policy 和参数等元数据。 它不等于 Queue 消息内容备份，也不证明 Quorum 数据可恢复。
```bash
docker exec rabbitmq-local rabbitmqctl export_definitions /tmp/definitions.json
docker cp rabbitmq-local:/tmp/definitions.json ./definitions.json
```
Definitions 可能包含密码 Hash、Endpoint 和拓扑信息，应加密并限制访问。 恢复前检查目标版本是否接受旧参数，尤其是已移除的 Mirrored Classic Queue Policy。
### 13.3 副本、备份与上游恢复源
Quorum 副本用于节点故障，不防止误删 Queue、错误 Policy、错误发布和全站损坏。 复制会同步逻辑错误，因此副本不是备份。
关键业务应同时保留：

- 数据库权威状态；
- Outbox 或可重放事件源；
- Definitions 与配置仓库；
- DLQ、人工处置和对账记录；
- 跨故障域备份或异步灾备流；
- 经过演练的重建顺序。
直接复制正在运行节点的数据目录不是通用的在线备份方案。 数据目录与 Node Name、Erlang Cookie、集群元数据、版本和磁盘状态相关，恢复必须严格遵循官方 Backup and Restore Guide。
### 13.4 恢复顺序
推荐按以下顺序恢复：

1. 网络、DNS、TLS、Secret 和节点身份；
2. RabbitMQ 节点、vhost、用户、权限与 Policy；
3. Exchange、Queue、Binding 和 Queue Type；
4. Quorum/Stream 成员与多数派健康；
5. 低速启动幂等 Consumer；
6. 恢复 Producer 或 Outbox Publisher；
7. 观察 Ready、Unacked、Redelivery、DLQ 和下游容量；
8. 对账业务权威状态与消费结果。
恢复成功不能只以 Queue 变空为标准。 必须证明关键订单、支付、库存或通知状态正确，并统计重复与缺失。
## 14. 常见故障排查
### 14.1 `PRECONDITION_FAILED`
常见原因是同名 Queue 或 Exchange 已存在，但声明属性不同。 排查顺序：

1. 读取 Channel Close 原因；
2. 查看现有资源的 Type、durable、Arguments 和 Effective Policy；
3. 对比应用发布版本与声明参数；
4. 不要在原 Channel 上继续操作，它已经关闭；
5. 对不可变属性使用新资源迁移。
### 14.2 `ACCESS_REFUSED`
检查连接选择的 vhost、用户认证、configure/write/read 正则和 Topic Permission。 能登录 Management UI 不表示拥有目标 Queue 的 AMQP 权限。 DLX 还要求声明 Queue 的用户对源 Queue 有 Read、对 DLX 有 Write。
### 14.3 消息发布成功但 Queue 没有消息
按顺序检查：

- 发布的 vhost 是否正确；
- Exchange 名与 Type 是否正确；
- Routing Key 是否匹配 Binding；
- 是否监听 mandatory Return；
- Alternate Exchange 是否接管了消息；
- 消息是否立即过期；
- Queue Length Policy 是否拒绝或移除了消息；
- Consumer 是否已经快速取走，消息进入 Unacked。
Publisher Confirm ACK 本身不能排除 Unroutable。
### 14.4 Ready 增长
先比较 Publish Rate 与 Deliver/Ack Rate，再按 Queue 和 Consumer 实例定位：

- Consumer 是否为 0 或反复断线；
- Consumer Capacity 是否不足；
- Prefetch 是否太小；
- 单条处理耗时是否上升；
- 数据库、缓存或 HTTP 下游是否饱和；
- 是否有热点 Queue 或单活顺序瓶颈；
- Retry 是否在放大流量。
扩容 Consumer 前确认下游仍有并发余量。
### 14.5 Unacked 增长
Unacked 增长通常不是“Broker 没删消息”，而是 Consumer 已领取但没有完成确认。 检查：

- 业务 Promise 是否悬挂；
- 数据库事务是否等待锁；
- ACK 是否在错误 Channel 上；
- Prefetch 是否远大于处理并发；
- Consumer 是否发生长时间 GC 或事件循环阻塞；
- ACK Timeout 是否触发 Channel 关闭和重复投递。
不要通过 Purge Queue 处理 Unacked；Purge 只影响 Ready 消息，且会造成业务丢失。
### 14.6 Redelivery 或 DLQ 激增
按 `x-death.reason`、错误码、Consumer Version 和 Queue 聚类。 区分 Schema 错误、权限错误、下游超时、业务不变量和实例崩溃。
如果大量消息因同一瞬时依赖失败：

- 暂停或降低 Consumer 并发；
- 停止即时 Requeue；
- 延长有界 Retry；
- 保护数据库和第三方 API；
- 修复后小批量回放并对账。
DLQ 不是永久存档。 它需要容量、保留期、访问审计、修复版本、回放速率和最终处置状态。
### 14.7 Quorum Queue 不可用
检查 Queue 成员、Leader 和多数派，而不是只看 RabbitMQ 节点总数。 一个 5 节点集群中的某条 Queue 可能只有 3 个成员；失去其中 2 个就失去多数派。
不要在未理解日志状态时强制删除或缩减成员。 优先恢复原成员、网络和磁盘，再按官方 Quorum Queue 恢复流程操作。 永久失去多数派时，可能只能从上游权威数据重建 Queue。
## 15. 优势、限制与选型结论
### 15.1 主要优势

- Exchange 与 Binding 提供成熟、直观的路由能力；
- Push Consumer、ACK 和 Prefetch 适合低延迟 Work Queue；
- TTL、DLX、Priority 和 Single Active Consumer 能覆盖常见任务需求；
- Quorum Queue 提供基于多数派的节点级复制；
- 多协议、Management UI、Prometheus 和客户端生态成熟；
- vhost、权限、Policy 和 Operator Policy 便于平台治理。
### 15.2 主要限制

- 普通 Queue ACK 后不可回放，长期日志不是默认模型；
- RabbitMQ 4.x Classic Queue 不复制，旧镜像方案已移除；
- 单 Queue 热路径难以通过无限增加 Consumer 水平扩展；
- DLX 默认转发并非 At-least-once，必须理解丢失窗口；
- Queue Type 和部分参数不可在线修改；
- TTL/DLX 延迟不是精确定时器；
- 跨地域 Federation/Shovel 会引入延迟、重复和冲突边界；
- 大量 Queue、Binding、Priority 和动态租户会增加控制面成本。
### 15.3 选择 RabbitMQ 的条件
当核心需求是灵活路由、短任务、低延迟 Push、消费背压和明确失败队列时，RabbitMQ 通常是合适起点。 关键任务使用 Quorum Queue、Publisher Confirm、Manual ACK、有限 Retry、DLQ 和业务幂等。
当核心需求是长保留、多订阅者独立回放、Partition 吞吐和流式计算时，应优先考察日志型平台，或明确采用 RabbitMQ Stream。 不要因为团队已经部署 RabbitMQ，就把所有异步数据都塞进同一种 Queue。
## 16. 高频面试题
### Exchange、Queue、Binding 和 Routing Key 分别做什么？
Exchange 接收发布并计算路由，Queue 保存待消费消息，Binding 定义 Exchange 到 Queue 的匹配规则，Routing Key 是发布时参与匹配的字符串。 Producer 通常依赖 Exchange 契约，不直接依赖 Consumer Queue 名。
### Publisher Confirm 与 Consumer ACK 有什么区别？
Publisher Confirm 表示 Broker 对发布请求的处理或持久化边界。 Consumer ACK 表示某次 Delivery 的业务处理已被 Consumer 确认。 二者处于消息链路两端，Confirm 不能证明 Consumer 已处理。
### 为什么 Confirm ACK 后消息仍可能没有进入 Queue？
消息无法路由时，Exchange 处理完成后仍可 Confirm ACK。 必须设置 `mandatory=true` 并监听 `basic.return`，或配置并监控 Alternate Exchange。
### durable Queue 加 persistent Message 是否绝对不丢？
不是。它们不自动提供多节点副本，也不能覆盖网络未知状态、误删、全站故障和业务错误。 关键消息还需要 Confirm、Quorum Queue、备份/上游重建源和幂等。
### 为什么 Delivery Tag 必须在原 Channel ACK？
Delivery Tag 只在 Channel 内单调递增和唯一。 在其他 Channel ACK 会得到 Unknown Delivery Tag 并关闭该 Channel。
### Prefetch 越大吞吐越高吗？
只在一定范围内成立。 过大 Prefetch 会增加 Consumer 与 Broker 内存、任务囤积、下游并发和故障重投范围；达到管线饱和后继续增大收益很小。
### 为什么 `nack(requeue=true)` 会形成重试风暴？
消息可能立即回到 Queue 头并再次投递，而故障条件没有变化。 多个 Consumer 会反复传递同一消息，消耗 CPU、网络和日志；应使用有延迟、有次数上限的 Retry Queue。
### DLX 是否保证消息不丢？
默认不保证。普通 DLX 内部重新发布不等待 Publisher Confirm，目标不可用时存在丢失窗口。 Quorum Queue 可配置 At-least-once Dead Letter，但会增加资源占用并仍可能重复。
### Classic Queue 和 Quorum Queue 如何选择？
需要临时、Exclusive 或可重建单副本任务时选择 Classic。 需要 durable、复制和节点故障容忍的关键任务时选择 Quorum，并接受共识延迟、奇数成员和多数派可用性边界。
### Quorum Queue 失去多数派会怎样？
它偏向一致性，会停止正常读写而不是在少数派继续接受可能冲突的数据。 需要恢复多数成员；永久丢失多数派时可能只能从权威数据重建。
### RabbitMQ Stream 与普通 Queue 的核心区别是什么？
普通 Queue ACK 后删除消息，Stream 在 Retention 内保留 Append-only Log，可从 Offset 或时间重复读取。 Stream 适合回放、高扇出和高吞吐，TTL、DLX、Priority 等普通 Queue 功能并不适用。
### 如何安全迁移 Queue Type？
创建新 Queue，复制 Binding，灰度双路由或使用受控迁移，启动幂等 Consumer，排空旧 Queue并对账，最后切断旧路由。 Queue Type 不可原地修改。
### 如何判断积压是 Consumer 不足还是 Consumer 卡住？
Ready 增长而 Unacked 稳定，通常是可投递消息堆积；Unacked 增长通常是 Consumer 已领取但处理或 ACK 卡住。 还要结合 Publish/Ack Rate、处理延迟、Consumer Capacity 和下游连接池判断。
