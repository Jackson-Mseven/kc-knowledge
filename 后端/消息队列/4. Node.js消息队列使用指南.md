# Node.js 消息队列使用指南

Node.js 接入消息队列时，最容易犯的错误是只把 `send`、`consume` 和 `ack` 当作几个 API。
真正需要设计的是消息契约、确认边界、并发上限、失败分类、幂等记录、关闭流程和运行观测。
Kafka 的 `Offset Commit`、RabbitMQ 的 `ack`、Redis Streams 的 `XACK` 都表示“某种消费状态已经被记录”，但它们不在同一个事务模型里。
本篇以 TypeScript 为例，先建立跨中间件的工程骨架，再分别给出 Kafka、RabbitMQ、Redis Streams 和 BullMQ 的接入方式。

## 1. 先确定语义，再选择客户端

### 1.1 Node.js 进程在消息链路中的职责

一个生产者进程通常负责：构造消息 Envelope、校验载荷、序列化、发送、等待 Broker 的确认、记录发送结果。
一个消费者进程通常负责：读取消息、恢复 Trace Context、校验版本、执行幂等业务事务、确认或转入重试/死信。
连接管理、重连、健康状态和优雅关闭属于进程生命周期的一部分，不能只放在某一个业务处理器里。

```text
业务代码
   |
   v
Envelope -> Schema 校验 -> Client Adapter -> Broker
                                      |
                                      v
                              Consumer Handler
                                      |
                 +--------------------+--------------------+
                 |                                         |
          本地事务提交                                  Retry / DLQ
                 |
            ACK / Commit / XACK
```

### 1.2 三类确认点不能混用

| 实现 | 读取进度的对象 | 成功确认的典型 API | 失败后通常发生什么 |
| --- | --- | --- | --- |
| Kafka | `topic + partition + offset` | `commitOffsets` 或客户端自动提交 | 从最近提交的 Offset 重读 |
| RabbitMQ | delivery tag 对应的投递 | `channel.ack(message)` | `nack`、重新入队或进入 DLX |
| Redis Streams | Stream ID 与 Consumer Group PEL | `XACK stream group id` | 保留在 PEL，可 `XAUTOCLAIM` |
| BullMQ | Job ID 与 Redis 锁 | Worker 返回成功 | Job 失败、重试或 stalled |

不要写一个名为 `ack()` 的公共函数，然后在里面把 Kafka commit、RabbitMQ ack 和 `XACK` 当成等价操作。
适配层可以统一“处理成功/失败”的应用结果，但必须保留各客户端的提交时机和重投语义。

### 1.3 依赖与版本边界

常用客户端及其职责如下：

| 系统 | Node.js 客户端 | 适合的抽象 |
| --- | --- | --- |
| Kafka | `kafkajs` | Topic、Partition、Consumer Group、Offset |
| RabbitMQ | `amqplib` | Exchange、Queue、Binding、ACK、Confirm |
| Redis Streams | `ioredis` 或 `redis` | Stream、Consumer Group、PEL |
| Redis 任务队列 | `bullmq` | Job、Worker、延迟任务、重试 |

先锁定 Node.js、TypeScript、客户端和 Broker 的兼容版本，再参考对应版本文档。
不要把旧版客户端示例中的参数直接复制到新版本；尤其要核对 TLS、重连、事务和消费回调的 API。

产品机制与运维边界分别见 [[后端/消息队列/5. RabbitMQ使用指南|RabbitMQ 使用指南]]、[[后端/消息队列/6. Kafka使用指南|Kafka 使用指南]] 和 [[后端/消息队列/7. RocketMQ使用指南|RocketMQ 使用指南]]；本篇只负责 Node.js 跨中间件的公共工程骨架与客户端示例。

## 2. 统一消息 Envelope

### 2.1 字段设计

Envelope 把路由、追踪、幂等和版本信息与业务载荷分开。建议至少包含：

| 字段 | 作用 | 约束 |
| --- | --- | --- |
| `messageId` | 标识一次逻辑消息 | Producer retry 时保持不变 |
| `eventType` | 业务事件或命令类型 | 使用稳定命名，不用数据库表名 |
| `schemaVersion` | 解释 `payload` 的版本 | 采用显式兼容策略 |
| `occurredAt` | 业务事实发生时间 | 使用 ISO 8601 或 epoch，并统一时区 |
| `producer` | 发布服务和版本 | 便于审计与回滚 |
| `correlationId` | 关联同一业务流程 | 不作为幂等键 |
| `causationId` | 指向触发当前消息的消息 | 允许为空 |
| `traceparent` | W3C Trace Context | 不记录完整凭证 |
| `partitionKey` | 决定局部顺序 | 同一聚合使用稳定键 |
| `payload` | 业务数据 | 不放密码、Cookie 和超大二进制 |

```typescript
import { randomUUID } from 'node:crypto';

export type MessageEnvelope<T> = {
  messageId: string;
  eventType: string;
  schemaVersion: number;
  occurredAt: string;
  producer: string;
  correlationId: string;
  causationId?: string;
  traceparent?: string;
  partitionKey?: string;
  attempt: number;
  payload: T;
};

export function createEnvelope<T>(input: {
  eventType: string;
  producer: string;
  payload: T;
  correlationId: string;
  partitionKey?: string;
  causationId?: string;
}): MessageEnvelope<T> {
  return {
    messageId: randomUUID(),
    eventType: input.eventType,
    schemaVersion: 1,
    occurredAt: new Date().toISOString(),
    producer: input.producer,
    correlationId: input.correlationId,
    causationId: input.causationId,
    partitionKey: input.partitionKey,
    attempt: 0,
    payload: input.payload,
  };
}
```

上例通过 `node:crypto` 显式导入 `randomUUID`。如果消息会在多个进程间重试，`messageId` 必须在第一次构造后持久化或随 Outbox 记录保存。

### 2.2 运行时校验

TypeScript 类型只在编译期存在，不能阻止不兼容的外部消息进入进程。
可以使用 `zod`、`@sinclair/typebox` 等成熟校验库；如果项目不想增加依赖，至少在入口做显式字段检查。

```typescript
export function assertEnvelope(value: unknown): asserts value is MessageEnvelope<unknown> {
  if (typeof value !== 'object' || value === null) {
    throw new Error('message must be an object');
  }

  const record = value as Record<string, unknown>;
  const requiredStrings = [
    'messageId',
    'eventType',
    'occurredAt',
    'producer',
    'correlationId',
  ];

  for (const field of requiredStrings) {
    if (typeof record[field] !== 'string' || record[field] === '') {
      throw new Error(`invalid envelope field: ${field}`);
    }
  }

  if (!Number.isInteger(record.schemaVersion) || (record.schemaVersion as number) < 1) {
    throw new Error('invalid schemaVersion');
  }

  if (!Number.isInteger(record.attempt) || (record.attempt as number) < 0) {
    throw new Error('invalid attempt');
  }

  if (!('payload' in record)) {
    throw new Error('missing payload');
  }
}
```

校验失败属于不可重试错误时，不要让客户端无限重投。记录 `eventType`、版本、消息 ID 和错误码后，将原消息送入隔离流或 DLQ。
若校验库抛出的错误包含完整载荷，日志层必须先脱敏。

### 2.3 序列化和 Header

JSON 易读、调试成本低，但字段类型和兼容约束需要团队自行维护。Avro、Protobuf 等二进制格式适合严格契约和较高吞吐，但必须配合 Schema Registry 或版本治理。
Kafka 常把 Envelope 放在 value，Trace Context 放在 headers；RabbitMQ 和 Redis 也可以将追踪字段放入 headers 或载荷。
无论放在哪里，消费者都应能从 DLQ 中恢复必要的上下文。

```typescript
export function encodeJson<T>(message: MessageEnvelope<T>): Buffer {
  return Buffer.from(JSON.stringify(message), 'utf8');
}

export function decodeJson<T>(value: Buffer | string): MessageEnvelope<T> {
  const parsed: unknown = JSON.parse(value.toString());
  assertEnvelope(parsed);
  return parsed as MessageEnvelope<T>;
}
```

不要把 `Buffer` 直接转换成无约束的对象后跳过校验。生产者和消费者必须共同约定字符集、压缩、最大载荷大小和空字段处理。

## 3. 配置、连接和错误边界

### 3.1 启动时校验配置

配置来自环境变量或密钥管理系统，代码只声明默认的安全上限。
Broker 地址、认证、TLS、Topic/Queue、Consumer Group、并发、批量、超时、Retry 和 DLQ 都应是显式配置。

```typescript
type RuntimeConfig = {
  brokerUrls: string[];
  topic: string;
  groupId: string;
  concurrency: number;
  maxAttempts: number;
  shutdownTimeoutMs: number;
};

function positiveInt(name: string, raw: string | undefined, fallback: number): number {
  const value = raw === undefined ? fallback : Number(raw);
  if (!Number.isInteger(value) || value < 1) {
    throw new Error(`${name} must be a positive integer`);
  }
  return value;
}

export function loadConfig(env: NodeJS.ProcessEnv = process.env): RuntimeConfig {
  if (!env.BROKER_URL || !env.MQ_TOPIC || !env.MQ_GROUP_ID) {
    throw new Error('BROKER_URL, MQ_TOPIC and MQ_GROUP_ID are required');
  }
  const brokerUrls = env.BROKER_URL.split(',').map((value) => value.trim()).filter(Boolean);
  if (brokerUrls.length === 0) throw new Error('BROKER_URL must contain a broker host:port');

  return {
    brokerUrls,
    topic: env.MQ_TOPIC,
    groupId: env.MQ_GROUP_ID,
    concurrency: positiveInt('MQ_CONCURRENCY', env.MQ_CONCURRENCY, 8),
    maxAttempts: positiveInt('MQ_MAX_ATTEMPTS', env.MQ_MAX_ATTEMPTS, 5),
    shutdownTimeoutMs: positiveInt(
      'MQ_SHUTDOWN_TIMEOUT_MS',
      env.MQ_SHUTDOWN_TIMEOUT_MS,
      30_000,
    ),
  };
}
```

生产环境不要把密码、TLS 私钥或完整连接串写入启动日志。启动时可以记录 broker 主机、Topic、Group 和配置版本，但要掩码凭证。

### 3.2 错误分类与退避

错误分类必须是有限集合，而不是对所有异常统一 `retry`。

```typescript
export type ErrorClass = 'transient' | 'rate_limited' | 'schema' | 'business' | 'auth' | 'unknown';

export type ClassifiedError = {
  category: ErrorClass;
  code: string;
  cause: unknown;
};

export function classifyError(error: unknown): ClassifiedError {
  const code = error instanceof Error ? error.name : 'UnknownError';
  const message = error instanceof Error ? error.message : String(error);

  if (/timeout|ECONNRESET|ECONNREFUSED|temporar/i.test(message)) {
    return { category: 'transient', code, cause: error };
  }
  if (/rate.?limit|throttl|429/i.test(message)) {
    return { category: 'rate_limited', code, cause: error };
  }
  if (/schema|deserialize|invalid envelope/i.test(message)) {
    return { category: 'schema', code, cause: error };
  }
  if (/unauthori[sz]ed|forbidden|permission/i.test(message)) {
    return { category: 'auth', code, cause: error };
  }
  if (/business|insufficient|already processed/i.test(message)) {
    return { category: 'business', code, cause: error };
  }
  return { category: 'unknown', code, cause: error };
}

export function retryable(category: ErrorClass): boolean {
  return category === 'transient' || category === 'rate_limited';
}

export function backoffMs(attempt: number, baseMs = 100, capMs = 5_000): number {
  const exponential = Math.min(capMs, baseMs * 2 ** attempt);
  const jitter = Math.floor(Math.random() * Math.max(1, exponential / 2));
  return Math.floor(exponential / 2 + jitter);
}

function sleepWithSignal(milliseconds: number, signal?: AbortSignal): Promise<void> {
  return new Promise<void>((resolve, reject) => {
    if (signal?.aborted) {
      reject(signal.reason ?? new Error('aborted'));
      return;
    }
    let timer: ReturnType<typeof setTimeout>;
    const onAbort = (): void => {
      clearTimeout(timer);
      reject(signal?.reason ?? new Error('aborted'));
    };

    timer = setTimeout(() => {
      signal?.removeEventListener('abort', onAbort);
      resolve();
    }, milliseconds);
    signal?.addEventListener('abort', onAbort, { once: true });
  });
}

export async function retry<T>(
  operation: (attempt: number) => Promise<T>,
  options: { maxAttempts: number; timeoutMs?: number; signal?: AbortSignal },
): Promise<T> {
  let lastError: unknown;
  const deadlineAt = options.timeoutMs === undefined
    ? undefined
    : Date.now() + options.timeoutMs;

  for (let attempt = 0; attempt < options.maxAttempts; attempt += 1) {
    options.signal?.throwIfAborted();
    if (deadlineAt !== undefined && Date.now() >= deadlineAt) {
      throw new Error('retry deadline exceeded');
    }
    try {
      const result = await operation(attempt);
      if (deadlineAt !== undefined && Date.now() > deadlineAt) {
        throw new Error('retry deadline exceeded');
      }
      return result;
    } catch (error) {
      lastError = error;
      const classified = classifyError(error);
      if (!retryable(classified.category) || attempt === options.maxAttempts - 1) {
        throw error;
      }
      const delay = backoffMs(attempt);
      const remaining = deadlineAt === undefined ? delay : deadlineAt - Date.now();
      if (remaining <= 0) throw new Error('retry deadline exceeded');
      await sleepWithSignal(Math.min(delay, remaining), options.signal);
    }
  }

  throw lastError;
}
```

通过 `timeoutMs` 或外部 `AbortSignal` 约束整个重试循环，而不是每次重试都重新获得一个完整超时。
不可重试错误应进入 DLQ 或人工处理；第三方 HTTP 调用还应传递业务幂等键，避免响应丢失造成重复扣款或重复发货。

## 4. KafkaJS：Topic、Partition 与 Offset

以下客户端代码块放在同一个 TypeScript 模块中，复用本篇前面定义的 `RuntimeConfig`、`MessageEnvelope`、`createEnvelope`、`encodeJson`、`decodeJson` 和 `assertEnvelope`。

### 4.1 Producer

KafkaJS 的 Producer 发送成功回调表示 Broker 返回了发送结果；持久性还取决于 Kafka 的 `acks`、副本和 `min.insync.replicas` 配置。
生产环境通常显式设置 `acks: -1`（等待 ISR）或使用客户端版本对应的可靠性选项，并区分单次 Produce Request Timeout 与整个业务发布生命周期。

```typescript
import { Kafka, logLevel, type Producer } from 'kafkajs';

export function createKafkaProducer(config: RuntimeConfig): Producer {
  const kafka = new Kafka({
    clientId: 'orders-api',
    brokers: config.brokerUrls,
    logLevel: logLevel.WARN,
  });
  return kafka.producer({
    idempotent: true,
    maxInFlightRequests: 5,
  });
}

export async function publishKafka<T>(
  producer: Producer,
  topic: string,
  message: MessageEnvelope<T>,
): Promise<void> {
  await producer.send({
    topic,
    acks: -1,
    timeout: 30_000,
    messages: [{
      key: message.partitionKey ?? message.messageId,
      value: JSON.stringify(message),
      headers: message.traceparent ? { traceparent: message.traceparent } : undefined,
    }],
  });
}

const producer = createKafkaProducer(loadConfig());
await producer.connect();
try {
  await publishKafka(producer, 'order-events', createEnvelope({
    eventType: 'OrderCreated',
    producer: 'orders-api',
    correlationId: 'request-123',
    partitionKey: 'order-1001',
    payload: { orderId: 'order-1001', amount: 1999 },
  }));
} finally {
  await producer.disconnect();
}
```

`idempotent: true` 主要抑制 Kafka Producer Session 内因重试造成的日志重复，不替代消费者的业务幂等。
KafkaJS `2.2.x` 的幂等 Producer 使用近似无上限的内部重试维持协议保证，不能用有限 `retries` 覆盖；示例中的 `timeout` 只约束单次 Produce Request。关键事件应先写 Outbox，由独立 Publisher 在有界内存、健康检查和停机策略下持续发送。
发送超时后不要根据“没有收到响应”断言消息不存在；复用 `messageId` 重试，并让消费者安全处理重复。

### 4.2 Consumer

KafkaJS 的 `eachMessage` 适合逐条处理，回调成功返回后客户端才会按配置提交进度。
高吞吐场景可以使用 `eachBatch`，但要自己管理批内失败、心跳和已处理 Offset。

```typescript
import { Kafka, type EachMessagePayload } from 'kafkajs';

const kafka = new Kafka({
  clientId: 'billing-worker',
  brokers: [process.env.KAFKA_BROKER ?? 'localhost:9092'],
});
const consumer = kafka.consumer({ groupId: 'billing-v1' });

async function handleKafkaMessage(
  { message, partition, topic }: EachMessagePayload,
  processMessage: (envelope: MessageEnvelope<{ orderId: string; amount: number }>) => Promise<void>,
): Promise<void> {
  if (!message.value) {
    throw new Error('empty Kafka message');
  }

  const envelope = decodeJson<{ orderId: string; amount: number }>(message.value);
  assertEnvelope(envelope);
  await processMessage(envelope);
  console.info(JSON.stringify({
    topic,
    partition,
    offset: message.offset,
    messageId: envelope.messageId,
    eventType: envelope.eventType,
    result: 'ok',
  }));
}

await consumer.connect();
await consumer.subscribe({ topic: 'order-events', fromBeginning: false });
const processMessage = async (
  envelope: MessageEnvelope<{ orderId: string; amount: number }>,
): Promise<void> => {
  // 生产代码在这里调用 Inbox + 业务事务；见后文的 PostgreSQL 示例。
  console.info(JSON.stringify({ messageId: envelope.messageId, result: 'business-processed' }));
};

await consumer.run({
  autoCommit: false,
  eachMessage: async (payload) => {
    await handleKafkaMessage(payload, processMessage);
    await consumer.commitOffsets([{
      topic: payload.topic,
      partition: payload.partition,
      offset: (BigInt(payload.message.offset) + 1n).toString(),
    }]);
  },
});
```

上例关闭自动提交，把业务成功与提交动作放在同一处理流程里。数据库事务和 Kafka Offset 仍不是同一个原子事务，所以传入的 `processMessage` 实现必须使用 Inbox、唯一约束或条件更新。
若要批量处理，提交的 Offset 必须是“已经成功处理的连续前缀之后一个位置”，不能在批内跳过失败消息后错误提交更大的位置。

### 4.3 Rebalance 与并发

Consumer Group 发生成员变更、订阅变化或 Partition 数变化时会 Rebalance。处理函数过慢、心跳阻塞或实例频繁重启都会让 Rebalance 变得抖动。
不要用大量同步 CPU 计算阻塞 Node.js 事件循环；CPU 密集任务放入 `worker_threads` 或独立服务。
同一聚合需要顺序时使用稳定 key；增加 Consumer 实例只有在有未分配 Partition 且下游仍有容量时才有效。

## 5. RabbitMQ：Exchange、Queue、ACK 与 Confirm

### 5.1 Confirm Channel 发布

RabbitMQ 的 Exchange 负责路由，Queue 保存待消费消息。Publisher Confirm 表示 Broker 已处理发布请求，但路由是否成功还应通过 mandatory 返回或拓扑配置验证。

```typescript
import amqp, { type ConfirmChannel, type Connection } from 'amqplib';

type RabbitResources = {
  connection: Connection;
  channel: ConfirmChannel;
};

export async function openRabbit(url: string): Promise<RabbitResources> {
  const connection = await amqp.connect(url);
  const channel = await connection.createConfirmChannel();
  await channel.assertExchange('orders', 'topic', { durable: true });
  return { connection, channel };
}

export async function publishRabbit<T>(
  channel: ConfirmChannel,
  message: MessageEnvelope<T>,
): Promise<void> {
  const body = Buffer.from(JSON.stringify(message));
  let returned = false;
  const onReturn = (returnedMessage: { properties: { messageId?: string } }): void => {
    if (returnedMessage.properties.messageId === message.messageId) returned = true;
  };
  channel.on('return', onReturn);

  try {
    const accepted = channel.publish('orders', 'order.created', body, {
      mandatory: true,
      persistent: true,
      contentType: 'application/json',
      messageId: message.messageId,
      type: message.eventType,
      headers: {
        schemaVersion: message.schemaVersion,
        traceparent: message.traceparent,
      },
    });

    if (!accepted) {
      await new Promise<void>((resolve) => channel.once('drain', resolve));
    }
    await channel.waitForConfirms();
    await new Promise<void>((resolve) => setImmediate(resolve));
    if (returned) throw new Error(`RabbitMQ message was unroutable: ${message.messageId}`);
  } finally {
    channel.off('return', onReturn);
  }
}
```

`publish()` 返回 `false` 时表示客户端写缓冲已满，不是发布失败；应等待 `drain` 形成背压。
Confirm 超时或连接断开时，消息状态可能未知。使用稳定 `messageId`，并让消费者去重。

### 5.2 Consumer、Prefetch 和 ACK

`prefetch` 限制未确认消息数量，是 RabbitMQ 消费端的重要背压阀。设置太大可能导致单实例囤积大量消息，设置太小则降低吞吐。

```typescript
import type { ConfirmChannel, ConsumeMessage } from 'amqplib';

export async function startRabbitConsumer(
  channel: ConfirmChannel,
  processMessage: (envelope: MessageEnvelope<{ orderId: string }>) => Promise<void>,
): Promise<void> {
  await channel.assertExchange('orders', 'topic', { durable: true });
  await channel.assertExchange('orders.dlx', 'direct', { durable: true });
  await channel.assertQueue('billing.dlq', { durable: true });
  await channel.bindQueue('billing.dlq', 'orders.dlx', 'billing.dead');
  await channel.assertExchange('orders.retry', 'direct', { durable: true });
  await channel.assertQueue('billing.retry.5s', {
    durable: true,
    arguments: {
      'x-message-ttl': 5_000,
      'x-dead-letter-exchange': 'orders',
      'x-dead-letter-routing-key': 'order.created',
    },
  });
  await channel.bindQueue('billing.retry.5s', 'orders.retry', 'order.created.retry');
  await channel.assertQueue('billing', {
    durable: true,
    arguments: {
      'x-dead-letter-exchange': 'orders.dlx',
      'x-dead-letter-routing-key': 'billing.dead',
    },
  });
  await channel.bindQueue('billing', 'orders', 'order.*');
  await channel.prefetch(16);

  await channel.consume('billing', async (raw: ConsumeMessage | null) => {
    if (!raw) return;

    try {
      const envelope = decodeJson<{ orderId: string }>(raw.content);
      await processMessage(envelope);
      channel.ack(raw);
    } catch (error) {
      const classified = classifyError(error);
      if (retryable(classified.category)) {
        const attempt = Number(raw.properties.headers?.attempt ?? 0) + 1;
        if (attempt >= 5) {
          channel.nack(raw, false, false);
        } else {
          const published = channel.publish('orders.retry', 'order.created.retry', raw.content, {
            persistent: true,
            contentType: raw.properties.contentType,
            messageId: raw.properties.messageId,
            type: raw.properties.type,
            headers: { ...(raw.properties.headers ?? {}), attempt },
          });
          if (!published) await new Promise<void>((resolve) => channel.once('drain', resolve));
          await channel.waitForConfirms();
          channel.ack(raw);
        }
      } else {
        channel.nack(raw, false, false);
      }
    }
  }, { noAck: false });
}
```

`nack(..., true)` 立即重新入队，若没有延迟或次数上限，坏消息会形成热循环。
上例把可重试消息显式发布到带 TTL 的 Retry Queue，等待过期后由 DLX 路由回主 Exchange；只有发布 Confirm 成功后才 ACK 原消息。
超过 5 次或遇到不可重试错误时，`nack(..., false, false)` 通过主 Queue 的 DLX 进入 `billing.dlq`，不会静默丢弃。
业务事务成功后再 `ack`；ACK 丢失时的重复投递由 Inbox 或唯一约束兜底。

## 6. Redis Streams 与 BullMQ

### 6.1 Redis Streams Consumer Group

Redis Streams 使用 Stream ID 标识记录。`XREADGROUP` 将消息交给某个 Consumer，并把未确认记录放入 Pending Entries List（PEL）。成功处理后用 `XACK` 移除 PEL 记录。

```typescript
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL ?? 'redis://localhost:6379');
const stream = 'order-events';
const group = 'billing';
const consumerName = `worker-${process.pid}`;

await redis.xgroup('CREATE', stream, group, '0', 'MKSTREAM').catch((error: unknown) => {
  if (!(error instanceof Error) || !/BUSYGROUP/.test(error.message)) throw error;
});

async function readRedisStream(
  processMessage: (envelope: MessageEnvelope<{ orderId: string }>) => Promise<void>,
): Promise<void> {
  const result = await redis.xreadgroup(
    'GROUP', group, consumerName,
    'COUNT', 10,
    'BLOCK', 1_000,
    'STREAMS', stream, '>',
  );

  for (const [, entries] of result ?? []) {
    for (const [id, fields] of entries) {
      try {
        const values = Object.fromEntries(chunk(fields, 2));
        const envelope = decodeJson<{ orderId: string }>(values.payload);
        await processMessage(envelope);
        await redis.xack(stream, group, id);
      } catch (error) {
        console.error(JSON.stringify({ stream, group, id, error: classifyError(error).code }));
        // 失败记录留在 PEL，由恢复程序 XAUTOCLAIM 或转入 DLQ。
      }
    }
  }
}

function chunk(values: string[], size: number): string[][] {
  const result: string[][] = [];
  for (let i = 0; i < values.length; i += size) result.push(values.slice(i, i + size));
  return result;
}
```

实际发送可使用 `XADD order-events MAXLEN ~ 100000 * payload <json>`。Stream 长度、Redis 内存、AOF/RDB、复制延迟和恢复点必须一起规划，不能把 Redis 当作无限日志。
长任务需要设置合理的 claim 空闲阈值；任务尚未完成就 `XAUTOCLAIM` 会造成并发重复处理。

```typescript
export async function reclaimRedisMessages(
  processMessage: (envelope: MessageEnvelope<{ orderId: string }>) => Promise<void>,
): Promise<void> {
  const [, entries] = await redis.xautoclaim(
    stream, group, consumerName, 60_000, '0-0', 'COUNT', 50,
  );

  for (const [id, fields] of entries) {
    const values = Object.fromEntries(chunk(fields, 2));
    try {
      const envelope = decodeJson<{ orderId: string }>(values.payload);
      await processMessage(envelope);
      await redis.xack(stream, group, id);
      await redis.hdel(`${stream}:${group}:attempts`, id);
    } catch (error) {
      const attempts = await redis.hincrby(`${stream}:${group}:attempts`, id, 1);
      const classified = classifyError(error);
      if (!retryable(classified.category) || attempts >= 5) {
        await redis.xadd(
          `${stream}.dlq`, '*',
          'originalId', id,
          'attempt', String(attempts),
          'errorCode', classified.code,
          'payload', values.payload ?? '',
        );
        await redis.xack(stream, group, id);
        await redis.hdel(`${stream}:${group}:attempts`, id);
      } else {
        console.error(JSON.stringify({ stream, group, id, attempts, error: classified.code }));
        // 保留在 PEL，下一轮按 idle 阈值再次接管；attempts 使重试有上限。
      }
    }
  }
}
```

### 6.2 BullMQ 任务队列

BullMQ 在 Redis 上提供 `Queue`、`Worker`、延迟任务和失败重试。它适合任务型工作流，不等价于长期不可变事件日志。

```typescript
import { Queue, Worker, type Job } from 'bullmq';

const connection = {
  host: process.env.REDIS_HOST ?? 'localhost',
  port: Number(process.env.REDIS_PORT ?? 6379),
};
const emailQueue = new Queue('email', { connection });

await emailQueue.add(
  'send-order-email',
  { orderId: 'order-1001', messageId: 'evt-1001' },
  {
    jobId: 'order-1001-confirmation',
    attempts: 5,
    backoff: { type: 'exponential', delay: 500 },
    removeOnComplete: { age: 86_400, count: 10_000 },
    removeOnFail: { age: 604_800 },
  },
);

export function createEmailWorker(
  sendEmailIdempotently: (data: { orderId: string; messageId: string }) => Promise<void>,
): Worker {
  return new Worker(
    'email',
    async (job: Job<{ orderId: string; messageId: string }>) => {
      await sendEmailIdempotently(job.data);
    },
    { connection, concurrency: 8, lockDuration: 60_000 },
  );
}

const worker = createEmailWorker(async (data) => {
  // 这里调用邮件供应商，并传递 data.messageId 作为供应商幂等键。
  console.info(JSON.stringify({ job: 'send-order-email', orderId: data.orderId, idempotencyKey: data.messageId }));
});

worker.on('failed', (job, error) => {
  console.error(JSON.stringify({ jobId: job?.id, error: error.message }));
});
```

任务处理函数必须幂等。`jobId` 去重只覆盖入队记录，不能保证外部邮件服务只发送一次。
CPU 密集任务应转移到 `worker_threads` 或独立服务；保留完成和失败 Job 时要设置 age/count，避免 Redis 无界增长。

## 7. 并发、背压与优雅关闭

### 7.1 一个简单的并发闸门

Node.js 的 Promise 并发不会自动考虑数据库连接池和下游限流。可以在应用层设置 semaphore，且让 Broker 的 prefetch、Kafka 批量或 BullMQ `concurrency` 与它保持一致。

```typescript
export class Semaphore {
  private available: number;
  private readonly waiters: Array<() => void> = [];

  public constructor(limit: number) {
    if (!Number.isInteger(limit) || limit < 1) throw new Error('invalid semaphore limit');
    this.available = limit;
  }

  public async acquire(): Promise<() => void> {
    if (this.available === 0) {
      await new Promise<void>((resolve) => this.waiters.push(resolve));
    }
    this.available -= 1;
    let released = false;
    return () => {
      if (released) return;
      released = true;
      this.available += 1;
      this.waiters.shift()?.();
    };
  }
}

const gate = new Semaphore(16);

export async function processWithLimit<T>(messages: T[], handle: (message: T) => Promise<void>): Promise<void> {
  await Promise.all(messages.map(async (message) => {
    const release = await gate.acquire();
    try {
      await handle(message);
    } finally {
      release();
    }
  }));
}
```

这个闸门只限制当前进程；多实例总并发还要乘以实例数，并纳入下游连接池预算。不要通过无限扩大应用内数组来掩盖 Broker 积压。

### 7.2 优雅关闭的通用流程

收到 `SIGTERM` 或 `SIGINT` 后，先把 readiness 设为失败，再停止拉取新消息，等待在途任务完成，最后提交确认并关闭连接。
超过截止时间时不要强行 ACK 未完成任务，让 Broker 按其租约或未确认规则重新投递。

```typescript
type StoppableConsumer = {
  stopPulling(): Promise<void>;
  close(): Promise<void>;
};

export function installShutdown(
  consumer: StoppableConsumer,
  closeDependencies: () => Promise<void>,
  inFlight: Set<Promise<unknown>>,
  timeoutMs: number,
): void {
  let shuttingDown = false;

  const shutdown = async (): Promise<void> => {
    if (shuttingDown) return;
    shuttingDown = true;
    readiness.set(false);
    await consumer.stopPulling();

    const waitForTasks = Promise.allSettled([...inFlight]);
    await Promise.race([waitForTasks, timeout(timeoutMs)]);
    await consumer.close();
    await closeDependencies();
  };

  process.once('SIGTERM', () => void shutdown());
  process.once('SIGINT', () => void shutdown());
}

function timeout(milliseconds: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, milliseconds));
}

const readiness = {
  value: true,
  set(value: boolean): void { this.value = value; },
};
```

`readiness` 在上例中是进程内状态，HTTP 探针应读取它；`liveness` 只检查事件循环和进程是否仍在推进，不要在 liveness 中执行重度 Broker 查询。
实际客户端的 `stopPulling` 可能叫 `pause`、`cancel` 或 `close`，应在适配器中实现，不要让业务处理器依赖具体客户端。

## 8. Inbox、Outbox 与数据库事务

### 8.1 Inbox：先记录去重，再执行业务更新

At-least-once 下，ACK 丢失、消费者重启和人工回放都会造成重复。Inbox 表应与业务更新使用同一个数据库事务，唯一约束承担并发下的最后防线。

```sql
CREATE TABLE inbox_events (
  consumer_name text NOT NULL,
  event_id text NOT NULL,
  payload_hash text NOT NULL,
  processed_at timestamptz,
  result jsonb,
  PRIMARY KEY (consumer_name, event_id)
);
```

下面的 PostgreSQL 形状使用 `INSERT ... RETURNING` 判断当前事务是否首次处理，避免“先查询再插入”的竞态：

```typescript
import { createHash } from 'node:crypto';
import type { Pool, PoolClient } from 'pg';

type OrderPaid = MessageEnvelope<{ orderId: string; paymentId: string }>;

export async function processOrderIdempotently(
  message: OrderPaid,
  pool: Pool,
): Promise<void> {
  const client: PoolClient = await pool.connect();
  try {
    await client.query('BEGIN');
    const payloadHash = createHash('sha256')
      .update(JSON.stringify(message.payload))
      .digest('hex');
    const inserted = await client.query(
      `INSERT INTO inbox_events (consumer_name, event_id, payload_hash)
       VALUES ($1, $2, $3)
       ON CONFLICT (consumer_name, event_id) DO NOTHING
       RETURNING event_id`,
      ['billing-v1', message.messageId, payloadHash],
    );

    if (inserted.rowCount === 0) {
      const existing = await client.query(
        `SELECT payload_hash, processed_at
         FROM inbox_events
         WHERE consumer_name = $1 AND event_id = $2
         FOR UPDATE`,
        ['billing-v1', message.messageId],
      );
      const row = existing.rows[0] as { payload_hash: string; processed_at: Date | null } | undefined;
      if (!row || row.payload_hash !== payloadHash) {
        console.error(JSON.stringify({
          consumer: 'billing-v1',
          eventId: message.messageId,
          error: 'inbox_payload_mismatch',
        }));
        throw new Error('inbox payload hash mismatch');
      }
      if (row.processed_at) {
        await client.query('COMMIT');
        return;
      }
    }

    const updated = await client.query(
      `UPDATE orders
       SET paid = true, payment_id = $1, version = version + 1
       WHERE id = $2 AND paid = false`,
      [message.payload.paymentId, message.payload.orderId],
    );

    if (updated.rowCount !== 1) {
      throw new Error('order is missing or already paid');
    }

    await client.query(
      `UPDATE inbox_events
       SET processed_at = now(), result = $1::jsonb
       WHERE consumer_name = $2 AND event_id = $3`,
      [JSON.stringify({ status: 'ok' }), 'billing-v1', message.messageId],
    );
    await client.query('COMMIT');
  } catch (error) {
    await client.query('ROLLBACK');
    throw error;
  } finally {
    client.release();
  }
}
```

如果相同 `event_id` 携带不同载荷，应该比较 `payload_hash` 并报警，而不是静默返回成功。
外部 HTTP、支付和邮件等不可回滚副作用不能只依赖 Inbox；为供应商传递业务幂等键，或先把动作写入可审计状态机。

### 8.2 Outbox：业务提交和待发布事件一起提交

```sql
BEGIN;

WITH changed AS (
  UPDATE orders
  SET status = 'PAID', version = version + 1
  WHERE id = $1 AND status = 'PENDING'
  RETURNING id, version
)
INSERT INTO outbox_events (
  event_id, event_type, aggregate_id, aggregate_version, payload, status
)
SELECT $2, 'OrderPaid', id, version, $3::jsonb, 'PENDING'
FROM changed;

COMMIT;
```

CTE 的 `changed` 为空时不会插入事件；应用仍应检查 Outbox `INSERT` 的 `rowCount`，在订单不在 `PENDING` 状态时向调用方返回明确结果。
发布器用租约或 `FOR UPDATE SKIP LOCKED` 领取记录，发送成功后标记 `PUBLISHED`。
“发送成功”和“标记已发布”之间仍可能崩溃，所以发布器也必须允许重复，且复用 `event_id`。
Outbox 的最老记录年龄、失败次数和隔离记录数量应纳入告警。

## 9. Trace、日志和指标

### 9.1 Trace Context

Producer 发布时将 W3C `traceparent` 写入 headers 或 Envelope。Consumer 读取后创建新的处理 Span，并把原 Context 作为父 Span。
不要把一个长时间异步消费任务错误地当作 Producer HTTP Span 的同步子调用；应记录消息因果关系和链接。

在 Node.js 中可以用 `AsyncLocalStorage` 保存当前处理上下文：

```typescript
import { AsyncLocalStorage } from 'node:async_hooks';

type MessageContext = {
  messageId: string;
  eventType: string;
  traceId?: string;
};

const context = new AsyncLocalStorage<MessageContext>();

export function withMessageContext<T>(value: MessageContext, fn: () => Promise<T>): Promise<T> {
  return context.run(value, fn);
}

export function log(fields: Record<string, unknown>, message: string): void {
  console.log(JSON.stringify({
    time: new Date().toISOString(),
    ...context.getStore(),
    ...fields,
    message,
  }));
}
```

### 9.2 结构化字段和指标

日志至少包含 `messageId`、`eventType`、Topic/Queue、Partition、Offset 或 delivery tag、Consumer Group、attempt、耗时和结果。
完整 payload、Authorization、Cookie、密码和支付数据必须脱敏或不记录。

建议指标包括：

- Producer confirm 成功率、发送延迟、重试次数、缓冲区等待和拒绝数；
- Consumer 成功率、处理延迟 p50/p95/p99、并发在途数、错误分类和优雅关闭耗时；
- Kafka `consumer lag`、RabbitMQ ready/unacked、Redis PEL/pending、BullMQ waiting/active/stalled；
- Retry、DLQ、Outbox 最老事件年龄、Schema 拒绝和下游超时；
- Broker 连接重连、TLS/认证错误、内存水位和复制延迟。

不要把 `messageId`、订单号等高基数字段直接作为 Metrics label；它们适合日志和 Trace。

## 10. 健康检查、部署与升级

### 10.1 Liveness 和 Readiness

`liveness` 只回答“进程是否还能运行”。事件循环长期阻塞、进程死锁时才应失败。
`readiness` 回答“当前实例是否可以安全接收消息”。正在关闭、订阅未建立、认证失效或关键依赖不可用时应摘除实例。
探针失败本身不应触发重度业务查询，也不应因为短暂的单条消息失败就重启整个消费者。

```typescript
import { createServer } from 'node:http';

let ready = false;
let alive = true;

const server = createServer((request, response) => {
  if (request.url === '/health/live') {
    response.writeHead(alive ? 200 : 503).end(alive ? 'ok' : 'not alive');
    return;
  }
  if (request.url === '/health/ready') {
    response.writeHead(ready ? 200 : 503).end(ready ? 'ready' : 'not ready');
    return;
  }
  response.writeHead(404).end();
});

export function setReady(value: boolean): void {
  ready = value;
}

server.listen(Number(process.env.PORT ?? 3000));
// 仅在 Broker 连接、订阅和必要依赖都成功后调用 setReady(true)。
```

### 10.2 容器和滚动升级

容器的 `terminationGracePeriodSeconds` 应大于最大单条处理时间、数据库提交时间和客户端关闭时间的总和。
滚动升级先把旧实例 readiness 置为失败，再停止拉取；未确认消息由 Broker 重投。
同一 Consumer Group 的实例不要共享冲突的静态 Consumer ID；如果客户端支持稳定成员身份，升级时要按其协议配置。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: billing-worker
spec:
  replicas: 3
  strategy:
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    spec:
      terminationGracePeriodSeconds: 90
      containers:
        - name: worker
          image: example/billing-worker:2026-08-04
          env:
            - name: MQ_CONCURRENCY
              value: "16"
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 3000
          livenessProbe:
            httpGet:
              path: /health/live
              port: 3000
```

上线前确认新版本可以读取旧 Schema，且旧消费者可以安全忽略新增字段。先灰度一个 Consumer Group 或实例，观察 Lag、错误率、重试和 DLQ，再扩大范围。

### 10.3 TLS、权限和秘密

生产连接必须启用 TLS（或 mTLS），凭证来自 Secret/密钥管理系统，不进入镜像、日志和消息载荷。
为每个服务、Topic/Queue 和操作授予最小权限：Producer 不应默认拥有消费和管理权限，Consumer 不应拥有删除任意 Topic 的权限。
对 DLQ 和回放工具设置更高的审计要求，记录谁在何时以什么版本重放了哪一批消息。

## 11. 测试策略

### 11.1 单元与契约测试

单元测试覆盖 Envelope 编解码、Schema 兼容、错误分类、退避上限、幂等键和关闭状态机。
契约测试验证 Producer 发送的字段、类型、版本和路由键符合 Consumer 的读取约定。

import test from 'node:test';
import assert from 'node:assert/strict';

test('retry keeps the logical message id', async () => {

    ids.push(message.messageId);

### 11.2 集成、压力和故障演练

每次演练都应回答“消息在哪里、谁拥有重试、何时会丢失、如何对账和回放”。

## 12. 上线检查清单

- [ ] Envelope 有稳定 `messageId`、版本、时间、Trace 和业务幂等键。
- [ ] Producer 等待明确的 Confirm，处理未知状态和有界重试。
- [ ] Consumer 在业务事务成功后 ACK/Commit/XACK，重复处理可安全执行。
- [ ] 并发、prefetch、批量和连接池有统一预算，应用内缓冲有上限。

- [ ] Outbox/Inbox 或其他跨存储一致性方案已压测并可对账。
- [ ] readiness、liveness、Lag、最老消息年龄、重试和 DLQ 有监控告警。
- [ ] SIGTERM 关闭流程经过演练，终止宽限期覆盖最长任务。
- [ ] TLS、最小权限、日志脱敏和秘密轮换已落实。
- [ ] 灰度升级验证旧消息、新 Schema 和回滚路径。

## 13. 常见问题

### 为什么 Kafka 的 commit 不能替代数据库事务？

Offset 只记录 Consumer Group 的读取进度；数据库写入失败而 Offset 已提交会丢失消息，数据库写入成功而 Offset 未提交会重复。使用 Inbox、唯一约束或 Kafka 事务边界将重复变成安全操作。

### RabbitMQ `nack(requeue=true)` 为什么可能拖垮系统？

坏消息会立即回到可投递队列，下一次处理仍然失败，形成高频重试并占用 Consumer。应按错误分类进入带延迟的 Retry Queue 或 DLQ，并设置最大次数。

### Redis Streams 的 PEL 代表什么？

PEL 代表 Consumer Group 已经领取但尚未 `XACK` 的记录，不代表业务事务一定未完成。Claim 前要检查空闲时间，Claim 后仍需按消息 ID 幂等。

### 增加消费者实例为什么没有提速？

可能已达到 Partition/Queue 并行度上限，也可能下游数据库、HTTP 连接池或 CPU 已饱和。先看 Lag、处理耗时和下游容量，再决定是否扩容。

### Node.js 消费者如何避免重复扣款？

使用稳定的业务幂等键（如 `paymentId`）和数据库唯一约束或 Inbox，在外部支付 API 中传递相同幂等键；处理成功后再确认消息，确认丢失时允许安全重试。
