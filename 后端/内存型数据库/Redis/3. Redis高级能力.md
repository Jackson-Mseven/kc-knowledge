# 三、Redis 高级能力

### 三大缓存问题

#### 穿透（查不存在的数据）

缓存穿透指的是：

> 用户不断查询一个**数据库中本来就不存在**的数据；因为 Redis 里没有，数据库里也没有，所以每次请求都会穿透 Redis，直接打到数据库。
> 
> 

例如查询商品：

```Bash
GET /api/products/999999999
```

流程：

```Bash
请求商品 ID 999999999
        ↓
Redis 中没有
        ↓
查询数据库
        ↓
数据库中也没有
        ↓
返回“商品不存在”
```

如果下一次还查询同一个不存在的 ID：

```Bash
Redis 中还是没有
数据库中还是没有
```

于是又会查数据库。

缓存穿透的问题在于：

```Bash
Redis 和数据库都没有数据
```

导致 Redis 无法起到保护数据库的作用。

---

##### 解决方案：缓存空值

当 Redis 没有数据、数据库也查不到时，不要什么都不缓存，而是在 Redis 中缓存一个“空结果”。

例如：

```Bash
product:999999 = NULL
TTL = 60 秒
```

下次再请求时：

```Bash
请求 product:999999
        ↓
Redis：命中 NULL
        ↓
直接返回“商品不存在”
        ↓
不查询数据库
```

> **注意点：**
> 
> **空值缓存应该设置较短 TTL**，例如：30 秒、60 秒、几分钟。
> 
> **不能永久缓存**，因为该数据以后可能真的被创建。
> 
> 例如：
> 
> ```Bash
> 现在商品 1001 不存在
> 一分钟后运营人员创建商品 1001
> ```
> 
> 如果空值永久存在，用户仍会被错误地告知“商品不存在”。
> 
> 

---

##### 解决方案：布隆过滤器

布隆过滤器可以理解成一个“快速预检查器”。

它不能准确告诉你：这个数据一定存在。

但它可以比较可靠地告诉你：这个数据一定不存在。

请求流程：

```Bash
请求商品 ID
    ↓
先检查布隆过滤器
    ↓
明确不存在？
    ↓
直接返回不存在
    ↓
不访问 Redis，也不访问数据库
```

示意：

```Bash
请求 product:999999
        ↓
布隆过滤器判断：一定不存在
        ↓
直接返回 404
```

对于可能存在的数据：

```Bash
请求 product:1001
        ↓
布隆过滤器判断：可能存在
        ↓
查询 Redis
        ↓
Redis 未命中再查询数据库
```

这里的“可能存在”很重要。

布隆过滤器可能误判：

```Bash
实际上不存在
但布隆过滤器说“可能存在”
```

于是仍然会继续查询 Redis 和数据库。

但它通常不会误判为：

```Bash
实际存在
但布隆过滤器说“一定不存在”
```

否则会造成真实数据无法访问。

> **注意点：**
> 
> - 数据新增时，要同步把 ID 加入过滤器；
> 
> - 删除数据后，普通 Bloom Filter 不方便删除；
> 
> - 需要评估误判率、内存和数据更新策略；
> 
> - 不能把它当作权限校验或最终事实来源。
> 
> Redis 提供 RedisBloom 模块，可使用类似命令：
> 
> ```Bash
> BF.ADD product:ids 1001
> BF.EXISTS product:ids 1001
> ```
> 
> 

---

#### 击穿（热点 key 过期）

缓存击穿指的是：

> 某个**原本存在且访问量特别高的热点数据**，在缓存过期的瞬间，大量请求同时发现缓存不存在，于是一起去查询数据库。
> 
> 

例如一个热门商品：

```Bash
product:1001
```

平时：

```Bash
大量用户请求
    ↓
Redis 命中
    ↓
数据库压力很小
```

但它的缓存恰好过期：

```Bash
product:1001 的 TTL 到期
```

此时 10,000 个请求同时到达：

```Bash
10,000 个请求
        ↓
Redis 都没有命中
        ↓
10,000 个请求同时查数据库
        ↓
数据库压力暴涨
```

这就是缓存击穿。

---

##### 解决方案：互斥锁/分布式锁

核心思想：

> 缓存失效时，只允许一个请求去查询数据库并重建缓存；其他请求等待、重试，或者返回旧数据。
> 
> 

流程：

```Bash
请求 A：Redis 未命中
    ↓
成功获得重建锁
    ↓
查询数据库
    ↓
写入 Redis
    ↓
释放锁

请求 B：Redis 未命中
    ↓
没有拿到锁
    ↓
等待一小段时间后重试 Redis
```

示意：

```Bash
大量请求
    ↓
Redis 未命中
    ↓
只有一个请求拿到锁
    ↓
查询数据库并回填 Redis
    ↓
其他请求重新读取 Redis
```

Redis 中常见的加锁方式：

```Bash
SET lock:product:1001 unique-token NX PX 5000
```

含义：

```Bash
NX：锁不存在时才创建
PX 5000：锁最多保留 5 秒
unique-token：当前持锁者的唯一标识
```

释放锁时必须校验 token，不能直接 `DEL`：

```Lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end

return 0
```

因为锁可能已经超时，并被另一个请求重新获得。旧请求如果直接 `DEL`，可能删掉新请求的锁。

**优点：**

- 数据通常比较新；

- 数据库只会收到少量重建请求；

- 适合热点数据失效后的同步重建。

**缺点：**

- 实现复杂度更高；

- 其他请求可能等待；

- 锁 TTL 设置不合理可能造成问题；

- 缓存重建很慢时，仍需处理超时、降级和重试。

---

##### 解决方案：逻辑过期 \+ 后台异步刷新

这是一种常用于热点数据的方案。

关键点是：

> Redis 中的数据不立刻物理删除，而是在值中保存一个“逻辑过期时间”。
> 
> 

例如缓存内容：

```Lua
{
  "data": {
    "id": 1001,
    "name": "热门商品"
  },
  "expireAt": 1735732800000
}
```

即使逻辑上过期，Redis Key 本身仍然存在。

请求流程：

```Lua
请求热点数据
    ↓
Redis 有缓存
    ↓
判断逻辑过期时间
    ↓
未过期：直接返回
已过期：仍先返回旧数据，同时尝试异步刷新
```

多个请求中只有一个请求成功获得刷新锁：

```Lua
请求 A：发现逻辑过期，拿到刷新锁，后台重建缓存
请求 B：发现逻辑过期，没拿到锁，直接返回旧数据
请求 C：发现逻辑过期，没拿到锁，直接返回旧数据
```

缓存更新完成后，新的数据替换旧数据。

**优点：**

- 不会出现“热点 Key 突然完全不存在”的窗口；

- 用户通常仍然能拿到旧数据；

- 数据库不会因为热点缓存到期而被大量请求冲击；

- 用户体验通常更稳定。

**缺点：**

- 用户可能短暂读到旧数据；

- 实现更复杂；

- 需要后台任务或异步执行能力；

- 不适合必须读取绝对最新数据的场景。

这个方案也常被称为：`Stale-While-Revalidate`（过期数据可用，后台刷新）。

---

##### 解决方案：热点 Key 不设置过期时间

对于少数非常重要、非常热的数据，可以不设置 TTL：

```Lua
SET product:1001 product-data
```

当数据发生变化时，主动更新或删除缓存：

```Lua
数据库更新
    ↓
更新 Redis，或者删除 Redis
```

优点：

- 不会因为 TTL 到期产生击穿。

缺点：

- 如果更新逻辑漏掉了缓存更新，可能长期返回旧数据；

- 缓存可能持续占用内存；

- 不适合大量普通 Key。

适合：

- 首页配置；

- 热门榜单；

- 系统配置；

- 高访问量但更新频率低的数据。

---

##### 解决方案：预热缓存

在热点活动开始前，提前把热点数据写入 Redis：

```Lua
秒杀活动开始前
    ↓
将活动商品、库存、商品详情预先加载到 Redis
```

这样活动刚开始时，不会有大量请求同时去数据库加载数据。

适合：

- 秒杀；

- 大促；

- 直播活动；

- 热门内容发布；

- 已知访问高峰。

但预热只是辅助方案，仍建议结合锁或逻辑过期，防止后续缓存失效。

---

#### 雪崩（大量 key 同时过期）

雪崩是指大量 Key 同时写入相同的过期时间，例如：

```Bash
EXPIRE cache:key 600
```

它们可能在同一时间集中失效，形成缓存雪崩。

##### 解决方案：添加随机时间

可以增加随机时间：

```Bash
TTL = 基础 TTL + 随机 TTL
```

例如：

```Bash
600 秒 + 0~60 秒随机值
```

---

### 大 Key 问题

Redis 大 Key（Big Key）指的是：

> 一个 Key 对应的 value 太大，或者一个集合类型 Key 中元素太多，导致一次操作它会消耗较多内存、网络带宽或 Redis 主线程时间。
> 
> 

它不是 Redis 的严格固定概念，而是要结合业务和机器配置判断。

Redis 的核心命令执行通常是单线程顺序进行的。

这意味着：

> 某个命令如果处理一个大 Key 花了很久，其他请求就需要等待。
> 
> 

例如：

```Bash
客户端 A：读取一个 50 MB 的 String
客户端 B：GET session:user:1
客户端 C：INCR counter
```

如果 A 的操作很慢，B 和 C 也可能出现延迟。

---

#### 大 Key 会带来哪些风险？

1. **阻塞 Redis，导致延迟升高**

    例如对一个很大的 Hash 执行：

    ```Bash
    HGETALL huge:hash
    ```

    Redis 要一次性读取并返回所有字段和值。

    如果这个 Hash 有几十万、几百万个字段：

    - Redis 主线程处理时间变长；

    - 序列化响应数据需要时间；

    - 网络传输需要时间；

    - 客户端解析数据也需要时间；

    - 其他 Redis 请求排队等待。

    类似的高风险命令包括：

    ```Bash
    GET huge:string
    HGETALL huge:hash
    SMEMBERS huge:set
    LRANGE huge:list 0 -1
    ZRANGE huge:zset 0 -1
    DEL huge:key
    ```

    注意：这些命令不一定都“不能用”，问题在于操作对象非常大。

2. **网络带宽被占满**

    假设一个 Key 有 50 MB：

    ```Bash
    GET huge:response
    ```

    每读取一次都可能传输 50 MB。

    如果 100 个客户端同时读取：

    ```Bash
    50 MB × 100 = 5 GB 网络数据
    ```

    即使 Redis CPU 没有完全打满，也可能导致：

    - 网络拥塞；

    - 请求超时；

    - 其他普通 Redis 请求变慢；

    - 应用服务器内存和 GC 压力增加。

3. **删除大 Key 时可能阻塞**

    例如：

    ```Bash
    DEL huge:set
    ```

    删除一个包含大量元素的 Set、Hash、List 或 ZSet，可能需要释放很多内存。

    如果同步删除耗时较长，会阻塞 Redis 主线程。

    更推荐在确认业务允许时使用：

    ```Bash
    UNLINK huge:set
    ```

    区别：

    ```Bash
    DEL：同步删除，可能阻塞主线程
    UNLINK：先让 Key 逻辑上消失，后续尽量异步释放内存
    ```

    但要注意，`UNLINK` 只是降低主线程阻塞风险，不代表删除没有资源消耗。

4. **过期时产生延迟抖动**

    如果一个大 Key 设置了 TTL：

    ```Bash
    EXPIRE huge:set 3600
    ```

    过期后 Redis 需要删除它。

    如果没有开启异步释放，过期删除也可能造成短暂卡顿。

    可评估配置：

    ```Bash
    lazyfree-lazy-expire yes
    ```

    让 Redis 尽量异步释放过期大 Key 的内存。

5. **持久化、复制和故障切换压力变大**

    大 Key 会影响：

    - RDB 快照；

    - AOF 重写；

    - 主从复制；

    - 副本节点同步；

    - Redis Cluster 的迁移和扩缩容。

    例如一个 500 MB 的 Key 位于某个 Cluster 节点：

    ```Bash
    迁移该槽位时
        ↓
    需要传输这个大 Key
        ↓
    迁移耗时变长、网络压力变大
    ```

    如果主从复制刚好遇到大 Key 写入，也会带来较大的复制流量和副本延迟。

6. **造成 Cluster 数据倾斜**

    Redis Cluster 按 Key 分片，不会把**同一个 Key**拆到多个节点。

    所以：

    ```Bash
    huge:ranking -> 1 GB
    ```

    无论 Cluster 有多少节点，这个 Key 都只能在一个槽位、一个主节点上。

    结果可能是：

    ```Bash
    节点 A：内存 20 GB
    节点 B：内存 5 GB
    节点 C：内存 4 GB
    ```

    即使总内存充足，节点 A 仍然可能先达到内存上限。

---

#### 如何发现大 Key？

##### 方法一：`redis-cli --bigkeys`

Redis CLI 提供了扫描工具：

```Bash
redis-cli --bigkeys
```

它会扫描 Key，并输出各类型中发现的最大 Key。

示意输出：

```Bash
Biggest string found so far 'cache:homepage' with 12582912 bytes
Biggest hash found so far 'user:settings' with 500000 fields
Biggest set found so far 'article:likes:1001' with 800000 members
```

注意：

- 它通常使用 `SCAN` 扫描，不像 `KEYS *` 那样一次阻塞整个 Redis；

- 但扫描大量 Key 仍会带来额外负载；

- 应优先在低峰期执行；

- 它找到的是扫描过程中的最大 Key，并非绝对实时结果。

如果想更关注内存占用，可使用：

```Bash
redis-cli --memkeys
```

---

##### 方法二：使用 `MEMORY USAGE`

查看某个 Key 大约占用多少内存：

```Bash
MEMORY USAGE user:1001
```

例如返回：

```Bash
5242880
```

表示大约占用：

```Bash
5 MB
```

查看元素数量：

```Bash
STRLEN large:string
HLEN large:hash
LLEN large:list
SCARD large:set
ZCARD large:zset
```

例如：

```Bash
HLEN user:settings
```

可以知道这个 Hash 有多少字段。

---

##### 方法三：慢日志和延迟监控

如果大 Key 被频繁操作，常常会出现在慢日志中：

```Bash
SLOWLOG GET 20
```

也可以查看：

```Bash
INFO commandstats
INFO memory
INFO stats
```

生产环境还应监控：

- Redis 命令延迟；

- CPU 使用率；

- 网络流量；

- 内存使用率；

- 主从复制延迟；

- Cluster 各节点内存是否均衡；

- 慢命令；

- 大 Key 数量和增长趋势。

---

#### 如何解决大 Key？

核心原则：

> 不要让一个 Key 无限增长；把大数据拆成多个较小的 Key，并且按需读取。
> 
> 

---

##### 方案一：拆分 String / 大 JSON

不推荐：

```Bash
product:all -> 100 MB JSON
```

可以按商品拆：

```Bash
product:1001 -> JSON
product:1002 -> JSON
product:1003 -> JSON
```

如果仍然需要列表，可以维护较小的分页索引：

```Bash
product:list:page:1
product:list:page:2
product:list:page:3
```

或者使用数据库分页查询，再缓存单个对象或单页结果。

---

##### 方案二：按时间分桶

不推荐：

```Bash
logs:all
```

可以改为：

```Bash
logs:2025-01-01
logs:2025-01-02
logs:2025-01-03
```

或更细：

```Bash
logs:2025-01-01:10
logs:2025-01-01:11
```

适合：

- 日志；

- 用户行为；

- 消息记录；

- 访问统计；

- 在线数据；

- 按日期统计的排行榜。

---

##### 方案三：按 ID 范围或哈希分片

例如点赞数据：

不推荐：

```Bash
article:1001:likes
```

如果一篇文章可能有上千万点赞，可以分桶：

```Bash
article:1001:likes:0
article:1001:likes:1
article:1001:likes:2
...
article:1001:likes:63
```

根据用户 ID 做哈希：

```Bash
bucket = hash(userId) % 64
```

用户 `user:123` 只会写入某一个桶。

这样单个 Set 不会无限增大。

注意：分桶后，统计总数、去重、查询全量数据都会更复杂，需要根据业务需求权衡。

---

##### 方案四：使用分页或游标读取

对于大集合，不要一次性取完。

不推荐：

```Bash
HGETALL huge:hash
SMEMBERS huge:set
LRANGE huge:list 0 -1
ZRANGE huge:zset 0 -1
```

推荐：

```Bash
HSCAN huge:hash 0 COUNT 100
SSCAN huge:set 0 COUNT 100
ZSCAN huge:zset 0 COUNT 100
```

List 可以按范围分页：

```Bash
LRANGE huge:list 0 99
LRANGE huge:list 100 199
```

> 注意：`SCAN` 系列的 `COUNT` 是建议值，不是严格保证每次刚好返回多少条。
> 
> 

---

##### 方案五：删除时优先考虑 `UNLINK`

如果要删除大 Key：

```Bash
UNLINK huge:key
```

而不是：

```Bash
DEL huge:key
```

对于大集合，`UNLINK` 通常能减少 Redis 主线程的阻塞时间。

但删除前仍要确认：

- 是否有业务正在依赖该 Key；

- 是否需要先停止写入；

- 是否会触发缓存击穿；

- 是否需要分批重建缓存。

---

##### 方案六：设置合理的上限和 TTL

例如排行榜只保留前 1000 名：

```Bash
ZREMRANGEBYRANK ranking:daily 0 -1001
```

更直观地说，保留分数最高的 1000 个成员时，需要根据排行榜排序方向设计清理命令；核心目的是：**限制集合最大长度**。

对于 List，可限制消息队列或最近记录数量：

```Bash
LPUSH user:1001:recent item
LTRIM user:1001:recent 0 999
```

表示只保留最近 1000 条。

对临时数据设置 TTL：

```Bash
EXPIRE cache:page:1 600
```

但要注意：

> TTL 只能清理“过期后的整体 Key”，不能解决一个仍在持续增长的大集合。
> 
> 

因此更重要的是设计容量上限和分片策略。

---

#### 生产排查顺序

发现 Redis 延迟升高时，可以按这个方向检查：

1. 是否有慢命令？

2. 是否有大 Key？

3. 是否有人使用 HGETALL、SMEMBERS、KEYS \* 等全量命令？

4. 是否在删除或过期大 Key？

5. 是否在执行 RDB、AOF 重写、主从全量同步？

6. 是否有热 Key、网络流量或 Cluster 数据倾斜？
