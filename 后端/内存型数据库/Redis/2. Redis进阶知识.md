# 二、Redis 进阶知识

### 过期策略

Redis 的过期策略可以理解为：

> 给 Key 设置一个生存时间，时间到了以后，Redis 会把它视为过期数据，并在**合适的时候**删除。
> 
> 

例如：

```Bash
SET session:user:1001 abc EX 3600
```

表示 `session:user:1001` 最多保存 3600 秒。

---

#### 如何记录过期时间？

Redis 会额外记录一个信息：

```Bash
Key：session:user:1001
值：abc
过期时间：某个绝对时间点
```

Redis 通常不是保存：`还剩 3600 秒`，而是保存：`在 2025-01-01 12:00:00 过期`。

所以 Redis 计算剩余时间时，本质上是：`过期时间 - 当前时间`。

这意味着：

- Redis 重启后仍然可以判断过期时间；

- 系统时间发生变化可能影响过期判断；

- 过期时间本身不是数据的一部分，而是 Key 的额外元数据。

---

#### 设置过期时间的常用方式

|**命令**|**说明**|**示例**|**返回值说明**|
|---|---|---|---|
|SET|新增/修改时设置过期时间|- `SET session:user:1001 abc EX 3600`：3600s 后过期<br>- `SET session:user:1001 abc PX 3600000`：3600s 后过期<br>- `SET lock:order:1001 token NX EX 30`：Key 不存在时设置，设置成功后 30 秒过期||
|EXPIRE|为已有的 Key 设置过期时间|`EXPIRE user:1001 3600`：3600s 后过期||
|PEXPIRE|为已有的 Key 设置过期时间（单位毫秒）|`PEXPIRE user:1001 60000`：60s 后过期||
|EXPIREAT|指定 Unix 时间戳过期时间|`EXPIREAT user:1001 1735732800`||
|PEXPIREAT|指定 Unix 时间戳过期时间（单位毫秒）|`PEXPIREAT user:1001 1735732800000`||
|TTL|查看剩余时间|`TTL user:1001`<br>|大于等于 0：剩余时间<br>`-1`：Key 存在，但没有设置过期时间<br>`-2`：Key 不存在，或者已经过期|
|PTTL|查看剩余时间（单位毫秒）|`PTTL user:1001`|同上|
|PERSIST|取消过期时间|`PERSIST user:1001`||

---

#### 删除 Key 的 2 种方式

##### 惰性删除（访问时检查）

惰性删除也叫**被动删除**。

它的意思是：

> Key 不会一到时间就立即删除，而是等有人访问它时，Redis 顺便检查它是否过期。
> 
> 

例如：

```Bash
SET cache:user:1001 Alice EX 10
```

10 秒之后，Key 的时间已经到了。

但 Redis 不一定立即从内存中删除它。

此时执行：

```Bash
GET cache:user:1001
```

Redis 会检查：是否过期？

如果已经过期：

```Bash
删除 Key
返回 nil
```

结果类似：

```Bash
(nil)
```

###### 优点

1. 不需要一直扫描所有 Key；

2. 访问到过期 Key 时才处理；

3. CPU 消耗较低；

4. 过期判断逻辑简单。

###### 存在的问题

如果某个 Key 过期后一直没人访问：

```Bash
Key 已经过期
但一直没有被读取
```

它可能继续占用内存。

因此 Redis 不能只依赖惰性删除，还需要定期删除。

##### 定期删除

定期删除也叫**主动删除**。

Redis 会周期性地检查一部分设置了过期时间的 Key：

```Bash
随机抽取一批 Key
检查它们是否过期
删除已经过期的 Key
```

Redis 不会每次都扫描全部 Key，因为这样会导致：

1. Key 数量很大

2. 扫描时间很长

3. Redis 主线程被阻塞

所以 Redis 使用抽样方式。

###### 定期删除的大致过程

可以简单理解为：

```Bash
循环执行：
    从设置了过期时间的 Key 中抽取一小批
    删除其中已经过期的 Key
    如果过期比例较高：
        继续检查
    否则：
        暂停本轮检查
    下一段时间再继续
```

Redis 会在后台周期中执行过期检查。

不同 Redis 版本在具体实现上有所优化，但核心思想不变：

> 不扫描所有 Key，而是分批、抽样、周期性清理。
> 
> 

---

### 内存淘汰策略

内存淘汰是指：

> Redis 达到 maxmemory 限制，例如配置：`maxmemory 1gb`，当 Redis 内存达到上限后，它可能根据淘汰策略删除 Key，即使这些 Key 还没有到期。
> 
> 

---

#### 如何配置内存淘汰策略

通过配置：`maxmemory-policy`，可以设置内存不足时如何淘汰。

---

#### 常见策略

##### `noeviction`

不淘汰已有数据。

写入新数据时直接报错：

```Plain Text
OOM command not allowed
```

适合不能随意丢数据的场景，但需要业务自己控制内存。

##### **`allkeys-lru`****（最常用）**

从所有 Key 中淘汰最近最少使用的 Key。

适合纯缓存。

##### **`volatile-lru`****（常用）**

只从设置了过期时间的 Key 中，根据 LRU 淘汰。

```Bash
只有带 TTL 的 Key 可能被淘汰
```

##### **`allkeys-lfu`****（常用）**

从所有 Key 中淘汰访问频率较低的 Key。

适合根据访问频率管理缓存。

##### `allkeys-random`

随机淘汰任意 Key。

##### `volatile-random`

从带 TTL 的 Key 中随机淘汰。

##### `volatile-ttl`

优先淘汰剩余 TTL 较短的 Key。

---

#### 删除过期 Key 的方式

Redis 删除过期数据时，可能涉及较大的数据结构。

例如一个很大的 List、Hash、Set 过期了，删除它可能需要释放大量内存。

Redis 支持异步释放：

```Bash
UNLINK key
```

与：

```Bash
DEL key
```

相比：

- `DEL`：同步删除，释放工作可能阻塞主线程；

- `UNLINK`：先从 Key 空间中移除，实际内存释放尽量放到后台线程。

Redis 还可以通过：

```Bash
lazyfree-lazy-expire yes
```

让过期删除尽量采用异步释放。

不过要注意：

> 异步释放主要减少主线程阻塞，不代表数据在过期后永远立刻释放所有物理内存。
> 
> 

---

### 持久化机制

Redis 默认把数据放在内存中。Redis 重启后，内存数据会丢失，因此需要把数据保存到磁盘。

Redis 主要提供两种持久化方式：

- RDB：定期保存某个时间点的数据快照

- AOF：记录每一次写操作

也可以同时使用：`RDB + AOF`。

---

#### RDB（快照）

RDB 全称是：Redis Database。

RDB 会在某个时间点，把 Redis 当前内存中的数据保存成一个二进制文件。

可以理解为：

```Bash
某一时刻的 Redis 数据状态
                ↓
保存成一个快照文件
                ↓
重启时加载这个快照
```

默认文件名通常是：`dump.rdb`。

例如某一时刻 Redis 中有：

```Bash
user:1 -> Alice
user:2 -> Bob
counter -> 100
```

Redis 会把这些数据保存到 RDB 文件中。

---

##### RDB 如何生成？

Redis 主要通过两种命令生成 RDB 文件。

1. `SAVE`

    `SAVE` 会直接在 Redis 主进程中生成快照。

    执行期间，Redis 主线程会被阻塞：

    ```Bash
    SAVE 开始
    Redis 暂停处理其他命令
    生成 RDB 文件
    SAVE 完成
    Redis 继续处理请求
    ```

    **因此生产环境通常不建议手动执行 ****`SAVE`****，因为数据量较大时可能阻塞 Redis。**

2. `BGSAVE`

    `BGSAVE` 表示后台生成快照。

    大致流程：

    ```Bash
    Redis 主进程
        │
        ├── 创建子进程
        │
        ├── 主进程继续处理客户端请求
        │
        └── 子进程生成 RDB 文件
    ```

    相比 `SAVE`，`BGSAVE` 不会长时间阻塞主线程。

    生产环境通常使用 `BGSAVE` 而不是 `SAVE`。

---

##### RDB 的自动触发配置

Redis 可以根据时间和修改次数自动执行快照。

配置示例：

```Bash
save 900 1
save 300 10
save 60 10000
```

含义是：

```Bash
900 秒内至少修改 1 次，触发快照
300 秒内至少修改 10 次，触发快照
60 秒内至少修改 10000 次，触发快照
```

这些规则是“满足任意一个就触发”。

例如：

```Bash
60 秒内修改超过 10000 次
```

就会触发一次后台快照。

查看当前配置：`CONFIG GET save`。

手动生成后台快照：`BGSAVE`。

查看最近一次保存时间：`LASTSAVE`。

---

##### RDB 的执行过程

使用 `BGSAVE` 时，通常会涉及操作系统的 `fork` 和写时复制机制。

简化流程：

1. Redis 主进程接收 BGSAVE

2. fork 创建子进程

3. 子进程读取当前数据并生成 RDB

4. 主进程继续处理新的请求

5. 子进程写入临时 RDB 文件

6. 写入完成后替换旧 RDB 文件

---

##### 写时复制是什么？

`fork` 后，父进程和子进程最开始可以共享相同的内存页面。

- 父进程：继续处理写请求

- 子进程：读取数据生成快照

如果某块数据没有变化，父子进程可以共享它。

如果主进程要修改某块内存，操作系统会复制这一块：

```Bash
主进程修改数据
        ↓
操作系统复制对应内存页
        ↓
主进程修改副本
子进程继续读取原来的内容
```

这就是写时复制，简称：`COW，Copy On Write`。

因此，RDB 后台保存期间：

- 主 Redis 仍然可以处理请求

- 写入越频繁，复制的内存页越多，大量写入时可能产生较高内存压力

---

##### 优点

1. **文件体积通常较小**

    RDB 是二进制快照，不是每次都记录完整命令，因此文件通常比较紧凑。

    适合：

    - 数据备份；

    - 文件传输；

    - 数据迁移；

    - 灾难恢复。

2. **恢复速度通常较快**

    Redis 加载 RDB 时，直接读取结构化数据。

    如果数据量相同，通常比逐条重放大量 AOF 命令更快。

3. **对运行时性能影响相对较小**

    RDB 不需要每次写操作都追加命令。

    主要开销发生在生成快照时。

4. **适合做定期备份**

    例如：

    ```Bash
    每天保存一个 RDB
    保留最近 7 天
    ```

    如果 Redis 数据被误删，可以从备份文件恢复。

---

##### 缺点

1. **可能丢失最近一段时间的数据**

    假设 RDB 每 5 分钟生成一次：

    ```Bash
    10:00 生成 RDB
    10:04 Redis 宕机
    ```

    那么：

    ```Bash
    10:00 ~ 10:04 的数据可能没有保存
    ```

    Redis 重启后只能恢复到 10:00 的状态。

    因此 RDB 的数据丢失范围，通常取决于快照间隔。

2. **`fork`**** 可能造成额外内存消耗**

    后台生成快照期间，如果写入很多数据，写时复制会产生更多内存页。

    可能导致：

    - 内存峰值升高；

    - 系统内存不足；

    - fork 耗时变长；

    - Redis 延迟升高。

3. **数据量越大，生成快照越耗时**

    虽然主进程可以继续处理请求，但生成快照本身仍然需要：

    - 遍历数据；

    - 序列化数据；

    - 写入磁盘；

    - 进行文件替换。

---

##### 如何处理过期 Key？

RDB 保存数据快照时，过期 Key 不会作为有效数据恢复。

Redis 重启加载 RDB 时，已经过期的 Key 会被忽略。

---

#### AOF（日志）

AOF 全称是：`Append Only File`。

AOF 不保存某个时间点的完整快照，而是记录 Redis 执行过的写命令。

例如执行：

```Bash
SET user:1 Alice
INCR counter
SADD online user:1
```

AOF 会记录这些写操作。

Redis 重启时：

1. 读取 AOF 文件

2. 逐条重新执行写命令

3. 恢复内存数据

> 可以理解为：
> 
> - RDB：保存最终结果
> 
> - AOF：保存产生结果的操作过程
> 
> 

---

##### AOF 记录什么命令？

AOF 主要记录会改变数据的命令，例如：

```Bash
SET
DEL
INCR
HSET
LPUSH
SADD
EXPIRE
```

通常不会记录只读命令，例如：

```Bash
GET
EXISTS
TTL
```

AOF 使用 Redis 的 RESP 协议格式保存命令。

它不是简单的日志文本，但内容通常可以阅读。

---

##### AOF 的同步策略

AOF 是否立即写入磁盘，由配置决定：

```Bash
appendfsync always
appendfsync everysec
appendfsync no
```

这是 AOF 最重要的配置之一。

###### `appendfsync always`

每次写命令都尝试同步到磁盘：

```Bash
写命令
  ↓
追加到 AOF 缓冲区
  ↓
立即 fsync
  ↓
返回
```

优点：

- 数据安全性最高；

- 发生宕机时，丢失的数据非常少。

缺点：

- 每次写都可能触发磁盘同步；

- 性能开销较大；

- 延迟可能明显增加。

适合对数据丢失极其敏感的场景，但也需要评估性能。

###### **`appendfsync everysec`****（常用）**

每秒同步一次：

```Bash
写命令
  ↓
追加到内存缓冲区
  ↓
后台每秒同步到磁盘
```

优点：

- 性能和安全性比较平衡；

- 通常最多可能丢失约 1 秒数据；

- 是比较常见的选择。

缺点：

- Redis 进程或机器突然故障时，可能丢失最近约 1 秒的数据；

- “约 1 秒”不是绝对保证，实际还受操作系统和磁盘影响。

###### `appendfsync no`

Redis 只把数据交给操作系统，不主动调用 `fsync`。

什么时候真正写入磁盘，由操作系统决定。

优点：

- 性能较高；

- Redis 自身磁盘同步开销较小。

缺点：

- 数据丢失时间不可控；

- 可能丢失更多最近数据。

---

##### AOF 的完整写入链路

一次写命令可能经历多个阶段：

```Bash
客户端发送命令
        ↓
Redis 执行命令，修改内存
        ↓
写入 AOF 缓冲区
        ↓
写入操作系统页缓存
        ↓
fsync 持久化到磁盘
```

这里要区分：

```Bash
写入 Redis 内存
写入 AOF 缓冲区
写入操作系统缓存
真正落盘
```

只有真正落盘后，机器突然断电时才更有保障。

---

##### AOF 重写是什么？

AOF 会不断追加命令，所以文件可能越来越大。

例如：

```Bash
SET counter 1
INCR counter
INCR counter
INCR counter
```

这些命令最终只是：

```Bash
counter = 4
```

如果一直记录所有历史操作，AOF 会包含大量冗余命令。

因此 Redis 会执行 AOF 重写：

```Bash
根据当前内存数据，重新生成一份更短的 AOF
```

原来的操作：

```Bash
SET counter 1
INCR counter
INCR counter
INCR counter
```

重写后可能变成：

```Bash
SET counter 4
```

---

###### AOF 自动重写配置

常见配置：

```Bash
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

大致含义：

```Bash
当前 AOF 文件大小，相比上次重写后增长超过 100%
并且文件至少达到 64 MB
```

就触发自动重写。

例如：

```Bash
上次重写后：100 MB
当前 AOF：201 MB
```

增长超过 100%，满足条件后就可能触发重写。

查看 AOF 状态：

```Bash
INFO persistence
```

可以关注：

```Bash
aof_enabled
aof_current_size
aof_base_size
aof_rewrite_in_progress
aof_last_rewrite_time_sec
```

---

###### 手动触发 AOF 重写

可以通过命令 `BGREWRITEAOF` 手动触发 AOF 重写。

通常不会直接修改旧 AOF 文件，而是：

1. 创建新的临时 AOF

2. 根据当前内存数据写入临时文件

3. 重写期间继续接收新的写命令

4. 新命令暂时保存到重写缓冲区

5. 重写完成后把增量命令追加到新 AOF

6. 用新 AOF 替换旧 AOF

这样可以尽量避免重写期间丢失新的写操作。

---

##### 如何处理过期 Key？

如果 Key 到期，Redis 会生成类似删除操作的内容：

```Bash
DEL expired:key
```

这样重启后可以保持相同结果。
