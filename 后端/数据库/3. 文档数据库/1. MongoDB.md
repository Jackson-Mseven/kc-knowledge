# MongoDB 建模、查询与集群

MongoDB 以 BSON 文档作为主要读写单位，适合数据天然围绕聚合根组织、一次请求通常读取完整对象的场景。它允许灵活结构，但不等于没有 Schema：字段约束、索引、版本迁移和数据质量仍需显式设计。

## 文档边界

单文档写入具有原子性，因此建模首先决定哪些数据必须一起变化。

| 选择 | 适合 | 主要风险 |
| --- | --- | --- |
| 嵌入 | 子对象数量有界、生命周期一致、经常随父对象读取 | 文档膨胀、热点更新、数组无限增长 |
| 引用 | 实体共享、独立查询或更新、关系数量无界 | 额外查询、应用层 Join、跨文档一致性 |

文档最大为 16 MiB；评论、流水等无界集合不应长期追加到同一数组。可以把高频摘要嵌入父文档，同时用独立集合保存完整明细，但要明确哪个副本权威以及如何修复不一致。

`$jsonSchema` 验证适合约束必填字段、BSON 类型和枚举；应用发布时采用向前兼容迁移，避免新旧实例同时运行时互相写入无法读取的数据。验证规则不能替代唯一索引等并发约束。

## 索引与查询

- 复合索引的字段顺序应同时服务等值过滤、排序和范围条件；用 `explain("executionStats")` 比较返回文档数与扫描键/文档数。
- 数组字段会产生 multikey 索引项；单个复合 multikey 索引不能同时索引同一文档中的多个数组字段，数组过大会放大索引与更新成本。
- Projection 可减少网络与解码成本，但只有查询字段全部被索引覆盖时才避免读取文档。
- 聚合管道应尽早 `$match`、限制字段和结果量。`$lookup`、全局排序及溢写磁盘会放大延迟，不能把管道当作无成本的关系查询层。
- 深分页避免反复使用大 `skip`，优先基于稳定排序键和 `_id` 做游标分页。

TTL 索引适合自动清理会话、临时结果等过期数据；清理是后台异步进行，不能把过期时间当作精确调度或立即不可见的安全边界。

## 事务与一致性选项

多文档事务需要 Replica Set 或 Sharded Cluster。它提供必要的一致性边界，但会持有更多资源、增加冲突与重试成本；如果大多数写入长期依赖跨集合事务，应重新评估聚合边界或关系模型。

一致性由多个选项共同决定：

- `writeConcern` 决定写入需要多少成员确认；`w: "majority"` 以多数派持久确认为常见可靠性边界。
- `readConcern` 决定读取允许看到什么状态；读取副本还受 `readPreference` 影响，可能读到旧数据。
- 驱动可能重试可重试写入或事务；业务操作仍需幂等，因为网络超时无法证明服务端未提交。

## Replica Set 与 Sharding

Replica Set 由 Primary 接收写入，Secondary 通过 oplog 复制，并在多数成员可达时选举新 Primary。副本解决节点故障和读扩展，不是备份：误删和错误更新也会被复制。

Sharded Cluster 由 `mongos` 路由、Config Server 保存元数据、多个 Shard 保存数据。分片键决定数据分布和查询是否能定向到少数分片：

- 范围分片支持区间查询，但单调增长键可能把写入集中到末端 Chunk；
- Hashed 分片通常分布更均匀，但范围查询可能广播；
- 不包含分片键的查询可能成为 Scatter-Gather，跨分片事务与全局排序也更昂贵。

备份必须得到一致的集群视图，并保留恢复所需的 oplog；恢复不仅要验证文档数量，还要验证索引、用户权限、分片元数据和应用可读性。
