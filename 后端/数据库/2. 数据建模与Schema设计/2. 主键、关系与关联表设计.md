# 主键、关系与关联表设计

## 主键策略

内部主键负责稳定标识行，业务编号负责对外展示，两者应分离。自增整数紧凑且写入局部性好；UUID 适合分布式生成但索引更大；有序 ID 需评估时钟、泄露与热点。主键不可频繁修改。

## 关系表达

一对一常由唯一外键表达；一对多由子表外键表达；多对多使用关联表。关联表不只是两列 ID：若关系本身有时间、角色、排序或状态，它就是独立实体，应有主键、约束与审计字段。

```sql
CREATE TABLE user_roles (
  user_id BIGINT NOT NULL,
  role_id BIGINT NOT NULL,
  granted_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (user_id, role_id)
);
```

## 外键与级联

外键防止引用不存在的数据。`CASCADE` 仅适合明确拥有关系的从属数据；订单、支付、审计记录等不应因删除用户而被隐式删除。高并发或跨服务场景可不使用物理外键，但必须有等价的引用校验和清理流程。

## 查询与索引

外键列通常需要索引，以支持 Join、删除检查和按父实体查询。多对多表的主键列顺序应匹配主要查询方向，反向访问可补充索引。

## 面试自测

1. 为什么多对多不能用逗号分隔 ID？

它无法可靠约束、索引、Join、删除单个关系和记录关系属性，且会破坏原子性。
