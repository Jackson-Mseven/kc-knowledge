# OLTP、OLAP、HTAP 与系统选型

数据库选型首先区分工作负载。把交易请求和大规模分析放到同一套未经设计的表与实例上，通常会让两类任务彼此拖慢。

## 三类工作负载

| 模式 | OLTP | OLAP | HTAP |
| --- | --- | --- | --- |
| 全称 | Online Transaction Processing | Online Analytical Processing | Hybrid Transactional/Analytical Processing |
| 查询形态 | 少量行、按键读写、短事务 | 大量扫描、聚合、分组 | 事务与分析在同一数据体系协同 |
| 关注指标 | 延迟、一致性、并发写入 | 吞吐、扫描效率、分析延迟 | 隔离、资源治理、同步延迟 |
| 常见存储 | MySQL、PostgreSQL | ClickHouse、BigQuery、数仓 | TiDB、混合架构或副本分析 |
| 典型场景 | 下单、支付、库存 | 日报、漏斗、用户画像 | 近实时运营看板 |

OLTP 表通常按业务实体组织并重视约束；OLAP 适合面向分析的列式、分区和预聚合模型。不要为了“实时”让复杂 BI 查询直接压在生产主库上。

## 选型过程

1. 写出数据实体、主键、唯一性、更新原子性与审计需求；
2. 收集真实读写模式：按主键、范围、Join、全文搜索、聚合或向量检索；
3. 估计峰值 QPS、数据增长、冷热比例、单行大小和保留期限；
4. 明确一致性、RPO、RTO、地域、合规和预算；
5. 优先使用团队能维护的单一权威数据库，再以测得的瓶颈引入专项存储；
6. 在接近生产的数据分布、并发和故障条件下压测与演练。

## 一个订单系统的组合

```text
API -> PostgreSQL/MySQL: 订单、付款、库存的权威事务数据
       -> Outbox/CDC -> Redis: 热点读与限流的可失效缓存
                      -> Search: 商品与订单检索索引
                      -> Warehouse: 报表和离线分析
```

写入路径必须先清楚定义权威库的提交结果。下游通过可重放事件更新，并准备去重、重试、对账和全量重建。

## HTAP 的取舍

HTAP 减少数据搬运和分析延迟，但不能消除资源竞争。评估时需确认：分析是否会影响事务 p99、是否有列式副本/隔离资源、数据同步延迟是否符合业务，以及团队能否诊断混合负载。对于多数中小系统，“OLTP 主库 + 异步分析副本/数仓”更容易控制风险。

## 选型检查清单

- 强约束、Join、多行原子更新：优先 MySQL/PostgreSQL；
- 聚合文档在边界内整体读写：评估 MongoDB；
- 全文相关性、分词和复杂检索：评估搜索引擎；
- 高基数实时分析：评估列式分析数据库；
- 明确多跳路径查询：评估图数据库；
- 不要因“未来可能很大”提前上分片或多数据库。

## 面试自测

1. 为什么 OLTP 与 OLAP 常分离？

OLTP 需要稳定的短事务延迟与写入正确性，OLAP 会扫描和聚合大量数据。分离可以隔离资源、采用不同存储布局，并避免报表影响核心交易。

2. 什么情况下应引入第二种数据库？

只有权威库通过正确 Schema、索引、缓存和读副本仍无法经济地满足明确访问模式时，例如全文搜索或大规模分析；引入后必须承担同步和一致性成本。
