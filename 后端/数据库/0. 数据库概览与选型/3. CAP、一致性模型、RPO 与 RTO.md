# CAP、一致性模型、RPO 与 RTO

分布式数据库设计需要区分多个同名但不同层次的概念：ACID 的一致性、CAP 的一致性，以及业务可接受的数据丢失与恢复时间都不是一回事。

## CAP 的正确理解

CAP 讨论的是发生网络分区（Partition）时，分布式系统对一致性（Consistency）和可用性（Availability）的取舍。

- **C**：所有非故障副本对同一读取返回一致结果；
- **A**：每个到达非故障节点的请求都能获得非错误响应；
- **P**：节点间网络分区或消息无限延迟仍被视为可能发生。

网络分区无法被实际系统彻底排除，所以关键问题不是“选 CP 还是 AP”，而是分区期间哪些操作必须拒绝或等待，哪些读取可接受陈旧，以及网络恢复后如何收敛。

## 常见一致性语义

| 语义 | 含义 | 适用示例 |
| --- | --- | --- |
| 线性一致性 | 成功写入后，后续读取看到该结果 | 余额、库存、权限变更 |
| 读己之写 | 用户提交后应看到自己的提交 | 发布内容后的详情页 |
| 单调读 | 同一会话不会从新版本回退到旧版本 | 多次刷新订单状态 |
| 最终一致性 | 副本在一段时间后收敛 | 搜索索引、异步统计 |
| 因果一致性 | 有因果关系的更新按因果顺序可见 | 评论与回复、协作状态 |

选择语义时要把体验写成可测试的规则，例如“下单后 30 秒内订单列表读主库”比“尽量一致”更可实现。

## RPO 与 RTO

- **RPO（Recovery Point Objective）**：故障后最多允许丢失多长时间的数据；
- **RTO（Recovery Time Objective）**：故障后最多允许多长时间恢复服务。

若支付系统 RPO 为零或接近零，就需要更严格的同步复制、日志与切换设计；若 RTO 为 15 分钟，则恢复流程、容量、演练结果都必须能证明该目标，而不是只依赖备份任务显示成功。

## 设计示例

```text
订单创建：主库本地事务提交 -> 返回订单号
订单搜索：异步写入搜索索引 -> 短暂不可见时回退订单详情
订单列表：写后会话粘滞读主库 -> 其他列表可读副本
```

这种设计把强一致性放在关键事务路径，把可延迟部分交给派生系统，并显式处理降级体验。

## 不要混淆的概念

- ACID 中的 Consistency 是业务约束在事务前后的成立；
- CAP 中的 Consistency 是多个副本的可观察读写顺序；
- 高可用是服务继续提供能力，不等于没有数据丢失；
- 复制减少故障影响，不等于独立备份；
- “最终一致”必须包含触发同步、重试、去重、观测与对账，而不是一句口号。

## 面试自测

1. CAP 是否表示系统只能同时拥有其中两个属性？

不是。CAP 的取舍只在网络分区期间出现；正常情况下系统可以同时提供一致读写和高可用。现实设计要说明分区时如何处理。

2. 主从复制为什么不能保证 RPO 为零？

异步复制下主库已确认的数据可能尚未到达副本就故障；即使同步复制，也要明确确认副本数量、故障模型和切换策略。
