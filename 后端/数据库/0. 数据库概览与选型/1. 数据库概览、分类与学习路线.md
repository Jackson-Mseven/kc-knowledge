# 数据库概览、分类与学习路线

数据库负责以可恢复、可查询、可并发控制的方式保存数据。学习数据库时，应先从数据模型和访问模式出发，而不是从某个产品的命令开始。

## 数据库承担的职责

- **持久化**：进程、主机或局部硬件故障后，已确认的数据可以恢复；
- **完整性**：用主键、唯一、外键和检查约束维持可验证的事实；
- **查询**：由索引、优化器和执行器以可接受成本返回结果；
- **并发控制**：让并发读写在明确的隔离与一致性规则下执行；
- **可靠性**：通过日志、复制、备份和演练降低数据丢失风险。

数据库不是业务逻辑的唯一位置。密码强度、余额上限、权限等规则应由服务端校验；其中可表达为数据不变量的部分，再由数据库约束兜底。

## 常见类别

| 类别 | 核心模型 | 常见产品 | 适合的问题 | 主要边界 |
| --- | --- | --- | --- | --- |
| 关系型数据库 | 表、关系、SQL | MySQL、PostgreSQL | 订单、支付、账户、库存 | Schema 和索引需认真设计 |
| 文档数据库 | 文档/BSON | MongoDB | 聚合文档、配置、内容 | 跨文档关系与一致性成本 |
| 缓存/Key-Value | Key 对 Value | Redis | 热读、会话、限流、计数 | 不天然替代权威数据源 |
| 搜索引擎 | 倒排索引 | Elasticsearch、OpenSearch | 全文检索、相关性排序、日志搜索 | 通常是派生索引 |
| 时序数据库 | 时间序列与标签 | TimescaleDB、InfluxDB | 指标、遥测、时间窗口分析 | 标签基数和保留期影响成本 |
| 分析型数据库 | 列式/MPP | ClickHouse、BigQuery | 大范围扫描、报表、BI | 不适合高频小事务 |
| 图数据库 | 节点和边 | Neo4j | 多跳关系、路径查询 | 通用业务生态较小 |

一个系统可以组合多种存储，但每类数据都要明确唯一的**权威来源**。例如订单主数据在关系库，搜索引擎索引和 Redis 缓存均是可重建的派生数据。

## 学习顺序

1. 从 [[后端/数据库/1. SQL/1. SQL 基础|SQL 基础]] 掌握关系表、DDL、DML 和查询条件；
2. 通过 [[后端/数据库/1. SQL/2. SQL 进阶|SQL 进阶]] 建立聚合、Join、子查询和窗口计算的集合思维；
3. 学习 [[后端/数据库/1. SQL/3. SQL 优化|SQL 优化]]，把索引、执行计划和表结构与实际成本关联起来；
4. 学习 [[后端/数据库/2. 关系型数据库/Mysql/3. 事务与隔离级别|MySQL 事务与并发控制]]，理解数据库如何保证并发正确性；
5. 深入具体产品：[[后端/数据库/2. 关系型数据库/Mysql/1. MySQL架构与执行原理|MySQL/InnoDB]]、[[后端/数据库/2. 关系型数据库/PostgreSQL/1. PostgreSQL、扩展类型与运维要点|PostgreSQL]]、[[后端/数据库/0. 数据库概览与选型/5. 专项数据库概览与选型|专项数据库]]；
6. 最后掌握迁移、备份、监控、扩展和故障演练。

## 生产中的最小闭环

```text
业务不变量 -> Schema 与约束 -> 参数化 SQL -> 索引与计划
  -> 短事务与幂等 -> 迁移/备份 -> 指标/告警 -> 恢复演练
```

缺少其中任何一环都可能造成问题：只写出查询而没有索引会慢；只依赖应用校验会发生并发竞态；有备份但不演练无法证明能恢复。

## 常见误区

- 把“关系型”理解成只能存结构化、固定字段的数据；关系库也可管理 JSON 等扩展数据，但高频关系查询仍应建模；
- 因为字段变化快就立即选 NoSQL，而不先分析是否需要关联查询、唯一性和多记录原子更新；
- 让应用同时写主库、缓存和搜索索引，却没有 Outbox/CDC、重试和重建路径；
- 把主从复制当成备份，忽略误删和逻辑错误会复制到副本。
