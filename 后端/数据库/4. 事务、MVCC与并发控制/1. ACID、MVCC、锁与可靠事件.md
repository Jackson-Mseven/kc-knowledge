# ACID、MVCC、锁与可靠事件

事务把一组读写作为业务单元提交或回滚。ACID 只提供基础保证，库存、扣款和重复请求仍需要约束、条件更新、锁和幂等方案共同实现。

## ACID 与隔离

原子性依赖回滚机制；持久性依赖 WAL/Redo 等日志；隔离性通过 MVCC 与锁降低不当并发影响；一致性要求提交前后满足约束与业务不变量。READ COMMITTED、REPEATABLE READ、SERIALIZABLE 的具体行为受数据库实现和查询形式影响，关键流程必须并发测试。

MVCC 让普通读取通常看到一致快照，不代表没有锁。写入、锁定读、唯一检查和范围操作仍可能等待；长事务会阻止旧版本清理、增加锁持有和复制延迟。

## 正确的并发写入

```sql
UPDATE inventory
SET available = available - ?
WHERE sku_id = ?
  AND available >= ?;
```

检查影响行数：一行表示扣减成功，零行表示库存不足或并发状态已变化。它优于先读取再更新。编辑类低冲突场景可用版本号乐观锁；必须串行化时使用短事务与精确 `FOR UPDATE`。

## 死锁与幂等

死锁由循环等待产生，数据库通常回滚其中一个事务。应用应限定次数地重试可恢复错误，并统一加锁顺序、缩短事务、建立合适索引。网络重试和消息重复则用幂等键、唯一约束或去重表防止重复副作用。

## Outbox

业务数据和待发事件在同一数据库事务内写入，后台再投递事件。消费者依据事件 ID 幂等，处理至少一次投递、积压、重试和重放。这比业务代码直接双写数据库与消息系统可靠。

## 面试自测

1. 为什么不能在事务中调用远程服务？

网络调用会拉长锁和版本保留时间，放大阻塞与死锁；应先提交本地事务，再用 Outbox 或补偿处理外部副作用。

2. 乐观锁何时不合适？

热点高冲突下持续重试会浪费吞吐，可能需要队列、分片或短时间悲观锁。
