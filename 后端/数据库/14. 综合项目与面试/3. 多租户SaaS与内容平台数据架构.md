# 多租户 SaaS 与内容平台数据架构

这两个案例分别展示“隔离边界”和“多存储协作”：前者先保证租户数据不能串读，后者先明确关系库、搜索与缓存谁是权威来源。

## 多租户 SaaS

| 模式 | 隔离与成本 | 适用边界 |
| --- | --- | --- |
| 每租户独立数据库 | 隔离、备份和定制最强；连接与迁移成本最高 | 高价值、强合规或超大租户 |
| 每租户独立 Schema | 共享实例，逻辑隔离较清晰；大量 Schema 迁移复杂 | 租户数中等、数据库原生支持完善 |
| 共享表 | 成本最低、统一迁移；最容易串租户且热点共享 | 大量中小租户、隔离要求可由多层控制满足 |

共享表中的所有租户数据表都应带可信上下文注入的 `tenant_id`。唯一约束和主要索引也要包含租户维度，例如 `(tenant_id, external_id)`；否则不同租户会互相占用业务键，查询也难以稳定定位租户范围。

应用不能接受客户端传入的租户 ID 后直接查询，而应从认证会话得到租户上下文。PostgreSQL Row-Level Security 等数据库策略可作为纵深防御，但后台任务、管理员连接和连接池会话变量必须显式测试，不能用它代替应用授权。

大租户可能形成热点，可将其迁入独立库并维护租户路由。迁移需要双读/双写或停写窗口、校验与回滚。导出、删除、备份恢复和审计都必须以租户为单位可执行，否则逻辑隔离无法满足数据生命周期要求。

## 内容平台的存储职责

| 组件 | 保存内容 | 一致性定位 |
| --- | --- | --- |
| 关系库 | 内容元数据、作者、权限、发布状态和版本 | 权威数据源 |
| 对象存储 | 图片、视频和大文件 | 由数据库保存对象键与状态 |
| 搜索索引 | 分词、相关性、过滤和聚合字段 | 可重建派生数据 |
| 缓存 | 热门详情、计数或权限结果 | 有界陈旧、可失效派生数据 |

发布内容时先在主库事务中更新状态并写 Outbox，再异步更新搜索和缓存。用户刚发布后的详情读取可走主库或 Session 一致性；搜索允许短暂延迟，并向产品明确新鲜度 SLO。搜索同步和重建机制见 [[后端/数据库/4. 搜索与索引数据库/2. 搜索索引同步与重建|搜索索引同步与重建]]。

缓存采用 Cache-Aside 时，写库成功后删除缓存；删除失败需依靠重试、事件或较短 TTL 收敛。缓存只存可重建结果，权限数据若缓存必须把用户/租户和权限版本纳入 Key。缓存实现见 [[后端/缓存/00. 目录|缓存目录]]。

搜索索引映射变化或数据损坏时，从权威库构建带版本的新索引，校验数量与抽样结果后原子切换别名；不要在原索引上做无法回滚的全量覆盖。异步链路持续对账主库版本和索引版本，删除事件也必须传播。
