# 交易系统：订单、库存、支付与秒杀

交易系统的核心不是“绝不失败”，而是在重复、超时、并发和局部故障下仍保持不超卖、不重复记账、状态只能合法迁移，并能对账恢复。

## 数据与不变量

| 数据 | 核心约束 |
| --- | --- |
| 订单 | 唯一业务单号；状态只能按状态机迁移；金额保存下单快照 |
| 库存 | 可售量不能为负；每次预占/释放可追溯且不能重复 |
| 支付 | 第三方交易号唯一；账本追加记录；回调可重复处理 |
| Outbox | 与业务变更同一事务写入；事件 ID 唯一；消费者幂等 |

订单表保存商品名称、单价、优惠和收货信息快照，避免商品或地址后续变化改写历史订单。支付记录与订单状态分开：一次订单可能有多次支付尝试、退款和渠道回调。

## 库存与状态迁移

条件更新把校验和写入放在一个原子操作中：

```sql
UPDATE inventory
SET available = available - :quantity,
    version = version + 1
WHERE sku_id = :sku_id
  AND available >= :quantity;
```

受影响行数为 0 表示库存不足或记录不存在。订单状态也应携带旧状态条件，例如只允许 `PENDING -> PAID`；不能先读状态再无条件更新，否则并发请求会越过状态机。

库存操作还需唯一业务键，例如 `(order_id, sku_id, operation)`，保证超时重试不会重复预占或释放。高竞争时可按 SKU 串行排队或分桶，但最终账本/数据库约束仍是正确性来源。

## 支付与跨服务事件

支付回调先以渠道交易号和请求摘要做幂等，再在短事务中写支付流水、条件更新订单并写 Outbox。事务提交后异步发布事件；消费者按事件 ID 去重。不要在数据库事务中调用支付渠道，也不要用“先提交订单，再尽力发消息”的双写。

客户端超时表示结果未知，不等于支付失败。查询接口应能按业务单号返回已完成结果；对账任务比较渠道账单、支付流水和订单状态，发现差异后走补单/退款流程，而非直接手改状态。

MySQL 的事务与并发机制见 [[后端/数据库/2. 关系型数据库/Mysql/3. 事务与隔离级别|MySQL 事务与并发控制]]；幂等和 Outbox 见 [[后端/数据库/8. 分布式数据库与水平扩展/3. 分布式事务与可靠消息|分布式事务与可靠消息]]。

## 秒杀链路

```text
身份/资格校验 -> 按用户和商品限流 -> 有界排队
-> 库存预占 -> 幂等创建订单 -> 超时未支付释放 -> 对账
```

入口限流防止无效请求进入核心链路，队列将突发流量变成数据库可承载的速率。缓存可快速返回活动信息或近似余量，但不能独自决定最终库存；缓存与数据库之间存在失败窗口时，以条件扣减或可审计预占账本为准。

预占必须有过期时间和唯一预占 ID。取消与支付可能并发，应通过状态条件更新保证只有一个分支生效。队列积压、预占未释放、重复消费和数据库故障都应有明确补偿与对账路径。
