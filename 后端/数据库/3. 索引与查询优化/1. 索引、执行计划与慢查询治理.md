# 索引、执行计划与慢查询治理

索引以额外空间、写入和维护成本换取更少的数据页访问。优化不是“让 SQL 用索引”，而是验证查询在真实数据分布下扫描更少行、等待更少资源。

## 索引设计

B+Tree 是关系型数据库的常见索引结构。复合索引 `(tenant_id, status, created_at)` 通常支持从 `tenant_id` 开始的连续条件；列顺序要综合等值过滤、范围、排序、选择性和返回列。

覆盖索引可避免回表，但不应为覆盖所有字段而把索引膨胀成另一张表。每新增索引都会增加插入、更新、删除、备份和统计成本。

## 可检索条件

避免在索引列上使用函数、隐式类型转换和前置通配符：

```sql
WHERE created_at >= ? AND created_at < ?
WHERE phone = ?
```

这通常比 `DATE(created_at) = ?` 或数字与字符串混比更容易走范围索引。包含搜索应使用倒排索引、全文检索或专项搜索服务。

## 执行计划

使用 `EXPLAIN` 或支持时的 `EXPLAIN ANALYZE` 检查：扫描行数、预估与实际差距、Join 策略、临时排序、回表、锁等待和缓存命中。小表全表扫描可能是最优计划，不能机械地把它判为问题。

## 治理闭环

```text
慢请求 -> 定位 SQL 与参数 -> 计划和指标 -> 假设 -> 小范围修改
-> 基准/压测 -> 灰度 -> 监控回归或回滚
```

深分页改用 Cursor；批量作业按主键分批；大表 DDL 先做锁与耗时评估。详见 [[后端/数据库/1. 关系模型与SQL/5. 查询基础：过滤、排序、分页与聚合|查询基础]]。

## 面试自测

1. 为什么范围条件后面的索引列不一定完全失效？

是否用于过滤或排序取决于具体谓词、索引、优化器和执行计划；“范围后失效”只是过度简化的口诀。

2. 慢 SQL 的第一步是什么？

收集完整 SQL 形态、参数分布、调用频率、计划、实际行数和锁/资源指标，再决定改 SQL、索引、事务还是容量。
