# SQL 审查、N+1 与数据访问边界

应用代码的复杂度不能掩盖数据库成本。代码审查需要同时检查 SQL 数量、参数、执行计划、事务范围和结果集规模。

## N+1 查询

N+1 指先查一批父记录，再为每条父记录单独查询关联数据：父记录数量增长时，数据库往返和查询数线性增长。常见来源是懒加载、循环内 Repository 调用和 GraphQL 字段解析。

可选修复方式各有边界：

- Join 一次取回：往返少，但多个一对多关联会产生笛卡尔式行膨胀；
- 预加载：先查父记录，再按父键集合分批查询子记录，通常是稳定折中；
- DataLoader/批处理：在一个请求窗口合并相同实体查询，并按请求隔离缓存；
- 聚合或投影：只取接口所需字段，避免加载完整对象图。

测试应断言查询数上限，并在接近生产的父子基数下检查总返回行数和 p95。仅看单条 SQL 是否命中索引无法发现 N+1。

## 生成 SQL 审查

对热点路径开启受控 SQL 日志或指标，按查询指纹观察调用次数、总耗时和扫描行数。审查时确认：

- 过滤、Join、排序与分页能否使用预期索引；
- ORM 是否隐式选择大字段、重复 Join、逐行更新或执行额外计数；
- 参数类型是否导致隐式转换，空数组、`NULL` 和时区是否符合语义；
- 批量写是否分块并受事务、锁和参数数量限制；
- 生产数据倾斜下估算行数是否仍接近实际行数。

具体执行计划分析见 [[后端/数据库/1. SQL/3. SQL 优化|SQL 优化]]。

## Repository 与 Unit of Work

Repository 应以业务聚合和查询意图提供接口，例如 `reserveInventory`，而不是机械复制每张表的 CRUD。它隐藏持久化实现，但不能隐藏事务是否已提交、读取一致性和批量行为。

Unit of Work 追踪一组变更并在一个事务中提交。边界通常与一个业务用例一致；跨服务长事务应改为本地事务加事件/补偿。简单查询无需叠加 Repository、DAO、Service 多层转发，抽象只有在隔离变化或表达业务语义时才有价值。

## 原生 SQL 的边界

窗口函数、递归 CTE、批量更新、锁提示或数据库特有能力可使用原生 SQL。值使用绑定参数；表名、列名和排序方向等标识符不能通过值参数化，必须从固定白名单映射。返回列应映射为明确类型，并为热点 SQL 保留计划和集成测试。

原生 SQL 不是“绕过安全”的许可。事务句柄、超时、取消、权限和审计规则应与 ORM 查询一致。
