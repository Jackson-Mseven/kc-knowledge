# ORM 机制、选型与 Schema 迁移

ORM 将数据库行、关系和查询映射为语言对象或类型化 API，减少参数绑定和结果转换样板。它不替代关系建模、事务、索引和执行计划。

## 核心机制

ORM 常组合以下能力：

- 模型/Schema 定义与数据库类型映射；
- 查询构造、参数化、结果映射和关联加载；
- 事务 API、连接管理和迁移生成；
- Identity Map、Dirty Checking、Active Record 或 Data Mapper 等对象生命周期机制。

对象图与关系集合并不等价。对象关联的懒加载可能隐式查询，级联保存/删除可能扩大事务范围，数据库默认值、触发器和计算列也可能让内存对象短暂过期。关键路径要确认实际 SQL、事务边界和返回行数。

## Node.js 常见方案

| 工具 | 模型 | 主要特点 | 主要边界 |
| --- | --- | --- | --- |
| Prisma | Schema 驱动、生成类型化 Client | 类型体验、关系查询和迁移工具完整 | 复杂 SQL/数据库特性常需 `$queryRaw`，生成层增加构建与调试环节 |
| Drizzle | TypeScript Schema + SQL 风格查询 | 接近 SQL、类型推导直接、抽象较薄 | 高层领域模式和部分生态能力需自行组织 |
| TypeORM | Data Mapper/Active Record | 装饰器实体、关系和成熟功能较多 | 隐式行为较多，复杂关系和迁移需严格审查 |
| Sequelize | Model/Active Record 风格 | 历史生态成熟、多方言支持 | 类型体验和抽象复杂度取决于版本与用法，生成 SQL 仍需检查 |

详细 API 与功能对比见 [[前端/Node/ORM/00. 目录|Node ORM 目录]]。选型应以数据库支持、SQL 可控性、迁移策略、类型安全、调试能力和团队经验为维度，而非只看 CRUD 代码量。

## 事务与关联加载

同一事务内的所有操作必须使用同一事务句柄/连接，禁止在回调中误用全局 Client。事务回调应短且无外部 IO；自动重试事务时，回调中的消息发送、邮件等副作用可能重复，应改用 [[后端/数据库/8. 分布式数据库与水平扩展/3. 分布式事务与可靠消息|Outbox 或幂等机制]]。

加载关联有三种常见策略：Join 一次查询、预加载分批查询、按需懒加载。Join 可能因一对多产生行膨胀，分批加载增加往返，懒加载容易形成 N+1；应根据基数与访问路径选择，而不是全局固定一种策略。

## Schema 迁移

迁移文件应进入版本控制并由同一流水线顺序执行。自动生成只负责产生候选差异，仍需审查锁表、数据重写、默认值、索引构建和回滚影响；生产环境不应使用会按实体定义直接“同步”并删除列的开发模式。

应用与 Schema 跨版本发布采用 Expand-Migrate-Contract：先新增兼容结构，再发布双写/回填和切读代码，验证后才删除旧结构。长时间 DDL、回填和恢复方法见 [[后端/数据库/9. 高可用、备份与数据可靠性/00. 目录|高可用、备份与迁移]]。

迁移状态表不是唯一事实：还要检测实际 Schema 与迁移历史的漂移，尤其是人工热修、分支合并和多服务共用数据库的场景。
