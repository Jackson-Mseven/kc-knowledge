# 数据库测试与 API 数据契约

Mock 只能验证应用分支，不能证明 SQL、约束、事务、锁、权限和迁移正确。数据库边界至少需要真实引擎的集成测试。

## 测试层次

| 测试 | 验证内容 |
| --- | --- |
| 单元测试 | 纯领域规则、错误映射、查询构造器输入 |
| Repository 集成测试 | SQL 结果、约束、类型、事务和权限 |
| 迁移测试 | 空库升级、上一版本升级、回滚/前滚兼容、数据回填 |
| 并发测试 | 条件更新、锁、死锁重试、幂等和唯一约束 |
| 性能回归 | 查询数、计划、扫描行数和关键路径延迟 |

测试应使用与生产相同主版本的临时数据库或容器，执行真实迁移并准备最小但有边界的数据。每个测试外层事务回滚很快，但无法覆盖提交后约束、异步消费者、连接切换和多事务并发；这些场景需显式提交并清理独立数据。

固定共享测试库会产生顺序依赖。优先使用每套测试独立 Schema/数据库、唯一业务键和确定性时间；涉及时区、排序规则、`NULL`、大数与小数精度时必须有边界样例。

## 幂等写契约

客户端为一次业务意图提供 `idempotency_key`，服务端将它与租户/调用方、请求摘要、处理状态和最终响应一起持久化。幂等记录与业务写入必须处在同一事务或具备等价原子性：

- 同 Key、同请求：返回首次结果；
- 同 Key、不同请求摘要：拒绝，防止错误复用；
- 首次处理中：等待、轮询或返回明确状态；
- 失败是否允许重试：按是否产生业务副作用定义，不能只看 HTTP 连接是否断开。

唯一约束是最后一道并发防线。进程内锁在多实例或重启后不能保证幂等。

## 分页契约

Offset 分页适合小数据和可随机跳页，但深分页扫描成本高，且并发插入会导致重复/遗漏。Cursor 分页应基于稳定、唯一的排序键，例如 `(created_at, id)`：下一页条件与排序方向严格对应，并把游标编码为不透明值。

相同过滤条件、排序规则和权限范围必须绑定到游标；仅用非唯一时间戳会丢失同一时刻的记录。总数查询可能比取一页更贵，API 应明确总数是精确、估算还是不返回。

## 错误与重试

驱动错误应在边界层映射为稳定业务错误，同时保留原始 SQLSTATE、约束名和 Trace ID 供日志诊断：唯一/外键/检查约束通常映射为冲突或无效输入，未找到不是数据库异常，连接中断或故障切换可映射为临时不可用。

只有幂等操作才能自动重试瞬时错误；死锁和序列化失败需从事务起点重放。不要向客户端暴露 SQL、表结构或敏感参数，也不要把所有数据库异常统一成可重试的 500。
