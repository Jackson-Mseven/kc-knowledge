# 数据集成：ETL、ELT、CDC 与流批处理

数据集成负责把来源数据可靠地搬运、转换并交付给下游。核心问题不是工具名称，而是事务边界、顺序、重复、Schema 变化和失败恢复。

## ETL、ELT 与处理时效

| 模式 | 转换位置 | 更适合 |
| --- | --- | --- |
| ETL | 在进入目标系统前转换 | 目标资源有限、写入前必须脱敏或强校验 |
| ELT | 先加载原始数据，再由分析平台转换 | 计算与存储可扩展、需要保留原始数据和灵活重算 |
| 批处理 | 对有界数据集按分区或时间运行 | 全量汇总、历史回填、允许分钟到天级延迟 |
| 流处理 | 持续处理无界事件 | 告警、实时指标、分钟或秒级数据新鲜度 |

流处理按事件时间计算时需处理乱序和迟到事件。Watermark 表示系统认为大多数事件已到达的进度，它决定窗口何时产出及迟到数据如何修正；实时结果通常是暂时值，需与离线结果定义最终收敛规则。

## CDC 的执行链路

Change Data Capture（CDC）通常先做一致性快照，再从该快照对应的 Binlog/WAL 位点持续读取已提交变更：

```text
一致性快照 -> 记录日志位点 -> 按事务读取增量
-> 规范化事件 -> 幂等写入下游 -> 持久化消费位点
```

必须明确以下语义：

- **事务与顺序**：只有提交记录对下游可见；全局顺序、分区内顺序和同一主键顺序不是同一保证。
- **重复与恢复**：消费者提交数据和保存位点之间可能失败，因此事件应带来源位点/主键，Sink 使用幂等覆盖或去重。
- **更新与删除**：更新可能只有前后镜像之一；删除需传播 Tombstone 或删除事件，不能把“未出现”当删除。
- **Schema 演进**：字段增删、类型变化和默认值需兼容旧事件与回放，DDL 事件必须与数据事件协调。
- **重做全量**：全量回填与实时增量要在明确位点汇合，避免时间窗口造成丢失或双写。

所谓 exactly-once 只有在来源、处理状态与 Sink 共同提供原子或幂等语义时才成立；消息系统“恰好一次”不能自动保证外部数据库只写一次。

## CDC 与 Outbox 的边界

CDC 反映表发生了什么变化，适合数据同步和审计；Outbox 在业务事务中显式写入“发生了什么业务事件”，事件名、版本和载荷可独立于表结构。订单状态改变不一定等于“订单已支付”，业务集成优先使用 Outbox，通用镜像可用 CDC。可靠投递机制见 [[后端/数据库/8. 分布式数据库与水平扩展/3. 分布式事务与可靠消息|分布式事务与可靠消息]]。

## 实时与离线对账

两条链路应共享事件 ID、业务时间、指标定义和维度版本。对账比较记录数、主键集合、金额等可加总指标和抽样明细；发现差异后按来源位点与任务版本重放。重放输出必须幂等，并隔离当前实时写入，防止修复任务再次污染结果。
