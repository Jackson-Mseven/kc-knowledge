# 维度建模、指标口径与数据治理

维度建模让分析查询围绕业务事件和分析上下文组织。建表前必须先声明事实表粒度：一行究竟代表一次订单、一个订单项，还是某商品某日库存快照。

## 事实表与维度表

- **事务事实表**：一行表示一次不可再分的事件，如支付流水；适合明细追溯和任意聚合。
- **周期快照事实表**：按固定周期记录状态，如每日库存；没有事件也可能需要一行。
- **累积快照事实表**：一行随流程节点更新，如订单从创建到完成；适合分析阶段耗时。
- **维度表**：描述用户、商品、地区、日期等上下文，使用稳定业务键或代理键关联事实。

星型模型让事实表直接连接维度，查询和理解成本低；雪花模型继续规范化维度，可减少冗余但增加 Join。维度建模是面向分析的反范式设计，不应照搬事务库表结构。

## 慢变维

维度属性变化时先决定历史报表应看到新值还是当时值：

- Type 1 覆盖旧值，不保留历史，适合纠错；
- Type 2 新增版本，记录生效区间，事实关联对应版本，适合组织、地区等历史分析；
- 重要变更也可单独建历史或快照表，避免在宽维度中无限扩张。

Type 2 的版本区间不能重叠；迟到事实需按业务发生时间匹配维度版本，而非按入仓时间匹配。

## 指标口径

每个指标至少定义：业务含义、事实粒度、计算公式、过滤条件、时间字段与时区、去重键、维度版本、刷新频率和负责人。例如“日支付金额”必须说明按支付成功时间还是订单创建时间、退款是否扣除、跨日退款如何修正。

可加性决定聚合方式：金额通常可跨维度与时间相加；库存快照不能跨时间直接相加；比率应汇总分子分母后再计算，不能平均各分组比率。

## 数据契约、血缘与质量

数据契约约束字段类型、可空性、枚举、主键、事件时间、兼容策略和质量阈值。破坏性变化应采用新增字段、双读或兼容窗口，不能让生产者单方面修改语义。

血缘记录“来源字段 -> 转换任务及版本 -> 输出字段 -> 报表/接口”，用于评估变更和定位错误。质量检查应绑定语义：

- 完整性：应到分区、记录或事件是否到齐；
- 唯一性：业务键是否重复；
- 有效性：类型、范围、枚举和引用是否满足约束；
- 一致性：源端与下游的行数、金额或状态是否收敛；
- 及时性：数据是否在承诺的新鲜度内到达。

失败记录应隔离并保留原因，修复后按输入分区和任务版本重放。生产数据脱敏、保留和删除策略还需遵守 [[后端/数据库/10. 数据库安全与治理/00. 目录|数据库安全与治理]]。
