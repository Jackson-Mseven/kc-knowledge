# Elasticsearch 与 OpenSearch 检索原理

Elasticsearch 与 OpenSearch 都以 Apache Lucene 为核心，擅长全文检索、相关性排序和多维聚合。索引通常是事务库的派生视图，而不是订单、余额等强一致数据的权威来源。

## 索引结构

文档写入后先进入内存缓冲区，刷新为不可变 Segment 后才对搜索可见，因此搜索是 Near Real-Time。Segment 合并会回收删除文档并整理文件，但同时消耗 I/O 与 CPU。

- 倒排索引保存“词项 -> 文档”关系，用于全文匹配。
- `doc_values` 以列式结构保存字段值，主要用于排序、聚合和脚本访问。
- 一个 Index 划分为 Primary Shard，可配置 Replica。Primary Shard 数量决定分布上限，也增加文件、内存和协调开销，并非越多越好。

## Mapping 与 Analyzer

`text` 字段经过 Analyzer 产生词项，适合全文搜索；`keyword` 保留完整值，适合过滤、排序和聚合。常见做法是同一逻辑字段建立 `text` 与 `keyword` 两个 Multi-Field。

Analyzer 的过程是 Character Filter -> Tokenizer -> Token Filter。索引期和查询期 Analyzer 必须语义兼容；中文分词、大小写、停用词和同义词配置会直接改变召回结果。动态 Mapping 可能把日期、数字或标识符推断成错误类型，关键索引应使用显式模板。

已写入字段的类型和分词结果无法原地重算。变更 Mapping 或 Analyzer 通常要创建新 Index、重建数据并通过 Alias 原子切换。

## 查询与相关性

- `filter` 只判断是否匹配，不参与评分，适合租户、状态、时间范围等结构化条件；`must`、`should` 等 Query Clause 参与相关性。
- BM25 根据词频、逆文档频率和字段长度评分。字段 Boost、业务热度和时间衰减可以调整排序，但应基于真实查询与人工标注集评估。
- 同义词会扩大召回，也可能引入歧义；搜索期同义词通常比重建整个索引更易迭代，但具体 Analyzer 链必须验证。
- Highlighter 生成展示片段，不是权限控制或内容脱敏机制。
- Terms、Cardinality 等聚合可能消耗大量内存；限制时间范围、桶数量和高基数字段。

## 运行边界

刷新间隔越短，可见性延迟越低，索引吞吐和 Segment 压力越大。副本提高读取能力与节点容错，但也成倍增加存储和写放大。容量规划需同时观察 Shard 大小与数量、Heap、Segment、合并、查询扇出和磁盘水位。

Elasticsearch 与 OpenSearch 源自同一代码基础，但许可证、发行节奏、插件和 API 已分别演进；迁移前必须用实际版本验证客户端、Mapping、查询 DSL、快照仓库和安全插件，不能假定完全兼容。
