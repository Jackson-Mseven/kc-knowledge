# 搜索索引同步与重建

搜索索引是可重建的派生数据。可靠同步的目标不是承诺瞬时一致，而是让延迟有界、重复和乱序可收敛、遗漏可发现、全量重建可切换。

## 为什么不能直接双写

应用先写数据库再写搜索，任一步超时都无法确定另一端状态；反向顺序也一样。两个独立系统之间没有共同事务，简单重试还可能把旧版本覆盖到新版本。

常见入口有两种：

- CDC 读取 Binlog/WAL，覆盖所有数据库变更，适合通用同步；事件偏底层，需处理事务提交顺序、Schema 变化、位点和表到文档的转换。
- Transactional Outbox 在业务事务内同时写数据与事件，再异步投递。它能表达“订单已支付”等业务语义，但只覆盖遵循 Outbox 的写路径。

消费者至少携带实体 ID、操作类型、业务版本或提交序号、Schema 版本和发生时间。写入索引要幂等，并拒绝旧版本覆盖新版本；删除使用带版本的 Tombstone，避免延迟的更新让已删文档复活。

## 全量重建

原地清空再灌入会造成搜索不可用，也难以回滚。稳定流程是：

1. 创建带版本的新 Index 和 Mapping；
2. 记录 CDC 高水位，从权威库读取一致快照写入新 Index；
3. 从高水位重放增量，直到延迟降至允许范围；
4. 对比数量、关键聚合、抽样内容和权限字段；
5. 用 Alias 切换读流量，保留旧 Index 作为短期回滚点；
6. 观察稳定后删除旧 Index，并记录可重新构建的版本与来源。

若快照与增量之间没有可衔接的日志位点，重建窗口中的写入可能永久遗漏。

## 一致性与可观测性

详情和敏感操作回查权威库；搜索列表应允许短暂旧数据，并在业务上定义最大可接受延迟。监控至少区分：源位点与消费位点、端到端事件年龄、失败重试/死信、版本冲突、各操作类型数量，以及抽样对账差异。

数据量相同不代表内容正确。对账应覆盖删除、租户与权限字段、Analyzer 版本、关键状态分布和业务聚合；修复程序复用同一幂等写入路径，避免第二套不可审计逻辑。
