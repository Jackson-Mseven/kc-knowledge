# SQL 优化

SQL 优化的目标是在结果正确的前提下减少扫描、排序、临时数据、随机访问和网络传输。是否“使用索引”不是最终标准，应结合执行计划中的实际行数、循环次数和资源消耗判断。

## 索引原理

索引是按键组织的数据访问结构，以额外存储和写入维护成本换取更少的数据读取。数据库常见的 B+Tree 索引适合等值、范围、前缀匹配和有序扫描；Hash 索引偏向等值查询；全文检索通常使用倒排索引。

索引叶子保存整行还是行位置由数据库实现决定。通过二级索引定位后仍需访问基础数据称为回表；查询所需列都能由索引提供时称为覆盖索引。

## 索引设计

复合索引按列顺序排序。例如查询：

```sql
SELECT id, created_at
FROM orders
WHERE tenant_id = ?
  AND status = ?
  AND created_at >= ?
ORDER BY created_at, id
LIMIT 50;
```

可从 `(tenant_id, status, created_at, id)` 评估复合索引。列顺序通常依次考虑：

1. 稳定出现的等值条件；
2. 范围条件；
3. `ORDER BY`、`GROUP BY` 所需顺序；
4. 返回列是否值得覆盖；
5. 真实查询频率和数据分布。

常见索引能力：

| 类型 | 作用 | 主要代价或限制 |
| --- | --- | --- |
| 主键索引 | 唯一标识一行 | 主键过宽会放大关联索引和缓存占用 |
| 唯一索引 | 并发下保证唯一性 | `NULL` 语义因数据库而异 |
| 复合索引 | 同时服务过滤、关联和排序 | 必须匹配前导列和查询模式 |
| 前缀索引 | 减小长字符串索引 | 区分度下降，通常不能覆盖完整列 |
| 函数索引 | 支持表达式查询 | 查询表达式必须与索引定义匹配 |
| 部分索引 | 只索引满足条件的行 | 查询条件必须能推出索引条件 |

索引并非越多越好。每个索引都会增加 `INSERT`、`UPDATE`、`DELETE`、日志、复制和缓存压力。应为稳定且高价值的访问模式建索引，而不是为偶发查询堆叠宽索引。

## 索引失效与全表扫描

“索引失效”通常表示查询条件无法形成有效的索引扫描边界，或优化器判断全表扫描成本更低。常见原因包括：

- 未使用复合索引的有效前导列；
- 在索引列上执行函数或计算；
- 列与参数类型不一致，触发隐式转换；
- `LIKE '%keyword%'` 无法使用普通有序索引进行前缀定位；
- 条件选择性很低，需要返回表中大部分行；
- 统计信息陈旧或数据严重倾斜。

应把条件改写为可搜索形式（Sargable）：

```sql
-- 可直接形成 created_at 的范围边界
WHERE created_at >= ? AND created_at < ?

-- 不要在普通索引列上计算
-- WHERE DATE(created_at) = ?
```

小表或需要读取多数行时，全表扫描可能是正确计划，不应强制索引。

## EXPLAIN 与执行计划

`EXPLAIN` 展示优化器选择的访问路径、Join 顺序、排序和聚合方式。支持实际执行分析的数据库可使用 `EXPLAIN ANALYZE`，但它会真正执行 SQL，不应直接用于代价未知的生产写操作。

阅读计划时重点观察：

- 全表扫描、索引扫描或仅索引扫描；
- 预估行数与实际行数的差距；
- 每个节点的循环次数；
- 扫描行数与最终返回行数；
- 排序、Hash 或临时表是否溢写磁盘；
- Join 输入规模、执行顺序和连接条件；
- 返回列宽、总行数及网络传输成本。

优化器成本是计划之间的相对估值，不是实际毫秒数。关键查询应使用接近生产的数据分布和参数验证。

## 查询改写

### 减少无效读取

- 只查询需要的列，避免无条件 `SELECT *`；
- 尽早使用高选择性条件缩小结果集；
- 使用稳定排序和 `LIMIT` 控制返回规模；
- 大偏移分页优先使用基于排序键的 Keyset Pagination；
- 避免在循环中逐条查询关联数据形成 N+1。

```sql
SELECT id, created_at, title
FROM articles
WHERE tenant_id = ?
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

### 优化 Join

- Join 条件必须完整，避免意外笛卡尔积；
- 为高频关联键建立匹配的索引；
- 先过滤或聚合再 Join 只能在语义等价时进行；
- 一对多 Join 会放大行数，分页和聚合前先确认结果粒度；
- 优化器可选择 Nested Loop、Hash Join 或 Merge Join，不能只凭 SQL 书写顺序判断性能。

### 正确使用子查询

子查询本身不等于低性能。只判断关联记录是否存在时，`EXISTS` 通常比 Join 后再去重更准确；只需要合并集合且允许重复时，`UNION ALL` 比 `UNION` 少一次去重成本。是否改写仍以执行计划为准。

## 数据库设计

查询优化始于表结构。建模时先识别实体、关系和业务不变量，再决定表、键、约束与索引。

### 三大范式

- 第一范式（1NF）：每列保存不可再拆分的单值，不用逗号分隔字符串模拟集合；
- 第二范式（2NF）：在满足 1NF 的基础上，非主键字段完全依赖整个候选键，避免只依赖复合键的一部分；
- 第三范式（3NF）：在满足 2NF 的基础上，非主键字段不依赖其他非主键字段，避免传递依赖。

范式用于减少重复事实及插入、更新、删除异常。经过测量后可为读取性能或历史快照适度反范式，但必须明确权威来源、更新时机和校验方式。

### 表与关系设计

- 一对多由子表外键表达，多对多使用关联表；
- 关系本身具有状态、角色或时间时，关联表应作为独立实体；
- 主键负责稳定标识，业务编号负责展示，两者通常分离；
- 唯一、非空、检查和外键约束用于承载不会随请求变化的业务不变量；
- 历史订单中的商品名、成交价和税率应保存快照，不能依赖当前商品数据还原。

### 字段类型选择

- 整数选择能覆盖业务范围的最小合理类型；
- 金额使用定点数或最小货币单位整数，并保存币种，避免浮点误差；
- 时间点统一存储明确时区语义的时间，生日和账期等日历日期使用 `DATE`；
- 短且固定的状态值使用受约束的有限集合；
- 长文本、JSON 和二进制大字段会增加行宽，应按过滤、更新和读取模式决定是否拆表；
- 字符集与排序规则决定可存字符、比较和排序结果，建表前应统一。

## 优化顺序

1. 确认 SQL 结果和业务语义正确；
2. 从慢查询统计或 Trace 判断调用频率与总成本；
3. 区分执行、锁等待、连接排队和结果传输；
4. 使用执行计划定位首个高成本或估算失真的节点；
5. 一次只调整 SQL、索引、统计信息或批量大小中的主要因素；
6. 比较延迟、吞吐、写入成本和资源占用，必要时回滚。
