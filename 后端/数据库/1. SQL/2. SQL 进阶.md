# SQL 进阶

进阶查询的核心是控制结果粒度：`GROUP BY` 改变粒度，Join 组合关系，子查询和 CTE 生成中间关系，窗口函数则在保留原始行的同时计算跨行结果。

下文示例统一使用：`users(id, name)`、`orders(id, user_id, status, amount, created_at)`、`employees(id, name, manager_id)`。

## 分组与聚合

`WHERE` 先过滤输入行，`GROUP BY` 再把分组键相同的行归为一组，聚合函数为每组计算一个值，`HAVING` 最后过滤分组结果。

```sql
SELECT
  user_id,
  COUNT(*) AS order_count,
  SUM(amount) AS total_amount,
  AVG(amount) AS average_amount,
  MAX(amount) AS maximum_amount,
  MIN(amount) AS minimum_amount
FROM orders
WHERE status = 'paid'
GROUP BY user_id
HAVING SUM(amount) >= 1000;
```

- `COUNT(*)` 统计行数，包含各列为 `NULL` 的行；`COUNT(amount)` 只统计 `amount` 非 `NULL` 的行。
- `SUM`、`AVG`、`MAX`、`MIN` 忽略 `NULL`；输入为空时通常返回 `NULL`，只有 `COUNT` 返回 `0`。需要默认值时显式使用 `COALESCE`。
- 标准 SQL 要求 `SELECT` 中未聚合的列都属于 `GROUP BY`。依赖 MySQL 宽松模式选择任意行值，会得到不稳定结果。
- `WHERE` 不能直接引用聚合结果；组级条件放入 `HAVING`。能在聚合前判断的条件仍应放在 `WHERE`，以免改变语义并扩大输入集。

Join 后再聚合时要先确认关系基数。一对多 Join 会复制“一侧”的值；例如订单同时关联订单项和优惠记录，直接 `SUM(orders.amount)` 可能重复计数。此时应先在子查询中聚合到目标粒度，再连接结果。

## 多表连接

Join 按 `ON` 条件组合两侧行；它不是“查找一条关联记录”，一侧匹配多行时会输出多个组合。

| 类型 | 结果语义 |
| --- | --- |
| `INNER JOIN` | 只保留两侧匹配的组合 |
| `LEFT JOIN` | 保留全部左侧行；无匹配时右侧列为 `NULL` |
| `RIGHT JOIN` | 保留全部右侧行；通常交换表顺序改写为更易阅读的 `LEFT JOIN` |
| `FULL OUTER JOIN` | 保留两侧所有行，无匹配的一侧补 `NULL` |
| `CROSS JOIN` | 生成笛卡尔积，共 `左侧行数 × 右侧行数` 行 |
| Self Join | 为同一张表设置不同别名，表达层级或同表关系 |

```sql
SELECT u.id, u.name, COUNT(o.id) AS paid_order_count
FROM users AS u
LEFT JOIN orders AS o
  ON o.user_id = u.id
 AND o.status = 'paid'
GROUP BY u.id, u.name;
```

过滤右表的条件放在 `ON` 中，未下单用户仍会保留。若写成 `WHERE o.status = 'paid'`，右侧为 `NULL` 的行会被过滤，结果等同于只保留匹配行。

```sql
-- Self Join：员工与直属经理
SELECT e.name AS employee_name, m.name AS manager_name
FROM employees AS e
LEFT JOIN employees AS m ON m.id = e.manager_id;

-- CROSS JOIN：显式生成全部用户与状态组合
SELECT u.id, s.status
FROM users AS u
CROSS JOIN (VALUES ('pending'), ('paid')) AS s(status);
```

`VALUES` 放在 `FROM` 中的具体语法存在方言差异。`FULL OUTER JOIN` 也不是所有产品都支持，例如 MySQL 没有原生实现；需要以 `LEFT JOIN`、反向反连接和 `UNION ALL` 组合时，必须处理重复行。连接键为 `NULL` 时，普通 `=` 不会认为两侧相等。

## 子查询与 EXISTS

子查询按出现位置承担不同角色：

- `WHERE` 中的子查询产生比较值、集合或存在性判断；
- `FROM` 中的子查询是派生表，通常必须有别名；
- `SELECT` 中只能使用标量子查询，即返回一列且至多一行。

`FROM` 派生表默认不能引用外层查询列；需要逐行依赖外层列时使用数据库支持的 `LATERAL` 或 `APPLY`，不要把相关逻辑误写成普通派生表。

```sql
-- WHERE：不相关子查询，不引用外层列
SELECT id, user_id, amount
FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders);

-- WHERE：相关子查询，计算每位用户自己的平均值
SELECT o.id, o.user_id, o.amount
FROM orders AS o
WHERE o.amount > (
  SELECT AVG(o2.amount)
  FROM orders AS o2
  WHERE o2.user_id = o.user_id
);

-- FROM：先聚合到每个用户一行，再连接
SELECT u.id, u.name, t.total_amount
FROM users AS u
JOIN (
  SELECT user_id, SUM(amount) AS total_amount
  FROM orders
  WHERE status = 'paid'
  GROUP BY user_id
) AS t ON t.user_id = u.id;

-- SELECT：每位用户最近一次下单时间
SELECT
  u.id,
  u.name,
  (SELECT MAX(o.created_at)
   FROM orders AS o
   WHERE o.user_id = u.id) AS last_order_at
FROM users AS u;
```

不相关子查询可独立求值；相关子查询引用外层行，逻辑上对每个外层候选行求值，但优化器可能把它改写为 Join 或半连接。不能仅凭写法判断性能，应查看执行计划。

标量子查询没有结果时产生 `NULL`，返回多行则报错。当条件只关心“是否存在”时，用 `EXISTS` 直接表达半连接语义：

```sql
SELECT u.id, u.name
FROM users AS u
WHERE EXISTS (
  SELECT 1
  FROM orders AS o
  WHERE o.user_id = u.id
    AND o.status = 'paid'
);
```

`EXISTS` 只判断是否至少有一行，子查询的选择列表没有业务含义。反向判断优先使用相关的 `NOT EXISTS`；`NOT IN (subquery)` 只要子查询结果含 `NULL`，整体比较就可能成为 `UNKNOWN`，导致意外地没有结果。

## UNION 与 UNION ALL

集合查询按列位置拼接结果：各分支必须返回相同列数，对应类型必须兼容，最终列名取自第一个分支。

```sql
SELECT id, user_id, amount, created_at
FROM orders
WHERE created_at >= DATE '2026-01-01'
UNION ALL
SELECT id, user_id, amount, created_at
FROM archived_orders
WHERE created_at >= DATE '2026-01-01'
ORDER BY created_at DESC, id DESC;
```

- `UNION ALL` 保留重复行，只负责拼接；
- `UNION` 对整行去重，通常需要排序或 Hash，成本更高；
- 末尾的 `ORDER BY`、`LIMIT` 作用于整个集合。若要限制单个分支，应按数据库方言为该分支加括号或子查询；
- `DATE` 字面量及隐式类型转换的支持存在方言差异，跨库 SQL 应显式统一类型。

只有业务语义确实要求去重时才使用 `UNION`。用它掩盖 Join 或数据模型产生的重复，通常会隐藏真正的基数错误。

## 窗口函数

聚合查询把多行折叠为一行；窗口函数保留每个输入行，并在其所属窗口内计算排名、累计值或相邻行。窗口由 `PARTITION BY` 分区、`ORDER BY` 定序、Frame 指定当前行参与计算的范围。

```sql
SELECT
  id,
  user_id,
  amount,
  ROW_NUMBER() OVER (
    PARTITION BY user_id
    ORDER BY created_at DESC, id DESC
  ) AS order_number,
  SUM(amount) OVER (
    PARTITION BY user_id
    ORDER BY created_at, id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_amount
FROM orders
WHERE status = 'paid';
```

常用函数：

- `ROW_NUMBER` 为每行生成连续序号，不处理并列；
- `RANK` 的并列值名次相同，并在之后留下名次空缺；
- `DENSE_RANK` 并列后不留空缺；
- `LAG`、`LEAD` 读取窗口中前一行或后一行；
- `SUM`、`AVG`、`COUNT` 等聚合函数加 `OVER` 后成为窗口聚合。

排名的 `ORDER BY` 必须加入唯一或稳定的破同列，否则并列行顺序不确定。带窗口内排序的聚合函数可能采用包含“同值行”的默认 `RANGE` Frame；累计计算应显式写出 `ROWS ...`，避免重复排序值改变结果。

窗口函数晚于 `WHERE`、`GROUP BY` 和 `HAVING` 计算，因此不能在同一查询块的 `WHERE` 中直接引用窗口结果。先放入派生表或 CTE：

```sql
WITH ranked_orders AS (
  SELECT
    id,
    user_id,
    amount,
    ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY created_at DESC, id DESC
    ) AS rn
  FROM orders
)
SELECT id, user_id, amount
FROM ranked_orders
WHERE rn <= 3;
```

窗口中的 `ORDER BY` 只定义计算顺序，不保证最终输出顺序；展示结果仍需最外层 `ORDER BY`。

## CTE 与递归 CTE

Common Table Expression（CTE）通过 `WITH` 为单条语句内的中间关系命名，适合拆解多阶段查询或复用同一结果：

```sql
WITH paid_totals AS (
  SELECT user_id, SUM(amount) AS total_amount
  FROM orders
  WHERE status = 'paid'
  GROUP BY user_id
)
SELECT u.id, u.name, p.total_amount
FROM users AS u
JOIN paid_totals AS p ON p.user_id = u.id
WHERE p.total_amount >= 1000;
```

CTE 是查询结构，不等同于临时表。数据库及版本可能选择内联、物化或重复执行它；热点 SQL 不能假设 CTE 天然更快或只计算一次。

递归 CTE 由锚点查询给出初始行，递归分支引用自身并逐层扩展，适合邻接表形式的树或图遍历：

```sql
WITH RECURSIVE organization AS (
  SELECT id, name, manager_id, 0 AS depth
  FROM employees
  WHERE manager_id IS NULL

  UNION ALL

  SELECT e.id, e.name, e.manager_id, o.depth + 1
  FROM employees AS e
  JOIN organization AS o ON e.manager_id = o.id
)
SELECT id, name, manager_id, depth
FROM organization;
```

脏数据中的环会导致重复扩展或达到数据库递归上限。遍历一般图时应记录访问路径并排除已访问节点，同时设置最大深度和查询超时。部分数据库要求 `WITH RECURSIVE`，SQL Server 则使用 `WITH`，语法和递归限制应按目标产品确认。

## CASE WHEN

`CASE` 是返回值的表达式，可出现在 `SELECT`、`ORDER BY`、聚合函数等位置；它不是过程式控制流。

```sql
SELECT
  user_id,
  SUM(CASE WHEN status = 'paid' THEN amount ELSE 0 END) AS paid_amount,
  COUNT(CASE WHEN status = 'pending' THEN 1 END) AS pending_count,
  CASE
    WHEN SUM(amount) >= 10000 THEN 'high'
    WHEN SUM(amount) >= 1000 THEN 'medium'
    ELSE 'low'
  END AS value_level
FROM orders
GROUP BY user_id;
```

搜索式 `CASE WHEN condition THEN value` 能表达范围和复合条件；简单式 `CASE expression WHEN value THEN result` 只比较相等。条件从上到下匹配，返回第一个命中的分支；省略 `ELSE` 时默认返回 `NULL`。各返回分支应能转换为共同类型，避免依赖可能损失精度的隐式转换。

## 视图

普通 View 保存查询定义，为复杂查询提供稳定名称，也可只暴露允许访问的列：

```sql
CREATE VIEW paid_order_summary AS
SELECT user_id, COUNT(*) AS order_count, SUM(amount) AS total_amount
FROM orders
WHERE status = 'paid'
GROUP BY user_id;

SELECT user_id, total_amount
FROM paid_order_summary
WHERE total_amount >= 1000
ORDER BY total_amount DESC;
```

普通视图通常不保存结果，也不会自动提升性能；优化器仍需执行其底层查询。Materialized View 才保存结果，但数据会在刷新前保持陈旧，且刷新语法和并发能力因产品而异。

视图还有以下边界：

- 视图不能接收参数；不同筛选条件由查询视图的语句提供；
- 视图内部的 `ORDER BY` 不保证外层结果顺序；最终顺序必须由最外层查询指定；
- 简单单表视图可能可更新，包含聚合、`DISTINCT`、集合操作或复杂 Join 的视图通常只读，具体规则依数据库而定；
- 权限可能按创建者或调用者身份检查。把视图作为安全边界前，必须确认产品的执行身份、行级安全和底层对象授权规则；
- 底层列变更可能使视图失效或悄然改变类型，定义中应使用显式列而不是 `SELECT *`。

## 函数与数据库程序对象

内置标量函数处理单行值，聚合函数把多行归并为一行，窗口函数则保留原始行。对索引列施加函数可能使普通索引无法形成有效扫描边界；应优先改写条件，确有稳定查询模式时再使用函数索引或生成列索引。

| 对象 | 用途 | 主要限制 |
| --- | --- | --- |
| Stored Function | 在表达式中返回单值 | 逐行调用可能放大成本，权限和确定性声明因产品而异 |
| Stored Procedure | 封装靠近数据的多步操作 | 调用方仍需明确事务、错误和版本迁移 |
| Trigger | 在 DML 前后同步执行 | 副作用隐蔽，会增加写入、锁和排障成本 |
| Scheduled Event/Job | 在数据库内定时执行任务 | 调度、选主和失败恢复能力依产品而异 |

这些对象是厂商方言，不具备通用 SQL 可移植性。Trigger 通常与原 DML 处于同一事务；程序对象应随 Schema Migration 版本化，并审查执行身份、复制行为和回滚方式。复杂业务流程和需要重试、告警、分布式协调的任务通常放在应用或任务平台中。

访问路径、索引选择、执行计划和查询改写见 [[后端/数据库/1. SQL/3. SQL 优化|SQL 优化]]。
