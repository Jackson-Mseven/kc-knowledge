# MySQL 事务与隔离级别

事务规定一组读写如何提交或回滚；InnoDB 通过 Undo、Read View 和锁控制并发可见性，通过 Redo 保证崩溃恢复。事务只能保证数据库内正确表达的不变量，不能自动撤销已经发生的远程调用。

## 事务边界与 ACID

| 属性 | InnoDB 提供的基础 | 需要额外明确的边界 |
| --- | --- | --- |
| Atomicity | 事务内修改全部提交或回滚 | 多数语句错误只回滚当前语句；应用要结束失败事务 |
| Consistency | 唯一键、外键、`CHECK`、锁和原子 DML | 未写成约束或更新条件的业务规则不会自动成立 |
| Isolation | MVCC、行锁和隔离级别 | 级别越高不等于所有业务不变量都安全 |
| Durability | Redo 与提交刷盘 | 实际丢失窗口取决于刷盘、存储和复制配置 |

MySQL 默认启用 `autocommit`，此时每条独立 DML 都是一个事务。需要多条语句共同提交时显式定义边界。下面仅展示语句顺序；应用必须检查每条语句的影响行数和错误，再决定 `COMMIT` 或 `ROLLBACK`：

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1 AND balance >= 100;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT; -- 任一步不满足业务条件时应由应用执行 ROLLBACK
```

- `SET TRANSACTION` 设置下一个事务；`SET SESSION TRANSACTION` 会改变后续事务，连接池复用时容易泄漏会话状态；
- 多阶段操作可用 `SAVEPOINT name`、`ROLLBACK TO SAVEPOINT name` 和 `RELEASE SAVEPOINT name` 局部回退；回滚到保存点不会释放此前获取的锁；
- 多数 DDL 会隐式提交，不能假定它与相邻 DML 一起回滚；
- 语句报错后事务未必自动结束。应用应捕获错误、执行 `ROLLBACK`，再把连接归还连接池；
- 事务内不要等待远程服务、用户输入或长计算；它们会延长锁和旧版本的存活时间；
- 客户端在 `COMMIT` 时断线可能无法判断服务端是否已经提交，重复执行前必须先查询业务结果。

## Undo Log、Redo Log 与 Binlog

三类日志位于不同层次，不能互相替代：

| 日志 | 所属层 | 解决的问题 |
| --- | --- | --- |
| Undo Log | InnoDB | 回滚未提交变更，构造 MVCC 历史版本 |
| Redo Log | InnoDB | 崩溃后重放已持久化的页变更 |
| Binlog | MySQL Server | 记录逻辑变更，用于复制、CDC 和 PITR |

提交时 InnoDB 先把事务状态写入可恢复的 Redo，再由 Server 写 Binlog，最后完成提交标记；崩溃恢复依据两者的事务状态决定 Prepared 事务提交或回滚。`innodb_flush_log_at_trx_commit` 和 `sync_binlog` 决定刷盘强度，放宽配置会扩大已返回成功事务的丢失窗口。

## 隔离级别与并发异常

- 脏读：读到其他事务尚未提交的数据；
- 不可重复读：同一事务再次读取同一行时看到不同的已提交版本；
- 幻读：同一谓词再次查询时，匹配的行集合发生变化；
- 丢失更新：两个事务基于旧值写回，其中一个结果被覆盖；
- 写偏差：事务修改不同记录，各自检查都通过，组合结果却破坏跨行约束。

| InnoDB 隔离级别 | 普通一致性读 | 关键边界 |
| --- | --- | --- |
| READ UNCOMMITTED | 可读取未提交版本 | 很少适合业务事务 |
| READ COMMITTED | 每次一致性读通常创建新 Read View | 后续语句可看到新提交，Gap Lock 使用更少 |
| REPEATABLE READ | 同一事务通常复用首次一致性读建立的 Read View | MySQL 默认；范围当前读依赖 Next-Key Lock，仍不能自动防止写偏差 |
| SERIALIZABLE | 对普通读取施加更强的锁定语义 | 并发更低，必须处理等待和失败 |

隔离级别描述可见性和冲突规则，不等于业务并发策略。库存、余额或状态迁移应优先用唯一约束、条件 `UPDATE`、显式锁或可串行化建模表达不变量。

## InnoDB MVCC 与 Read View

InnoDB 聚簇记录包含最近修改事务 ID 和指向 Undo 的回滚指针。更新不会为整行复制一份独立快照，而是由当前记录沿 Undo 形成历史版本链；Purge 只回收已不再被任何活跃 Read View 需要的版本。

Read View 记录创建快照时仍活跃的事务集合及其边界。读取某个版本时，可见性可概括为：

1. 当前事务自己的修改可见；
2. 版本在快照创建前已经提交则可见；
3. 版本由快照中的活跃事务创建，或在快照之后才创建，则不可见；
4. 不可见时沿 Undo 链寻找更早版本。

普通 `SELECT` 通常是一致性读，不阻塞普通写。带 `FOR SHARE` 或 `FOR UPDATE` 的锁定读，以及 `UPDATE`、`DELETE`，属于当前读：它们基于较新的可用版本执行并加锁。一个事务中混用快照读和当前读时，两者看到的范围可能不同，不能把“可重复读”理解为所有 SQL 永远看到同一物理状态。

锁类型、范围和冲突处理见 [[后端/数据库/2. 关系型数据库/Mysql/4. 锁机制|MySQL 锁机制]]。

## 长事务

长事务会长期持锁和 Read View，阻止 Purge 清理 Undo，导致 History List 增长、读取版本链变慢，并放大复制、DDL、回滚和故障恢复成本。常见来源是空闲未提交连接、事务内远程调用和使用事务快照做大批量导出。

```sql
SELECT trx_mysql_thread_id, trx_started, trx_state, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
```

连接监控应同时记录事务开始时间、最后一条 SQL 和业务请求。大报表优先使用副本、快照表或分析系统；在线事务应限定处理行数和持续时间。
