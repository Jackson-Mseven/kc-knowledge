# MySQL 锁机制

InnoDB 的锁解决并发读写冲突，但锁住的是索引记录或索引范围，不是抽象的“业务行”。锁的范围由访问路径、索引、隔离级别和语句类型共同决定。

## 表锁与行锁

| 类型 | 作用 | 典型来源 |
| --- | --- | --- |
| 表锁 | 保护整张表，粒度大、并发低 | `LOCK TABLES`、部分表级操作 |
| Metadata Lock（MDL） | 保护表定义，防止 DDL 与访问冲突 | 查询或 DML 持有至事务结束，DDL 申请排他 MDL |
| Record Lock | 锁定索引中的一条记录 | 唯一键等值更新或锁定读 |
| Gap Lock | 锁定索引记录之间的间隙，阻止范围内插入 | InnoDB `REPEATABLE READ` 的范围当前读 |
| Next-Key Lock | Record Lock 加前方 Gap Lock | 范围更新、范围锁定读 |
| Insert Intention Lock | 表示准备在间隙插入 | 并发插入时协调不同位置 |

InnoDB 的主键索引是聚簇索引。缺少合适索引时，范围扫描可能访问并锁住远多于结果集的记录；因此锁优化首先是让锁定谓词走正确索引。InnoDB 不会因为锁行过多自动把行锁升级为表锁；大事务仍会消耗锁内存并扩大等待范围。

## 共享锁与排他锁

- **共享锁（S）**：多个事务可以同时持有，但会阻止冲突的排他修改；
- **排他锁（X）**：用于修改或准备修改，不能与其他 S/X 锁兼容；
- **意向锁（IS/IX）**：表级协调信号，表示事务准备在更细粒度持有 S/X，不等于锁住整张表。

锁定读示例：

```sql
START TRANSACTION;

SELECT id, status
FROM orders
WHERE id = 42
FOR UPDATE;

UPDATE orders
SET status = 'paid'
WHERE id = 42 AND status = 'pending';

COMMIT;
```

`FOR UPDATE` 适合准备修改的记录，`FOR SHARE` 适合必须保护读取结果的场景；两者都应放在短事务内。`NOWAIT` 可在冲突时立即失败，`SKIP LOCKED` 可用于 Worker 领取任务，但返回的是不完整、不稳定的视图，不适合普通业务查询。

## 间隙锁与临键锁

在索引上执行范围当前读时，InnoDB 可能锁住“记录 + 前方间隙”，防止其他事务插入使范围结果发生变化。精确命中唯一索引时通常只需 Record Lock；非唯一索引或范围条件可能使用 Next-Key Lock。

`READ COMMITTED` 的普通搜索和索引扫描通常禁用 Gap Lock，外键约束检查和重复键检查是核心例外。不能只根据 SQL 文本判断锁范围，应结合 `EXPLAIN`、索引定义和 `performance_schema` 观察。

## 乐观锁与悲观锁

### 条件更新

能用一条带前置条件的 DML 表达不变量时，不必先查再改：

```sql
UPDATE inventory
SET available = available - ?
WHERE sku_id = ?
  AND available >= ?;
```

影响一行表示成功，零行表示库存不足或状态已经变化。订单状态、余额扣减和唯一业务键都适合优先采用这种原子判断。

### 乐观锁

低冲突编辑可用版本号检测覆盖：

```sql
UPDATE documents
SET content = ?, version = version + 1
WHERE id = ? AND version = ?;
```

影响行数为零时重新读取、合并或提示冲突。热点资源反复冲突时，乐观锁会浪费大量工作，应改用短事务悲观锁、队列或重新分片。

### 悲观锁

冲突概率高、且必须读取多个值后决策时，在短事务中使用 `FOR UPDATE`。锁内不能执行网络请求、等待用户或长计算；悲观锁只能把竞争变成等待，不能消除死锁。

## 死锁

死锁是等待图形成环，例如事务 A 持有记录 1 等待记录 2，事务 B 持有记录 2 等待记录 1。InnoDB 通常选择一个受害事务回滚。

降低概率：

1. 所有代码路径按同一稳定顺序锁定多行；
2. 为锁定条件建立合适索引，缩小扫描和锁范围；
3. 缩短事务，移除远程调用和长计算；
4. 限制一次批量修改的行数；
5. 从死锁日志确认真实 SQL 和加锁顺序，不要只提高等待超时。

常见错误码：

- `1213`（Deadlock）：整个事务已被回滚，应从事务起点有限重试；
- `1205`（Lock wait timeout）：默认通常只回滚当前语句，应用应显式回滚事务后再决定是否重试。

重试必须限制次数、使用退避和随机抖动，并确保业务命令幂等。约束错误、语法错误和持续资源不足不应盲目重试；提交阶段客户端断线时，先确认业务结果再决定是否重放。

## 锁等待诊断

```sql
SHOW ENGINE INNODB STATUS;

SELECT *
FROM performance_schema.data_locks;

SELECT *
FROM performance_schema.data_lock_waits;

SELECT *
FROM sys.innodb_lock_waits;
```

`data_locks` 显示已持有和正在请求的锁，`data_lock_waits` 连接请求方和阻塞方。还应查看阻塞事务的开始时间、最后一条 SQL、使用的索引和修改量。杀掉阻塞会话可能触发长时间回滚；调整 `innodb_lock_wait_timeout` 只改变等待时长，不会缩小锁范围。事务可见性和长事务见 [[后端/数据库/2. 关系型数据库/Mysql/3. 事务与隔离级别|事务与隔离级别]]，执行计划见 [[后端/数据库/2. 关系型数据库/Mysql/5. MySQL性能优化|MySQL 性能优化]]。
