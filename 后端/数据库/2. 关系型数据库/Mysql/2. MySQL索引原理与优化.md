# MySQL 索引原理与优化

索引用额外空间和写入维护成本换取更少的数据页访问。MySQL 优化器决定是否使用索引；“存在索引”不等于“执行计划会选它”，最终应比较扫描行数、回表次数、排序和实际耗时。

## InnoDB 的 B+Tree

InnoDB 的普通索引按 B+Tree 组织，节点对应固定大小的数据页，默认页大小通常为 16 KiB：

- 非叶子节点保存分隔键和子页指针，高扇出使树通常只有少量层级；
- 叶子节点按键有序并相互链接，适合等值、范围、前缀和顺序扫描；
- 读页先经过 Buffer Pool，一次逻辑查找是否产生磁盘 I/O 取决于缓存命中；
- 插入到已满页会发生页分裂，过宽或高度随机的键会增加空间与写入成本。

Hash 适合等值定位但不保序。InnoDB 的自适应 Hash Index 是引擎基于热点 B+Tree 页自动维护的内部加速结构，不是用户为表声明的通用 Hash 索引，也不能支持范围和排序。

## 聚簇索引与二级索引

InnoDB 的表数据就是主键 B+Tree，因此一张表只有一个聚簇索引：

- 聚簇索引叶子保存完整行；
- 有显式主键时使用主键；否则选择第一个所有列均为 `NOT NULL` 的唯一索引，仍没有时生成隐藏行 ID；
- 二级索引叶子保存“二级键 + 主键”，通过二级索引查询其他列时还要访问主键树，即回表；
- 查询所需列都能从某个索引取得时形成覆盖索引，可省去回表。

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
  status VARCHAR(20) NOT NULL,
  created_at DATETIME(6) NOT NULL,
  amount DECIMAL(12, 2) NOT NULL,
  INDEX idx_orders_tenant_status_created (
    tenant_id, status, created_at DESC, id DESC
  )
) ENGINE = InnoDB;
```

主键会出现在所有二级索引叶子中。长字符串或宽复合主键会放大每个二级索引；完全随机的主键还会降低插入局部性。主键应稳定、非空、尽量紧凑，但不能只为顺序写入牺牲全局唯一性等业务约束。

MyISAM 的索引与数据文件分离，索引叶子指向记录位置，属于非聚簇组织。聚簇与非聚簇描述的是数据和索引的组织关系，不是“主键索引”与“普通索引”的同义词。

## 索引类型

| 类型 | 作用 | 关键边界 |
| --- | --- | --- |
| `PRIMARY KEY` | 唯一标识并组织 InnoDB 行 | 每表一个；应避免宽且频繁变化的键 |
| `UNIQUE` | 并发下保证非 `NULL` 键值唯一 | MySQL 允许唯一索引中出现多个 `NULL` |
| 普通/联合索引 | 服务过滤、Join、排序与覆盖查询 | 列顺序必须匹配稳定的查询模式 |
| 前缀索引 | 只索引字符串前 N 个字符，降低空间 | 区分度下降，通常不能覆盖完整列 |
| Functional Index | 索引表达式结果 | 查询表达式需与定义一致；底层由隐藏生成列实现 |
| `FULLTEXT` | 按词项检索自然语言文本 | 受解析器、停用词和语言分词影响，不能替代通用搜索系统 |
| `SPATIAL` | 加速空间对象关系查询 | 数据类型、坐标系和谓词需符合空间索引规则 |
| Invisible Index | 暂时不让优化器选择索引 | 用于评估删除影响；维护写入成本仍然存在 |

MySQL 没有 PostgreSQL 式的 Partial Index。若只需索引部分业务状态，可评估生成列加索引，但要计入表达式语义和维护成本。

## 联合索引与最左前缀

联合索引 `(tenant_id, status, created_at, id)` 先按 `tenant_id` 排序，再在同一租户内按 `status`、`created_at`、`id` 排序。因此它可以直接形成下列连续扫描范围：

```sql
SELECT id, created_at
FROM orders
WHERE tenant_id = 42
  AND status = 'paid'
  AND created_at >= '2026-08-01 00:00:00'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

规则可概括为：连续匹配前导列，优先利用等值条件，遇到第一个范围条件后，后续列通常不能继续缩小同一索引扫描区间，但仍可能用于 Index Condition Pushdown、覆盖或排序。`WHERE` 中条件的书写顺序不重要，索引定义顺序才重要。

以下查询缺少 `tenant_id`，通常不能像完整前缀那样高效定位：

```sql
SELECT id
FROM orders
WHERE status = 'paid';
```

MySQL 在特定条件下可能选择 Skip Scan 等优化，因此“违反最左前缀就绝不使用索引”并不准确；仍应以执行计划和真实数据为准。设计列顺序时同时考虑等值过滤、范围、排序、覆盖、选择性和查询频率，不能只机械地把高基数列放在最前。

## 为什么没有得到有效索引扫描

所谓“索引失效”通常有两类：条件不能形成索引边界，或优化器判断索引随机访问与回表比全表扫描更贵。

| 写法或场景 | 原因 | 改写方向 |
| --- | --- | --- |
| `DATE(created_at) = '2026-08-01'` | 普通索引保存原列值，函数结果不在索引中 | 改为左闭右开时间范围，或建立匹配的 Functional Index |
| `name LIKE '%keyword'` | 前导通配符无法确定 B+Tree 起点 | 可接受时改为前缀匹配；任意包含检索使用全文索引 |
| 列与参数类型、字符集不一致 | 隐式转换可能作用在索引列上 | 统一 Schema 与绑定参数类型，检查 Collation |
| 缺少联合索引前导列 | 数据未按后续列全局连续排列 | 建立匹配访问模式的索引，避免盲目复制相似索引 |
| 低选择性条件返回大部分表 | 大量回表可能比顺序全扫更贵 | 不强制索引；重新确认返回规模和覆盖需求 |
| `OR` 各分支缺少可用索引 | 无法为所有分支建立低成本访问路径 | 分别建合适索引，或在语义等价时拆成 `UNION ALL` |
| 统计信息过期或数据倾斜 | 成本估算与实际分布不符 | `ANALYZE TABLE`，必要时评估 Histogram |

```sql
-- 可使用 created_at 的普通范围索引
WHERE created_at >= '2026-08-01 00:00:00'
  AND created_at <  '2026-08-02 00:00:00'
```

`IS NULL`、`!=`、`NOT IN` 并不会在语法上必然禁用索引；是否值得使用取决于 `NULL` 分布、选择性和成本。小表或需要读取多数行时，`ALL` 全表扫描可能就是正确计划。

## EXPLAIN 执行计划

`EXPLAIN` 展示估算计划，`EXPLAIN ANALYZE` 会真正执行语句并输出实际耗时、行数与循环次数。后者可能产生完整查询成本，不要直接对代价未知的生产语句使用。

```sql
EXPLAIN FORMAT=TREE
SELECT id, created_at
FROM orders
WHERE tenant_id = 42
  AND status = 'paid'
  AND created_at >= '2026-08-01 00:00:00'
ORDER BY created_at DESC, id DESC
LIMIT 20;

EXPLAIN ANALYZE
SELECT id, created_at
FROM orders
WHERE tenant_id = 42
  AND status = 'paid'
  AND created_at >= '2026-08-01 00:00:00'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

传统表格格式重点字段：

| 字段 | 如何解读 |
| --- | --- |
| `type` | 访问方式；常见有 `const`、`eq_ref`、`ref`、`range`、`index`、`ALL`。`index` 可能是全索引扫描，并不等于高效 |
| `possible_keys` / `key` | 候选索引与实际选择；`key = NULL` 不应脱离表大小和返回比例判断 |
| `key_len` / `ref` | 实际使用的键长度和匹配对象，可辅助判断联合索引用到哪些部分 |
| `rows` / `filtered` | 估算扫描行数与过滤比例，不是实际值 |
| `Extra: Using index` | 覆盖索引，不需要读取聚簇行 |
| `Extra: Using index condition` | 使用 Index Condition Pushdown，减少回表，但不等于完全覆盖 |
| `Extra: Using filesort` | 需要额外排序；名称不表示一定落盘 |
| `Extra: Using temporary` | 中间结果需要内部临时表，应继续检查分组、排序和行数 |

分析顺序：先找实际处理行数最大的节点，再比较估算与实际行数、循环次数、扫描与返回比例、排序和回表。`actual rows × loops` 比单看节点耗时更能暴露 Nested Loop 内层被重复执行的问题。估算严重偏差时先检查统计信息、数据倾斜和列相关性，再决定改 SQL、索引或表结构。

索引优化必须放在完整查询语义中判断。通用的 Join、子查询、分页和查询改写见 [[后端/数据库/1. SQL/3. SQL 优化|SQL 优化]]；MySQL 的解析、优化器和执行器边界见 [[后端/数据库/2. 关系型数据库/Mysql/1. MySQL架构与执行原理|MySQL 架构与执行原理]]。
