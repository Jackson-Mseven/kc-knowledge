# MySQL 性能优化

MySQL 优化先判断时间消耗在执行、锁等待、连接排队、刷盘还是结果传输，再调整 SQL、索引、表结构或配置。只看单次最慢 SQL、Buffer Pool 命中率或“是否走索引”都可能误判。

## 定位性能瓶颈

常用入口：

```sql
SHOW FULL PROCESSLIST;

SELECT *
FROM sys.statement_analysis
ORDER BY total_latency DESC
LIMIT 20;

SELECT *
FROM sys.innodb_lock_waits;
```

Slow Query Log 用于收集超过阈值或特定条件的查询；Performance Schema 记录语句摘要、阶段、等待、锁和 IO；sys Schema 提供更易读的聚合视图。日志和 APM 必须对 SQL 参数脱敏。

| 现象 | 优先定位 |
| --- | --- |
| CPU 高、扫描行数高 | Top SQL、执行计划、统计信息、排序和回表 |
| 查询等待但 CPU/IO 不高 | 阻塞事务、锁范围、MDL、连接池排队 |
| 写入周期性停顿 | Redo 容量、刷脏、Checkpoint、存储延迟 |
| 连接数耗尽 | 慢事务、空闲未提交连接、连接池上限 |
| 临时磁盘增长 | 大排序、Hash/临时表、宽结果集 |
| 副本延迟 | 大事务、Binlog 生成速率、Applier 和磁盘资源 |

## SQL 优化

### 执行计划

先用代表性参数执行 `EXPLAIN FORMAT=TREE`，确认安全后再用 `EXPLAIN ANALYZE` 比较预估与实际行数。重点寻找扫描过多、循环次数过大、Filesort、临时表、错误 Join 顺序和返回结果过宽。

### 减少无效读取

- 只返回需要的列，避免无条件 `SELECT *`；
- 让过滤条件保持 Sargable，不在索引列上计算或触发隐式类型转换；
- 为列表使用稳定排序和 `LIMIT`；深分页改用基于 `(排序列, id)` 的 Keyset Pagination；
- 避免循环逐条查询关联数据形成 N+1，按结果基数选择 Join 或批量 `IN`；
- 批量更新按稳定索引键分批提交，限制事务时长和日志突发。

```sql
SELECT id, created_at, title
FROM articles
WHERE tenant_id = ?
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

### Join 与子查询

Join 条件必须完整，连接键应有匹配索引；先过滤或聚合再 Join 只有在结果语义等价时才成立。一对多连接会放大行数，聚合和分页前要先明确“一行代表什么”。

子查询不是天然低效。只判断存在性时 `EXISTS` 通常比 Join 后去重更准确；相关子查询能否被优化器改写要看执行计划，不应机械替换。

通用 SQL 改写见 [[后端/数据库/1. SQL/3. SQL 优化|SQL 优化]]。

## 索引优化

复合索引应匹配高频等值条件、范围、排序和覆盖需求。优化时关注：

- 扫描行数是否显著大于返回行数；
- 二级索引是否产生大量随机回表；
- 排序能否利用索引顺序；
- 索引选择性和统计信息是否反映真实分布；
- 宽索引、重复索引和随机主键对写入、缓存及复制的影响。

新增索引要记录服务的 SQL 指纹；删除前覆盖完整业务周期，并检查唯一约束、外键检查和低频报表。索引结构、最左匹配、失效场景和计划解读见 [[后端/数据库/2. 关系型数据库/Mysql/2. MySQL索引原理与优化|索引原理与优化]]。

## 表结构设计优化

- 主键短、稳定且不可变；InnoDB 二级索引会保存主键，过宽主键会放大所有索引；
- 整数和定点数按业务范围选择合理类型，金额不用二进制浮点；
- 统一 `utf8mb4` 和 Collation，避免 Join 两侧字符集/排序规则不一致；
- 把高频读取的小字段和低频大字段分开，减少行宽、页读取和 Buffer Pool 污染；
- JSON 适合边界有限、整体读取的数据；需要约束、关联、排序或高频筛选的属性应独立成列，并按需使用生成列/函数索引；
- 规范化用于减少更新异常；只有实测 Join 或聚合瓶颈时才引入快照、汇总或反范式，并定义校验与重建；
- 分区主要用于数据生命周期和分区裁剪，不会自动让所有查询更快，也不能替代索引。

大表 DDL 可能等待 MDL、重建数据和消耗临时空间；表结构调整应使用兼容迁移和分批回填，见 [[后端/数据库/2. 关系型数据库/Mysql/6. MySQL运维|MySQL 运维]]。

## 配置优化

配置必须从工作负载、硬件和故障目标推导，不使用固定“最佳参数”。

| 配置方向 | 影响 | 风险边界 |
| --- | --- | --- |
| `innodb_buffer_pool_size` | 数据/索引页缓存 | 过大挤压系统、连接和其他缓存内存 |
| Redo 容量 | 写入突发和 Checkpoint 频率 | 过小导致前台刷盘，过大延长最坏恢复时间 |
| `innodb_flush_log_at_trx_commit` | Redo 刷盘强度 | 放宽会扩大故障丢失窗口 |
| `sync_binlog` | Binlog 刷盘强度 | 放宽影响复制/PITR 的持久边界 |
| 连接上限与线程 | 并发和排队 | 过高增加内存、调度和锁竞争 |
| 临时表/排序内存 | 减少磁盘临时文件 | 通常按连接或操作分配，过大可能内存爆发 |

参数调整一次只改变主要变量，记录基线、峰值和回滚方式，同时观察吞吐、P95/P99、错误率、锁等待、Redo/Binlog、复制延迟和系统资源。提高缓存或连接数不能修复错误 SQL、长事务和热点锁。
