# PostgreSQL 性能诊断、参数与扩展

PostgreSQL 调优应先判断瓶颈是计划、锁、连接、内存溢写、Vacuum 还是存储。参数只是改变资源分配和算法阈值，无法修复错误 SQL 或数据模型。

## 执行计划与运行状态

```sql
EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS)
SELECT ...;

SELECT pid, state, xact_start, query_start, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE state <> 'idle';
```

`EXPLAIN ANALYZE` 会执行语句。重点看实际与估算行数、每节点 `loops`、Shared Buffer hit/read、临时文件、排序/Hash 批次和 WAL。一次冷缓存结果与长期生产分布不同，应结合 `pg_stat_statements` 的聚合调用次数、总耗时、行数和临时块；该视图需要预加载并启用扩展。

`pg_stat_activity` 用于发现长事务和等待，`pg_locks` 用于还原阻塞关系，`pg_stat_user_tables`/`pg_stat_user_indexes` 用于观察扫描、Dead Tuple 和维护时间。统计只能说明观察窗口内的行为，不能仅凭低扫描次数删除约束索引或低频报表索引。

## 关键参数的真实作用

| 参数 | 作用 | 常见误区 |
| --- | --- | --- |
| `shared_buffers` | PostgreSQL 共享页缓存 | 设得越大不一定越快，还需给 OS Cache 和查询内存留空间 |
| `work_mem` | 单个排序、Hash 等节点的上限 | 不是每连接一次分配；一个并行复杂查询可能使用多份 |
| `maintenance_work_mem` | Vacuum、建索引等维护操作内存 | 并行维护和 Autovacuum Worker 会放大总占用 |
| `effective_cache_size` | 优化器对可用缓存的估计 | 不会实际分配内存 |
| `max_wal_size` | Checkpoint 间 WAL 目标上限之一 | 不是绝对硬上限，也不控制归档/Slot 保留 |
| `random_page_cost` | 优化器成本模型 | 为“强制走索引”盲目调低会伤害其他查询 |

热点大表的 Autovacuum 触发阈值应按绝对变更量调整 `scale_factor` 和 `threshold`，并确保 Worker、IO 和维护窗口足够。仅提高 Worker 数而不考虑 IO 会让前台查询与多个 Vacuum 互相争用。

## 常见症状

| 症状 | 优先检查 |
| --- | --- |
| 计划突然变差 | 估算/实际行数、统计更新时间、参数分布、版本变化 |
| 临时文件增长 | 排序/Hash 节点、输入规模、`work_mem`，不要直接全局大幅提高 |
| 表持续膨胀 | 长事务、Dead Tuple、Autovacuum 频率、HOT 比例 |
| `pg_wal` 增长 | 归档失败、复制 Slot、Standby 延迟、大事务 |
| 连接耗尽 | 长查询、`idle in transaction`、连接池模式与上限 |
| Checkpoint 延迟尖峰 | WAL 生成速率、Checkpoint 频率、存储吞吐与刷盘分布 |

## 扩展边界

| 扩展 | 能力 | 引入前确认 |
| --- | --- | --- |
| PostGIS | 空间类型、函数与 GiST/SP-GiST 索引 | SRID、坐标变换、索引谓词、升级兼容 |
| TimescaleDB | Hypertable、时间分块、压缩和保留策略 | 社区/商业能力边界、Chunk 规划、备份恢复 |
| pgvector | Vector Type、距离操作符、HNSW/IVFFlat ANN 索引 | 召回率、构建内存、过滤条件与索引版本 |

扩展运行在数据库进程内，版本必须与 PostgreSQL、操作系统和托管服务兼容。升级前要确认二进制与数据格式，备份恢复环境也必须安装兼容扩展。把时序、空间或向量能力放进 PostgreSQL 可以减少系统数量，但高吞吐、独立扩缩容或专项检索需求仍可能适合独立系统。

复制与恢复见 [[后端/数据库/2. 关系型数据库/PostgreSQL/4. PostgreSQL复制、WAL归档与PITR|复制、WAL 归档与 PITR]]。
