# PostgreSQL、扩展类型与运维要点

PostgreSQL 的核心特征是进程式连接模型、Heap 与独立索引、基于 Tuple 的 MVCC、WAL 恢复，以及可扩展的类型、操作符和索引体系。它擅长复杂关系查询和扩展数据能力，但需要持续管理连接、Vacuum、WAL 和表膨胀。

## 进程与内存

主进程负责监听连接并启动 Backend Process；客户端连接通常对应一个服务端 Backend。Checkpointer、Background Writer、WAL Writer、Autovacuum Worker 等后台进程分别承担刷盘和维护工作。

关键内存区域包括：

- `shared_buffers`：PostgreSQL 共享数据页缓存；
- WAL Buffers：提交前暂存 WAL；
- 每个查询节点可能使用的 `work_mem`：排序、Hash、物化等；
- 操作系统 Page Cache：PostgreSQL 并不绕过它，因此不能只看 `shared_buffers` 判断缓存命中。

大量直连会消耗进程和内存，并增加上下文切换。应用通常通过 PgBouncer 等连接池限制活跃 Backend；Transaction Pooling 模式会破坏部分会话级特性，使用临时表、Session Advisory Lock、`LISTEN/NOTIFY` 或会话参数前需确认兼容性。

## Heap、Tuple 与 TOAST

表数据存放在 Heap Page 中，索引与 Heap 分离。Tuple Header 包含 `xmin`、`xmax` 等可见性信息；`ctid` 只是当前物理位置，更新或表重写后会变化，不能作为持久业务 ID。

`UPDATE` 通常创建新 Tuple，并把旧版本标记为过期。若未修改任何索引列且当前页有空间，可使用 HOT（Heap-Only Tuple）更新，减少索引写入。频繁更新的表可通过合理 `fillfactor` 为同页新版本预留空间，但会增加初始表体积。

TOAST 对超大字段进行压缩或页外存储。读取少量普通列不一定加载完整大字段，但频繁修改大值仍会产生明显 WAL 和存储成本。Free Space Map 记录页中可用空间；Visibility Map 标记页面是否全部可见/冻结，帮助 Vacuum 和 Index Only Scan。

## MVCC、WAL 与 Checkpoint

PostgreSQL 通过快照判断 Tuple 版本是否可见。WAL 先于数据页持久化，崩溃后重放日志恢复一致状态；Checkpoint 确保此前脏页逐步落盘并形成恢复起点。Checkpoint 过密会增加写入压力，过疏则需要更多 WAL 空间并延长恢复。

Vacuum 将不再对任何快照可见的 Dead Tuple 标记为可复用，通常不会把普通表文件缩回操作系统；`VACUUM FULL` 会重写并锁表，应只在明确收益和停机/切换方案下使用。

Autovacuum 同时承担三件事：

1. 回收旧 Tuple 空间；
2. `ANALYZE` 更新优化器统计；
3. Freeze 旧事务 ID，防止 Transaction ID Wraparound。

长事务、`idle in transaction`、长期复制槽和更新热点会延迟清理，造成表/索引膨胀、统计滞后或 WAL 堆积。Autovacuum 参数应按大表和热点表单独调整，不能只依赖全局默认。
