# PostgreSQL 复制、WAL 归档与 PITR

PostgreSQL 物理复制传输整个集群的 WAL，逻辑复制传输选定表的行变更。备份与 WAL 归档解决历史恢复；副本主要解决可用性和读扩展，两者不能互相替代。

## 物理流复制

Primary 上的 WAL Sender 将 WAL 流式发送给 Standby，Standby 的 WAL Receiver 接收并重放。异步复制下，Primary 返回提交时 Standby 可能尚未收到 WAL；同步复制可以等待指定 Standby 达到配置的确认级别，以提交延迟换取更小 RPO。

关键位置包括 WAL 生成、发送、接收、刷盘和重放位置。只看单个“延迟秒数”会漏掉网络传输正常但重放受阻的情况。

Hot Standby 可执行只读查询。长查询需要的旧版本与 Standby 重放清理记录冲突时，系统必须选择延迟重放或取消查询；增加容忍窗口会放大复制延迟和 WAL/膨胀成本。

Replication Slot 防止 Primary 删除订阅者尚未消费的 WAL。断开的 Slot 若无人处理，会让 `pg_wal` 持续增长直至磁盘耗尽，因此必须监控 Slot 活跃状态和保留字节，并设置明确的处置策略。

## 逻辑复制

Publication 定义发布表和操作，Subscription 完成初始拷贝后持续应用逻辑变更。它适合选择性同步、跨主要版本迁移和 CDC，但不是完整 Schema 复制方案：

- DDL 通常需单独发布并保证兼容顺序；
- `UPDATE`/`DELETE` 需要可识别旧行的 Replica Identity，通常使用主键；
- Sequence 状态和未发布对象需要单独迁移；
- 订阅端冲突、长事务和复制 Slot 同样可能造成延迟或 WAL 堆积。

## 基础备份、WAL 归档与 PITR

PITR 需要一份一致的 Base Backup，以及从备份起点到目标时刻连续可用的归档 WAL。恢复时将备份还原到隔离环境，配置恢复目标时间、事务 ID 或 Restore Point，重放 WAL 后提升实例。

只有“备份任务成功”不能证明可恢复。恢复演练必须验证：

- Base Backup 与所需 WAL 全部存在、可解密且校验通过；
- 恢复到目标时间后，关键表和业务不变量正确；
- 恢复耗时满足 RTO，归档间隔和复制模式满足 RPO；
- 目标时刻明确避开误操作事务，同时包含此前正确事务；
- 恢复实例不会误连生产客户端或向外发送任务。

## 故障切换

提升 Standby 前应选择 WAL 最完整且健康的候选者，并隔离旧 Primary，避免 Split Brain。切换后需要更新连接入口、重建其他副本，并处理新 Timeline；旧 Primary 不能简单直接加入，通常需重新做 Base Backup 或在条件满足时使用 `pg_rewind`。

同步复制也不能替代 Fencing 和备份。它降低已确认事务丢失风险，却会把 Standby/网络故障传导为提交延迟或不可用，必须为降级策略做明确选择。
