# PostgreSQL 事务、锁与并发控制

PostgreSQL 的普通查询读取 MVCC 快照，通常不会阻塞普通写入。写写冲突、锁定读、DDL 和 Serializable 依然需要锁或冲突检测，因此“MVCC 无锁”是错误理解。

## 隔离级别

| 级别 | PostgreSQL 行为 |
| --- | --- |
| READ UNCOMMITTED | 实际按 READ COMMITTED 处理 |
| READ COMMITTED | 每条命令获取新快照，后续语句可看到其他事务新提交 |
| REPEATABLE READ | 事务保持快照，提供 Snapshot Isolation，但仍可能发生写偏差 |
| SERIALIZABLE | 在快照隔离上使用 SSI 检测危险依赖，无法串行化时中止事务 |

Serializable Snapshot Isolation（SSI）通过 Predicate Lock 和读写依赖识别可能产生序列化异常的事务。Predicate Lock 主要用于冲突检测，不一定阻塞写入；事务可能在提交阶段收到 SQLSTATE `40001`，应用必须回滚并重试整个事务。

唯一约束、排他约束和条件更新仍应优先表达可由数据库直接验证的不变量。Serializable 不能替代请求幂等，也不能撤销事务外副作用。

## 行锁与表锁

PostgreSQL 提供多种行锁强度：

- `FOR UPDATE`：准备修改或删除记录；
- `FOR NO KEY UPDATE`：不会改变被外键引用键值的更新可使用较弱锁；
- `FOR SHARE` 与 `FOR KEY SHARE`：保护读取的行免受相应更新；
- `NOWAIT` 立即失败，`SKIP LOCKED` 跳过已锁记录。

`SKIP LOCKED` 适合多个 Worker 领取任务，返回的是不一致视图，不适合普通业务查询。行锁不会自动阻止插入满足某谓词的新行；跨行约束需要 SSI、锁住共同的父/汇总行，或使用排他约束等重新建模。

表锁有多个模式。普通 DML 获取较弱模式，`ALTER TABLE` 等 DDL 常需要 `ACCESS EXCLUSIVE`，会与绝大多数操作冲突。即使 DDL 本身只改元数据，也可能长时间等待旧事务，并阻塞排在其后的查询。

Advisory Lock 以应用定义的整数键互斥，分 Session 和 Transaction 级。数据库不理解它保护哪条数据，所有代码路径必须遵循同一协议；Session 级锁还容易因连接池复用而泄漏。

## 死锁与超时

PostgreSQL 检测等待环后中止一个事务。统一多行加锁顺序、缩短事务和完善锁定谓词索引可降低死锁。

三个超时解决不同问题：

- `lock_timeout`：等待锁超过上限就终止语句；
- `statement_timeout`：语句总执行时间上限；
- `idle_in_transaction_session_timeout`：事务打开但客户端长期无操作时终止会话。

超时后当前事务可能进入失败状态，必须执行 `ROLLBACK`。只对死锁、`40001` 和明确的瞬时错误进行有限、带抖动的整事务重试；约束错误和逻辑错误不应重试。

MySQL/InnoDB 的快照、隔离和锁实现不同，见 [[后端/数据库/2. 关系型数据库/Mysql/3. 事务与隔离级别|MySQL 事务、MVCC 与隔离级别]]。
