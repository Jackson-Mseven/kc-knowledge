# 指标、SLO 与容量规划

数据库监控的目标不是“指标全”，而是回答三个问题：用户是否受影响、瓶颈在哪里、距离容量上限还有多远。

## 从业务 SLI 到数据库信号

先为关键读写路径定义服务等级指标（SLI），再选择能解释它的数据库指标：

| 层级 | 核心信号 | 说明 |
| --- | --- | --- |
| 用户请求 | 成功率、p50/p95/p99、超时率 | 分位数揭示长尾，平均值会掩盖少量严重慢请求 |
| 数据语义 | 数据新鲜度、读己之写、重复或丢失数 | 副本和异步链路“可用”不等于结果满足业务一致性 |
| 连接 | 活跃/空闲连接、获取等待、拒绝数 | 池等待升高通常表示应用并发超过数据库吞吐能力 |
| 查询 | QPS、查询指纹、总耗时、扫描/返回行数 | 优化优先看累计资源消耗，不只看单次最慢 SQL |
| 并发 | 活跃事务、长事务、锁等待、死锁 | 长事务会放大锁竞争、版本清理和日志保留压力 |
| 资源 | CPU、内存、IOPS、IO 延迟、磁盘、网络 | 饱和度要与查询和等待事件同时解释 |
| 可靠性 | 复制延迟、复制错误、备份年龄、恢复演练结果 | 这些指标直接约束一致性、RPO 和 RTO |

计数器应观察单位时间增量，延迟应使用直方图和分位数；实例、SQL 指纹等标签必须限制基数，不能把原始 SQL 或用户 ID 作为时序标签。

## SLO 与告警

不同路径需要不同 SLO。例如登录查询关注成功率和 p99，报表关注完成时间，异步同步关注数据新鲜度。告警应基于持续业务影响或错误预算消耗，而非单次 CPU 越线；每条告警至少能定位服务、实例和 Runbook。

复制延迟要同时观察字节/日志位置差与时间差：低写入期间“秒数延迟”可能失真。备份成功也不足以证明可恢复，应监控最近一次可验证恢复点，并定期按 [[后端/数据库/9. 高可用、备份与数据可靠性/00. 目录|恢复流程]] 演练。

## 容量模型

容量由数据增长、工作集和峰值吞吐共同决定：

```text
存储需求 ≈ 表数据 + 索引 + MVCC/日志保留 + 临时空间 + 安全余量
连接总预算 = 数据库可承载连接 - 管理/迁移/监控预留
单实例池上限 ≤ 连接总预算 / 应用实例峰值数
```

- 表容量按日增量、保留期和删除回收滞后估算；副本与备份另计，不能只看主库文件大小。
- 内存应覆盖主要热数据和索引工作集；Buffer Pool 命中率需结合物理读延迟判断，单独追求 99% 没有意义。
- CPU 适合判断计算饱和，IOPS 与 IO 延迟用于判断存储排队；磁盘满还会阻断日志、临时文件和恢复操作。
- 用业务峰值而非日均值做吞吐预算，并保留故障切换后少一个节点仍能承载流量的余量。

容量预测必须用真实增长率持续校正。线性外推不适用于突发活动、数据倾斜和索引新增，应给出正常、峰值和故障三个场景。
