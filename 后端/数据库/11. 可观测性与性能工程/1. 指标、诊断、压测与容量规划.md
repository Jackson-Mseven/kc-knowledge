# 指标、诊断、压测与容量规划

性能工程从可观测性开始。数据库请求变慢可能来自 SQL、锁、连接池、CPU、磁盘、网络或副本，必须用链路和指标定位而非凭直觉加机器。

## 核心指标

- 请求：QPS、成功率、p50/p95/p99、错误码、Top SQL；
- 连接：活跃连接、连接池等待、拒绝连接、事务时长；
- 执行：扫描行数、慢查询、临时表/排序、锁等待、死锁；
- 资源：CPU、内存、Buffer Pool 命中、磁盘空间、IOPS、IO 延迟、网络；
- 可靠性：复制延迟、复制错误、备份年龄、恢复演练结果。

## 诊断路径

```text
告警或慢请求 -> trace 定位 SQL/参数 -> 连接池与等待
-> EXPLAIN/锁状态 -> CPU/IO/缓存/副本 -> 修复与回归验证
```

先区分“执行慢”与“等待慢”。优化前记录基线和目标，改动后用相同数据、并发和参数复测。指标应链接 Runbook、业务影响和负责人。

## 压测与容量

压测数据必须包含真实的数据量、倾斜、冷热比例和并发，而非空表单条查询。容量规划基于增长率、保留期、索引/副本放大、备份窗口与恢复时间留余量；磁盘接近耗尽时性能和恢复都会恶化。

## 面试自测

1. p99 升高而平均值正常说明什么？

可能存在锁竞争、GC、IO 抖动、热点或副本切换等长尾问题；平均值会掩盖少量用户的严重体验。

2. 为什么连接池等待不能只靠增大池大小解决？

根因可能是慢 SQL、长事务或数据库资源饱和。更多连接会增加上下文切换和锁竞争，进一步恶化系统。
