# 性能诊断与链路追踪

数据库“慢”可能发生在连接池排队、网络、锁等待、执行、结果传输或副本追赶阶段。诊断顺序应从受影响请求向下收敛，而不是先改参数或加索引。

## 诊断路径

```text
确认影响范围与时间窗
  -> Trace 定位服务、实例、数据库节点和 SQL 指纹
  -> 拆分连接获取、事务、锁等待、执行、网络耗时
  -> 检查执行计划、参数分布与扫描行数
  -> 对照 CPU、IO、内存、日志、复制和变更事件
  -> 形成假设，以相同负载验证修复
```

先判断是单条 SQL、同类查询、单个节点还是全局变慢。只有执行时间增加才直接进入 SQL/计划分析；连接池等待增长可能是下游饱和、连接泄漏或长事务，盲目增大池会增加数据库并发与争用。

## 查询与等待

- **Top SQL**：分别按总耗时、调用次数、平均/尾延迟、逻辑读和临时空间排序。高频中等慢查询通常比偶发最慢查询消耗更多资源。
- **执行计划**：保留 SQL 指纹、参数类型、计划版本和统计信息更新时间；比较估算行数与实际行数，可识别数据倾斜、统计信息过期和错误 Join 顺序。
- **锁等待**：找到阻塞者、等待者、持锁 SQL 与事务开始时间。增加超时只能更快失败，不能修复缺失索引、加锁顺序或过长事务。
- **内存与临时空间**：Buffer Pool 未命中会转为物理读；Hash、Sort 或临时表溢出会转为磁盘 IO。命中率高也不能证明索引和访问路径合理。
- **复制与后台任务**：复制延迟、Checkpoint、Vacuum/Purge、备份和批量回填可能争用 IO 或保留旧版本，应与前台延迟同时间轴分析。

执行计划的具体读法见 [[后端/数据库/1. SQL/3. SQL 优化|SQL 优化]]，MySQL 的锁和死锁机制见 [[后端/数据库/2. 关系型数据库/Mysql/4. 锁机制|MySQL 优化器、锁与诊断]]。

## Trace 与 SQL 的关联

应用应在 Span 中记录数据库系统、操作类型、库名、节点、SQL 指纹、连接等待和行数，不记录密码、Token 或完整敏感参数。原始 SQL 可在受控慢查询日志中保存并脱敏；时序标签只保留低基数字段。

头部采样容易漏掉尾延迟，可组合低比例常规采样、错误必采和慢请求尾部采样。Trace ID 应能关联应用日志、数据库会话或查询注释，但注释不能改变 SQL 指纹聚合或泄露用户数据。

## 变更验证

优化前后必须保持数据集、参数分布、并发和缓存状态可比，同时观察延迟、吞吐、扫描行数、锁、CPU 与 IO。索引、Schema、ORM 或数据库版本变化都可能触发计划回归；必要时灰度发布并保留回滚路径，避免只验证一条“快参数”。
