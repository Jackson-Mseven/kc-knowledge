# 读写分离、分片与分布式一致性

水平扩展不是一个功能，而是把单机数据库原本统一提供的存储、查询、事务和约束拆到多个节点。只有瓶颈已经量化，且单库优化或纵向扩容无法满足容量、吞吐或可用性目标时，额外复杂度才有价值。

## 扩展手段的边界

| 手段 | 解决的问题 | 新增问题 |
| --- | --- | --- |
| 垂直拆分 | 按业务域隔离资源和故障 | 跨库 Join/事务、数据所有权 |
| 读写分离 | 扩展只读吞吐、隔离报表 | 复制延迟、读路由、故障切换 |
| 水平分片 | 突破单节点容量和写吞吐 | 路由、热点、跨分片查询与事务、迁移 |
| 分布式 SQL | 由数据库提供透明分片与分布式事务 | 共识延迟、兼容性、热点与运维成本 |

读副本不是即时副本。刚写完就从副本读取可能看不到自己的写入；登录状态、支付结果等需要 Read-Your-Writes 的路径应读 Primary、使用会话一致性能力，或等待副本追上已知日志位点。副本延迟升高时，把更多流量切向副本会进一步恶化积压。

## 推荐演进顺序

1. 修正 Schema、索引、SQL、长事务和连接池，确认 CPU、I/O、锁或容量的真实瓶颈；
2. 归档冷数据、拆分报表负载；读压力占主导时增加只读副本；
3. 按业务域垂直拆分，使数据所有权和事务边界清晰；
4. 只有单节点容量或写吞吐达到长期上限时，才按稳定业务键水平分片；
5. 在写入生产数据前设计路由、全局 ID、扩缩容、回滚和跨分片查询。

分片后，数据库通常只能保证分片内的唯一性和事务。关键业务不变量应尽量与分片键一致，使相关数据落在同一分片；确实跨分片的流程再选择 [[后端/数据库/8. 分布式数据库与水平扩展/3. 分布式事务与可靠消息|分布式事务或可靠消息]]。

CAP 讨论的是发生网络分区时一致性与可用性的取舍，不是日常状态下“三选二”。实际设计还要明确一致性级别、陈旧窗口、超时行为与恢复方式，见 [[后端/数据库/0. 数据库概览与选型/3. CAP、一致性模型、RPO 与 RTO|CAP 与一致性模型]]。
