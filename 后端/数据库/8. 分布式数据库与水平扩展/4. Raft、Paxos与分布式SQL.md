# Raft、Paxos 与分布式 SQL

共识协议解决的是：多个副本在节点故障和网络分区下，对一串状态变更的顺序达成一致。它不验证业务数据是否正确，也不自动让跨系统副作用原子化。

## Raft 的核心机制

Raft 将时间划分为 Term，每个 Term 最多一个 Leader。客户端写入先追加到 Leader Log，复制到多数成员后才可提交，再按相同顺序应用到状态机。日志项由 Term 和 Index 标识；选举规则保证日志较旧的候选人不能覆盖已提交记录。

拥有 `2f + 1` 个投票成员的集群最多容忍 `f` 个成员不可用，同时仍形成多数派。五节点比三节点多容忍一个故障，但每次同步提交仍需多数确认，成员数不是免费的吞吐扩展。

Follower 与 Leader 失联后发起选举；随机选举超时降低重复平票。成员变更必须使用协议支持的安全过程，不能同时替换多数成员。Linearizable Read 还需确认当前 Leader 仍持有合法领导权，不能仅从任意本地副本返回。

Paxos 用 Prepare/Promise 与 Accept/Accepted 让多数派接受同一 Proposal；Multi-Paxos 在稳定 Leader 下复用领导权以连续提交日志。Raft 与 Paxos 的表述和工程实现不同，但核心安全性都依赖多数派交集，而不是“数据复制三份”本身。

## 分布式 SQL 如何组合这些能力

典型分布式 SQL 把 Key Range/Tablet 分散到节点，每个范围由一个共识组复制；上层通过 MVCC 时间戳、事务协调和分布式执行计划提供 SQL 与事务。一次跨范围事务可能涉及多个共识组，因此延迟取决于网络往返、冲突和参与范围数。

CockroachDB 采用 PostgreSQL Wire Protocol 和相近 SQL 语义，以 Range 和 Raft 复制数据；TiDB 提供 MySQL 兼容 SQL 层，TiKV 负责分布式事务存储，PD 管理时间戳与调度，并可用 TiFlash 承担分析副本。兼容协议不等于与 PostgreSQL/MySQL 完全等价，函数、锁语义、DDL、驱动和运维工具都要按目标版本验证。

## 选择边界

- 跨地域强一致写入受物理网络延迟约束，数据库不能消除光速；把 Leader/Leaseholder 放在主要写入地域。
- 单个热门 Key、单调范围和超大事务仍可能形成热点；“自动分片”不等于自动均衡业务访问。
- 长事务、跨大量 Range 的 Join/扫描会放大协调和失败重试成本。
- 评估 SQL 兼容性、备份恢复、变更数据捕获、扩缩容、故障演练与退出路径，而不只比较基准吞吐。
