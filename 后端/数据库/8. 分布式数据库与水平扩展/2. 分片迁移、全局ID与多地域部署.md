# 分片迁移、全局 ID 与多地域部署

## 分片键与路由

好的分片键同时满足四点：高基数且分布较均匀、出现在主要查询中、与事务边界一致、生命周期内基本不变。只满足“均匀”并不够；随机键会把每次业务查询变成广播。

| 分片方式 | 优点 | 代价 |
| --- | --- | --- |
| Range | 范围查询和顺序扫描自然 | 单调键产生尾部写热点，分布易倾斜 |
| Hash | 写入通常更均匀 | 范围查询需访问多个分片 |
| Directory/映射表 | 可按租户迁移并定制放置 | 路由表成为关键依赖，需要缓存失效和高可用 |

热点既可能来自数据量，也可能来自访问频率。大租户、热门实体和单调时间键即使行数均匀，仍可能压垮单个分片；常见处理是隔离大租户、在业务键后增加可控散列桶，或把热点写入聚合为异步流水，但都会增加查询合并成本。

## 跨分片查询与约束

Scatter-Gather 的延迟受最慢分片决定，并消耗所有分片资源。全局排序需要每个分片返回候选再归并；深分页会重复拉取大量无用数据，应使用稳定复合游标并尽量先限定租户/分片。高频全局报表应由 CDC 构建分析视图，而不是直接扫在线分片。

唯一索引通常只保证分片内唯一。用户名等全局唯一值可由独立目录表预占，或把约束改为 `(tenant_id, value)` 范围内唯一。目录服务必须处理预占超时、释放和幂等重试。

全局 ID 的选择不等同于分片路由：

- 数据库号段服务有序且索引友好，但依赖号段分配；
- Snowflake 类 ID 含时间与节点号，吞吐高，但必须处理时钟回拨和节点号冲突；
- UUID/ULID 无中心生成，UUID v4 随机写入会降低 B-Tree 局部性，时间有序方案还要评估是否暴露生成时间。

不要让外部客户端依赖 ID 中的分片位；否则以后重分片会破坏路由兼容性。

## 在线迁移

迁移期间必须明确每个 Key 的权威位置。常用过程是：记录源位点并复制快照 -> 持续应用 CDC -> 对账 -> 将目标 Key 的写路由切到新分片 -> 等待旧请求排空 -> 切读 -> 保留短期回滚窗口。若使用双写，必须定义部分成功、重复和乱序的收敛规则；仅“同时写两边”不是一致性方案。

校验至少比较主键集合、版本/校验和、关键聚合和抽样业务读取。路由元数据带版本，旧路由收到请求时应重定向或拒绝，而不是继续接受写入。

## 多地域

跨地域同步写入至少支付一次网络往返与多数派确认延迟。常见方案按复杂度递增：

- 单主地域写入，其他地域只读或灾备：冲突最少，但远端写延迟高；
- 按租户或数据归属指定 Home Region：本地写入快，跨归属事务复杂；
- Active-Active 多地域写入：可用性高，但必须为每类数据定义冲突检测与合并，余额、库存等不变量不能靠 Last-Write-Wins。

数据驻留要求决定哪些副本、备份和日志可以跨境；这应进入数据模型和路由规则，而不是部署后的过滤配置。
