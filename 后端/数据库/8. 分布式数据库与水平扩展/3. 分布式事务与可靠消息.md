# 分布式事务与可靠消息

分布式一致性的第一步不是选择协议，而是识别业务不变量。能通过聚合边界或分片键把不变量收敛到一个本地事务时，通常比任何跨服务事务都可靠。

## 方案差异

| 方案 | 原子边界 | 适合 | 主要失败成本 |
| --- | --- | --- | --- |
| 2PC/XA | 多个支持 Prepare/Commit 的资源 | 必须同步提交且参与者可控 | 协调者、锁持有、阻塞与恢复复杂度 |
| TCC | 业务资源的 Try/Confirm/Cancel | 可预留资源、需要较强实时一致性 | 空回滚、悬挂、重复调用和业务侵入 |
| Saga | 一串本地事务与补偿 | 长流程、允许中间状态 | 补偿不等于回滚，隔离性弱 |
| Outbox + 消息 | 本地数据与事件同事务提交 | 异步副作用和最终一致 | 重复、乱序、积压与对账 |

2PC 的 Prepare 阶段要求参与者把可提交状态持久化并保留资源，全部成功后协调者再决定 Commit。它能提供强原子性，但协调者或网络故障会延长锁与不确定状态；不能把第三方 HTTP 接口直接变成 XA 参与者。

TCC 的 Try 预留库存/额度，Confirm 正式生效，Cancel 释放。三个操作都必须幂等；Cancel 可能先于 Try 到达形成空回滚，Try 也可能在 Cancel 后迟到形成悬挂，因此状态机需要记录全局事务与分支状态。

Saga 每步提交本地事务，失败后按逆序执行补偿。补偿是新的业务动作：退款可能失败，邮件无法“撤回”，价格也可能变化。需定义可补偿、可重试和必须人工介入的步骤，并避免其他流程读取尚未完成的中间状态。

## 幂等与去重

超时重试和消息至少一次投递都可能让同一命令执行多次。调用方应为一次逻辑命令生成稳定的 Idempotency Key，服务端通过唯一约束记录请求摘要、处理状态和结果：首次请求执行业务并保存结果；重复 Key 且载荷相同则返回原结果，载荷不同则拒绝。

自然业务键（支付流水号、外部订单号、事件 ID）可直接承担去重职责。只在内存记录 Key 无法跨进程和重启去重，“先查询再插入”也存在并发窗口，最终必须依赖唯一约束。Key 的保留时间应覆盖客户端、消息和人工重放的最长窗口。

## Outbox 的可靠边界

业务表与 Outbox Event 在同一本地事务写入，发布器读取未发送事件并投递。消息中间件确认与数据库标记之间仍会失败，所以消费者必须基于事件 ID 或业务版本幂等；不要把“至少一次投递”描述为 Exactly-Once 业务效果。

事件应包含稳定 ID、聚合 ID、版本、类型和 Schema 版本。对同一聚合按版本应用，检测缺口与旧事件；不同聚合之间不假设全局顺序。积压、死信、重复率和最老未处理事件年龄必须可观测。

一致性完成条件不是“消息发送成功”，而是业务结果可以对账和修复。为关键状态建立源表与下游结果的差异查询，修复操作复用幂等命令，而不是直接手改多个系统。

Outbox 只保证业务数据与事件记录共同提交，不保证消息只投递一次；消费者仍需按事件 ID 或业务版本去重。事务提交与日志持久化机制见 [[后端/数据库/2. 关系型数据库/Mysql/00. 目录|MySQL 与 InnoDB]]。
