# 多地域故障与演练

分布式系统的故障通常是“部分成功”：某些节点、客户端或路由仍可工作，另一些已经超时。演练要验证系统在这些灰色状态下是否保持数据不变量，而不只是进程能否重启。

## 典型故障模型

| 故障 | 主要风险 | 正确边界 |
| --- | --- | --- |
| 单节点/AZ 失联 | 副本重建、延迟升高 | 多数派继续服务，容量仍能承受峰值 |
| 网络分区 | 双主、旧 Leader 接受写入 | 少数派拒绝写，使用 Fencing 隔离旧主 |
| 整个地域不可用 | 仲裁丢失、跨区流量激增 | 按既定 RPO/RTO 切换，不临时修改一致性规则 |
| 时钟漂移 | ID 冲突、租约/时间戳异常 | 监控时钟并让超阈值节点退出关键角色 |
| 路由元数据陈旧 | 写入旧分片、重复请求 | 路由带版本，旧位置拒绝或转发 |
| 再平衡中断 | 快照与增量不一致 | 迁移可续传、可对账，源端保留到切换稳定 |

Fencing Token 是单调递增的任期/租约版本；存储端只接受当前 Token 的写入，从而阻止失联旧主继续修改数据。仅依赖“旧主应该已经停机”无法防止脑裂。

## 多地域冲突

Active-Active 必须按数据类型定义合并规则。集合追加可用唯一事件合并，个人偏好可用版本覆盖；余额扣减、库存下限和唯一用户名涉及不变量，通常需要归属单写、配额预分配或共识事务。Last-Write-Wins 依赖时间顺序，会静默丢失并发写入，不是通用冲突解决方案。

## 演练判定

一次有效演练应给出具体故障、持续时间和通过条件，例如：断开一个 AZ 后写入不丢失、P99 仍低于目标、复制积压在恢复后限定时间内清零、旧主无法写、恢复节点不会覆盖新数据。还应验证客户端超时与重试不会产生重复业务效果。

演练前确认剩余容量和停止条件；演练后对比事务版本、业务聚合和复制位点，而不是只检查节点状态为 Green。无法自动修复的情形必须落到有明确决策人和回滚条件的 Runbook，参见 [[后端/数据库/9. 高可用、备份与数据可靠性/2. 恢复策略、Runbook与容量风险|恢复策略与 Runbook]]。
