# 查询基础：过滤、排序、分页与聚合

SQL 是声明式集合语言：描述结果集合，而非逐行循环。查询正确性同时要求明确筛选语义、稳定排序和可接受的数据访问成本。

## 基础查询模式

```sql
SELECT id, status, total_amount, created_at
FROM orders
WHERE user_id = ?
  AND created_at >= ?
  AND status IN ('pending', 'paid')
ORDER BY created_at DESC, id DESC
LIMIT ?;
```

避免习惯性 `SELECT *`，它会增加网络传输、回表、反序列化和未来 Schema 变更的耦合。`ORDER BY` 应包含可打破并列的稳定列，例如 `id`，否则分页结果可能不稳定。

## 聚合

```sql
SELECT user_id, COUNT(*) AS order_count, SUM(total_amount) AS gross_amount
FROM orders
WHERE status = 'paid'
  AND created_at >= ?
GROUP BY user_id
HAVING SUM(total_amount) >= ?;
```

`WHERE` 在聚合前过滤行，`HAVING` 在分组后过滤组。聚合空集、`NULL`、时区与金额精度都需要明确业务语义。

## 分页

Offset 分页直观但深页需要跳过大量记录，且写入期间可能重复或漏读。时间线通常更适合 Keyset/Cursor 分页：

```sql
SELECT id, created_at, status
FROM orders
WHERE user_id = ?
  AND (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT ?;
```

游标必须包含稳定排序键，并匹配复合索引。它不天然支持跳转到任意页码；若产品需要页码，应接受对应成本或提供近似方案。

## 常见错误

- 把 `NULL` 当作普通值比较；
- 未限定排序就分页；
- 使用函数包裹索引列导致范围访问失效；
- 在应用内拉取全量再过滤或聚合；
- 用深 Offset 处理无限增长的列表。

实际优化见 [[后端/数据库/3. 索引与查询优化/1. 索引、执行计划与慢查询治理|索引、查询优化与执行计划]]。

## 面试自测

1. `WHERE` 和 `HAVING` 有什么区别？

`WHERE` 过滤参与分组的原始行，`HAVING` 过滤聚合完成后的分组结果。能在 `WHERE` 中完成的过滤通常应尽早完成。

2. 为什么 Cursor 分页较稳定？

它依据上页最后一条记录的排序键继续扫描，而不是按行数跳过。新插入的前置数据较少造成已有页的偏移变化。
