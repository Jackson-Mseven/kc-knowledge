# 多表查询：Join、子查询、EXISTS 与集合操作

多表查询的核心是先明确结果的粒度，再选择关联方式。若一行代表“订单”，就不能在关联订单项后误把每个订单项当作一个订单。

## Join

```sql
SELECT o.id, o.status, o.total_amount, u.display_name
FROM orders AS o
JOIN users AS u ON u.id = o.user_id
WHERE o.created_at >= ?
ORDER BY o.created_at DESC;
```

- `INNER JOIN` 仅返回两侧匹配记录；
- `LEFT JOIN` 保留左表记录，右侧不存在时为 `NULL`；
- `CROSS JOIN` 产生组合，只有确实需要笛卡尔积时使用；
- 关联条件遗漏或错误会让行数爆炸。

Join 两侧的关联列应有合适索引。外键约束不一定自动创建索引，需按数据库产品和查询模式确认。

## EXISTS 与子查询

```sql
SELECT u.id, u.email
FROM users AS u
WHERE EXISTS (
  SELECT 1
  FROM orders AS o
  WHERE o.user_id = u.id
    AND o.status = 'paid'
);
```

当只关心关联记录是否存在时，`EXISTS` 通常比 Join 后再去重更贴切。子查询能表达局部集合，但是否高效仍要查看优化器计划；不要凭形式断言哪种写法一定快。

## 集合操作

- `UNION` 合并并去重；
- `UNION ALL` 直接拼接结果，通常成本更低；
- `INTERSECT` 取交集；
- `EXCEPT` 取差集。

参与集合操作的列数和类型需要兼容。数据量大时，应确认去重、排序和临时空间成本。

## N+1 查询

先查 N 条订单，再循环查询每条订单的用户或商品，会产生 N+1 次访问。优先采用 Join、批量 `IN` 查询或 ORM 预加载，并用 SQL 日志和指标确认实际查询数量。不要用一个超大 Join 取代所有场景，否则可能因一对多展开导致应用内存暴涨。

## 面试自测

1. `LEFT JOIN` 后在 `WHERE` 中写右表条件为什么可能变成内连接？

右表不存在时列为 `NULL`，`WHERE right_table.status = 'paid'` 会把这些行过滤掉。若要保留左表行，应把右表筛选条件放入 `ON` 子句并明确空值语义。

2. 什么时候优先使用 `EXISTS`？

当目标是判断关联记录是否存在且不需要返回右表字段时，`EXISTS` 直接表达意图，也能避免一对多 Join 带来的重复行。
