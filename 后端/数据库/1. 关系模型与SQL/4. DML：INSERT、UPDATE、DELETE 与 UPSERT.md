# DML：INSERT、UPDATE、DELETE 与 UPSERT

Data Manipulation Language（DML）修改表中的数据。写操作正确性的重点是参数化、影响行数、约束冲突、事务边界和可重试性。

## 基本写入

```sql
INSERT INTO users (email, display_name)
VALUES (?, ?);

UPDATE orders
SET status = 'cancelled'
WHERE id = ?
  AND status = 'pending';

DELETE FROM sessions
WHERE expires_at < CURRENT_TIMESTAMP;
```

参数占位符随驱动变化，例如 `$1`、`?` 或命名参数；值绝不能通过字符串拼接进入 SQL。`UPDATE` 和 `DELETE` 必须先确认筛选条件、预期影响行数和回滚路径。

## 条件更新与状态机

状态迁移应把前置状态放进 `WHERE`，并检查受影响行数：

```sql
UPDATE inventory
SET available = available - ?
WHERE sku_id = ?
  AND available >= ?;
```

影响一行才代表扣减成功。它避免了先读库存再写库存的竞态；但订单创建、支付回调和消息重试仍需用唯一约束与幂等键保护。

## UPSERT 的边界

不同产品使用 `INSERT ... ON CONFLICT`、`INSERT ... ON DUPLICATE KEY UPDATE` 或 `MERGE`。UPSERT 适合明确的唯一键冲突场景，但应注意冲突更新是否会覆盖用户字段、触发审计、改变更新时间或造成热点竞争。

```sql
INSERT INTO user_preferences (user_id, theme, updated_at)
VALUES (?, ?, CURRENT_TIMESTAMP)
ON CONFLICT (user_id)
DO UPDATE SET theme = EXCLUDED.theme, updated_at = CURRENT_TIMESTAMP;
```

以上为 PostgreSQL 语法；MySQL 需要使用其方言。不要把不同数据库的 UPSERT 语义直接互换。

## 批量操作

大范围更新/删除按主键或时间窗口拆小批，记录 checkpoint，限制速率并观测锁、复制延迟和日志空间。任何生产批量 DML 都应先在只读查询中确认条件和影响行数。

## 面试自测

1. 为什么状态更新要带旧状态条件？

它让状态迁移成为一次原子比较并更新，能避免并发请求将已完成或已取消的订单错误覆盖。

2. UPSERT 是否天然幂等？

不一定。其业务效果取决于冲突键和更新字段；例如每次冲突都累加计数就不是普通的覆盖幂等，需要结合请求 ID 或去重记录设计。
