# SQL 注入、参数化查询与动态 SQL 白名单

SQL 注入是把不可信输入当作 SQL 语法执行的问题。防护核心是参数绑定、最小权限和对无法参数化标识符的严格白名单。

## 参数化查询

```ts
import { Pool } from 'pg'

const pool = new Pool({ connectionString: process.env.DATABASE_URL })

export async function findOrder(orderId: number) {
  if (!Number.isSafeInteger(orderId) || orderId <= 0) {
    throw new Error('invalid order id')
  }

  const result = await pool.query(
    'SELECT id, user_id, status, total_amount FROM orders WHERE id = $1',
    [orderId],
  )

  return result.rows[0] ?? null
}
```

占位符只绑定值，不绑定 SQL 关键字、表名、列名或排序方向。不同驱动的占位符形式不同，但都应使用驱动提供的参数 API。

## 动态排序的安全写法

```ts
const sortableColumns = {
  createdAt: 'created_at',
  totalAmount: 'total_amount',
} as const

type SortKey = keyof typeof sortableColumns

function toSortColumn(value: string): string {
  if (!(value in sortableColumns)) {
    throw new Error('invalid sort key')
  }
  return sortableColumns[value as SortKey]
}
```

表名、列名与 `ASC`/`DESC` 必须由固定映射生成，不能直接插入用户字符串。分页大小也要设置上限，避免查询被恶意放大。

## 纵深防护

- 应用账号只授予需要的库、表与 DML 权限；
- 输入校验用于业务合法性，但不能取代参数化；
- 日志记录结构化错误，避免回显完整 SQL、堆栈和敏感参数；
- 迁移账号与业务账号分离，生产业务账号不拥有 DDL 权限；
- 定期审查 ORM 的原生查询接口与动态筛选构造。

## 面试自测

1. 使用 ORM 后还会有 SQL 注入吗？

普通条件 API 通常会参数化值，但原生 SQL、字符串拼接、动态字段和错误的模板接口仍可能注入。应审查最终生成 SQL 的构造路径。

2. 为什么不能参数化列名？

绑定参数代表数据值，不参与 SQL 语法解析。列名属于标识符，必须用代码中定义的白名单映射控制。
