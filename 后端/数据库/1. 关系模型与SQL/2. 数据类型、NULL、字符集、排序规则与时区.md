# 数据类型、NULL、字符集、排序规则与时区

数据类型不仅决定存储大小，也决定比较、排序、精度、索引和跨系统传输语义。类型设计含糊往往会在报表、国际化或数据迁移时暴露。

## 类型选择原则

| 数据 | 推荐做法 | 避免 |
| --- | --- | --- |
| 金额 | `DECIMAL(p, s)` 或最小货币单位整数 | `FLOAT`、`DOUBLE` |
| 布尔 | 原生布尔或受约束的小整数 | 用任意字符串表示状态 |
| 时间点 | UTC 时刻，明确数据库类型 | 混用本地时间与无时区字符串 |
| 日期 | 生日、账期用 `DATE` | 用带时区时间戳表示日期 |
| 枚举状态 | 受约束字符串或字典表 | 没有约束的自由文本 |
| JSON | 扩展字段、原始事件 | 用 JSON 逃避高频关系建模 |

`DECIMAL(12, 2)` 适合最多十位整数、两位小数的定点数。货币还应保存币种和舍入规则；不能假设所有币种都是两位小数。

## NULL 与三值逻辑

`NULL` 表示未知或不适用，不等于空字符串、0 或 `false`。比较结果可能是 `TRUE`、`FALSE` 或 `UNKNOWN`，而 `WHERE` 只保留 `TRUE`。

```sql
SELECT id FROM orders WHERE paid_at IS NULL;
SELECT id FROM orders WHERE paid_at = NULL;
```

第一条查询未支付订单；第二条通常不返回任何行。设计前要区分“未填写”“未知”“不适用”和“默认值”，并尽量用 `NOT NULL` 缩小歧义。

## 字符集与排序规则

生产系统通常统一使用 Unicode 字符集，例如 MySQL 的 `utf8mb4`。排序规则（collation）决定字符串的比较、大小写与重音是否等价，影响 `UNIQUE` 的含义和索引排序。用户名、邮箱和搜索词是否大小写敏感应是明确的业务规则，而非默认配置的偶然结果。

## 时间和时区

将“时刻”和“本地日期”分开：订单创建时间适合存 UTC 时刻；用户生日、营业日、账期截止日通常应保存 `DATE` 与业务时区。展示时再转换为用户时区。夏令时会导致某些本地时刻不存在或重复，不能靠字符串拼接处理。

## 面试自测

1. 为什么金额不能使用浮点数？

二进制浮点无法精确表示很多十进制小数，累积计算会出现误差。定点数或最小单位整数可定义精确的舍入与比较规则。

2. `NULL` 为什么不能用 `=` 比较？

未知值与任意值比较都不是确定真，结果为 `UNKNOWN`。应使用 `IS NULL` 或 `IS NOT NULL`。
