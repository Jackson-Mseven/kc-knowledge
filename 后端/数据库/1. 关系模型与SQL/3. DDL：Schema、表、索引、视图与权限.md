# DDL：Schema、表、索引、视图与权限

Data Definition Language（DDL）定义数据库结构。生产 DDL 应通过版本化迁移执行，不能靠手工控制台操作维持环境一致。

## 常用对象

- **Schema**：命名空间或逻辑隔离单元；
- **Table**：保存行数据与约束；
- **Index**：以空间和写入成本换取查询访问路径；
- **View**：封装稳定查询接口，普通视图通常不保存数据；
- **Materialized View**：保存查询结果，需要明确刷新策略；
- **Role/Grant**：定义账户权限与最小访问范围。

```sql
CREATE INDEX idx_orders_user_created_at
ON orders (user_id, created_at DESC);

CREATE VIEW paid_order_summary AS
SELECT user_id, COUNT(*) AS order_count, SUM(total_amount) AS total_amount
FROM orders
WHERE status = 'paid'
GROUP BY user_id;

GRANT SELECT, INSERT, UPDATE ON orders TO app_writer;
```

索引与视图的语法、刷新和权限模型因产品而异。应用账号通常不应有 `DROP`、账号管理或任意 Schema 修改权限。

## 迁移原则

采用 Expand-Migrate-Contract：先新增兼容字段或表，再回填并切换应用读取，确认旧版本退场后最后删除旧结构。大表建索引、改列类型或增加约束可能产生锁与表重写，必须在接近生产规模环境测试。

## 视图的适用边界

视图能隐藏复杂 Join、限制暴露列、为报表提供稳定接口；但不会自动让查询变快。若视图嵌套复杂、缺少索引或返回过多数据，优化器仍要承担相应成本。

## 权限最小化

- 业务读写、迁移、分析、备份和运维使用不同角色；
- 按库、Schema、表和操作授权，避免业务账户使用超级用户；
- 密码和证书放入 Secret 管理系统，支持轮换；
- 审计 DDL、权限变更与敏感表读取。

## 面试自测

1. 为什么线上加索引也需要谨慎？

创建索引会扫描数据、占用 IO 和磁盘，并可能持锁或影响复制。即使数据库支持在线 DDL，也要评估版本、表大小、并发写入与回滚方案。

2. 视图能替代权限控制吗？

视图可减少暴露列，但仍要配合底层表权限、角色划分和应用授权；不能把视图当作唯一安全边界。
