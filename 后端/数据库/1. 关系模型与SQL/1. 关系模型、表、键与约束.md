# 关系模型、表、键与约束

关系模型用表表达实体，用外键表达引用关系，用约束把业务中不可违反的规则交给数据库验证。它是所有可靠 SQL 设计的起点。

## 基本术语

| 概念 | 作用 | 示例 |
| --- | --- | --- |
| 表 | 同类实体的集合 | `users`、`orders` |
| 行/元组 | 一条实体事实 | 一笔订单 |
| 列/属性 | 实体的一个字段 | `created_at` |
| 主键 | 稳定且唯一地标识一行 | `orders.id` |
| 候选键 | 也可唯一标识行的业务键 | `users.email` |
| 外键 | 约束引用目标存在 | `orders.user_id` |
| 检查约束 | 限制合法值或范围 | `amount >= 0` |

## 一个可执行的订单模型

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  email VARCHAR(255) NOT NULL UNIQUE,
  display_name VARCHAR(80) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
  id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  user_id BIGINT NOT NULL,
  status VARCHAR(20) NOT NULL,
  total_amount DECIMAL(12, 2) NOT NULL,
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES users(id),
  CONSTRAINT ck_orders_status CHECK (status IN ('pending', 'paid', 'cancelled')),
  CONSTRAINT ck_orders_total_amount CHECK (total_amount >= 0)
);
```

方言会影响自增列、时间函数与检查约束细节，但“由约束表达不变量”的原则不变。

## 约束比先查后写可靠

应用先执行 `SELECT` 判断邮箱是否存在，再插入，无法抵抗并发请求：两个请求都可能在插入前读到不存在。`UNIQUE` 才是最终裁判；应用应捕获唯一冲突并返回稳定的业务结果。

外键能防止悬挂引用，但在高吞吐、跨服务或分库场景也会增加写入耦合。是否启用要看边界，而不是一律禁用；即使不用外键，引用完整性也要由可靠流程验证。

## 主键选择

- 自增整数紧凑、索引局部性好，适合单库；
- UUID 方便分布式生成，但索引更大，随机写入可能降低局部性；
- ULID 等有序 ID 兼顾分布式与大致时间顺序，仍需评估实现和泄露语义；
- 业务编号应与内部主键分开，避免需求变化影响引用关系。

## 面试自测

1. 主键和唯一约束有什么不同？

两者都要求唯一；主键还承担行身份，通常不可为空且每表只有一个。唯一约束可有多个，用来表达邮箱、租户内编码等候选键。

2. 为什么应用校验不能代替数据库约束？

并发、重试、旧版本服务和脚本可能绕开应用校验。约束在数据写入边界统一执行，能作为最终兜底。
