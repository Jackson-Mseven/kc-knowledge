# 工程化、测试、SSR 与发布

Web Component 的浏览器 API 是标准的，但源码编译、组件注册、类型分发、SSR、版本兼容和跨框架测试仍需要完整工程体系。

## 推荐目录

```text
src/
  components/
    button/
      acme-button.ts
      acme-button.css.ts
      acme-button.test.ts
  styles/
    tokens.css
  define.ts              # 集中注册全部标签
  index.ts               # 导出类，不强制注册
test/
  fixtures/              # 原生/React/Vue 集成页
  e2e/
custom-elements.json
package.json
```

把“导出类”和“产生全局注册副作用”分开，消费者可以选择一次注册全部组件或按需注册。

```ts
// index.ts
export { AcmeButton } from './components/button/acme-button.js'

// define.ts
import { AcmeButton } from './components/button/acme-button.js'

if (!customElements.get('acme-button')) {
  customElements.define('acme-button', AcmeButton)
}
```

## 构建目标

现代组件库通常发布标准 ESM，保留浏览器能原生处理的模块结构，并针对明确浏览器范围转换语法。是否打包成单文件取决于分发场景：

- npm 应用依赖：保留模块和 Tree Shaking，交给应用构建器；
- CDN 单标签脚本：可提供独立 bundle；
- 第三方嵌入：还要考虑依赖去重、CSP、SRI 和加载失败；
- 旧浏览器：按产品支持矩阵决定 Polyfill/差异构建，不默认扩大体积。

不要转译 Custom Element 类时破坏原生 class 继承语义。目标浏览器若过旧，需要使用经过验证的 Polyfill 和构建配置，而不是只把语法降级。

## package.json 与 Exports

```json
{
  "name": "@acme/elements",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./define": {
      "types": "./dist/define.d.ts",
      "import": "./dist/define.js"
    },
    "./button": {
      "types": "./dist/components/button/acme-button.d.ts",
      "import": "./dist/components/button/acme-button.js"
    }
  },
  "sideEffects": ["./dist/define.js", "./dist/**/*.css"]
}
```

实际字段按构建产物调整。含 `customElements.define()` 的模块具有副作用，错误标记 `sideEffects: false` 可能被消费者构建器删除。Exports 中每个公开路径都视为版本化 API。

## TypeScript DOM 类型

组件类应加入 `HTMLElementTagNameMap`：

```ts
export class AcmeDialog extends HTMLElement {
  open = false
  showModal(): void {}
  close(): void {}
}

declare global {
  interface HTMLElementTagNameMap {
    'acme-dialog': AcmeDialog
  }
}
```

这样 `document.querySelector('acme-dialog')`、`document.createElement('acme-dialog')` 能得到具体类型。React/Vue 的模板/JSX 类型可能需要独立适配包，避免核心包硬依赖所有框架类型。

## Custom Elements Manifest

Custom Elements Manifest 是描述标签、Attribute、Property、Event、Slot、CSS Part 和 CSS Custom Property 的机器可读元数据，可供文档站、IDE、Storybook 和框架 Wrapper 生成工具消费。

元数据必须从实际源码/类型生成并进入 CI 校验，防止文档与实现漂移。组件的事件 detail 类型、默认值、反射行为和弃用信息仍应有人工说明。

## SSR 与 Declarative Shadow DOM

普通服务端可以输出 Custom Element 标签和 Light DOM，但 Shadow Root 需要 Declarative Shadow DOM 才能随 HTML 流建立：

```html
<acme-profile name="Ada">
  <template shadowrootmode="open">
    <style>:host { display: block }</style>
    <article><strong>Ada</strong></article>
  </template>
</acme-profile>
```

SSR 架构需要决定：

- 服务端是否执行组件 render；
- Shadow DOM 是声明式输出还是客户端创建；
- 如何序列化 Property，非原始对象不能直接放 Attribute；
- 客户端是 Hydration、事件绑定还是重新渲染；
- JS 失败时首屏内容是否仍可阅读和操作；
- 服务端与客户端组件版本不一致时如何降级。

Lit 有对应 SSR/Hydration 工具，但需按使用的具体版本、框架和部署环境采用官方方案。不要把客户端 LitElement 直接放到任意 Node DOM 模拟器就假设能正确 SSR。

## 避免 FOUC 与布局偏移

- 用 Declarative Shadow DOM 带出关键结构和样式；
- 为宿主预设 `display`、最小尺寸或 aspect-ratio；
- 未定义回退内容与升级后内容结构尽量一致；
- 关键组件模块尽早 preload/modulepreload，但不阻塞无关首屏；
- 不用 `:not(:defined) { display: none }` 隐藏会参与布局的大块内容；
- 字体、图片和异步数据仍按普通 Web 性能方法治理。

## 单元与组件测试

适合真实浏览器运行的 Web Test Runner、Vitest Browser Mode 或对应项目工具；纯 DOM 模拟环境不一定完整实现 Custom Elements、Shadow DOM、ElementInternals 和布局。

```ts
import { expect, fixture, html } from '@open-wc/testing'
import '../src/define.js'

it('点击后发出 count-change', async () => {
  const element = await fixture(html`<acme-counter count="1"></acme-counter>`)
  const eventPromise = new Promise<CustomEvent>((resolve) => {
    element.addEventListener('count-change', (event) => resolve(event as CustomEvent), {
      once: true,
    })
  })

  element.shadowRoot!.querySelector('button')!.click()
  const event = await eventPromise
  expect(event.detail.count).to.equal(2)
})
```

测试优先断言公共行为：Attribute/Property、Event、Slot、表单值、焦点和可访问语义。只有组件内部算法需要时才过度依赖私有 Shadow DOM 结构。

## E2E 与跨浏览器

Playwright 适合测试组件展示页和真实应用集成。关键矩阵至少覆盖 Chromium、Firefox、WebKit，尤其关注：

- 自定义元素定义前/后升级；
- Shadow DOM 查询、焦点和事件 retargeting；
- Form-associated、ElementInternals 和原生校验；
- Declarative Shadow DOM 与 Hydration；
- React/Vue Property 和自定义事件；
- 键盘、读屏相关可观察状态；
- CSP、动态 import 和 CDN 加载失败。

Playwright Locator 能在很多情况下跨 open Shadow DOM 定位，但 XPath 和 closed root 等行为不同。测试不要依赖 closed 内部实现。

## 可访问性与视觉回归

- axe 等自动扫描基础规则；
- 键盘按完整交互模式测试焦点顺序；
- 在真实读屏组合验证关键控件；
- 截图覆盖默认、Hover、Focus、Disabled、Invalid、Loading、RTL、深色和高对比；
- 视觉基线固定字体、DPR、动画和平台环境；
- Slot、长文本、字体放大和容器窄宽纳入故事/用例。

## 版本治理

以下变化通常可能是 Breaking Change：

- 删除/重命名标签、Attribute、Property、Method、Event；
- 修改 Event detail、冒泡/composed/cancelable 语义；
- 删除或重命名 Slot、Part、公共 CSS Token；
- 修改表单值格式、默认值和校验行为；
- 改变焦点、键盘或 ARIA 语义；
- 改变宿主默认 display/尺寸，造成布局变化；
- 提高浏览器、框架或 TypeScript 最低版本。

使用 SemVer、Changesets/发布说明和迁移文档。废弃 API 可在开发环境警告一个版本周期，但不能在生产控制台刷屏。

## 发布检查清单

- ESM 和类型声明能被目标构建器正确解析；
- 全量注册与按需注册都能工作；
- 同一标签重复加载行为明确；
- 包的 sideEffects、exports、CSS 与资源路径正确；
- Custom Elements Manifest 和文档同步；
- 原生 HTML、React、Vue 集成用例通过；
- SSR/无 JS/慢 JS 情况有可接受回退；
- Chrome、Firefox、Safari 目标版本测试通过；
- 包体、实例创建、更新和内存符合预算；
- CSP、Trusted Types、依赖漏洞和 Source Map 策略已验证。
