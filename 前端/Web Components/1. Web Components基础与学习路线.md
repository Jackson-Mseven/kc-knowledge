# Web Components 基础与学习路线

Web Components 是一组浏览器原生标准，用于创建可复用、自定义且能够封装内部实现的 HTML 元素。它不是单一框架，也不负责路由、请求、全局状态和完整应用架构。

## 核心标准

| 能力 | 作用 | 核心 API |
| --- | --- | --- |
| Custom Elements | 注册自定义标签及生命周期 | `customElements.define()`、`HTMLElement` |
| Shadow DOM | 建立 DOM 和样式封装边界 | `attachShadow()`、`shadowRoot` |
| HTML Templates | 声明暂不渲染的可克隆结构 | `<template>`、`DocumentFragment` |
| Slots | 把使用者内容投影到组件内部 | `<slot>`、`slot`、`slotchange` |
| ES Modules | 分发、加载和组织组件代码 | `import`、`export` |

这些标准可以独立使用。组件可以只实现 Custom Element，不创建 Shadow DOM；普通页面也能使用 `<template>`，无需注册组件。

## 最小示例

```html
<user-greeting name="Ada"></user-greeting>

<script type="module">
  class UserGreeting extends HTMLElement {
    static observedAttributes = ['name']

    constructor() {
      super()
      this.attachShadow({ mode: 'open' })
    }

    connectedCallback() {
      this.render()
    }

    attributeChangedCallback() {
      if (this.isConnected) this.render()
    }

    render() {
      const name = this.getAttribute('name') ?? '访客'
      this.shadowRoot.textContent = `你好，${name}`
    }
  }

  customElements.define('user-greeting', UserGreeting)
</script>
```

自定义元素名称必须包含连字符，例如 `user-greeting`，这是为了与未来新增的原生 HTML 标签区分。注册表以当前 Window 为范围，同名元素不能重复注册。

## 浏览器解析与升级

浏览器遇到尚未注册的 `<user-greeting>` 时，先把它当作未知 HTMLElement 放入 DOM。模块加载并执行 `customElements.define()` 后，已有匹配节点会被 upgrade，构造函数和相应生命周期随后执行。

因此要考虑：

- 定义前元素可能短暂显示未初始化内容；
- 属性和子节点可能在升级前就已经存在；
- 组件脚本加载失败时仍应保留可理解的回退内容；
- `customElements.whenDefined('user-greeting')` 可等待定义完成；
- `customElements.upgrade(root)` 可主动升级某个分离 DOM 子树。

可用 CSS 降低未定义时的视觉跳变，但不要无期限隐藏内容：

```css
user-greeting:not(:defined) {
  visibility: hidden;
}
```

## 两类自定义元素

### Autonomous custom element

自主自定义元素继承 `HTMLElement`，使用自己的标签名：

```html
<app-dialog></app-dialog>
```

这是兼容性、工具链和心智负担最稳定的主流方案。

### Customized built-in element

定制内置元素继承 `HTMLButtonElement` 等，并通过 `is` 使用：

```js
class ConfirmButton extends HTMLButtonElement {}
customElements.define('confirm-button', ConfirmButton, { extends: 'button' })
```

```html
<button is="confirm-button">删除</button>
```

它能保留内置语义，但浏览器支持和框架集成不如自主元素一致。生产组件通常优先自主元素，再通过 ElementInternals、ARIA 和键盘行为补足语义。

## 与框架组件的区别

| 维度 | Web Components | React/Vue 等框架组件 |
| --- | --- | --- |
| 运行标准 | 浏览器原生 | 框架运行时 |
| 跨框架消费 | 较好 | 通常需要适配 |
| 样式封装 | Shadow DOM 原生提供 | CSS Modules、Scoped CSS 等 |
| 响应式渲染 | 需要自写或使用 Lit | 框架内置 |
| 状态/路由/数据 | 不提供 | 生态完整 |
| SSR/Hydration | 需要额外方案 | 框架通常有成熟方案 |
| 语义与表单 | 需要主动实现 | 通常有框架封装但仍依赖 HTML |

Web Components 更像组件的跨技术栈分发协议。设计系统、支付/地图等嵌入式组件、CMS 小部件和微前端边界通常适合；单一框架内部的普通业务组件不必仅为“标准化”全部改写。

## 适用场景

- 设计系统需要同时服务 React、Vue、原生 HTML 或多个遗留系统；
- 第三方嵌入式组件要以一个标签交付；
- 长生命周期组件库希望降低对单一框架的绑定；
- 微前端需要组件级 DOM/样式边界；
- 浏览器插件向未知页面注入隔离 UI；
- CMS/低代码平台需要可声明的自定义标签。

不适合仅凭这一点决定：

- 团队只有一个框架且已有成熟组件库；
- 强依赖框架 Context、路由、Server Components 或专有 SSR；
- 组件只是页面内部的一次性业务片段；
- 期望 Shadow DOM 自动解决权限、安全和应用级隔离。

## 能力边界

- Shadow DOM 是封装边界，不是安全沙箱；
- closed Shadow Root 不是可靠的保密或权限机制；
- Custom Element 注册表不自动解决多版本依赖冲突；
- DOM 封装不提供网络、JavaScript 全局变量和存储隔离；
- Web Components 不能替代 iframe 的进程/Origin 级隔离；
- “框架无关”表示消费者接口基于 DOM 标准，不表示实现没有运行时依赖。

## 最小生产检查

- 标签名带组织前缀，避免全局冲突；
- Attribute、Property、Event、Slot、Part 构成清晰公共 API；
- 生命周期重复连接时不会重复订阅或泄漏；
- 支持键盘、读屏、字体缩放、Reduced Motion 和高对比；
- 主题通过稳定 token/Part 暴露，而不是让消费者穿透内部 DOM；
- 自定义事件的名称、payload、冒泡和 composed 行为有文档；
- 测试定义前升级、动态移动、断开重连和多个实例；
- ESM、类型声明、包 exports、版本和浏览器支持范围明确。
