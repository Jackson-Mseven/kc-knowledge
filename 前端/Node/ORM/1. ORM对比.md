# Node ORM 对比

| 工具 | 类型 | 类型体验 | 抽象风格 | 适合场景 |
| --- | --- | --- | --- | --- |
| Prisma | ORM/生成 Client | 强 | Schema + Client | TypeScript API、快速交付 |
| Drizzle | ORM/Query Builder | 强 | SQL-like | Serverless、强调 SQL 控制 |
| TypeORM | 传统 ORM | 中强 | Entity/Decorator | Nest、传统实体模型 |
| Sequelize | 传统 ORM | 中 | Model/Association | 成熟遗留与多数据库项目 |
| MikroORM | Data Mapper | 强 | Unit of Work | 复杂领域与关系模型 |
| Knex | Query Builder | 需自建 | SQL Builder | 自主数据层、复杂 SQL |
| Mongoose | MongoDB ODM | 中强 | Document/Schema | MongoDB 文档模型 |

## 选型建议

- 快速 TypeScript CRUD：Prisma；
- 接近 SQL、轻运行时/边缘：Drizzle；
- Nest 与装饰器 Entity：TypeORM；
- 既有成熟 Sequelize 项目：继续治理通常优于盲目迁移；
- 复杂领域、Unit of Work：MikroORM；
- 需要最大 SQL 控制且愿意自建抽象：Knex；
- MongoDB：Mongoose 或原生 Driver，不能与 SQL ORM直接比较。

## 通用评估

数据库/驱动支持、迁移可靠性、事务语义、类型推导、Raw SQL、连接池、Serverless/Edge、生态维护和团队 SQL 能力。用真实复杂查询、批量写入和事务做 PoC，不只比较简单 CRUD。

## 能力矩阵

| 能力 | Prisma | Drizzle | TypeORM | Sequelize | MikroORM | Knex | Mongoose |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Schema 来源 | Prisma DSL | TypeScript | Decorator/Schema | Model | Decorator/Schema | Migration/SQL | Mongoose Schema |
| 类型安全 | 很强、生成 | 很强、推导 | 较强 | 中等 | 很强 | 基础泛型 | Schema 推导 |
| 关系抽象 | include/nested | Relations/Join | Entity Relation | Association | Collection/UoW | 手写 Join | populate/引用 |
| 迁移 | Prisma Migrate | Drizzle Kit | CLI Migration | CLI Migration | Migrator | 内建 Migration | 通常自行治理 |
| 原生查询 | Raw SQL | `sql` 核心能力 | QueryBuilder/raw | Raw Query | QB/raw | 核心能力 | Aggregation |
| 状态追踪 | 无传统 UoW | 无 | Entity save | Model Instance | Unit of Work | 无 | Document tracking |

## PoC 检查清单

1. 关系查询与分页是否生成合理 SQL；
2. 跨 Service 事务是否共享同一连接；
3. 批量写入、upsert、锁和隔离级别是否满足业务；
4. CTE、窗口函数、RLS 和数据库扩展如何表达；
5. 迁移能否处理大表、回填、索引和零停机；
6. 容器、Serverless/Edge 的连接池是否正确；
7. 查询日志、慢查询和 trace 是否可观测；
8. 包大小、冷启动、生成步骤与 CI 成本。

## 通用风险

ORM 不能替代索引、执行计划、事务边界和数据库知识。重点防止 N+1、无界关联加载、连接池耗尽、自动同步 Schema、慢迁移、Raw SQL 注入和“类型安全即数据可信”的误解。
