# Node 框架对比

以下比较面向常见 HTTP API/BFF 场景。框架不是架构、性能或安全的替代品，最终需结合团队经验、部署运行时、依赖生态、观测能力和真实压测决定。

## 1. 核心对比

| 框架 | 核心定位 | 运行时/底座 | 架构约束 | 适合场景 |
| --- | --- | --- | --- | --- |
| Express | 成熟极简 Web 框架 | Node HTTP | 很低 | 传统 API、BFF、遗留项目、自由组合中间件 |
| Koa | async 洋葱模型轻内核 | Node HTTP | 很低 | 定制中间件流、希望自行搭建服务基座 |
| Fastify | 高性能、schema 驱动 | Node HTTP | 中等，插件封装 | 高吞吐 JSON API、契约和序列化要求高 |
| Hono | 跨运行时/边缘轻量框架 | Fetch/Web Standards | 低 | Worker、边缘 API、跨 Node/Bun/Deno 工具 |
| Egg | 企业约定式 Koa 框架 | Node + Koa | 高 | 已有 Egg 体系、需统一目录与生命周期约定 |
| Nest | 模块化、依赖注入框架 | Express 或 Fastify | 高 | 大型 TypeScript 服务、多人协作、复杂领域 |

## 2. 优劣势速览

| 框架 | 主要优势 | 主要代价 |
| --- | --- | --- |
| Express | 生态和教程最成熟，入门快，兼容性强 | 大项目规范、校验、类型与目录需要自行选择 |
| Koa | 洋葱中间件表达力强，async/await 控制流自然 | 核心能力少，组合与治理负担落在团队 |
| Fastify | schema、序列化、插件封装和性能表现突出 | 需适应 Fastify 插件模型，迁移 Express 生态有成本 |
| Hono | 轻量、跨运行时、贴近 Web 标准 | 平台能力差异大，传统 Node 包不一定可用 |
| Egg | 约定成熟，企业项目上手有统一路径 | 框架生命周期与约定较重，新项目需评估长期策略 |
| Nest | 结构化强、DI 和横切能力完整、TypeScript 体验好 | 样板和抽象多，简单服务可能显得过重 |

## 3. 决策路径

1. **必须部署到边缘/多运行时吗？** 是：优先 Hono，并先验证数据库、认证、任务和可观测性在目标平台可用。
2. **需要强模块化、依赖注入、多人长期协作吗？** 是：优先 Nest；若团队已有 Egg 体系且维护成本可控，也可继续 Egg。
3. **需要 schema 驱动的高吞吐 JSON 服务吗？** 是：优先 Fastify，使用真实下游、真实 payload 压测。
4. **是小型 API/BFF 或既有 Express 项目吗？** Express 往往足够；需要更精简的 async 中间件模型可选 Koa。
5. **框架选择仍不明确吗？** 选择团队最熟悉、能建立类型校验、测试、日志、监控、部署与安全基线的方案，避免仅因 benchmark 或潮流迁移。

## 4. 通用基线

无论选择哪个框架，生产服务都应具备：

- 参数与请求体运行时校验、认证与授权、统一错误响应；
- 请求 ID、结构化日志、指标、错误追踪和超时；
- 限流、请求体上限、安全响应头、CORS/CSRF 策略；
- 数据库连接池、健康检查、优雅关闭、幂等与重试策略；
- 单元/集成测试、依赖锁定、CI 与部署回滚能力。

## 5. 常见误区

- **“Fastify 一定更快”**：业务服务的瓶颈常在数据库、网络、序列化或下游依赖；先压测与 profile。
- **“Nest 自带企业级能力”**：Nest 提供组织方式，不会自动提供正确的领域模型、权限、事务、可观测性与安全策略。
- **“Hono 能跑在 Node 就等同于所有 Node 服务”**：边缘与 Node 的系统能力、连接模型和部署约束不同。
- **“Express/Koa 太简单就不适合生产”**：生产质量取决于工程基线和团队治理，轻框架同样可以稳定运行。
