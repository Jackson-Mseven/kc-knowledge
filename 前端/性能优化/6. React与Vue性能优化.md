# React 与 Vue 性能优化

框架性能优化的核心不是到处缓存，而是保持组件纯粹、把状态放在正确位置、缩小更新范围，并让昂贵资源按需加载。

## 1. 通用原则

- 状态尽量靠近使用它的组件，避免一个全局状态变化让整棵树更新；
- 派生数据在渲染中计算或使用 computed/memo，避免复制出多个数据源；
- 列表使用稳定业务 key；
- 拆分大型组件和上下文，但不要为了性能制造过度碎片化 API；
- 用框架 Profiler 找真实重复渲染，不要凭感觉优化。

## 2. React

### 更新范围

- 父组件渲染默认会执行子组件函数，即使 DOM 最终没有变化；
- `memo` 可在 props 浅比较相等时跳过子组件渲染；
- `useMemo` 缓存计算结果，`useCallback` 缓存函数引用；它们都有比较、内存和认知成本；
- Context value 变化会通知消费者。按更新频率拆 Context，稳定 value，或使用支持 selector 的状态层。

### State 与 Effect

- 不要用 Effect 计算派生 state，否则多一次提交并可能出现中间状态；
- 事件逻辑放事件处理函数，不通过 Effect 观察状态再执行；
- 大量同步更新可用分页、局部状态、transition 或虚拟列表降低阻塞；
- `useTransition`/`useDeferredValue` 用于标记非紧急更新，不会减少计算总量，应同时优化昂贵工作。

### React 性能工具

- React DevTools Profiler 查看 commit、组件渲染耗时和触发原因；
- `<Profiler>` 可程序化采样，但生产采集需控制开销；
- Chrome Performance 将框架 commit 与浏览器 Layout/Paint 联合分析；
- React Compiler 可自动处理部分 memoization，但应按项目版本、构建链和官方建议采用，不能替代状态设计。

## 3. Vue

### 响应式与组件更新

- `computed` 缓存派生值；避免在模板调用昂贵函数；
- 保持传给子组件的 props 稳定，例如传布尔结果而非让每个子项读取频繁变化的全局值；
- `v-once` 适合永不更新内容，`v-memo` 可有条件跳过子树更新，使用前验证维护收益；
- `shallowRef`/`shallowReactive` 可减少巨大不可变结构的深层响应式成本，但更新时必须替换根引用。

### Watch 与生命周期

- `watch` 副作用需取消旧请求和订阅，避免竞态与泄漏；
- 不要使用深度 watch 监听巨大对象，改为监听具体字段或规范化状态；
- `KeepAlive` 会保留组件内存和状态，应设置 include/max 并处理 activated/deactivated；
- 异步组件与路由懒加载降低首屏 bundle，但需要加载和错误 UI。

### Vue 性能工具

- Vue DevTools Performance/组件检查器观察更新；
- 开发构建可启用 `app.config.performance` 写入浏览器 Performance timeline；
- 联合 Chrome Performance 检查组件更新后是否产生大 Layout/Paint。

## 4. 状态库

- Redux/Zustand/Pinia/Jotai 等都应使用细粒度 selector，避免订阅整个 store；
- selector 返回新对象会导致比较失败，可拆 selector、使用 shallow equality 或 memoized selector；
- 规范化实体数据减少深层复制和重复对象；
- 不要把临时表单、hover、局部展开状态全部放进全局 store。

## 5. SSR 与 Hydration

- SSR HTML 出现快不等于可交互，仍需下载和执行客户端 JS 完成 hydration；
- Hydration mismatch 会导致额外工作或重建，应保证服务端/客户端初始输出一致；
- Streaming SSR 与 Suspense 可更早发送内容，但边界过多会增加复杂度；
- Server Components 可减少部分客户端 JS，但受框架、缓存、数据边界和部署约束影响。

## 6. 检查清单

先回答：哪个交互慢？哪个组件重复渲染？每次渲染耗时多少？渲染后是否触发大布局？优化后 commit、INP 和业务指标是否改善？没有证据时不要批量加入 memo。
