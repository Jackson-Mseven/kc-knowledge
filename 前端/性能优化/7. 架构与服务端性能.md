# 架构与服务端性能

前端体验从 DNS、CDN 和服务端开始。仅压缩前端代码无法修复高 TTFB、慢 API、串行数据依赖和不合理渲染架构。

## 1. CSR、SSR、SSG 与 ISR

| 模式 | 优势 | 代价 | 适合 |
| --- | --- | --- | --- |
| CSR | 部署简单、交互后导航自然 | 首屏依赖 JS 和 API，SEO/弱设备压力 | 登录后应用、后台系统 |
| SSR | 可更早返回页面内容、个性化 | 服务成本、缓存和 hydration 复杂 | 动态内容、SEO 页面 |
| SSG | CDN 缓存强、TTFB 低、稳定 | 构建时间、内容更新延迟 | 文档、营销、内容站 |
| ISR/按需再生 | SSG 性能与增量更新折中 | 新旧内容窗口、平台依赖 | 大量可缓存内容页 |

架构选择应按页面而不是整个站点一刀切。很多应用可同时使用静态页面、SSR 和客户端导航。

## 2. Streaming 与渐进式呈现

- 服务端尽早发送 HTML shell 与关键内容；
- Suspense/流式边界允许慢数据晚到，但应避免页面大量闪烁和布局偏移；
- 首字节早不代表主要内容早，仍要监控 LCP 与完整流结束；
- 代理、压缩和平台 buffering 可能让小 chunk 不能立即到达浏览器。

## 3. BFF 与 API 聚合

BFF 可减少浏览器跨域和多次往返，在服务端并行聚合下游，并统一认证和裁剪字段。风险：

- 聚合服务成为单点和延迟放大器；
- 下游超时、重试和部分失败必须设计；
- 返回巨大“万能接口”会浪费传输和解析；
- 前后端部署耦合与缓存 key 更复杂。

## 4. API 设计

- 分页、字段裁剪、压缩和条件请求；
- 并行独立请求，消除瀑布式依赖；
- 批量接口解决 N+1，但设置批量大小上限；
- 关键写操作使用幂等键；
- 超时、取消和稳定错误码；
- GraphQL 需要查询复杂度、深度、DataLoader 和持久化查询治理。

## 5. CDN 与边缘

- 静态资源使用内容哈希和长期边缘缓存；
- 页面/API 可使用 `s-maxage`、stale-while-revalidate；
- 个性化 Cookie/Authorization 可能降低命中，需明确 cache key；
- Edge Compute 适合重写、认证前置、轻聚合和地域逻辑，重事务仍靠中心服务；
- 监控命中率、回源流量、边缘 p95 TTFB 和各地区错误。

## 6. 数据库与服务端

前端 API 慢时常见根因是缺索引、N+1、慢事务、连接池耗尽、缓存击穿和下游依赖。需要通过 trace 将浏览器 request ID 关联到网关、服务、数据库和消息系统。

## 7. 第三方服务

- 支付、地图、客服、广告和埋点都可能阻塞或失败；
- 非关键 SDK 延迟到同意、空闲或交互后加载；
- 使用 facade 占位，避免第三方加载造成 CLS；
- 设置超时、降级和熔断，不让第三方故障阻塞核心页面；
- 定期审计数据发送、权限、体积和实际使用率。

## 8. 发布策略

- 前端资源不可原地覆盖，使用版本化 URL；
- HTML 与静态文件部署顺序保持兼容；
- 灰度发布比较性能与错误指标；
- 出现资源加载失败、白屏或指标恶化时可快速回滚；
- Service Worker 与 CDN 缓存需要独立的更新/回滚预案。
