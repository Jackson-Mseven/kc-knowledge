# 性能监控与排查流程

性能问题必须能够被发现、复现、归因和验证。单次截图或“感觉变快”不足以证明优化有效。

## 1. RUM 采集

采集 Web Vitals、导航、资源、Long Task、自定义业务时点和错误。每条数据至少关联：页面、版本、设备、网络、地区、会话、实验组和采样率。

```ts
import { onCLS, onINP, onLCP } from 'web-vitals'

const report = (metric) => navigator.sendBeacon('/rum', JSON.stringify({
  name: metric.name,
  value: metric.value,
  id: metric.id,
  path: location.pathname,
  version: APP_VERSION,
}))

onCLS(report)
onINP(report)
onLCP(report)
```

生产采集要控制体积、采样和隐私。URL 查询、用户输入、请求头和 DOM 文本可能包含敏感信息，不应直接上报。

## 2. Performance API

- `performance.mark/measure`：记录自定义业务阶段；
- `PerformanceObserver`：观察 navigation、resource、paint、longtask、layout-shift 等条目；
- Resource Timing 跨源详细数据需要服务端 `Timing-Allow-Origin`；
- Server-Timing 响应头可把服务端阶段展示到浏览器时间线。

## 3. 排查页面加载慢

1. 确认影响范围：页面、版本、设备、地区、缓存状态；
2. Network 看 DNS、TLS、TTFB、资源优先级和瀑布；
3. 找 LCP 元素，分解其资源发现、下载和渲染延迟；
4. Coverage/bundle report 找未使用 JS/CSS；
5. Performance 看主线程是否阻止内容绘制；
6. 在目标网络设备复测，并等待 RUM 验证。

## 4. 排查交互卡顿

1. RUM 找到 INP 差的交互名称和页面；
2. Performance 录制点击/输入；
3. 区分 input delay、processing、presentation delay；
4. 展开 Long Task，定位 handler、框架 render、layout/paint；
5. 缩小更新范围、拆任务、消除强制布局；
6. 比较优化前后交互 trace 和 INP 分布。

## 5. 排查内存泄漏

1. 设计可重复动作：进入页面、打开关闭弹窗、离开页面；
2. 执行多轮并触发诊断 GC；
3. 比较 Heap Snapshot 的对象数量和 Retained Size；
4. 检查 Detached DOM、监听器、定时器、缓存和闭包引用；
5. 修复 cleanup，重复同一流程确认基线不持续上涨；
6. 观察真实长会话的崩溃和内存指标。

## 6. 工具分工

| 工具 | 适合问题 |
| --- | --- |
| Lighthouse | 自动审计和基础回归，不代表全部真实用户 |
| WebPageTest | 多地区/设备、视频、请求瀑布和重复测试 |
| DevTools Network | 请求、缓存、协议、优先级、响应头 |
| DevTools Performance | 主线程、渲染、Long Task、交互 |
| Memory | Heap、分配、Detached DOM |
| React/Vue DevTools | 组件更新和框架 Profiler |
| Bundle Analyzer | 依赖组成、重复包和 chunk |
| RUM/APM/Tracing | 真实用户、服务端与跨系统归因 |

## 7. 性能告警

- 使用滑动窗口、最小样本量和版本维度降低噪声；
- 同时关注绝对阈值和相对回退；
- 告警必须指向负责人、页面和版本，并附诊断入口；
- 发布后短期观测错误、LCP、INP、资源失败和 API p95；
- 性能 SLO 应与业务转化、留存和任务成功率关联。

## 8. 优化报告模板

```text
问题：移动端商品页 p75 LCP 4.1s
范围：v2.3.0、东南亚、冷缓存用户
根因：LCP 图片由客户端 API 返回后才发现，且下载 1.8 MB
改动：SSR 输出图片 URL；srcset/AVIF；fetchpriority=high
结果：实验室 4.0s -> 2.2s，RUM p75 4.1s -> 2.7s
副作用：CDN 转换成本 +8%，已纳入预算
```

把证据、改动、收益、副作用和回滚写清楚，才能让性能优化可复用而非一次性技巧。
