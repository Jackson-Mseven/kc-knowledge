# JavaScript 与内存优化

JavaScript 性能问题通常来自代码执行过多、任务过长、数据结构不合适、频繁分配或对象长期被引用。优化前必须用 CPU Profile、Performance 和 Heap Snapshot 找到证据。

## 1. 长任务拆分

- 单个主线程任务超过约 50 ms 会被记录为 Long Task；
- 把非原子的批处理拆为小块，在块之间让出主线程；
- `scheduler.yield()`、Scheduler API 的可用性需做兼容处理，也可使用 MessageChannel/定时器；
- 关键状态变更必须保持一致性，不能为了拆分制造中间错误状态。

## 2. Worker

适合移入 Worker 的任务：大数据解析、图片/音频处理、搜索索引、复杂计算、压缩。Worker 不适合直接 DOM 操作，消息传输和启动也有成本。

- 使用 Transferable 转移 ArrayBuffer，避免大数据复制；
- 复用 Worker 池而非每个任务创建线程；
- 限制队列长度、支持取消、超时和错误恢复；
- Worker 数不应盲目等于 CPU 核数，移动设备资源更有限。

## 3. 算法和数据结构

- 用 Map/Set 代替重复 O(n) 数组查找；
- 预构建索引、缓存纯计算结果；
- 大数组避免多次 map/filter 中间分配，可在确有热点时合并遍历；
- 排序、序列化和正则在大输入下评估复杂度；
- 虚拟化和分页通常比优化每次循环常数更有效。

## 4. 垃圾回收

现代引擎通常按对象生命周期分代回收，并使用增量/并发技术降低暂停。应用层重点是减少无意义分配和解除无用引用，而不是依赖具体 GC 算法。

常见泄漏：

- 未移除的事件监听器和订阅；
- 定时器、Observer、WebSocket 未清理；
- 全局 Map/缓存无限增长；
- 闭包引用大对象；
- 已移除 DOM 仍被 JS 引用；
- 未完成请求和异步回调长期持有组件状态。

## 5. 缓存设计

内存 memo/cache 必须有容量、TTL 或 LRU 淘汰。以对象为 key 且不希望阻止回收时可使用 WeakMap，但 WeakMap 不可遍历，不能替代所有缓存。

缓存会交换 CPU/网络与内存、一致性复杂度。命中率低或计算很便宜时，缓存可能得不偿失。

## 6. JSON 与结构化数据

- 大 JSON 下载、解析和对象创建都在主线程产生开销；
- API 分页、精简字段、流式协议或二进制格式要结合复杂度选择；
- `JSON.stringify` 也可能阻塞，日志和持久化不能无界序列化整个状态树；
- 循环引用、BigInt、Date 和精度需要明确序列化协议。

## 7. 诊断流程

1. Performance 找到 Long Task 与对应调用栈；
2. CPU Profile 检查 Self Time、Total Time 与调用次数；
3. 重复稳定操作，比较 Heap Snapshot；
4. 查看 Retainers 找到对象为何仍可达；
5. 修复后重复相同操作确认堆能回落，并观察线上长期会话。

## 8. 注意事项

- 微基准容易被 JIT、预热、死代码消除和设备差异误导；
- 不要为了减少函数调用破坏清晰架构；
- `useMemo`、对象池和手写循环不是默认更快；
- 先减少总工作量，再讨论局部语法快慢。
