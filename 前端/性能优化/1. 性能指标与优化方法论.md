# 性能指标与优化方法论

性能优化的目标是让真实用户更快看到内容、更快完成交互，并在长时间使用中保持稳定。正确流程是：**定义体验目标 -> 采集真实数据 -> 定位瓶颈 -> 设定预算 -> 实施改动 -> 验证与防回退**。

## 1. 用户体验阶段

| 阶段 | 用户问题 | 代表指标 |
| --- | --- | --- |
| 导航与响应 | 服务器开始响应了吗？ | TTFB |
| 内容出现 | 页面是否有可见反馈？ | FCP |
| 主要内容 | 核心内容是否已经显示？ | LCP |
| 可交互性 | 操作后是否快速反馈？ | INP、Long Task |
| 视觉稳定 | 内容是否意外移动？ | CLS |
| 持续使用 | 是否越来越卡、内存上涨？ | FPS、Heap、错误率 |

## 2. Core Web Vitals

### LCP

Largest Contentful Paint 衡量视口内最大候选内容元素完成绘制的时间。常见候选是大图片、视频 poster、背景图或大文本块。

LCP 可拆解为：

```text
TTFB + 资源发现延迟 + 资源下载耗时 + 元素渲染延迟
```

优化方向：CDN/缓存降低 TTFB；让 LCP 资源在 HTML 中尽早可发现；不要对首屏 LCP 图片懒加载；压缩和响应式图片；减少阻塞 CSS/JS 与主线程长任务。

### INP

Interaction to Next Paint 观察一次访问期间点击、键盘和触摸交互的延迟分布，关注较慢交互而非只看首次输入。

一次交互延迟包括：输入排队时间、事件处理时间、浏览器完成下一帧渲染的时间。优化方向：拆分长任务、减少事件处理和同步渲染、缩小状态更新范围、避免强制布局、延迟非关键工作。

### CLS

Cumulative Layout Shift 衡量没有用户预期的布局位移。常见原因：图片/广告无尺寸、字体切换、异步插入顶部内容、动画改变布局属性。

优化：预留尺寸；使用稳定占位；只在用户触发后插入内容；字体 fallback 指标匹配；动画使用 transform；不要把有意的用户交互位移误判为问题。

## 3. 实验室数据与真实用户数据

- Lab：Lighthouse、WebPageTest、DevTools，环境可控、适合复现与诊断，但不能代表全部用户。
- RUM：在真实设备、网络和用户路径采集，适合评价业务真实体验，但噪声更多且需要隐私治理。
- CrUX 等字段数据可看聚合体验；自建 RUM 可关联版本、路由、地区和业务转化。

应同时使用：Lab 找原因，RUM 判断问题规模与改动是否真正有效。

## 4. 百分位与分组

只看平均值会掩盖长尾。常用 p50 看典型体验，p75 评价大多数用户，p95/p99 定位严重长尾。至少按以下维度切分：

- 页面/路由、版本和实验组；
- 移动/桌面、设备能力和内存；
- 4G/3G/Wi-Fi、地区和运营商；
- 新用户/回访、缓存命中/未命中；
- 登录态、数据规模和关键业务操作。

## 5. 性能预算

性能预算应覆盖：

- 首屏 JS/CSS/字体/图片压缩后体积；
- 初始请求数、第三方脚本数和主线程执行时间；
- LCP、INP、CLS 与业务接口 p95；
- 单次路由切换资源增量、内存增长和错误率。

预算应进入 CI、构建报告和发布监控。预算不是永不变化的数字，而是需要评审的产品约束。

## 6. 优化优先级

使用“影响用户数 × 严重程度 × 实施信心 ÷ 成本”排序。一般优先处理：

1. 阻塞所有用户的故障、白屏和错误；
2. 核心路径上的服务端/网络瓶颈；
3. 大体积首屏资源与明显长任务；
4. 影响大量用户的布局偏移和交互卡顿；
5. 有证据的局部微优化。

## 7. 常见错误

- 只优化 Lighthouse 分数，不看真实业务路径；
- 没有基线就修改，无法证明收益；
- 把所有资源 preload、所有组件 memo、所有元素提升图层；
- 用高端开发机与本地网络作为唯一测试环境；
- 只关注首次加载，忽略交互、路由切换和内存泄漏；
- 为极小收益引入复杂缓存或不可维护代码。
