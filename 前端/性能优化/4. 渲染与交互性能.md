# 渲染与交互性能

渲染性能取决于主线程能否及时完成 JavaScript、样式、布局、绘制和合成。核心原则是减少每帧工作量、缩小失效范围，并优先保证用户输入响应。

## 1. 帧流水线

典型过程：JavaScript -> Style -> Layout -> Paint -> Composite。60 Hz 每帧约 16.7 ms，高刷新率预算更少；浏览器和系统也要占用时间，业务代码可用预算小于理论值。

## 2. 布局抖动

DOM/样式写入后立刻读取 `offsetWidth`、`scrollTop`、`getBoundingClientRect()` 等可能触发强制同步布局。循环交错读写会反复 layout。

```js
// 先批量读，再批量写
const rects = elements.map((el) => el.getBoundingClientRect())
requestAnimationFrame(() => {
  elements.forEach((el, i) => { el.style.transform = `translateY(${rects[i].top}px)` })
})
```

## 3. 动画

- 优先 transform/opacity，避免每帧修改 top/left/width；
- 使用 `requestAnimationFrame` 同步视觉更新；
- `will-change` 仅在动画热点短期使用，结束后移除；
- 大图层、滤镜、阴影和透明会增加 GPU/合成成本；
- 尊重 `prefers-reduced-motion`，动效不能妨碍可访问性。

## 4. DOM 与列表

- 大 DOM 会增加样式、布局、内存和查询成本；
- 大列表使用窗口化/虚拟化，只渲染视口附近元素；
- 动态行高、滚动定位、焦点、屏幕阅读器和打印是虚拟列表难点；
- 使用稳定 key 复用节点，避免列表更新导致全部重建；
- 分页或渐进渲染常比一次渲染数万节点更稳健。

## 5. 事件与输入

- 事件处理尽快完成，昂贵工作拆分或延后；
- 高频 scroll/pointermove 使用节流、rAF 或最新值覆盖，不要积压每个事件；
- touch/wheel 监听器在不需要 preventDefault 时设置 passive；
- debounce 适合输入停止后执行，throttle 适合控制持续事件频率；
- 防抖不能让关键输入反馈完全消失，应立即更新本地 UI，延迟重请求。

## 6. ResizeObserver 与 IntersectionObserver

- IntersectionObserver 适合懒加载、曝光和进入视口判断，避免手写滚动时不断读取布局；
- ResizeObserver 监测元素尺寸变化，但回调中再次无条件修改尺寸可能形成循环；
- Observer 回调仍在主线程，批量 entries 并不意味着处理免费。

## 7. Canvas、SVG 与 DOM

- DOM/CSS 适合可访问、交互丰富、节点量有限的 UI；
- SVG 适合矢量和需要逐节点交互的图形，节点过多也会变慢；
- Canvas 适合大量像素/对象高频绘制，但需自行处理命中测试、文本、可访问性和状态；
- WebGL/WebGPU 适合大规模 GPU 图形，开发复杂度更高。

## 8. INP 优化步骤

1. 在 RUM 找到慢交互类型和页面；
2. Performance 录制真实操作，分辨输入延迟、handler、渲染延迟；
3. 删除或延迟无关工作；
4. 缩小状态更新和 DOM 影响；
5. 拆分长任务或使用 Worker；
6. 回到真实用户数据验证 p75/p95。
