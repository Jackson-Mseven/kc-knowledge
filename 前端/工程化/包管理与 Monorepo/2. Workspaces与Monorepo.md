# Workspaces 与 Monorepo

Monorepo 在一个仓库管理多个应用和包。Workspace 是包管理器对多包链接、统一安装和命令过滤的基础支持；任务编排、缓存和代码边界通常由 Turborepo/Nx 等补充。

## 典型结构

```text
repo/
├── apps/
│   ├── web/
│   └── admin/
├── packages/
│   ├── ui/
│   ├── config-eslint/
│   └── shared/
├── pnpm-workspace.yaml
└── package.json
```

```yaml
packages:
  - apps/*
  - packages/*
```

内部依赖使用 `workspace:*` 明确来自当前仓库：

```json
{ "dependencies": { "@repo/ui": "workspace:*" } }
```

## 优势

- 原子提交同时更新应用和共享包；
- 统一 lint、TypeScript、测试和发布规范；
- 代码复用、重构和依赖可视化更直接；
- CI 可根据依赖图只运行受影响任务。

## 代价

- 仓库、CI 和权限边界更复杂；
- 公共包容易变成无边界的 shared 垃圾场；
- 全量测试/构建随规模增长，需要任务缓存和 affected 机制；
- 发布版本、变更日志和所有权需要额外工具治理。

## 包边界

- 按领域或稳定能力拆包，不按每个小函数拆包；
- 每个包定义公开入口 `exports`，禁止应用导入其他包内部文件；
- 避免循环依赖，使用依赖图和 lint 规则约束层级；
- UI、配置、领域、基础设施包职责分离；
- 内部源码直引还是独立构建取决于工具链和发布需求，应全仓统一约定。

## 任务执行

```bash
pnpm --filter @repo/web dev
pnpm --filter @repo/web... build
pnpm -r --parallel test
```

过滤语法需要团队文档化。根脚本负责统一入口，各 package 保持可独立运行的 `build/test/lint/typecheck` 契约。

## 何时不适合 Monorepo

团队和项目完全独立、权限必须严格隔离、技术栈/发布周期差异巨大，或组织尚无维护 CI/依赖边界能力时，多仓库可能更简单。Monorepo 是协作模型，不是规模升级的必选项。
