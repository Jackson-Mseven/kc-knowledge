# 包管理器与依赖治理

包管理器负责解析依赖图、下载包、生成 lockfile、建立 node_modules/链接结构并执行脚本。工程上应固定包管理器与版本，提交 lockfile，并把依赖升级和供应链风险纳入治理。

## npm、Yarn 与 pnpm

| 工具 | 特点 | 常见适用场景 |
| --- | --- | --- |
| npm | Node 默认配套，生态兼容广 | 普通项目、降低环境门槛 |
| Yarn | Workspaces、约束和不同安装模式 | 已有 Yarn 体系的大型仓库 |
| pnpm | 内容寻址存储、严格依赖、Workspace | Monorepo、节省磁盘、强调依赖边界 |

pnpm 通过全局内容寻址存储复用包，并用链接构建依赖结构。严格性可暴露“代码使用了未在 package.json 声明的幽灵依赖”。不同工具的 node_modules 布局不同，原生扩展、旧工具和依赖错误声明需要验证。

## Lockfile

- `package.json` 描述允许的版本范围，lockfile 固定完整解析结果和完整性信息；
- 应提交 lockfile，CI 使用冻结安装，如 `pnpm install --frozen-lockfile` 或 `npm ci`；
- 不要手工编辑 lockfile；冲突应由对应包管理器重新解析并审查；
- 升级包管理器主版本可能改变 lockfile，应作为独立变更评审。

## Corepack 与版本固定

```json
{
  "packageManager": "pnpm@10.0.0",
  "engines": { "node": ">=22 <23" }
}
```

使用 Corepack/版本管理工具保证本地和 CI 一致。`engines` 是否强制取决于包管理器配置，不能只写字段就认为已生效。

## dependencies 分类

- `dependencies`：生产运行需要；
- `devDependencies`：构建、测试、lint 等开发依赖；
- `peerDependencies`：库要求消费者提供的共同依赖，如 React；
- `optionalDependencies`：安装失败可继续，代码必须处理缺失；
- `overrides/resolutions`：临时统一传递依赖版本，需要记录原因和移除计划。

## 依赖治理

1. 新增依赖前检查维护状态、体积、许可证、权限、发布历史和替代方案；
2. 定期小批升级，避免一次跨越多个主版本；
3. CI 运行安全审计，但结合可利用路径判断风险，不机械追求零告警；
4. 安装脚本具有执行代码能力，高安全环境可限制 lifecycle scripts 并维护允许名单；
5. 删除未使用依赖，检查重复版本和 bundle 影响。

## 注意事项

- 不在仓库混用多个 lockfile；
- 不依赖全局安装的构建工具，脚本使用项目本地版本；
- CI 缓存包管理器下载存储，而不是盲目缓存整个 node_modules；
- 私有 registry Token 使用最小权限，不能写入 `.npmrc` 提交或构建产物。
