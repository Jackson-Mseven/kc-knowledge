# Commitlint 与提交规范

提交规范让历史可检索，并可驱动变更日志和版本发布。Conventional Commits 常见格式：

```text
feat(cart): support coupon selection

BREAKING CHANGE: coupon API now requires currency
```

## 类型

| type | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复 |
| `docs` | 文档 |
| `refactor` | 不改变外部行为的重构 |
| `perf` | 性能改进 |
| `test` | 测试 |
| `build` / `ci` | 构建或 CI |
| `chore` | 其他维护 |

## 配置

```js
// commitlint.config.js
export default { extends: ['@commitlint/config-conventional'] }
```

```sh
# .husky/commit-msg
pnpm exec commitlint --edit "$1"
```

## 设计原则

- scope 使用稳定领域/包名，不用开发者姓名或临时编号；
- subject 描述“做了什么”，正文解释原因和取舍；
- Breaking Change 必须明确影响和迁移方式；
- issue/PR 关联放 footer；
- 一个提交保持一个可理解的目的，便于 review、bisect 和 revert。

## 与 Squash Merge

若仓库采用 squash，最终 PR 标题/合并提交才是发布输入，CI 应校验 PR 标题。不要要求每个临时 WIP 提交完美，却忽略最终合并信息。

## 注意事项

Commitlint 只校验消息格式，不证明变更质量。Hook 可被跳过，CI 必须兜底。规则过于严格会诱导开发者填写无意义文本，应保持简洁并提供示例。
