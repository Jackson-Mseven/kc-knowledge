# 工程化、测试与发布

## 项目结构

```text
extension/
├── src/background/
├── src/content/
├── src/popup/
├── src/options/
├── public/manifest.json
├── locales/
└── tests/
```

Vite/Rollup/webpack 等构建多入口，输出目录必须包含 Manifest、HTML、JS、CSS、图标和 locale。文件名策略要与 Manifest/动态加载匹配。

## 类型与兼容

使用 Chrome types 或 WebExtension polyfill 类型；避免把仅 Chrome API 编译通过误当跨浏览器兼容。平台差异集中在 adapter，并生成 Chrome/Firefox 特定 Manifest。

## 测试

- 单元：消息 reducer、规则生成、存储迁移、URL 匹配；
- 组件：Popup/Options UI；
- 集成：Mock chrome API，验证权限和消息；
- E2E：加载解压扩展的真实浏览器，验证注入、Popup、Worker 重启和升级；
- 安全：恶意页面消息、XSS、越权 Host、Token 泄露；
- 性能：Content Script 对页面 INP/内存影响、后台事件耗时。

## 版本与迁移

Manifest version 字段递增；存储 schema 独立版本化。更新应兼容旧 Content Script/Port，并提供 migration。发布前打包产物重新安装测试，而不是只测 dev build。

## 商店发布

- 准备图标、截图、说明、隐私政策和单一用途描述；
- 权限与功能对应，宽泛 Host 权限会增加审核和用户疑虑；
- 不包含远程执行代码、混淆恶意逻辑和未披露数据收集；
- Chrome Web Store 与 Firefox Add-ons 审核/签名流程不同；
- 分阶段发布，监控崩溃、评分、权限变化和核心事件。

## CI/CD

执行 lint、typecheck、unit、build、Manifest schema 校验、依赖/Secret 扫描、E2E 和 zip；产物关联 commit 并保留回滚。商店凭证使用 Secret/OIDC 和最小权限，禁止在 fork PR 暴露。

## 发布安全

启用发布账号 MFA；限制管理员；审计第三方 SDK 与数据传输；紧急事件可下架/停止发布并撤销服务端 Token，但已安装版本不会瞬间消失，因此服务端协议必须可禁用危险功能。
