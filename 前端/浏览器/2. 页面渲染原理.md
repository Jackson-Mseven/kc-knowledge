# 页面渲染原理

浏览器把 HTML、CSS 和 JavaScript 转换为屏幕像素的过程通常称为关键渲染路径。主流程可概括为：**解析 -> 样式计算 -> 布局 -> 绘制 -> 分层 -> 光栅化 -> 合成**。

## 1. HTML 解析与 DOM

- 网络字节先按响应编码解码为字符，再经过 tokenization 形成标签、属性和文本 token，最后构建 DOM 树。
- HTML 解析具有容错规则，错误嵌套不一定报错，而可能被浏览器按规范修复；不要依赖修复后的偶然结构。
- 解析器发现同步普通脚本时通常暂停解析，等待脚本下载并执行，因为脚本可能调用 `document.write` 修改输入流。
- 预加载扫描器会提前发现后续资源并并行下载，以减少解析阻塞带来的网络空闲。

### 脚本加载方式

| 写法 | 下载 | 执行时机 | 顺序 |
| --- | --- | --- | --- |
| 普通 `<script>` | 阻塞解析等待下载 | 下载后立即执行 | 文档顺序 |
| `defer` | 与解析并行 | DOM 解析完成后、`DOMContentLoaded` 前 | 保持文档顺序 |
| `async` | 与解析并行 | 下载完成立即执行 | 不保证顺序 |
| `type="module"` | 与解析并行 | 默认类似 defer | 模块依赖顺序 |

动态 `import()` 按需加载模块，适合路由或功能级代码分割，但应处理加载失败、重复请求和用户等待状态。

## 2. CSSOM 与样式计算

- CSS 被解析为 CSSOM。浏览器结合选择器匹配、层叠、继承、来源、层级和优先级，计算每个元素的最终样式。
- CSS 通常被视为渲染阻塞资源：没有关键 CSS，浏览器无法稳定生成首屏渲染结果。
- 复杂选择器不一定是现代页面的主要性能瓶颈；大 DOM、频繁失效和动态修改通常影响更大。
- `@import` 可能形成串行请求链，关键样式更适合 `<link rel="stylesheet">`。

## 3. Render Tree

渲染树由需要显示的 DOM 节点及其计算样式组成：

- `display: none` 的节点及后代不进入渲染树；
- `visibility: hidden` 仍参与布局，只是不绘制可见内容；
- 伪元素虽然不是真实 DOM 节点，但可能生成渲染对象；
- `<head>`、脚本等非视觉节点通常不进入渲染树。

## 4. 布局（Layout/Reflow）

布局根据盒模型、包含块、格式化上下文和视口计算元素几何位置与尺寸。影响布局的常见变化包括：

- 修改宽高、边距、字体、内容或 DOM 结构；
- 改变视口、滚动条、布局模式；
- 读取要求精确几何信息的属性，例如 `offsetWidth`、`getBoundingClientRect()`。

布局可能影响祖先、后代或大量兄弟节点。使用 `contain`、稳定尺寸、虚拟列表和更小的 DOM 范围可以限制影响。

### 强制同步布局与布局抖动

```js
// 不推荐：每轮写样式后立即读取布局
for (const item of items) {
  item.style.width = '100px'
  console.log(item.offsetWidth)
}

// 推荐：批量读取，再批量写入
const widths = items.map((item) => item.offsetWidth)
items.forEach((item) => { item.style.width = '100px' })
```

浏览器通常会延迟批量计算样式和布局。写 DOM 后立即读取几何信息，会迫使浏览器提前同步完成计算；反复读写交错形成 layout thrashing。

## 5. 绘制（Paint）

绘制阶段把背景、边框、文字、阴影、图片等转为有顺序的绘制指令。以下变化常触发重新绘制但不一定重新布局：

- `color`、`background`、`box-shadow`；
- 文本、边框或可见性变化；
- 图层内容发生改变。

绘制区域、绘制复杂度和图层大小都会影响成本。大面积模糊阴影、滤镜和透明叠加在低端设备上尤其昂贵。

## 6. 分层、光栅化与合成

- 浏览器根据滚动、变换、视频、3D 上下文等因素建立合成层。
- 绘制指令被分割为瓦片，由光栅线程转换为位图纹理。
- 合成线程根据图层变换和顺序组合最终画面，常可在不重新布局和绘制的情况下处理 `transform` 和 `opacity` 动画。

`will-change` 只是提示浏览器未来可能变化，不是“开启 GPU”的万能开关。大量长期图层会增加显存、光栅和合成成本，应只在确定的热点元素上短期使用。

## 7. 重排、重绘与合成的关系

| 变化示例 | Layout | Paint | Composite |
| --- | --- | --- | --- |
| 修改 `width`、字体大小 | 通常需要 | 通常需要 | 需要 |
| 修改背景色 | 通常不需要 | 需要 | 需要 |
| 修改 `transform`、`opacity` | 通常不需要 | 已有独立层时可不需要 | 需要 |

这只是常见情况，实际是否提升图层和失效范围由浏览器决定。不能仅靠属性名称断言绝对不会 paint。

## 8. 动画与帧预算

60 Hz 屏幕每帧约 16.7 ms，浏览器还需处理输入、脚本、样式、布局、绘制和系统工作，因此留给业务 JavaScript 的时间更少。高刷新率设备的帧预算更紧。

- 使用 `requestAnimationFrame` 在下一次绘制前更新视觉状态；后台页面中调用频率通常会被降低。
- 动画优先改变 `transform` 与 `opacity`，但仍要检查合成层和纹理大小。
- JavaScript 动画要避免每帧创建大量对象、强制布局或执行重计算。
- CSS 动画不必然总比 JavaScript 快，关键在动画属性和主线程工作量。

## 9. 图片、字体与布局稳定性

- 图片设置 `width`/`height` 或 `aspect-ratio` 预留空间，减少 CLS。
- 使用响应式图片 `srcset`/`sizes`、现代格式和合理压缩，避免下载远大于显示尺寸的图片。
- Web Font 会影响文字显示与布局。使用合适的 `font-display`、预加载关键字体并控制字形子集。
- 骨架屏和占位符尺寸应接近真实内容，否则数据到达后仍会发生明显布局位移。

## 10. 调试方法

- DevTools Performance 查看 Main、Style、Layout、Paint、Composite 和 Long Task。
- Rendering 面板可开启 Paint Flashing、Layout Shift Regions、Layer Borders 等辅助视图。
- Layers/3D 视图用于理解合成层，但不要以“层越多越快”为目标。
- 先用用户可感知指标和 trace 确认瓶颈，再优化具体阶段。
