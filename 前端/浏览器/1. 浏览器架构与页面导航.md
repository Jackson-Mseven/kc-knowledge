# 浏览器架构与页面导航

浏览器不是一个简单的 HTML 查看器，而是集网络客户端、JavaScript 运行时、渲染引擎、安全沙箱、存储系统和开发工具于一体的复杂应用。以下以 Chromium 的多进程设计为主要参考，不同浏览器的进程划分和实现细节会有所差异。

## 1. 浏览器的主要组件

| 组件 | 主要职责 |
| --- | --- |
| Browser Process | 地址栏、导航、权限、下载、Cookie、进程管理和窗口 UI |
| Renderer Process | 解析 HTML/CSS、执行页面 JavaScript、布局、绘制；通常运行在沙箱中 |
| Network Process | DNS、连接管理、HTTP、TLS、缓存和代理等网络能力 |
| GPU Process | 光栅化、图层合成和 GPU 资源管理 |
| Storage/Utility Process | IndexedDB、文件、音视频解码等受隔离服务，具体划分因版本而异 |

- 多进程带来隔离性：单个页面崩溃不必拖垮整个浏览器，恶意页面也更难直接访问系统资源。
- 多进程也有成本：每个进程需要内存，跨进程通信（IPC）会增加复杂度和延迟。
- Chromium 的 Site Isolation 会尽量让不同站点运行在不同渲染进程中，降低跨站数据被攻击利用的风险。
- “一个标签页一个进程”只是近似说法。进程复用、iframe、站点隔离、扩展和浏览器策略都会改变实际划分。

## 2. 渲染进程中的主要线程

- **主线程**：解析 HTML、构建 DOM、执行大部分 JavaScript、计算样式、布局和部分绘制工作。
- **合成线程**：管理图层、处理合成和部分滚动输入，不必每次都等待主线程。
- **光栅线程**：把绘制指令转换为位图瓦片，现代浏览器通常会并行光栅化。
- **Worker 线程**：Web Worker、Service Worker 等可执行 JavaScript，但不能直接操作页面 DOM。

主线程同时承担 JavaScript、样式和布局等任务。因此长 JavaScript 任务会推迟输入响应、布局和绘制，造成页面卡顿。

## 3. 从输入 URL 到开始导航

1. 浏览器判断输入是 URL、搜索词还是内部命令。
2. 规范化 URL，补充协议、端口和路径，检查是否命中历史记录或搜索建议。
3. 检查 HSTS、浏览器缓存、Service Worker、扩展规则和企业代理策略。
4. 发起导航。Browser Process 与 Network Process 协作获取资源。
5. 确定响应类型和安全策略后，为目标站点选择或创建 Renderer Process。
6. 提交导航，把响应数据交给渲染进程，更新地址栏、历史记录和页面状态。

导航请求与普通 `fetch` 不完全相同。它会影响浏览器历史、文档生命周期、进程选择和安全上下文。

## 4. DNS、连接与请求

浏览器获取资源前大致经历：

1. 查询浏览器、操作系统或本地解析器的 DNS 缓存。
2. 未命中时由递归 DNS 解析域名，得到 IPv4/IPv6 地址。
3. HTTP/1.1 或 HTTP/2 通常建立 TCP 连接，再完成 TLS；HTTP/3 基于 QUIC，内建 TLS 1.3。
4. 发送 HTTP 请求。请求可能经过代理、CDN、负载均衡和应用网关。
5. 接收响应头和响应体，应用 Cookie、缓存、CSP、MIME 等策略。

浏览器可能进行 DNS 预解析、预连接、连接复用和 Early Hints 处理，但这些优化受隐私、资源优先级和连接限制影响。

## 5. 导航响应处理

浏览器会检查：

- HTTP 状态码和重定向；
- `Content-Type` 与 `X-Content-Type-Options`；
- `Content-Disposition` 是否要求下载；
- CSP、COOP、COEP、CORP 等安全响应头；
- 是否由 Service Worker 拦截并返回响应；
- 是否允许在当前 frame 中加载，如 `frame-ancestors`；
- 下载内容是否需要安全扫描。

收到 HTML 后可以边下载边解析，不必等整个文档下载完。解析器发现 CSS、脚本、字体、图片等资源时，会交给预加载扫描器和网络栈尽早发起请求。

## 6. 文档生命周期与事件

常见事件顺序是一个概念模型，具体资源和脚本会影响时间：

1. 创建新 Document，解析 HTML。
2. `DOMContentLoaded`：DOM 已解析完成，`defer` 脚本已执行；不等待普通图片等资源完成。
3. `load`：页面及其依赖资源通常已加载完成。
4. 用户离开时可能触发 `pagehide`、`visibilitychange`；`beforeunload` 并不可靠且会影响某些缓存能力。
5. 页面可能进入 Back/Forward Cache（bfcache），返回时直接恢复，而不是重新加载。

推荐使用 `visibilitychange`、`pagehide` 处理保存与暂停逻辑，不要依赖 `unload` 发送关键数据。少量统计数据可使用 `navigator.sendBeacon()` 或带 `keepalive` 的请求，但仍需服务端容忍丢失和重复。

## 7. iframe 与浏览上下文

- iframe 创建嵌套浏览上下文，拥有独立 Document、全局对象和导航历史片段。
- 同源 iframe 可以相互访问 DOM；跨源 iframe 受同源策略限制，只能通过 `postMessage` 等受控机制通信。
- `sandbox` 可限制脚本、表单、弹窗和同源能力；权限策略 `Permissions-Policy` 可限制摄像头、麦克风等能力。
- 第三方 iframe 会增加网络、内存、脚本和隐私成本，应延迟加载并控制权限。

## 8. 前进后退缓存（bfcache）

bfcache 会把完整页面状态保存在内存中，用户前进/后退时快速恢复 DOM、JavaScript 堆和滚动位置。

- 通过 `pageshow`/`pagehide` 的 `event.persisted` 判断页面是否从 bfcache 恢复。
- 某些不可安全冻结的行为可能阻止进入 bfcache；具体规则随浏览器演进，应使用 DevTools 检查。
- 不要假设页面初始化代码只执行一次。恢复后应重新确认过期数据、连接和计时器状态。

## 9. 注意事项

- 浏览器行为不是单一标准算法的直接实现，不同内核、版本和设备会有差异。
- 避免依赖精确事件先后和毫秒级定时；用状态与能力检测表达逻辑。
- `DOMContentLoaded` 快不代表页面可交互，真实体验还取决于主线程任务、关键资源和输入延迟。
- 调试导航问题时按 DNS、连接、TLS、HTTP、缓存、Service Worker、渲染进程逐层排查。
