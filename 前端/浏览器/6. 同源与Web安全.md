# 同源策略与 Web 安全

浏览器安全模型的核心是限制一个来源的代码任意读取另一个来源的数据，并通过权限、沙箱、响应头和用户授权控制高风险能力。

## 1. Origin 与同源

一个 origin 由 `scheme`、`host`、`port` 三部分组成。三者全部相同才是同源：

```text
https://app.example.com:443
```

与 `http://app.example.com`、`https://api.example.com`、`https://app.example.com:8443` 都不同源。不同源脚本通常可以发起部分请求，但不能直接读取响应内容；图片、脚本、样式等资源加载规则又各不相同。

## 2. CORS

CORS 是服务端通过响应头授权浏览器跨源读取的机制。

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Vary: Origin
```

- 简单请求可直接发送，再由浏览器决定是否向脚本暴露响应。
- 复杂请求先发送 OPTIONS 预检，服务端返回允许的方法、请求头和缓存时间后才发送实际请求。
- 带凭证请求不能使用 `Access-Control-Allow-Origin: *`。
- CORS 解决的是浏览器读取权限，不代替身份认证、CSRF 防护和服务端权限校验。

## 3. XSS

XSS 是攻击者控制的脚本在受害者站点上下文中执行。类型包括存储型、反射型和 DOM 型。

防护：

- 默认使用框架转义输出；避免 `innerHTML`、`eval`、动态模板和不必要的 `v-html`/`dangerouslySetInnerHTML`。
- 对不同上下文分别做 HTML、属性、URL、JavaScript、CSS 编码，不能用一种转义覆盖所有场景。
- 设置 CSP，使用 nonce/hash 控制可信脚本；逐步通过 Report-Only 观察违规。
- Cookie 使用 `HttpOnly`、`Secure`、合适 `SameSite`，但不能把 Cookie 属性当成完整 XSS 防护。

## 4. CSRF

CSRF 利用浏览器自动携带 Cookie 的特性，诱导用户向目标站点发起带身份的状态变更请求。

- SameSite Cookie 可降低跨站携带，但要考虑登录跳转、第三方集成和兼容性。
- 使用不可预测的 CSRF Token，并在服务端校验 `Origin`/`Referer` 作为额外信号。
- 状态变更不能只依赖 GET；但把 POST 改成唯一防护也不够。
- 使用 Authorization Header 的 Token 不会自动携带，但 XSS 仍可能盗用页面可访问的 Token。

## 5. 点击劫持与嵌入

- `Content-Security-Policy: frame-ancestors 'self'` 控制谁能嵌入页面。
- `X-Frame-Options: DENY/SAMEORIGIN` 是较旧但仍常见的防护头。
- 对允许嵌入的合作方使用明确白名单，不要为了修复 iframe 问题关闭所有保护。

## 6. 现代安全响应头

| 响应头 | 目标 |
| --- | --- |
| CSP | 限制脚本、样式、图片、连接等来源 |
| HSTS | 让浏览器后续使用 HTTPS |
| COOP | 隔离窗口组，控制跨窗口关系 |
| COEP | 要求跨源资源明确授权，支持更强隔离能力 |
| CORP | 资源声明允许被哪些站点加载 |
| Referrer-Policy | 控制 Referer 泄露范围 |
| Permissions-Policy | 限制摄像头、麦克风、地理位置等能力 |
| X-Content-Type-Options | 防止 MIME 嗅探 |

启用 COOP/COEP 可能影响第三方脚本、跨源图片、广告和嵌入内容，应先观测并逐项适配。

## 7. HTTPS 与证书

HTTPS 使用 TLS 提供机密性、完整性和服务端身份认证。浏览器会验证证书域名、有效期、签发链和安全策略。

- 页面 HTTPS 并不自动保证所有子资源安全；混合内容会被阻止或升级。
- HSTS 可防止部分降级攻击，但首次访问前仍可能存在风险，应结合预加载策略谨慎启用。
- 不要在前端写入私钥、长期密钥或认为混淆等于加密。

## 8. URL、DOM 与开放重定向

- 处理用户 URL 时使用 `new URL()` 解析并校验协议、主机和路径，不要用简单字符串包含判断。
- 防止 `javascript:`、`data:`、危险协议、开放重定向和不受信任的 iframe 来源。
- DOM XSS 需要审查数据流：输入来源 -> 拼接/解析 -> 危险 sink；静态类型和接口声明不能阻止恶意字符串。

## 9. 权限与隐私

摄像头、麦克风、定位、通知、剪贴板等能力需要安全上下文、用户授权和浏览器策略。权限可能被用户拒绝、撤销或按站点/顶级站点分区。

- 只在用户明确动作和实际需要时请求权限。
- 第三方资源会带来跟踪、Cookie、供应链和数据泄露风险；限制来源、权限和数据传输。
- 任何可公开的前端代码都不能隐藏真正的秘密，服务端必须重新鉴权。

## 10. 安全排查方法

1. 建立资产清单：页面、接口、Cookie、Token、第三方脚本、iframe、上传点。
2. 标出信任边界：用户输入、跨源响应、服务端渲染数据、富文本和外部配置。
3. 检查输出上下文、CORS、CSP、Cookie、CSRF、权限和日志脱敏。
4. 用浏览器安全面板、Network 响应头、CSP 报告、依赖审计和渗透测试验证。
