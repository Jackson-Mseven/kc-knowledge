# 网络协议与浏览器缓存

浏览器网络性能由连接建立、请求优先级、协议复用、服务端响应、传输体积和缓存共同决定。优化的目标不是“请求越少越好”，而是在正确性前提下减少关键路径时间和重复传输。

## 1. HTTP 版本

| 版本 | 核心能力 | 主要限制 |
| --- | --- | --- |
| HTTP/1.1 | 持久连接、分块传输、Host | 并发常依赖多连接；同连接响应顺序存在队头阻塞 |
| HTTP/2 | 二进制分帧、多路复用、HPACK 头压缩 | TCP 丢包会影响同连接全部流 |
| HTTP/3 | 基于 QUIC、流独立恢复、连接迁移 | 部署、网络中间设备与回退策略更复杂 |

HTTP/2/3 下盲目把所有资源合成一个巨大文件可能降低缓存粒度和按需加载能力。应根据页面依赖图、压缩、缓存和优先级设计拆包。

## 2. 请求与响应要点

- 方法语义：GET/HEAD 应安全且幂等，PUT/DELETE 语义上幂等，POST 通常不幂等。实际重试仍需业务幂等设计。
- 301/308 表示永久重定向，302/307 表示临时重定向；307/308 明确保留原方法和请求体。
- `Content-Type` 描述媒体类型，`Content-Encoding` 描述 gzip/br 等传输编码。
- `Accept-Encoding` 用于协商压缩；Brotli 常用于 HTTPS 静态资源，动态响应需权衡 CPU 成本。
- `Vary` 告诉缓存响应随哪些请求头变化。设置 `Vary: *` 或过多维度会显著降低命中率。

## 3. HTTP 缓存模型

浏览器缓存可粗分为：

1. **新鲜缓存**：满足 `Cache-Control` 时直接复用，不发请求。
2. **重新验证**：携带 `If-None-Match` 或 `If-Modified-Since`，未变化返回 304。
3. **重新获取**：返回完整新响应。

### Cache-Control

| 指令 | 含义 |
| --- | --- |
| `max-age=N` | 响应在 N 秒内新鲜 |
| `s-maxage=N` | 共享缓存/CDN 的新鲜时间 |
| `no-cache` | 可以存储，但使用前必须重新验证 |
| `no-store` | 不应存储响应 |
| `public` / `private` | 可由共享缓存存储 / 仅私有缓存 |
| `immutable` | 新鲜期内内容不会改变，避免不必要验证 |
| `stale-while-revalidate` | 允许先返回旧内容并后台更新 |
| `stale-if-error` | 上游失败时允许使用旧内容 |

`no-cache` 不等于“不缓存”，这是常见误区。敏感内容是否使用 `no-store` 还需结合浏览器、代理和产品需求评估。

## 4. ETag 与 Last-Modified

- `ETag` 是资源版本标识，客户端用 `If-None-Match` 验证；内容未变返回 304。
- `Last-Modified` 精度和语义较弱，客户端用 `If-Modified-Since` 验证。
- 同时存在时通常优先 ETag。分布式服务生成 ETag 时要保证不同实例语义一致。
- 304 没有响应体，但仍有网络往返，不如有效的强缓存快。

## 5. 静态资源缓存策略

推荐：

- HTML：短缓存或 `no-cache`，保证能较快发现新入口资源。
- 带内容哈希的 JS/CSS/图片：`Cache-Control: public, max-age=31536000, immutable`。
- 文件内容变化必须生成新 URL；不能让同一个长期缓存 URL 对应不同内容。
- Service Worker、HTML 和 CDN 配置共同参与缓存时，要设计版本升级与回滚，避免旧入口引用已删除资源。

## 6. Memory Cache、Disk Cache 与 Service Worker

- Memory Cache 生命周期短、速度快，具体复用策略由浏览器决定。
- Disk Cache 可跨页面或会话持久化，受容量、隐私模式和淘汰策略影响。
- Service Worker 可通过 Cache API 实现编程式缓存，但它不是 HTTP 缓存的简单替代；两层缓存可能同时存在。
- DevTools 显示的 `(memory cache)`、`(disk cache)`、`from ServiceWorker` 有助于判断来源。

## 7. 资源提示与优先级

- `dns-prefetch`：提前解析域名。
- `preconnect`：提前完成 DNS、连接和 TLS，适合确定会请求的关键跨源。
- `preload`：当前页面必需且浏览器不易及时发现的关键资源；必须设置正确 `as` 和 CORS 属性。
- `prefetch`：低优先级获取未来可能使用的资源。
- `modulepreload`：预加载 ESM 模块及相关处理。
- `fetchpriority`：提示图片等资源优先级，不保证绝对调度顺序。

过度 preload 会抢占带宽，让真正关键资源更慢。资源提示要通过瀑布图验证。

## 8. CDN 与边缘缓存

- CDN 按 cache key 缓存响应，key 通常包含 URL，并可能受 Host、查询参数、Header 和 Cookie 影响。
- 个性化响应若错误标为 public，可能泄露给其他用户；必须正确设置缓存范围和 `Vary`。
- 缓存刷新/失效传播不是瞬时的，发布系统应使用内容哈希和兼容窗口。
- CDN 命中率、回源率、边缘 TTFB 和错误率应纳入监控。

## 9. CORS 与预检的网络影响

跨源复杂请求可能先发送 OPTIONS 预检。服务端通过 `Access-Control-Max-Age` 允许浏览器缓存预检结果，但浏览器有自身上限。

- 简单请求也受同源读取限制，只是通常不预检。
- CORS 不是服务端鉴权；非浏览器客户端不会被浏览器同源策略约束。
- 携带凭证时不能使用 `Access-Control-Allow-Origin: *`，应返回明确允许的 Origin，并设置 `Vary: Origin`。

## 10. 排查清单

1. 查看 DNS、连接、TLS、TTFB、Content Download 各阶段耗时。
2. 确认是否存在重定向链、串行依赖或未复用连接。
3. 检查状态码、`Cache-Control`、Age、ETag、Vary 和 Service Worker。
4. 检查资源压缩、尺寸、优先级和是否加载了未使用代码。
5. 用真实网络条件和用户指标验证，不只在本地高速网络测试。
