# Mock、集成与契约测试

Mock 的目的是控制不可预测边界和制造异常场景，不是把被测系统所有依赖都替换掉。过度 Mock 会让测试通过但真实集成失败。

## 1. 测试替身

| 类型 | 用途 |
| --- | --- |
| Dummy | 只用于填参数，不参与行为 |
| Stub | 返回预设结果 |
| Spy | 记录调用，常包裹真实实现 |
| Fake | 简化但可工作的实现，如内存仓库 |
| Mock | 带预期交互的替身 |

优先验证最终输出和状态；只有调用本身是契约时才断言调用次数和参数。

## 2. MSW

Mock Service Worker 在网络边界拦截请求，浏览器和 Node 测试可共享 handler：

```ts
export const handlers = [
  http.get('/api/profile', () => HttpResponse.json({ id: '1', name: 'Ada' })),
]
```

- 未匹配请求应报错，避免测试意外访问外网；
- 每个测试后 resetHandlers；
- handler 响应结构应来自真实 API schema/fixture，而非随意编造；
- 测试延迟、断网、错误码和无效响应。

## 3. 集成测试

集成测试可组合组件、路由、状态库、网络 Mock 和存储，验证用户行为跨模块流动。与 E2E 不同，它通常运行在模拟 DOM 或组件浏览器环境，速度更快。

## 4. 契约测试

契约测试确认前端消费者与后端提供者对请求/响应的一致理解：

- OpenAPI/JSON Schema 生成类型并在 CI 校验；
- Consumer-driven contract 记录消费者期望，由 Provider 验证；
- 关键 fixture 通过运行时 schema 解析；
- 检查可选字段、null、枚举扩展和向后兼容。

TypeScript 接口只在编译期存在，不能证明线上 JSON 符合接口。

## 5. 测试数据库与服务

- 使用容器/临时数据库提供真实数据库语义；
- 迁移脚本必须在测试环境运行；
- 每个测试使用事务回滚、独立 schema 或唯一数据；
- 外部支付/短信使用官方 sandbox 或受控 fake，绝不调用真实生产能力。

## 6. 注意事项

- 不 Mock 正在测试的逻辑；
- 不直接 Mock 私有模块路径；重构不应无故破坏行为测试；
- Fake 与真实实现要有共享契约测试，防止语义漂移；
- 固定 fixture 应小而有意义，避免复制巨大生产响应。
