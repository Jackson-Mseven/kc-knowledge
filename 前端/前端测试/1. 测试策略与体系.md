# 前端测试策略与体系

测试的目标是用可接受的成本降低发布风险、支持重构并缩短故障反馈时间。好的测试验证用户可观察行为和稳定契约，而不是复制实现细节。

## 1. 测试分层

| 层级 | 测试对象 | 优点 | 局限 |
| --- | --- | --- | --- |
| 静态检查 | 类型、语法、规范 | 最快、反馈早 | 不能证明运行行为 |
| 单元测试 | 纯函数、Hook、工具、状态逻辑 | 快、定位准 | 不能覆盖真实集成 |
| 组件测试 | 组件渲染、交互、可访问语义 | 接近用户行为 | DOM 环境与真实浏览器有差异 |
| 集成测试 | 多模块、API、路由、存储协作 | 发现边界问题 | 环境和数据管理更复杂 |
| E2E | 浏览器中的完整关键流程 | 置信度高 | 慢、失败定位成本高 |

测试金字塔强调底层测试数量更多，但现代前端更适合“测试奖杯”：静态检查与集成/组件测试占重要位置，少量 E2E 覆盖关键链路。比例应由风险决定，不追求固定数字。

## 2. 风险驱动

优先测试：支付、登录、权限、数据丢失风险、核心转化、复杂状态机、频繁变更代码和曾发生故障的边界。低价值展示代码不必为覆盖率写脆弱测试。

## 3. AAA 与 Given-When-Then

- Arrange/Given：准备数据与环境；
- Act/When：执行一个用户动作或调用；
- Assert/Then：验证可观察结果。

每个测试聚焦一个行为，可包含多个与同一行为相关的断言。测试名称应描述条件与结果，而不是函数名。

## 4. 可测试性设计

- 纯计算与 I/O 分离；
- 时间、随机数、网络和存储通过边界注入或集中封装；
- 组件接收数据和回调，不在深层隐藏大量全局依赖；
- 使用稳定的业务接口，不为测试暴露私有实现；
- 依赖方向清晰，避免模块导入时立即执行副作用。

## 5. 测试应避免什么

- 断言内部 state、私有方法、框架实例结构；
- 大量浅渲染或只检查组件存在；
- 为了覆盖率写没有业务含义的断言；
- 依赖执行顺序、真实时间、外网和共享脏数据；
- 随意更新 Snapshot 而不审查行为变化；
- 把 E2E 当成唯一测试层。

## 6. 测试计划模板

```text
功能：修改收货地址
主要成功路径：填写 -> 校验 -> 保存 -> 列表更新
失败路径：网络错误、地址无权限、重复提交
边界：超长文本、特殊字符、过期登录
测试层：schema 单测、表单组件集成、保存流程 E2E
不覆盖：浏览器原生地址自动填充的内部行为
```
