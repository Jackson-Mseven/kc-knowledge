# Playwright 端到端测试

E2E 在真实浏览器中验证用户关键流程，覆盖页面、网络、路由、存储和后端协作。应少而关键，确保确定性、可并行和可诊断。

## 1. 基本示例

```ts
import { expect, test } from '@playwright/test'

test('user can complete checkout', async ({ page }) => {
  await page.goto('/products/1')
  await page.getByRole('button', { name: '加入购物车' }).click()
  await page.getByRole('link', { name: '购物车' }).click()
  await expect(page.getByText('商品 1')).toBeVisible()
  await page.getByRole('button', { name: '结算' }).click()
  await expect(page).toHaveURL(/\/checkout/)
})
```

Playwright locator 和 assertion 会自动等待元素达到目标状态。避免 `waitForTimeout`，等待可观察的 URL、响应、文本或控件状态。

## 2. Locator 策略

优先 role + accessible name、label、placeholder、稳定业务 test id。避免易变 CSS、XPath 和位置索引。一个 locator 应表达用户如何识别目标。

## 3. 测试数据

- 每个测试创建独立用户/订单，使用唯一前缀；
- 通过受控 API 或数据库 fixture 准备数据，不通过长 UI 链为每个测试造数据；
- 测试后清理，或使用隔离租户/临时数据库；
- 并行执行时不能共享可变账号和固定记录。

## 4. 登录状态

使用 setup project 完成一次登录并保存 `storageState`，其他测试复用。涉及不同角色时分别建立状态文件。敏感认证状态不能提交公共仓库，并应使用测试环境短期账号。

## 5. 网络与错误场景

```ts
await page.route('**/api/orders', (route) => route.fulfill({
  status: 500,
  contentType: 'application/json',
  body: JSON.stringify({ code: 'FAILED' }),
}))
```

关键主路径最好连接真实测试后端；使用 route Mock 精确覆盖难制造的超时、500、空数据。不要把所有 E2E 都变成前端 Mock 测试。

## 6. 多浏览器和设备

按真实用户分布选择 Chromium、WebKit、Firefox 和移动视口。不是每条测试都必须跑所有矩阵：关键冒烟跨浏览器，完整回归可按风险分层。

## 7. 调试与产物

- 首次失败保留 trace、截图、视频和控制台/网络信息；
- 使用 trace viewer 查看动作前后 DOM、网络和日志；
- CI 重试用于识别偶发问题，不能掩盖不稳定测试；
- 对 flaky 测试记录负责人和原因，修复前隔离而非无限重试。

## 8. Page Object

Page Object 适合复用稳定业务动作，不应包装每个 locator 成无意义方法。优先暴露 `checkout()` 等领域动作，同时保留测试中的关键断言可读性。

## 9. 并行与分片

测试必须相互独立才能安全并行。CI 可按 shard 分发；记录历史耗时均衡分片。长流程拆为独立场景，但不要破坏真正需要端到端验证的业务链。
