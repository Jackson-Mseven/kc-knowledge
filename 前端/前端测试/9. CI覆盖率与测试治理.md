# CI、覆盖率与测试治理

测试只有稳定进入开发和发布流程才产生持续价值。CI 应快速反馈、保留诊断产物并阻止高风险回退。

## 1. 推荐流水线

1. 安装锁定依赖并恢复可信缓存；
2. 格式/lint、类型检查；
3. 单元和组件测试；
4. 构建；
5. 契约/集成测试；
6. 部署临时环境；
7. E2E 冒烟、视觉和性能预算；
8. 汇总报告与门禁。

可并行的任务并行执行；失败时取消昂贵下游任务。缓存 key 必须包含 lockfile、运行时和配置。

## 2. 覆盖率

覆盖率包括 statement、branch、function、line。它告诉哪些代码被执行，不证明断言正确。

- 对核心域设分支覆盖要求，对生成代码、类型声明和难以触达的防御代码合理排除；
- 使用 changed-files/diff coverage 防止新代码拉低质量；
- 不为达到 100% 测私有实现或写无意义调用；
- Mutation Testing 可检验断言能否杀死行为改变，但成本较高，适合核心逻辑。

## 3. Flaky Test

常见原因：固定等待、共享数据、时区时间、随机数、动画、网络、异步未清理、依赖顺序。

治理：记录失败率；保留 trace；确定负责人；隔离测试并设修复期限；有限重试用于收集证据，不能把重试成功视为质量正常。

## 4. 测试速度

- 单元测试使用 node 环境，只有 DOM 测试启用 jsdom；
- 按历史耗时分片 E2E；
- 避免每个测试重复启动服务和创建浏览器；
- 使用项目依赖图只运行受影响测试，同时定期跑完整回归；
- 慢测试应显示排行并持续治理。

## 5. 环境与数据

- 测试环境配置 schema 校验；
- 数据可重复创建和清理；
- 临时环境使用唯一命名与自动过期；
- 数据库迁移、feature flag 和 API 版本必须与被测构建匹配；
- 不允许测试写入生产服务。

## 6. 质量报告

报告应包含失败测试、截图/trace、覆盖率变化、性能预算、视觉差异和 flaky 趋势。测试名称、附件和日志必须让非作者也能定位问题。

## 7. 测试代码维护

测试代码也是生产资产：类型检查、lint、代码评审、依赖升级、重复抽象和废弃测试清理同样必要。公共 helper 保持领域语义，避免形成隐藏大量副作用的万能测试工具。
