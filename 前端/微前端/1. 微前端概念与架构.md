# 微前端概念与架构

微前端把大型前端系统按业务领域拆分为可独立开发、测试和部署的应用，再由基座或运行时组合成统一产品。它解决的是组织和交付边界，不是单纯的代码分割技术。

## 适用场景

- 多团队长期维护一个大型产品，需要独立发布节奏；
- 遗留系统渐进迁移，新旧框架需要共存；
- 不同业务域生命周期、权限和技术栈差异明显；
- 多个产品需共享统一导航、认证和设计规范。

小团队、单一技术栈、强耦合页面通常优先模块化 Monorepo。微前端会引入运行时、部署、通信、测试和观测复杂度。

## 核心角色

- **基座/Shell**：全局布局、导航、认证入口、路由分发和异常边界；
- **子应用/Micro App**：拥有明确业务边界和生命周期；
- **共享平台能力**：设计系统、SDK、埋点、权限、国际化；
- **集成契约**：路由、生命周期、通信事件、依赖版本和错误格式。

## 设计原则

1. 按业务领域拆分，不按页面组件或技术层随意拆；
2. 子应用可独立开发、测试、部署和回滚；
3. 跨应用契约少而稳定，禁止互相导入内部源码；
4. 基座保持薄，不能成为所有业务逻辑的集中地；
5. 用户体验统一：导航、设计、权限、错误和性能标准一致。

## 拆分边界

可参考 DDD bounded context。订单、商品、营销等领域比 Header、Button 等视觉区域更适合作为应用边界。一个页面跨多个领域时，优先由页面所属应用通过 API 组合；运行时拼接大量细粒度组件会增加时序和故障面。

## 微前端与 Monorepo

Monorepo 是源码与协作组织方式，微前端是运行时/部署架构，两者可同时使用。Monorepo 中的多个应用仍可独立部署；多仓库也不自动成为微前端。

## 成本清单

- 重复框架和依赖导致体积增加；
- 路由、样式、全局变量和事件冲突；
- 本地联调与端到端测试环境复杂；
- 子应用版本与基座兼容矩阵；
- 跨应用状态和事务难以保持一致；
- 首屏加载、错误归因和监控链路更复杂。
