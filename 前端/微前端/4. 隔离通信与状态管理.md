# 隔离、通信与状态管理

## JavaScript 隔离

- iframe 提供真实 Realm/进程级边界；
- Proxy 沙箱可记录和恢复 window 属性，但无法完美隔离所有浏览器副作用；
- 子应用禁止随意修改全局原型、document 事件和单例；
- 第三方脚本、CSS-in-JS 容器和动态 publicPath 需要单独适配。

## CSS 隔离

- 命名空间/BEM：简单但依赖纪律；
- CSS Modules：构建期局部类名，不能隔离全局选择器；
- Shadow DOM：边界强，但主题、Portal、弹层和第三方样式需适配；
- Scoped CSS/运行时前缀：可能改变选择器语义和性能。

统一 reset 由基座管理，子应用不要覆盖 `body/html/*`。弹层明确挂载容器和 z-index 层级协议。

## 通信方式

| 方式 | 适用 | 注意点 |
| --- | --- | --- |
| Props | 基座向子应用传稳定能力 | 接口版本化，避免传巨大可变对象 |
| CustomEvent/Event Bus | 松耦合业务事件 | 命名空间、schema、取消订阅 |
| URL | 可分享导航状态 | 不放秘密和巨大状态 |
| Shared Store | 少量全局状态 | 容易强耦合和全局重渲染 |
| postMessage | iframe/跨窗口 | 校验 origin、source、消息 schema |
| 后端/API | 最稳定业务事实 | 最终一致、缓存和权限 |

事件描述“发生了什么”，如 `cart:item-added`，不要暴露子应用内部 setter。定义 payload schema、版本和 owner。

## 状态边界

- 身份、主题、locale、导航可由基座提供；
- 领域状态归所属子应用；
- 跨应用共享业务事实优先通过后端和 URL，而不是全局前端 store；
- 跨应用操作需要 saga/工作流和补偿，不应假设一次前端事件构成事务。

## 认证与权限

基座可统一登录状态，但每个后端 API 必须独立鉴权。子应用隐藏菜单不是权限控制。Token 传递避免暴露长期凭证；可采用同站 HttpOnly Cookie 或 BFF。
