# 微前端实现方案与选型

## 方案对比

| 方案 | 隔离 | 集成程度 | 优势 | 主要代价 |
| --- | --- | --- | --- | --- |
| 路由分发/多页 | 强 | 低 | 简单稳定、天然独立部署 | 页面切换刷新、共享体验有限 |
| iframe | 最强 | 低 | JS/CSS/DOM 天然隔离，可嵌第三方 | 路由、尺寸、通信、SEO和体验复杂 |
| Web Components | 组件级 | 中 | Web 标准、框架无关、Shadow DOM | 状态/路由/SSR生态需额外设计 |
| single-spa/qiankun | 应用级 | 高 | 生命周期、路由装载、渐进迁移成熟 | 沙箱、样式、公共依赖和调试成本 |
| Module Federation | 模块级 | 很高 | 运行时远程模块与依赖共享 | 版本兼容、远程失效和强耦合风险 |

## 路由分发

Nginx/CDN 按路径把 `/orders`、`/marketing` 指向不同应用。适合独立性优先、可接受完整导航的系统，也是迁移初期最稳健方案。

## iframe

适合安全隔离要求高、第三方系统、低频嵌入。使用 `postMessage` 通信时必须校验 `event.origin` 和消息 schema；通过 sandbox/Permissions-Policy 限制能力。不要把 `*` 作为敏感消息目标源。

## single-spa 与 qiankun

子应用通常导出 bootstrap、mount、unmount 生命周期；基座根据路由激活。qiankun 在此基础上提供 HTML Entry、沙箱和样式隔离等能力。适合完整应用组合和遗留迁移。

## Web Components

Custom Elements 封装生命周期，Shadow DOM 提供样式边界。适合设计系统或跨框架组件，不自动解决应用级路由、数据和部署协调。

## Module Federation

Host 运行时加载 Remote 暴露模块，并可共享 React/Vue 等依赖。适合跨应用组件、能力模块和动态集成；若 Remote 接口频繁变化，会形成分布式前端单体。

## 选型路径

优先回答：需要整应用还是组件组合？是否必须无刷新？隔离强度？是否跨框架？能否同步发布？若只需组织代码，先选 Monorepo；若独立部署是硬需求，再选择最简单满足需求的微前端方案。
