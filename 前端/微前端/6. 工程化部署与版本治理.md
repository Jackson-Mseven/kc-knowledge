# 工程化、部署与版本治理

## 独立流水线

每个子应用独立 lint、类型、测试、构建、发布和回滚；基座维护集成契约与关键 E2E。产物不可变，版本关联 commit、Source Map 和构建元数据。

## Manifest

```json
{
  "catalog": {
    "version": "2.4.1",
    "entry": "https://cdn.example.com/catalog/2.4.1/remoteEntry.js",
    "integrity": "sha384-..."
  }
}
```

Manifest 支持环境、灰度、快速切换和回滚。更新应原子化，缓存时间短或可重新验证；远程静态资源内容哈希长期缓存。

## 版本兼容

- 基座能力定义版本，如 `platformApiVersion`；
- 子应用声明支持范围，加载前检查；
- Breaking Change 采用 expand/migrate/contract；
- 监控真实运行的基座/子应用版本矩阵；
- 保留旧资源覆盖长会话和灰度窗口。

## 设计系统

共享设计 token、组件和图标可保持体验一致。组件库版本不宜由基座强行运行时注入给所有技术栈；通过包版本、CSS variables 和兼容层治理更清晰。

## CI 测试层级

- 子应用：单元、组件、独立 E2E；
- 契约：生命周期、props、events、types、manifest；
- 基座：路由激活、加载失败、权限和导航；
- 集成：生产候选版本组合的关键业务 E2E；
- 发布后：Smoke、错误率、性能和回滚演练。

## 发布顺序

向后兼容时 Remote 可先发布；基座切换 manifest 后灰度。删除旧 API/资源必须确认无活跃消费者。数据库/API 变更同样遵守向后兼容窗口。

## 所有权

每个应用、契约和共享包有 owner、SLO、值班和升级责任。没有组织所有权的微前端会把代码耦合变成发布耦合和跨团队等待。
