# 全栈与应用框架对比

| 框架 | 当前路线 | 核心模型 | 优势场景 | 主要注意点 |
| --- | --- | --- | --- | --- |
| Next.js | App Router 16.x | RSC、Server Action、Route Handler、缓存 | React 全栈、电商、SaaS、内容与混合应用 | 缓存和运行时复杂、版本演进快 |
| Remix / React Router | Framework Mode | 嵌套路由、Loader、Action、Form、渐进增强 | Web 标准表单、数据驱动应用、多部署运行时 | Remix v2 与当前 RR API 要区分 |
| Astro | v7 Islands | 静态 HTML、Client/Server Islands、内容集合 | 内容站、文档、营销、媒体、内容电商 | 高交互 SPA 不是默认强项 |
| Umi | 4.6 / Umi Max | 路由、插件、企业最佳实践 | 国内中后台、统一企业 React 工程 | 主要是前端应用框架，不是通用后端框架 |

## 渲染与数据

| 能力 | Next.js | React Router Framework | Astro | Umi |
| --- | --- | --- | --- | --- |
| CSR | 支持 | 支持 | 可通过框架岛/SPA | 核心场景 |
| SSR | 核心能力 | Framework Mode 支持 | Adapter + on-demand | 需按 Umi SSR 能力/版本配置 |
| SSG/预渲染 | 支持 | 支持 | 默认强项 | 支持构建静态 SPA/MPA，语义不同 |
| 服务端写入 | Server Actions/Route Handler | Action | Actions/Endpoint | 通常调用独立后端 API |
| 局部 hydration | RSC + Client boundary | 路由 hydration | Islands 原生 | 传统 React SPA hydration |

## 选型建议

- React 全栈、需要 RSC 和混合缓存：Next.js；
- 重视 HTTP/Form 渐进增强、路由数据并行和多运行时：React Router Framework Mode；
- 内容为主、交互为岛、追求少 JavaScript：Astro；
- 国内企业中后台、希望布局权限请求等开箱即用：Umi Max；
- 如果后端已独立且只是普通 SPA，Vite + React/Vue 可能比全栈框架更简单。

## 共同评估维度

部署平台锁定、缓存语义、数据库连接、认证授权、流式能力、错误边界、SEO、客户端 JavaScript、团队经验、升级节奏、可观测性和退出成本。框架的类型安全不能替代运行时校验与服务端权限。
