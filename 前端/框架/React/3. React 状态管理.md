# React 状态管理

> 基于官方入门文档整理：
> [Redux](https://redux.js.org/introduction/getting-started)、[Zustand](https://zustand.docs.pmnd.rs/learn/getting-started/introduction)、[Jotai](https://jotai.org/)。

## 1. 先判断是否真的需要全局状态

- 组件内部使用的交互状态优先放在 `useState` 或 `useReducer` 中。
- 多个组件需要协调的状态，先尝试状态提升（lifting state up）或 Context。
- 当状态跨页面/跨层级共享、更新逻辑复杂、需要独立于组件树访问，或需要更好的调试与组织能力时，再考虑状态管理库。
- 不要把所有数据都放进全局 store：表单输入、弹窗开关等局部状态若不跨组件共享，留在组件内通常更简单。

## 2. Redux：可预测的集中式状态管理

### 核心模型

- Redux 是用于可预测、可维护的全局状态管理的 JavaScript 库，可配合 React 或其他视图库使用。
- 状态集中存放在 `store` 中；UI 通过 `dispatch(action)` 描述发生的事件；`reducer` 根据旧 state 和 action 计算新 state。
- Redux 强调单向数据流：`UI -> dispatch action -> reducer -> store 更新 -> UI 读取新 state`。
- reducer 必须是纯函数：不修改原 state、不发请求、不产生随机结果或其他副作用。
- Redux DevTools 可观察 action 和 state 变化，适合需要追踪复杂业务状态的场景。

### Redux Toolkit（RTK）

- 官方明确推荐使用 **Redux Toolkit** 编写 Redux 逻辑，而不是手写 Redux Core 样板代码。
- `configureStore` 简化 store 配置，并提供合理的默认中间件与开发工具支持。
- `createSlice` 将 state、reducer 和自动生成的 action creator 放在一起，按功能领域组织代码。
- RTK 内部使用 Immer。reducer 中可写 `state.value += 1` 这种“可变”语法，实际会产出新的不可变 state；不要因此在 reducer 中做副作用。
- React 项目通常用 `react-redux` 的 `<Provider store={store}>` 提供 store，组件中用 `useSelector` 读取状态、`useDispatch` 派发 action。

```ts
import { configureStore, createSlice } from '@reduxjs/toolkit'

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    incremented: state => {
      state.value += 1
    },
  },
})

export const { incremented } = counterSlice.actions
export const store = configureStore({ reducer: counterSlice.reducer })
```

### 适用场景与注意点

- 适合大型应用、跨域业务状态复杂、团队需要统一约束、需要强可追踪性或时间旅行调试的情况。
- 将异步请求、缓存和服务端数据与纯客户端 UI 状态区分开。RTK Query 适合处理数据获取、缓存和失效；不要手写重复的请求状态机。
- 不要为了一个简单的共享布尔值引入 Redux；它的结构化与约束也带来一定学习和代码成本。

## 3. Zustand：基于 Hook 的轻量 store

### 核心模型

- Zustand 是小型、快速、可扩展的状态管理方案，API 以 Hook 为中心，默认不要求 Provider。
- `create` 创建一个 store hook。store 可以保存原始值、对象和操作函数；组件调用 hook 的选择器订阅所需切片。
- 组件只会因所选状态变化而重新渲染，因此应优先写精确选择器，如 `useBear(state => state.bears)`。
- `set` 默认合并顶层 state；深层对象更新仍需自行创建新引用。需要完全替换时可使用 `set(nextState, true)`。
- store hook 可在 React 组件外通过 `useStore.getState()`、`subscribe()` 等方式访问，但要避免把 UI 生命周期与全局副作用耦合得过紧。

```ts
import { create } from 'zustand'

const useBearStore = create(set => ({
  bears: 0,
  increasePopulation: () =>
    set(state => ({ bears: state.bears + 1 })),
}))

function BearCounter() {
  const bears = useBearStore(state => state.bears)
  return <h1>{bears} bears around here</h1>
}
```

### 中间件与实践

- Zustand 提供 `persist`、`devtools`、`immer`、`subscribeWithSelector` 等中间件，用于持久化、调试和扩展订阅能力。
- 多个独立领域可拆成多个小 store，或按 slice 模式组合；不要把无关状态塞进一个巨大的 store。
- 在选择器中每次都创建对象/数组会导致引用变化。需要组合多个值时，使用稳定选择器或配合浅比较工具，避免不必要渲染。

### 适用场景

- 适合中小型项目，或希望用较少样板代码共享状态的 React 应用。
- 适合跨组件的客户端状态、全局 UI 状态、轻量业务状态；它在 React 并发渲染和订阅一致性方面已处理常见问题。
- 若需要严格的 action 追踪、统一 reducer 约束或大型团队规范，Redux Toolkit 往往更合适。

## 4. Jotai：原子化状态管理

### 核心模型

- Jotai 使用 **atom（原子）** 构建全局 React 状态。每个 atom 是最小状态单元，组件只订阅自己读取的 atom。
- primitive atom 保存基础值：`const countAtom = atom(0)`。
- derived atom 从其他 atom 读取并计算值，形成依赖图；依赖 atom 变化时，派生 atom 自动重新计算。
- 原子级订阅能减少 Context 的额外渲染，通常不必为了切分消费范围而手动大量 memoization。
- `useAtom` 同时读写 atom；`useAtomValue` 只读；`useSetAtom` 只写，可避免不需要读取状态的组件因值变化重渲染。

```ts
import { atom, useAtom, useAtomValue, useSetAtom } from 'jotai'

const countAtom = atom(0)
const doubleCountAtom = atom(get => get(countAtom) * 2)

function Counter() {
  const [count, setCount] = useAtom(countAtom)
  const doubleCount = useAtomValue(doubleCountAtom)
  return <button onClick={() => setCount(c => c + 1)}>{count} / {doubleCount}</button>
}
```

### Provider、原子与实践

- Jotai 可使用默认 store，也可用 `<Provider>` 创建隔离的 store 范围；后者适合 SSR、测试或同一组件树中的独立实例。
- 原子对象本身依赖引用身份。若在组件渲染中动态创建 atom，应使用 `useMemo` 或其他稳定方式保存引用，否则可能造成重复初始化甚至循环渲染。
- 可写派生 atom 可将复杂更新封装为领域操作；异步 atom、storage 工具和框架集成由其 utilities/extensions 提供。
- 状态从小 atom 组合而来，而非必须维护单一大 store；以业务边界和共享范围划分 atom。

### 适用场景

- 适合细粒度共享状态、复杂派生状态、多处局部状态组合，以及希望接近 `useState` 使用体验的项目。
- 当状态自然能拆成独立原子时，Jotai 的依赖图与按 atom 重渲染通常比大型单一 store 更直接。
- 若团队偏好明确的事件日志、单一状态树和强流程约束，应优先考虑 Redux Toolkit。

## 5. 选型对比

| 维度 | Redux Toolkit | Zustand | Jotai |
| --- | --- | --- | --- |
| 状态组织 | 集中式 store，以 slice/reducer 划分 | 一个或多个 store，以状态和 action 组织 | 多个 atom，通过依赖关系组合 |
| 更新方式 | `dispatch(action)` -> reducer | 直接调用 store action / `set` | `useAtom` setter 或可写 atom |
| React 接入 | 通常需要 `Provider` 和 React-Redux hooks | 默认无需 Provider | 默认 store 可免 Provider，也支持 Provider 隔离 |
| 渲染粒度 | selector 订阅的结果变化时更新 | selector 订阅的切片变化时更新 | 读取的 atom 变化时更新 |
| 优势 | 约束强、可追踪、生态与调试成熟 | API 小、样板少、使用直接 | 原子化、派生状态自然、细粒度订阅 |
| 更适合 | 大型复杂业务与团队协作 | 轻量共享状态和中小型应用 | 原子化领域模型与复杂派生状态 |

## 6. 通用实践清单

1. 先划分状态范围：局部、最近共同父级、Context、全局 store；范围越小越好。
2. 不可变地更新对象和数组，避免修改已有 state 引用。
3. 将服务端缓存与客户端状态分开管理；请求缓存、失效和重新验证不等同于 UI state。
4. 让组件订阅最小必要的数据，避免订阅整个 store 或在 selector 中无意义地创建新引用。
5. 将复杂更新收敛为有名字的 action、reducer 或写 atom，不在多个组件散落重复的状态转换。
6. 优先根据业务复杂度和团队协作成本选型，不以库的体积或流行度作为唯一标准。
