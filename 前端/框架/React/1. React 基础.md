# React 基础

> 依据 [React 中文官网 Learn](https://react.docschina.org/learn) 整理。React 的核心思路是：**UI 是状态的函数**。组件根据当前 props 和 state 描述 UI；当状态变化时，React 重新渲染并将必要的变更提交到 DOM。

## 1. React 的基本心智模型

- React 应用由**组件**组成。组件是返回 JSX 的 JavaScript 函数，可组合成从按钮到整页界面的任意层级。
- 组件名必须以大写字母开头，HTML 原生标签使用小写字母。
- 一次渲染可以理解为 React 调用组件函数，得到某个时刻的 UI 快照；提交（commit）阶段再把与上次相比的必要变化应用到 DOM。
- 渲染代码应保持纯粹：只根据输入计算 JSX，不直接修改外部变量、DOM 或发起网络请求。副作用放在事件处理函数或 Effect 中。
- 在开发环境的 `StrictMode` 下，React 可能额外调用渲染和 Effect，以帮助发现不纯的逻辑；代码应能经受这种检查。

## 2. 描述 UI

### JSX

- JSX 是在 JavaScript 中描述 UI 的语法扩展。它比 HTML 严格：标签必须闭合，组件必须返回一个根节点，可使用 Fragment `<>...</>` 避免额外 DOM。
- JSX 属性通常使用驼峰命名，例如 `className`、`onClick`、`tabIndex`；内联样式传入对象，如 `style={{ color: 'red' }}`。
- 使用 `{}` 在 JSX 中嵌入 JavaScript 表达式，例如 `{user.name}`、`src={user.imageUrl}`。其中只能放表达式，不能直接放 `if`、`for` 等语句。
- React 不限制 CSS 方案，可使用普通 CSS、CSS Modules、CSS-in-JS 或框架提供的方案；选择时重点关注作用域、可维护性和构建约定。

### Props 与组件组合

- Props 是父组件传给子组件的只读输入。组件不能修改自己的 props；需要变化时，由父组件传入新的值。
- `children` 是 JSX 嵌套内容对应的 prop，适合构建容器、布局和可组合组件。
- 解构 props 可使接口更清晰：`function Avatar({ person, size = 100 }) { ... }`。默认值只在 prop 缺失或为 `undefined` 时生效。
- 将可复用的视觉单元拆为组件，但不必为每一行 JSX 都创建组件；以职责、复用性和独立变化为边界。

### 条件与列表渲染

- 条件渲染使用普通 JavaScript：提前 `return`、`if/else`、三元表达式 `condition ? A : B` 或 `&&`。
- 注意 `0 && <Item />` 会渲染 `0`。若左侧是数值，应写成 `count > 0 && <Item />`。
- 列表通常用 `array.map()` 生成 JSX。每个同级元素必须有稳定且唯一的 `key`。
- `key` 用于让 React 识别列表项的身份，插入、删除和排序时尤为重要。优先使用数据的持久 ID；不要在渲染时生成随机 key，也不要在顺序会变时使用数组下标。
- `key` 不会作为普通 prop 传给组件；需要 ID 时应显式传入，例如 `<Row key={item.id} id={item.id} />`。

## 3. 添加交互

### 事件

- 将事件处理函数传给 JSX，例如 `onClick={handleClick}`，而不是在渲染时调用 `onClick={handleClick()}`。
- 事件处理函数适合处理由用户动作直接引发的操作：更新状态、提交表单、发请求、导航等。
- React 事件会沿组件树冒泡。可通过 `event.stopPropagation()` 阻止冒泡，通过 `event.preventDefault()` 阻止浏览器默认行为；二者含义不同。
- 事件处理函数可以作为 props 向下传递，用于让父组件决定子组件发生交互时的行为。

### State 与渲染

- `useState` 返回当前 state 和 setter：`const [count, setCount] = useState(0)`。调用 setter 请求一次新的渲染。
- state 是某次渲染中的快照。事件处理函数读取的是当前渲染时捕获的值，因此连续多次 `setCount(count + 1)` 不等于连续加三。
- 当新状态依赖旧状态时，传入更新函数：`setCount(c => c + 1)`。React 会按队列依次处理这些更新。
- React 会批处理同一事件中的 state 更新，以减少不必要的渲染；不要依赖 setter 调用后本地变量立即改变。
- 每个组件实例拥有独立 state。将同一组件渲染两次，会得到两份独立状态。

### 不可变更新

- state 应视为只读。不要直接修改对象、数组或嵌套对象后再复用原引用。
- 更新对象用展开运算符创建新对象：`setUser(u => ({ ...u, name: 'Ada' }))`；更新数组可使用 `map`、`filter`、`slice`、展开语法生成新数组。
- 嵌套对象更新要复制从修改位置到根的每一层。若结构过深，可重新设计 state 结构或使用 Immer 等工具。
- 数组的 `sort()`、`reverse()`、`push()` 等会修改原数组；先复制再操作，避免破坏旧 state 快照。

## 4. 状态管理

### 设计 State

- 只保存最小的、会随时间变化的数据。能从 props 或现有 state 计算得到的值是**派生数据**，通常应在渲染期间计算，而不是再存一份 state。
- 避免重复、矛盾和深度嵌套的 state。例如既保存 `firstName`、`lastName`，又保存 `fullName`，容易产生不同步。
- 选择合适的状态归属：哪个组件需要协调这些数据，就把 state 放到它们最近的共同父组件。
- 这称为“状态提升”。父组件通过 props 把数据和事件处理函数下传，形成单向数据流。
- 需要跨较深层级共享时，可用 Context 传递；Context 适合主题、当前用户、路由等相对稳定的全局信息，不应代替所有局部 state。

### Reducer 与 Context

- 当多个事件以复杂规则更新同一组 state 时，可用 `useReducer(reducer, initialState)` 集中更新逻辑。
- reducer 接收旧 state 和 action，返回新 state；应保持纯粹，不修改旧 state，也不在其中执行副作用。
- Action 通常描述“发生了什么”，如 `{ type: 'added', text }`；reducer 决定如何更新。
- `useReducer` 与 Context 常结合使用：Context 提供 state 与 dispatch，reducer 统一复杂页面的更新规则。

### 保留与重置 State

- React 根据组件在 UI 树中的位置保存 state，而不是根据 JSX 中组件标签的文字保存。
- 同一位置、同一组件类型的重新渲染通常保留 state；移除组件或替换为不同类型会重置它。
- 可通过改变 `key` 明确要求 React 把同一位置视为新组件，从而重置其 state，例如切换不同聊天对象时重置输入框。

## 5. Effect 与外部系统

- Effect 用于将 React 与外部系统同步，例如 DOM API、订阅、定时器、网络连接或第三方组件。它在提交到屏幕后运行。
- 不要把“由用户点击直接触发”的逻辑放进 Effect，例如购买、提交表单；这类操作应留在事件处理函数中。
- 也不要用 Effect 来计算可从已有数据推导的值；直接在渲染中计算即可，避免额外一次渲染。
- `useEffect(() => { setup(); return cleanup; }, [deps])`：依赖变化时，React 先执行上次清理函数，再运行新的 setup；组件卸载时也会清理。
- 依赖数组应包含 Effect 中读取的所有响应式值（props、state、组件内定义的变量与函数）。不要为了消除告警而随意忽略依赖，应先调整代码结构。
- 异步请求可能乱序返回。Effect 中应在清理阶段忽略过期结果或取消请求，避免旧请求覆盖新界面。
- 若不涉及外部系统，通常不需要 Effect。必要时可以用 `useRef` 保存不驱动渲染的可变值，或让浏览器/框架处理默认行为。

## 6. 常用 Hook 与规则

| Hook | 用途 | 要点 |
| --- | --- | --- |
| `useState` | 声明局部状态 | 用 setter 更新；依赖旧值时使用更新函数。 |
| `useReducer` | 管理复杂状态更新 | reducer 必须纯粹，action 描述事件。 |
| `useEffect` | 同步外部系统 | 处理 setup/cleanup 和依赖，不用于派生数据。 |
| `useContext` | 读取最近的 Context 值 | Provider 的 value 变化会让消费者重新渲染。 |
| `useRef` | 保存不参与渲染的值或 DOM 节点 | 修改 `ref.current` 不会触发重新渲染。 |
| `useMemo` | 缓存昂贵计算结果 | 是性能优化，不应用来保证业务正确性。 |
| `useCallback` | 缓存函数引用 | 配合 `memo` 或作为 Hook 依赖时才常有价值。 |

- Hook 只能在函数组件或自定义 Hook 的顶层调用，不能写在循环、条件、嵌套函数或普通事件处理函数中。
- 自定义 Hook 用 `use` 开头，用于复用状态逻辑而不是复用 UI；它可以调用其他 Hook。
- `useMemo`、`useCallback` 和 `memo` 都是性能优化工具。先确保组件纯粹、state 位置合理，再根据实际性能问题使用。

## 7. 常见易错点

1. **直接修改 state**：可能导致 UI 未更新、历史快照被污染。始终返回新对象或新数组。
2. **把 props 复制到 state**：会造成两个数据源；除非确实需要“初始值”或刻意与 prop 脱钩，否则直接使用 prop。
3. **使用不稳定的 key**：随机 key 会让列表项每次都重建，丢失输入状态并影响性能。
4. **滥用 Effect**：派生数据、事件逻辑和纯计算不需要 Effect。
5. **遗漏 Effect 依赖**：闭包会捕获旧值，表现为读取到过期 state 或 props。
6. **把 ref 当作 state**：ref 的变化不触发渲染；需要让 UI 更新的数据必须放在 state 中。

## 8. React 19

> 依据 [React 19 官方发布说明](https://react.dev/blog/2024/12/05/react-19) 与 [升级指南](https://react.dev/blog/2024/04/25/react-19-upgrade-guide) 整理。React 19 已稳定发布；升级前应结合项目所用框架、路由和组件库确认兼容版本，并运行官方 codemod/类型检查与回归测试。

### Actions 与表单

- React 19 支持在 `startTransition` 中使用异步函数。此类异步更新约定称为 **Action**，可帮助处理 pending 状态、错误边界和乐观更新。
- `<form action={fn}>`、`<button formAction={fn}>` 等可直接接收函数。Action 成功后，React 会自动重置非受控表单；需手动重置时使用 `requestFormReset`。
- `useActionState(action, initialState)` 返回 `[state, formAction, isPending]`，用于保存上一次 Action 结果、获取可传给表单的 Action 和提交状态。它取代了 Canary 阶段的 `useFormState` 命名。
- `useFormStatus()` 从最近的父级 `<form>` 读取提交状态，适合封装不想层层透传 `pending` 的提交按钮等设计系统组件。

```jsx
import { useActionState } from 'react'

function ProfileForm() {
  const [message, saveProfile, isPending] = useActionState(
    async (_previous, formData) => {
      const result = await updateProfile(formData)
      return result.error ?? '保存成功'
    },
    null,
  )

  return (
    <form action={saveProfile}>
      <input name="name" required />
      <button disabled={isPending}>{isPending ? '保存中' : '保存'}</button>
      {message && <p>{message}</p>}
    </form>
  )
}
```

### `useOptimistic` 与 `use`

- `useOptimistic(state, updateFn?)` 用于在异步 Action 等待期间先显示乐观 UI；请求完成后 React 会回到来自真实 state 的值。服务端仍必须保证校验、幂等与错误处理。
- `use(resource)` 可在渲染期间读取 Promise 或 Context。读取 Promise 时会触发 Suspense，必须由合适的 `<Suspense>` 边界处理。
- 与普通 Hook 不同，`use` 可以在条件和循环中调用，但只能在组件或 Hook 的渲染阶段调用。
- 不要在 Client Component 的渲染过程中临时创建 Promise 再传给 `use`；官方要求使用支持 Suspense 缓存的框架/数据层提供的 Promise，否则会出现未缓存 Promise 警告与重复请求风险。

### Server Components、静态渲染与资源提示

- **React Server Components（RSC）** 允许组件在客户端应用或 SSR 服务器之外的服务器环境预先执行，常由框架实现。它不是普通 SSR 的同义词，也不意味着所有 React 应用都必须使用 RSC。
- React 19 增加 `react-dom/static` 的 `prerender`、`prerenderToNodeStream`，可等待数据后生成静态 HTML；与持续边加载边输出内容的流式 SSR API 用途不同。
- 新增资源预加载相关 API，例如 `prefetchDNS`、`preconnect`、`preload`、`preloadModule`、`preinit`、`preinitModule`。应根据真实资源关键路径使用，过度预加载会争抢带宽。

### 其他改进与迁移要点

- React 19 改进了 Suspense：当组件在更新时挂起，会先提交最近一次更新的 fallback，再并行准备被挂起树的渲染。
- 支持将 `ref` 作为函数组件 prop 使用，减少部分 `forwardRef` 使用场景；不要为兼容旧代码盲目批量删除 `forwardRef`，应按组件库与 TypeScript 版本测试。
- Provider 可以使用 `<Context value={value}>` 形式；旧的 `<Context.Provider>` 仍可在迁移中逐步处理。
- 升级时应检查已移除/弃用的 API、TypeScript 类型变化和第三方依赖兼容性。不要只改 React 版本号就直接发布。

### React 19 常见问题

#### Action 能替代所有数据请求库吗？

不能。Action 更适合表单提交和数据变更的 pending、错误、乐观更新协作；缓存、请求去重、失焦重取、分页、离线策略等仍可能需要框架或专门的数据层。先按数据读取与写入的生命周期设计边界。

#### `use` 是否意味着可以在任意组件中直接请求数据？

不意味着。`use` 读取 Promise 需要 Suspense 边界和可缓存的数据来源；在 Client Component render 中新建 Promise 不是受支持的通用请求模式。优先遵循所用框架的数据获取约定。

#### `useOptimistic` 是否会让后端失败自动消失？

不会。它只管理 UI 临时状态。后端仍要负责鉴权、输入校验、幂等、冲突处理和错误返回；客户端应在 Action 失败时提供可理解的反馈，并以服务端最终状态为准。
