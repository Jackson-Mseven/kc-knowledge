# 状态机详解

## 什么是状态机（State Machine）

状态机是一种描述**系统当前处于什么状态、接收事件后允许如何变化，以及变化时执行什么逻辑**的模型。

一个有限状态机（FSM）通常由以下部分组成：

- **State（状态）**：系统在某个时刻的明确阶段；
- **Event（事件）**：外部输入或内部结果，例如 `PAY`、`RESOLVE`；
- **Transition（转换）**：当前状态收到某事件后迁移到哪个状态；
- **Initial State（初始状态）**：机器启动时的状态；
- **Final State（终止状态）**：流程完成后不再接受普通转换的状态；
- **Action（动作）**：转换发生时执行的同步副作用或状态更新；
- **Guard（守卫）**：根据条件决定转换是否允许；
- **Context（上下文）**：状态节点之外需要保存的数据。

订单可以表示为：

```text
待支付 --PAY_SUCCESS--> 已支付 --SHIP--> 已发货 --RECEIVE--> 已完成
   └------CANCEL------> 已取消
```

转换表明确规定：

```text
待支付 -> 已支付     合法
待支付 -> 已完成     非法
已发货 -> 待支付     非法
```

状态机的价值不是把 `if/else` 换一种写法，而是让**合法状态集合和合法转换集合成为显式模型**。

## 为什么需要状态机

登录、表单提交、文件上传、支付、订单、播放器、弹窗、引导流程和审批流，本质上都包含状态和事件。

多个布尔值很容易产生无效组合：

```ts
type RequestState = {
  loading: boolean
  success: boolean
  error: boolean
}
```

理论上三个布尔值有 8 种组合，但业务可能只允许 idle、loading、success、error 四种。以下状态显然矛盾：

```ts
{ loading: true, success: true, error: true }
```

使用判别联合可以先在类型层消除非法组合：

```ts
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error }
```

完整状态机进一步规定每个状态能接收哪些事件，从而避免任意赋值。

## 手写一个有限状态机

```ts
type State = 'idle' | 'loading' | 'success' | 'error'
type Event = 'FETCH' | 'RESOLVE' | 'REJECT' | 'RETRY'

const transitions: Record<State, Partial<Record<Event, State>>> = {
  idle: { FETCH: 'loading' },
  loading: { RESOLVE: 'success', REJECT: 'error' },
  success: { FETCH: 'loading' },
  error: { RETRY: 'loading' },
}

function transition(state: State, event: Event): State {
  const next = transitions[state][event]
  if (!next) throw new Error(`Invalid transition: ${state} -> ${event}`)
  return next
}
```

手写 FSM 适合状态和事件很少的场景。规模增加后还需要处理上下文、Guard、异步取消、层级状态、并行状态、Actor、可视化和测试，此时专用库更可靠。

## FSM 与 Statechart

传统 FSM 的状态数量可能随业务组合快速膨胀。Statechart 在 FSM 上增加：

- **层级状态**：父状态包含多个子状态，共享转换；
- **并行状态**：多个相互独立的状态区域同时存在；
- **历史状态**：返回复合状态时恢复之前的子状态；
- **入口/退出动作**：进入或离开状态时执行逻辑；
- **延迟/瞬时转换**：时间或条件满足后自动迁移。

```text
订单处理中
├── 支付
│   ├── 未支付
│   └── 已支付
└── 履约
    ├── 待发货
    └── 运输中
```

如果两个维度真正独立，可使用并行状态；如果存在强约束，应重新设计领域状态，避免制造不可能的组合。

## Guard、Action 与 Context

Guard 必须是可预测的条件判断，不执行副作用：

```ts
const canSubmit = ({ context }) => context.acceptedTerms && context.formValid
```

Action 用于记录日志、发送通知或更新 Context。业务关键副作用应明确发生时机，并考虑重复执行和失败恢复。

Context 保存用户输入、计数器、错误和服务结果等扩展数据。不要把所有应用状态都塞进一个 Machine Context；状态机只管理该流程拥有的数据。

## 异步状态与竞态

异步请求至少应建模：loading、success、error、取消/重试。只在 Effect 中观察布尔值发请求，容易出现旧请求覆盖新结果。

状态机可把异步服务绑定到某个状态：进入 loading 启动服务，离开时取消或忽略结果；只有仍处于对应状态时才接收完成事件。

```text
idle --SUBMIT--> submitting
submitting --done.invoke--> success
submitting --error.platform--> failure
failure --RETRY--> submitting
submitting --CANCEL--> idle
```

网络请求是否可安全重试还取决于接口幂等性，状态机不能替代服务端幂等键和事务设计。

## XState

[XState](https://github.com/statelyai/xstate) 是 JavaScript 生态中成熟的 Statechart 与 Actor 模型实现，支持层级、并行状态、Guard、Action、异步 Actor、可视化和框架集成。

```ts
import { createActor, createMachine } from 'xstate'

const toggleMachine = createMachine({
  id: 'toggle',
  initial: 'inactive',
  states: {
    inactive: { on: { TOGGLE: 'active' } },
    active: { on: { TOGGLE: 'inactive' } },
  },
})

const actor = createActor(toggleMachine)
actor.subscribe((snapshot) => console.log(snapshot.value))
actor.start()
actor.send({ type: 'TOGGLE' })
```

### 带 Context 和 Guard

```ts
import { assign, createMachine } from 'xstate'

const formMachine = createMachine({
  context: { accepted: false },
  initial: 'editing',
  states: {
    editing: {
      on: {
        ACCEPT: { actions: assign({ accepted: true }) },
        SUBMIT: { target: 'submitting', guard: ({ context }) => context.accepted },
      },
    },
    submitting: {},
  },
})
```

### 优势

- 严格表达合法状态与转换；
- 支持复杂 Statechart、Actor 与异步流程；
- 状态图可视化，适合产品、开发和测试共同评审；
- 可从状态图生成测试路径，调试 Snapshot 和事件历史；
- React、Vue 等框架可订阅 Actor Snapshot。

### 局限

- Statechart、Actor、invoke、Guard 等概念有学习成本；
- 简单 UI 使用完整 Machine 可能显得过重；
- 状态粒度设计不合理会得到巨大状态图；
- Machine 配置仍需要模块边界、类型和测试，不能自动保证业务模型正确。

## Stately

[Stately Studio](https://stately.ai/docs/studio) 是 XState 官方生态中的可视化建模工具，可绘制状态图、讨论转换并与 XState 配置协作。

它适合审批、订单、支付、AI Workflow 等需要多人评审的流程。可视化图应作为可执行模型或与代码保持自动同步，否则图与实现会逐渐漂移。

## Robot3

[Robot3](https://github.com/matthewp/robot) 是轻量、函数式的状态机库，API 较少：

```ts
import { createMachine, interpret, state, transition } from 'robot3'

const machine = createMachine({
  off: state(transition('toggle', 'on')),
  on: state(transition('toggle', 'off')),
})

const service = interpret(machine, () => render(service.machine.current))
service.send('toggle')
```

优势是体积小、模型直接、学习成本较低；不足是可视化、层级/并行状态和 Actor 生态不如 XState，复杂流程往往需要更多自建约定。

## Zustand + FSM

如果 React 项目已使用 Zustand，可把当前状态和转换表放进 Store：

```ts
const transitions = {
  idle: { FETCH: 'loading' },
  loading: { RESOLVE: 'success', REJECT: 'error' },
} as const

const useStore = create((set, get) => ({
  status: 'idle',
  send(event) {
    const next = transitions[get().status]?.[event]
    if (next) set({ status: next })
  },
}))
```

这种方式没有额外依赖、与现有 Store 融合方便，但 Zustand 本身不是状态机库。Guard、异步取消、层级状态、可视化和合法性都需自行实现，复杂度增长后容易重新发明不完整的 XState。

## Redux Toolkit + Listener Middleware

Redux reducer 可以表达事件到状态的转换，Listener Middleware 处理异步副作用：

```ts
listenerMiddleware.startListening({
  actionCreator: loginRequested,
  effect: async (action, api) => {
    try {
      const user = await login(action.payload)
      api.dispatch(loginSucceeded(user))
    } catch (error) {
      api.dispatch(loginFailed(String(error)))
    }
  },
})
```

优势是 Redux DevTools、生态和应用级事件流成熟；但它不是严格 Statechart。Reducer 若没有判别联合和转换校验，仍可能接受当前状态不合法的 Action。

## 状态机与状态管理的区别

状态管理关注“状态存在哪里、如何读取和更新”；状态机关注“系统允许有哪些状态、什么事件能导致什么转换”。Redux、Zustand 可以保存状态机快照，XState Actor 也可作为状态源，两者不是必然竞争关系。

## 与 React/Vue 集成

- 组件根据 Snapshot 渲染，通过 `send(event)` 表达用户意图；
- UI 不应直接写 Machine Context；
- Machine 定义尽量与框架组件分离，便于独立测试；
- 组件卸载时停止 Actor/订阅，或由上层持有以跨路由保留流程；
- 只订阅需要的快照切片，避免无关 Context 变化造成整树更新。

## 测试状态机

状态机适合表驱动和模型测试：

```ts
it.each([
  ['idle', 'FETCH', 'loading'],
  ['loading', 'RESOLVE', 'success'],
  ['loading', 'REJECT', 'error'],
])('%s + %s -> %s', (state, event, expected) => {
  expect(transition(state, event)).toBe(expected)
})
```

测试重点：

- 每个合法转换和 Guard 边界；
- 非法事件不改变状态或产生明确错误；
- 入口/退出 Action 的执行次数；
- 异步成功、失败、取消、超时和重试；
- 最终状态、历史状态和并行区域；
- 从状态图生成路径，覆盖关键业务流程。

## 建模注意事项

1. 状态名称表达业务事实，如 `awaitingPayment`，不要使用 `step2`；
2. Event 使用过去发生或用户意图，例如 `PAYMENT_CONFIRMED`、`SUBMIT`；
3. 不把每个变量值都提升为状态节点；只有会改变允许事件/行为的模式才是 State；
4. Context 保存数据，状态节点表达行为模式；
5. Guard 保持纯粹，副作用放 Action/Actor；
6. 先画最小主流程，再补失败、取消、超时和恢复；
7. 状态机不能替代后端权限、事务、幂等和一致性校验。
